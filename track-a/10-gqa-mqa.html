L10 · MQA / GQA / MLA: The KV Compression Wars

The KV cache from L09 is the binding constraint on concurrency at long context. Three architectures attack it by storing fewer distinct keys and values — sharing them (MQA, GQA) or compressing them into a latent (MLA). The whole trade fits in three lines of arithmetic, and the quality cost is a measurable consequence of one information-theoretic fact.

1 · Why it exists #

From L09: with multi-head attention the KV cache is 2·L·dmodel·bytes per token — and that dmodel factor is the killer, because the cache is nearly as large as the weights' per-token width while the weights are shared by every token in the batch and the cache is not. Concretely: 32 layers, dmodel = 4096, fp16 gives 512 KiB per token; a 128k-token context needs 68.7 GB for a single request. At that point you are buying GPUs to hold keys and values for one user, and batching — the only way to reach decent arithmetic intensity — becomes impossible.

The insight behind this whole family: queries do not need to be cached. Each decode step computes one new query vector per head and throws it away. Keys and values persist and therefore cost memory. If several query heads could share one set of keys and values, the cache shrinks by the sharing factor and nothing about the queries changes. MQA (one shared KV head) and GQA (H/G shared KV heads) are exactly that idea with different group sizes; MLA instead keeps per-head caches but stores them as a much smaller shared latent.

KV-cache layout is the highest-leverage architecture decision in a serving business. Halving bytes per token doubles the concurrent users per GPU at fixed context, or doubles the context at fixed users, with no change to the FLOP count.

2 · The mental model #

Analogy. MHA gives every analyst their own filing cabinet. MQA gives the whole floor one shared cabinet (cheap storage, everyone fights over the same folders). GQA gives every clique of four analysts a shared cabinet. MLA does something different: it stores one compressed archive of the filing cabinet and expands it on demand — cheaper storage, but you pay decompression on every read.

Where the analogy breaks. The filing cabinet is not just storage; it is representational capacity. Query heads sharing a KV head can only differ in how they score the shared keys, not in what those keys contain. So sharing removes a dimension of expressiveness that cannot be recovered by learning — it is a hard information bottleneck. That is why MQA costs quality (a well-documented observation in the MQA literature), why GQA's intermediate setting was adopted widely as the practical point (GQA, arXiv:2305.13245), and why MLA spends extra compute (an up-projection and a decoupled RoPE part) to avoid paying the full bottleneck. A second break: MQA's cache is 1/H of MHA's, not zero — at 32 layers and dhead = 128 it is still 16 KiB/token, which is 2×109 bytes for a 128k context.

What sharing removes

The ability of different heads to retrieve different content from the same token position. They can still weight the same content differently — that is a strictly weaker set of functions.

What sharing does not change

Query projections, attention FLOPs (QKT still n×n per head), output projection, or feedforward cost. It is a pure memory/latency optimisation with a quality tax.

MQA vs GQA

MQA is GQA with G = 1. GQA with G = H is exactly MHA. Everything in between is a dial, and the dial is "how much representational freedom am I willing to pay for memory".

MLA's move

Cache a low-rank latent c of dimension cKV, reconstruct K and V from it via up-projections at read time. Bytes/token drop from 2·H·dhead to cKV (plus a small decoupled RoPE part), at the cost of an extra matmul per read.

3 · The mechanism #

MHA: Hkv = H   |   GQA: Hkv = H/G   |   MQA: Hkv = 1

KV bytes/token = 2 × L × Hkv × dhead × bytes_per_element

MLA: KV bytes/token = L × (cKV + drope) × bytes_per_element GQA keeps dhead fixed and drops Hkv by factor G, so memory drops by exactly G. In a rewrite you must change the projection shape, not just the cache size: WK, WV become dmodel × (Hkv·dhead) instead of dmodel×dmodel. MLA caches a latent cKV plus a separate small RoPE-carrying part drope, and reconstructs K,V with up-projections at every step.

The mapper: which KV head does query head h use?

# GQA: replicate the H_kv key/value heads onto the H query heads. stdlib only. def repeat_kv(k, H, G): """k: (H_kv=G, n, d_head) -> (H, n, d_head); query head h uses kv head h // (H // G).""" group = H // G return [k[h // group] for h in range(H)] H, G, n, dh = 8, 2, 5, 3 kv = [[[float(h) * 10 + p + j for j in range(dh)] for p in range(n)] for h in range(G)] rep = repeat_kv(kv, H, G) for h in range(H): src = int(rep[h][0][0] // 10) print(f"query head {h} -> kv head {src}")

Verified output:

query head 0 -> kv head 0 query head 1 -> kv head 0 query head 2 -> kv head 0 query head 3 -> kv head 0 query head 4 -> kv head 1 query head 5 -> kv head 1 query head 6 -> kv head 1 query head 7 -> kv head 1

Two facts worth noting: the mapping is h // (H/G), so heads that share a KV head are contiguous in head index — get this wrong (using h % G) and the model still trains, just worse, because the grouping is arbitrary but the trained weights are not. And when H is not divisible by G, you must pad or choose a compatible G; there is no meaningful "GQA with 3.5 groups".

The memory table, computed

def kv_bytes(n_ctx, L, H_kv, dh, batch, bpe=2): return 2 * L * H_kv * dh * n_ctx * batch * bpe for name, Hk in [("MHA H_kv=32", 32), ("GQA H_kv=8", 8), ("GQA H_kv=4", 4), ("MQA H_kv=1", 1)]: print(f"{name:14s} KV @128k ctx, 32 layers, fp16: {kv_bytes(131072, 32, Hk, 128, 1)/1e9:7.2f} GB") for L, H, dh, label in [(32, 32, 128, "7B-class"), (80, 64, 128, "70B-class")]: mha = kv_bytes(131072, L, H, dh, 1) / 1e9 gqa = kv_bytes(131072, L, 8, dh, 1) / 1e9 print(f"{label}: MHA {mha:.1f} GB -> GQA(8) {gqa:.1f} GB = {mha/gqa:.0f}x") for name, latent, rope in [("MHA full", 32*128, 0), ("MLA c=512 + 64 rope", 512, 64)]: per_tok = 32 * (latent + rope) * 2 print(f"{name:22s}: {per_tok/1024:6.1f} KiB/token -> {per_tok*131072/1e9:5.2f} GB @128k")

Verified output:

MHA H_kv=32 KV @128k ctx, 32 layers, fp16: 68.72 GB GQA H_kv=8 KV @128k ctx, 32 layers, fp16: 17.18 GB GQA H_kv=4 KV @128k ctx, 32 layers, fp16: 8.59 GB MQA H_kv=1 KV @128k ctx, 32 layers, fp16: 2.15 GB 7B-class: MHA 68.7 GB -> GQA(8) 17.2 GB = 4x 70B-class: MHA 343.6 GB -> GQA(8) 42.9 GB = 8x MHA full : 256.0 KiB/token -> 34.36 GB @128k MLA c=512 + 64 rope : 36.0 KiB/token -> 4.83 GB @128k

Read the 70B row: the saving from GQA scales with H, so the bigger the model's head count, the larger the absolute win — which is exactly why GQA is standard in large open models and why MQA alone was considered too lossy at that width. And note MLA's row: it beats GQA-8 by another ~3.6× at the same dmodel, because the latent (512 + 64 = 576 elements) is far smaller than 8 KV heads × 128 = 1024 elements. MLA's win is therefore largest at small Hkv; it is not a free lunch but a different point on the same frontier.

Why MLA needs a decoupled RoPE part

RoPE (L08) rotates the keys by an angle that depends on position. If keys were reconstructed from a cached latent, the rotation would have to commute with the up-projection — but a rotation is position-dependent and the latent is position-free, so it does not commute. MLA sidesteps this by storing a separate small d_rope-dimensional component that does receive the rotation, and concatenating it with the reconstructed keys at read time. That is the entire reason the formula has two terms, and it is a good example of how a positional choice from one lesson forces an architectural constraint three lessons later.

What it costs at decode: the read side

bytes read per decode step ≈ weights (N·bpe) + batch × ctx × KV bytes/token
GQA/MLA shrink the second term; MLA adds an up-projection matmul to the first term's compute (not bytes) This is why GQA is nearly free in FLOPs: you still do n x n scores per query head, you just index a smaller KV tensor. MLA trades FLOPs for bytes, which is favourable when you are bandwidth-bound — i.e. in decode.

4 · Your hands #

Experiment 1 — Prove GQA equals MHA when G = H, exactly

The strongest possible check on a GQA implementation: with G = H it must reproduce multi-head attention bit-for-bit. Any difference means the mapper or the projection shape is wrong.

import numpy as np rng = np.random.default_rng(0) def softmax(x): x = x - x.max(-1, keepdims=True); e = np.exp(x); return e / e.sum(-1, keepdims=True) n, d_model, H = 7, 16, 4; dh = d_model // H X = rng.normal(size=(n, d_model)) Wq = rng.normal(size=(d_model, d_model)) / np.sqrt(d_model) Wk0 = rng.normal(size=(d_model, d_model)) / np.sqrt(d_model) # full-width MHA matrices Wv0 = rng.normal(size=(d_model, d_model)) / np.sqrt(d_model) def gqa(g): # slice the first g*dh columns, so g = H reproduces MHA bit-for-bit Wk, Wv = Wk0[:, :g*dh], Wv0[:, :g*dh] Q = (X @ Wq).reshape(n, H, dh).transpose(1,0,2) K = (X @ Wk).reshape(n, g, dh).transpose(1,0,2) V = (X @ Wv).reshape(n, g, dh).transpose(1,0,2) K = K[np.arange(H) // (H // g)]; V = V[np.arange(H) // (H // g)] # repeat_kv A = softmax(Q @ K.transpose(0,2,1) / np.sqrt(dh)) return A @ V, A Q = (X @ Wq).reshape(n, H, dh).transpose(1,0,2) O_mha = softmax(Q @ (X @ Wk0).reshape(n, H, dh).transpose(1,0,2).transpose(0,2,1) / np.sqrt(dh)) @ (X @ Wv0).reshape(n, H, dh).transpose(1,0,2) O4, _ = gqa(4); O1, _ = gqa(1) print("G=H equals MHA bit-for-bit:", np.allclose(O4, O_mha)) print("G=1: heads still differ (own Q projection):", not np.allclose(O1[0], O1[1]))

Observed: G=H reproduces MHA exactly (True); under G=H the heads differ (True); under G=1 the heads still produce different outputs (True) even though they share K and V — because each head has its own query projection. That is the exact mechanism of the quality cost: heads can disagree about weighting but not about content. The first assertion is the one to keep in CI: G=H must match the L06/L07 reference to the last bit, and it does. Falsifier: if heads produced identical outputs under G = 1, your implementation is collapsing the query heads as well, which would be a real bug.

Experiment 2 — Build the frontier for your own model

Pick G to hit a memory budget instead of copying a paper's number. The function below is the complete decision rule for a 128k-context, batch-1 request.

def frontier(L, H, dh, ctx, budget_gb, bpe=2): print(f"L={L} H={H} d_head={dh} ctx={ctx} budget={budget_gb} GB") for G in [1, 2, 4, 8, 16, H]: if H % G: continue gb = 2 * L * (H // G) * dh * ctx * bpe / 1e9 print(f" G={G:2d} (H_kv={H//G:2d}): {gb:7.2f} GB -> batch {int(budget_gb//gb)} -> {budget_gb/gb:5.2f} concurrent requests") frontier(32, 64, 128, 131072, 64)

Observed for the 70B-class shape (L=32, H=64, d_head=128, 128k context, fp16): G=1/MQA 2.15 GB → 29.8 concurrent requests; G=8 (Hkv=8) 17.18 GB → 3.73; G=16 → 7.45; G=64/MHA 137.44 GB → 0.47 — MHA does not even fit one request. The decision is not "biggest G for quality" but "smallest G that meets the concurrency SLO, then measure the quality delta". Both numbers are computable before you train anything, which is why KV layout is an architecture decision, not a tuning knob.

Experiment 3 — Where the decode time actually goes

Compare bytes read per decode step across layouts at 32k context. This tells you whether KV compression will move your p99 latency or only your concurrency.

params = 32 * 20e6 # illustrative layer budget ctx = 32768; L = 32; dh = 128 for Hk in [32, 8, 1]: kv = 2 * L * Hk * dh * ctx * 2 print(f"H_kv={Hk:2d}: KV {kv/1e6:8.1f} MB + weights {params*2/1e6:.1f} MB -> {100*kv/(kv+params*2):5.1f}% of bytes read")

Observed at 32k context: KV is 93.1% of bytes read per decode step under MHA, 77.0% under GQA-8 and still 29.5% under MQA (where weights now dominate). So at long context, decode latency is governed by cache bandwidth and the L10 optimisations help latency as well as concurrency. At short context (say 2k) the KV term falls below the weights for every layout except MHA, and KV compression buys almost no latency — it only buys batch capacity. Measure your own bytes/step and divide by achievable bandwidth before promising an SLO.

5 · Failure modes #

  • Projection shape not updated with Hkv. Symptom: a GQA config loads but the cache is full-size, so concurrency is unchanged — the saving never materialises. Check W_k.shape against H_kv*d_head.
  • Wrong group mapping (h % G instead of h // (H/G)). Symptom: trains, but slightly worse than the correctly-grouped run; a checkpoint converted from MHA with the wrong mapping looks "almost right". Nothing crashes.
  • H not divisible by G. Symptom: reshape error at load, or a silently truncated head count if // is used. Assert divisibility at config parse time.
  • Converting a trained MHA model to GQA naively. Symptom: large loss jump that never recovers. Averaging the KV heads of a trained MHA model and continuing from there works as initialisation; freezing everything else does not.
  • Expecting MQA to be free. Symptom: a palpable quality drop at equal parameters, especially on tasks needing multiple simultaneous retrievals (many-item copying). The bottleneck is real and shows up as a capability ceiling, not as noise.
  • MLA without a decoupled RoPE path. Symptom: long-context behaviour collapses while short-context looks fine — positional information was reconstructed rather than rotated. The d_rope term is not optional.
  • Cache dtype mixed across layouts. Symptom: GQA cache quantised to fp8 while MLA latent kept in bf16 — the comparison of two serving options is apples-to-oranges. Compare at equal quantisation and equal quality.

7 · Self-check #

Q1. A model has L = 48, H = 32, dhead = 128, fp16. Give KV bytes/token for MHA, GQA-4 and MQA.

Reveal answer

MHA: 2×48×32×128×2 = 786,432 B (768 KiB). GQA-4 (Hkv=8): 2×48×8×128×2 = 196,608 B (192 KiB). MQA (Hkv=1): 2×48×1×128×2 = 24,576 B (24 KiB). Ratios 1 : 1/4 : 1/32, exactly the group sizes.

Q2. You have 48 GB of usable HBM after weights for cache. How many concurrent 16k-token requests fit under each layout from Q1?

Reveal answer

Per request = 16,384 tokens × bytes/token. MHA: 16,384×786,432 = 12.88 GB → 3. GQA-4: 3.22 GB → 14. MQA: 0.40 GB → 119 (in principle — in practice other limits bind first). This is the entire business case for KV compression in one line.

Q3. Diagnostic: a model converted from MHA to GQA-4 keeps the old Wk/Wv shapes and slices them at runtime. Quality is fine but memory does not drop. Why?

Reveal answer

Because the stored cache is still H×d_head per layer — slicing produces the repeated tensor but nothing saved it. The saving comes from storing only Hkv heads and expanding (repeating) at read time, not from expanding first. Fix: allocate the cache as Hkv heads and apply repeat_kv after the read, inside the attention kernel.

Q4. Why does MLA need a separate d_rope component, and why does that imply extra bytes instead of a free rotation?

Reveal answer

MLA reconstructs K from a cached latent via an up-projection. RoPE multiplies K by a position-dependent rotation Rpos, which does not commute with that up-projection (the latent is position-free and would have to be re-rotated per position). So the rotated part must be stored already-rotated, in its own subspace: d_rope values per layer per token. The alternative — reconstructing then rotating — is valid mathematically but destroys the cache saving because you would need to store the pre-rotation latent for each of the H heads, which is what MLA exists to avoid.

Q5. If KV sharing costs quality, why is MQA (G = 1) ever acceptable?

Reveal answer

Because the quality cost is a function of what the task needs. MQA keeps a full-width single KV head — content capacity is reduced only in the sense that heads cannot retrieve different things from the same position — and for short-context, high-throughput tasks that is often free. The trade is worst at long context (more simultaneous retrievals needed) and at large H (bigger reduction), so MQA tends to be used where the cache dominates and the capability ceiling is not binding, and GQA is used when it is. That decision is an evaluation, not a preference: compare at matched compute on your own retrieval-heavy task.
