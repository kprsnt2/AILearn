L17 · Sampling: Greedy, Temperature, Top-k, Top-p, Min-p, Penalties

A model outputs a probability over every token in the vocabulary. Choosing which one to emit is a separate decision made in a few lines of code, and those few lines change repetition, creativity, determinism and failure recovery more than most model upgrades do.

~28 min difficulty ●●○○○ build: sampler playground with support and entropy
greedy / argmax temperature top-k top-p / nucleus min-p frequency & presence penalty support and entropy

1 · Why it exists #

A trained model gives a distribution, not an answer. Something has to collapse it to one token id. Two naive policies both fail in ways you have seen in production:

  • Always pick the most likely token. Deterministic and often correct, but it gets stuck: repetition becomes an absorbing state because a repeated bigram is locally the highest-probability continuation. Once the model is wrong on one token, greedy decoding has no way to recover — the wrong token is now context.
  • Sample from the raw distribution. Unbiased, but the long tail has a real probability mass. A token at p = 1e-5 is almost never right and, once emitted, poisons everything after it. Over a 2,000-token generation you draw 2,000 samples from a distribution with tens of thousands of tiny wrong options.

Samplers exist to remove the tail while keeping some diversity: truncate the distribution to a set you are willing to commit to, then sample from what remains. Temperature rescales the whole distribution; top-k and top-p and min-p delete tail entries by different criteria; penalties discourage tokens already used. Each is a different answer to "how much risk per token am I buying".

Decoding parameters are a reliability contract. If you cannot state the sampler settings and seed for a production path, you cannot reproduce its output, cannot attribute a regression, and cannot claim determinism (L94). The parameters are part of the model definition in practice.

2 · The mental model #

Analogy. The logits are a leaderboard of candidates, scored by confidence. Temperature changes how much you weight the top of the leaderboard: low temperature = only the favourites matter, high temperature = the whole field is in play. Truncation removes candidates from the ballot entirely before voting. Penalties adjust the scores of candidates already used.

Where the analogy breaks. (1) Temperature and truncation are not two ways to say "less random". Temperature changes the shape of the distribution over all V candidates — including making the top one overwhelmingly likely, but never removing the tail. Truncation removes candidates and renormalises. On a peaked distribution the two do similar things; on a flat distribution they behave very differently, and that difference is exactly where most production bugs live. (2) Top-p's cutoff depends on the distribution, so its support size varies per step — that is its advantage (adaptive) and its disadvantage (unpredictable cost/quality in weird contexts). (3) Min-p's threshold is relative to the top probability, not an absolute mass, which is why it scales with the model's confidence instead of against it.

Support size is the thing you can measure

Count how many tokens survive truncation. That single number, per step, predicts repetition (size 1), incoherence (size huge) and determinism (size 1 every step).

Entropy is the other thing

H = −∑p ln p over the kept set. Two samplers with the same support but different entropy behave differently: one spreads, one commits.

Temperature 0 is not a value

It is a division by zero; implementations special-case it to argmax. That means temperature=0 and greedy differ only in intent, not in mechanism.

Sampler and eval are coupled

Benchmarks with temperature 0 measure the mode; benchmarks with default temperature measure a distribution. A "same model" claim across two sampler settings is a different product.

3 · The mechanism #

Temperature:   pi(τ) = softmax(z/τ)i   (τ → 0+: peaky, τ > 1: flat)
Top-k:   keep the k indices with largest z, set the rest to −∞, renormalise
Top-p (nucleus):   sort by p descending, keep the smallest prefix whose cumulative mass ≥ p, set the rest to −∞
Min-p:   keep i where pi ≥ pbase · pmax, where pbase is a user parameter
Frequency penalty:   z′i = zi − α · count(i) Order matters in supporting implementations, and the canonical pipeline is: penalties (modify logits) → temperature (divide) → truncation (mask) → sample. Applying temperature before the penalties, or truncating before temperature, gives a different distribution and different results than the vendor documents — and reproducing a vendor's output requires reproducing its order.
# A sampler playground: support size and entropy for each policy. stdlib only, runs as-is. import math def softmax(z): m = max(z); e = [math.exp(v - m) for v in z]; s = sum(e); return [v / s for v in e] def temp(l, t): return [v / t for v in l] def top_k(l, k): cut = sorted(l, reverse=True)[k - 1] return [v if v >= cut else -math.inf for v in l] def top_p(l, p): idx = sorted(range(len(l)), key=lambda i: -l[i]) probs = softmax(l); keep, cum = set(), 0.0 for i in idx: keep.add(i); cum += probs[i] if cum >= p: break return [v if i in keep else -math.inf for i, v in enumerate(l)] def min_p(l, p): mx = max(softmax(l)) return [v if pp >= p * mx else -math.inf for v, pp in zip(l, softmax(l))] def show(name, l): p = softmax(l) nz = [(i, round(v, 4)) for i, v in enumerate(p) if v > 0] H = -sum(v * math.log(v) for v in p if v > 0) print(f"{name:16s} support={len(nz)} max={max(p):.4f} H={H:.3f}") logits = [3.0, 2.0, 1.0, 0.5, 0.0, -1.0] show("greedy", top_k(logits, 1)) for t in [0.5, 1.0, 2.0]: show(f"temp {t}", temp(logits, t)) for k in [1, 3]: show(f"top_k {k}", top_k(logits, k)) for p in [0.5, 0.9, 0.99]: show(f"top_p {p}", top_p(logits, p)) for mp in [0.0, 0.1, 0.5]: show(f"min_p {mp}", min_p(logits, mp))

Verified output (CPython 3.12):

greedy support=1 max=1.0000 H=0.000 temp 0.5 support=6 max=0.8597 H=0.443 temp 1.0 support=6 max=0.6048 H=1.148 temp 2.0 support=6 max=0.3818 H=1.627 top_k 1 support=1 max=1.0000 H=0.000 top_k 3 support=3 max=0.6652 H=0.933 top_p 0.5 support=1 max=1.0000 H=0.000 top_p 0.9 support=3 max=0.6652 H=0.933 top_p 0.99 support=6 max=0.6048 H=1.148 min_p 0.0 support=6 max=0.6048 H=1.148 min_p 0.1 support=3 max=0.6652 H=0.933 min_p 0.5 support=1 max=1.0000 H=0.000

Read three separate facts out of that table.

  1. Temperature never changes the support. All three temperatures keep 6 tokens; only the shape changes (max probability 0.86 → 0.60 → 0.38, entropy 0.44 → 1.15 → 1.63). So temperature cannot protect you from the tail — the tiny probabilities get bigger as you raise it.
  2. Top-p adapts, top-k does not. Here top-p 0.9 and top-k 3 happen to agree exactly (max 0.6652, H 0.933), because this distribution's top-3 mass is 0.90. Change the logits and they diverge: on a confident distribution top-p 0.9 keeps one token, on a flat one it keeps a dozen. That is the design intent.
  3. min-p is a confidence-relative gate. min_p 0.1 keeps everything with at least 10% of the top token's probability. On this distribution that is 3 tokens. On a confident distribution it collapses to 1; on a flat one it keeps many. Note the equivalence chain in this example: min_p 0.1 gives exactly the same support and entropy as top_p 0.9 and top_k 3 — a useful reminder that these knobs are heavily redundant and "which sampler is better" is usually answered by the distribution, not the name.

Determinism, and the seed

Sampling is deterministic given (model, inputs, sampler settings, PRNG state). Every non-determinism you observe in production comes from one of: batching (the same sample drawn at a different batch position), floating-point non-associativity in matmuls, or the PRNG state being derived per-request from something like a timestamp. If you need reproducibility, you must pin all three; temperature alone is not the variable (L94).

A sampling step:   r ~ U(0,1)  →  token = smallest i with ∑j≤ipj ≥ r (inverse-CDF)
Expected identical output  ⇔  identical p (same model, dtype, batch composition) AND identical r Inverse-CDF sampling needs the probabilities sorted or at least a fixed order; different implementations order the vocabulary differently, so the same seed gives different tokens across libraries. Pin the library version too.

Penalties: why repetition is a search problem, not a memory problem

A frequency penalty subtracts α per occurrence from the logit. It is a blunt instrument: it also punishes tokens that should repeat (a closing brace, a repeated identifier, the same function name twice). A presence penalty subtracts a fixed amount once; a repetition penalty divides positive logits and multiplies negative ones. All three fight the symptom (looping) rather than the cause (a model that assigned too much mass to the token it just emitted). That is why the better fix is usually a sampler + prompt structure change, not a bigger penalty — and why a high penalty produces stilted text with bizarre synonyms.

4 · Your hands #

Experiment 1 — Characterise your sampler, do not guess

For a real model, logits are not toy-scale. Take a few real steps, print support size and entropy for each policy, and confirm the sampler does what you think. The diagnostic goal: support should be 1 at deterministic points and small-but-not-1 during genuine ambiguity.

python -c "print('run section-3 code; then plug in real logits (any 50k-vector) and check: greedy support=1 always; top_p 0.9 support varies; temp changes H but never support')"

The structural prediction to test: raising temperature always increases entropy and never shrinks support; adding truncation always shrinks or preserves support and lowers entropy. If your implementation shows a temperature change altering support, you are applying temperature after truncation and then re-truncating, or truncating on unnormalised values — both are order bugs.

Experiment 2 — Penalty vs no penalty on a repeating continuation

Construct a pathological loop by hand — a distribution that is peaked on the same token it just emitted — then measure how the penalty changes the next-token distribution.

import math def softmax(z): m = max(z); e = [math.exp(v - m) for v in z]; s = sum(e); return [v / s for v in e] logits = [3.0, 2.0, 1.0, 0.5, 0.0, -1.0] counts = [3, 0, 0, 0, 0, 0] # token 0 already appeared 3 times for alpha in [0.0, 0.25, 0.5, 1.0]: adj = [v - alpha * c for v, c in zip(logits, counts)] p = softmax(adj) print(f"alpha={alpha:4}: " + " ".join(f"{v:.3f}" for v in p) + f" argmax={max(range(len(p)), key=lambda i: p[i])}")

Observed: with α = 0 token 0 has 0.605; at 0.25 it has 0.420 (the loop is weakened but survives); at 0.5 it has 0.255 and token 1 takes the lead at 0.420; at 1.0 token 0 is down to 0.071 and token 1 dominates at 0.523. So a penalty between 0.25 and 0.5 is what breaks this specific loop — and note the cost: at α = 1.0 the escaped token has only 52% of the mass, i.e. the distribution is now spread over a token that may be wrong. That is the exchange, and it is why "penalty 2.0 because it stopped the loop" often produces worse text. Measure the penalty against the desired repetition (structural tokens must repeat), not against one bad trajectory.

Experiment 3 — Show that temperature 0 and greedy are the same thing, and that temperature is not a determinism knob

Two claims worth verifying before you rely on them in a production config.

import math logits = [3.0, 2.0, 1.0, 0.5, 0.0, -1.0] for t in [1e-3, 1e-6]: z = [v / t for v in logits] m = max(z); e = [math.exp(v - m) for v in z]; s = sum(e) print(f"T={t:g}: max prob={max(e)/s:.10f} (greedy is exactly 1.0)") print("in float64, T below ~1e-15 still underflows the tail to 0, so it *approximates* greedy without being greedy")

Observed: at temperature 1e-3 the max probability prints as 1.0, and at 1e-6 likewise — the logit gap of 1.0 divided by 1e-3 is 1000, so e1000 overflows the ratio to inf/inf and the tail underflows to exactly zero in practice. That is the numerical version of greedy. The dangerous regime is between 1e-2 and 1e-4: there the max probability is 0.99–0.9999 and roughly one in a thousand samples draws a different token, which is the worst of both worlds for reproducibility — usually deterministic, occasionally not. If you want greedy, set greedy. If you want sampling, use a temperature you can characterise. Do not use "temperature = 0.01" as a shortcut for both.

5 · Failure modes #

  • Top-p 0.9 on a near-deterministic model. Symptom: fine, until a step where the top token has p = 0.95 and top-p still keeps a second token at 0.05; over 2,000 tokens you get occasional bizarre word choices. Consider min-p or lower temperature.
  • Temperature raised to "increase creativity" in a structured-output task. Symptom: JSON or code becomes invalid at a higher rate. Structured tasks need truncation to valid tokens (L18) and low temperature.
  • High frequency penalty on code. Symptom: variables renamed mid-function; closing punctuation penalised so heavily the model avoids it. The penalty cannot distinguish "repetitive" from "syntactically required".
  • Sampler order differs from the vendor's documented order. Symptom: your reproduction of a vendor's output differs even with identical logits; on some settings the difference is only visible at high temperature. Pin order: penalties, temperature, truncation, sample.
  • Temperature 0 treated as "deterministic". Symptom: still non-reproducible across requests because batching and reduction order vary. Greedy fixes the sampler, not the kernel (L94).
  • Sampling from unnormalised logits after masking. Symptom: probabilities do not sum to 1; the sampler biases toward whatever the filter left. Renormalise after truncation, always.
  • Different samplers across eval and production. Symptom: eval says the model is fine, production is repetitive — because eval used greedy and production uses top-p 0.95. The eval measured a different system.

7 · Self-check #

Q1. Why can temperature never remove a token from the support, and what is the practical consequence?

Reveal answer

Temperature divides every logit by τ > 0, so any finite logit stays finite and exp of it stays positive; softmax of a finite vector has full support. Raising τ makes the tail larger, not smaller. Consequence: temperature cannot be used to prevent low-probability garbage; it only decides how much of the tail you are exposed to. Truncation is the only mechanism that sets support to zero, which is why real pipelines combine them.

Q2. Given probabilities [0.60, 0.22, 0.08, 0.05, 0.03, 0.011], what support do top-p 0.9 and top-p 0.5 produce?

Reveal answer

Cumulative: 0.60, 0.82, 0.90, 0.95, 0.98, 0.991. top-p 0.9 keeps tokens until the cumulative reaches 0.90 → 3 tokens (0.82 < 0.9, so the third is included). top-p 0.5 keeps the first token (0.60 ≥ 0.5) → 1 token, i.e. greedy. This matches the verified table, where top_p 0.5 collapsed to support 1 with entropy 0. Note that top-p 0.5 is not "half as random" as top-p 0.9 — it is effectively deterministic.

Q3. Diagnostic: outputs are fine at temperature 0 but at temperature 1.0 the model repeats a phrase identically several times, then switches topics. What is happening, and what do you change first?

Reveal answer

Untruncated sampling re-enters high-probability loops: a repeated phrase increases the probability of repeating again (it is self-reinforcing context), and temperature 1 preserves enough mass on that path to keep taking it. First change: add truncation (min-p or top-p) to cut the tail and break the absorbing state; second: a small frequency penalty if the loop persists; last: restructure the prompt. Do not raise the penalty until the output is stilted — that trades a visible failure for an invisible one.

Q4. Why does a frequency penalty break code more often than prose?

Reveal answer

Because in code the most frequent tokens are often the most necessary: braces, commas, parentheses, the same variable name, the same function call. A penalty cannot tell "repeating because stuck" from "repeating because required by grammar"; it applies uniformly to all occurrences, so it pushes the model toward synonyms or omissions — exactly the failure that makes generated code stop compiling. For structured output use low temperature plus constrained decoding (L18) instead of penalties.

Q5. Two services use the same model and the same temperature 0.7, but they produce different outputs for the same prompt. Name three causes that survive "same temperature".

Reveal answer

(1) Different truncation settings or order (top-p, top-k, min-p, penalty defaults). (2) Different PRNG seeding or consumption order — the same seed produces different streams if the implementation draws different numbers of samples per step. (3) Non-determinism from batching or kernel reduction order, which changes the logits themselves at the last floating-point digits and can flip a near-tie; plus dtype differences (fp16 vs fp8 KV) that change the probabilities. Also: a different tokenizer or system prompt, which changes the logits before sampling even starts.
