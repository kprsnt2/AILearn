L01 · Tokenization: The Physics of the Text Interface

The model never sees text — it sees a list of integers whose count is your bill and whose boundaries decide which arithmetic it can never do. Tokenization is the one layer where a "cosmetic" change silently changes context limits, pricing and evaluation scores.

~28 min difficulty ●●○○○ build: BPE trainer + token cost meter
BPE byte fallback merge order determinism vocab size tradeoff tokens-per-word round-trip test token cost meter

1 · Why it exists #

A neural network is a pile of matrix multiplications. It cannot multiply by the letter r. So a decision had to be made before any learning could start: what is the atomic unit of text? Character-level models make sequences brutally long — an 8,000-token budget is only a few kilobytes of text — and attention is quadratic. Word-level models explode: any new word, typo, or \\x00 is out of vocabulary, so the model sees <unk> and loses information permanently. Byte-pair encoding exists because it is the cheapest compromise that is also lossless: start from bytes, then repeatedly glue together the most frequent adjacent pair.

The failure it was invented to stop is concrete: a vocabulary that cannot represent its input. Once you accept any byte string must be representable, you inherit the whole cost model of modern LLM serving: a prompt is billed per token, a context window is measured in tokens, and throughput is tokens/second. The tokenizer, not the text, is the interface.

You do not have a "text" bill, you have a "token" bill. Every cost, latency and context-window number you negotiate is denominated in tokens produced by one specific tokenizer, and re-tokenization between models is not free.

Two consequences you can measure today, and will in section 4: English prose costs roughly 1.2–1.5 tokens per word under common tokenizers (V=50k-class), code and non-Latin scripts cost substantially more per character than English, and the same sentence passed through two different tokenizers yields different token counts, different truncation points, and different per-token perplexity.

2 · The mental model #

Analogy (and where it breaks). A tokenizer is a lookup table applied before the model runs: the encoder replaces the longest dictionary entries it knows with index numbers, and the model works entirely on those numbers.

Where the analogy breaks: a compression dictionary is usually tuned to the payload, while a BPE vocabulary is learned once from a general corpus and frozen. So it is optimal for average text and expensive for your text. Try this now, because it is the whole sharp edge of the topic:

python -c "t='CMS-2024-0042 / ledger/9f3a1c77e0b4d5a6.json'; print(len(t),'chars,',len(t.encode()),'bytes')"

Verified: 44 chars, 44 bytes — pure ASCII, so bytes equal characters here (section 4 shows where that stops being true). Those 44 bytes are six events to a human (an agency, a year, a record number, a file name, a hash) and will be roughly 8–14 tokens to a 50k-class vocabulary, because none of that structure appeared often enough in the training corpus to earn a merge. Rare text pays full character price, and therefore full attention price, since attention cost is quadratic in token count (L06).

What the model actually sees

An integer sequence [id_0 … id_T-1], each id indexing a row of the embedding table. Position t is not a character, not a word, not a syntactic unit.

What the model cannot see

The string. "1749" might be five ids or two. Digit grouping is a property of the tokenizer, so "the model can't do arithmetic" is really "the tokenizer never showed it aligned columns".

What stays deterministic

Given the same vocabulary file and merge list, encoding is a pure function: no sampling, no device dependence. Token ids are reproducible exactly when generations are not — that is your primary audit anchor.

What breaks

Whitespace is fused into tokens ("the" ≠ " the"), so count depends on formatting, and one trailing newline can shift the final segmentation and change a scored logprob.

3 · The mechanism #

Training: greedy pairwise merges

Start from the byte sequence of every word (with an end-of-word sentinel so "low" and "lower" are not forced into one token). Count every adjacent symbol pair, weighted by word frequency. Merge the single most frequent pair into a new symbol. Repeat Vtarget − 256 times. This is exactly what Sennrich et al. proposed for subword units and what GPT-2 popularised with bytes as the base alphabet.

(a, b)* = argmax(a,b) ∑w∈vocab freq(w) · countab(w) a, b are adjacent symbols; frequency-weighted counts make rare words contribute almost nothing. Ties are broken by symbol order, which is what makes training reproducible.
# BPE trainer — stdlib only. Runs as-is. def bpe_train(words, n_merges): wl = {tuple(list(w) + ["</w>"]): c for w, c in words.items()} merges = [] for _ in range(n_merges): pairs = {} for syms, c in wl.items(): for i in range(len(syms) - 1): pairs[syms[i], syms[i+1]] = pairs.get((syms[i], syms[i+1]), 0) + c if not pairs: break best = max(pairs, key=lambda k: (pairs[k], k)) # freq first, then lexicographic merges.append(best) new = {} for syms, c in wl.items(): out, i = [], 0 while i < len(syms): if i < len(syms) - 1 and (syms[i], syms[i+1]) == best: out.append(syms[i] + syms[i+1]); i += 2 else: out.append(syms[i]); i += 1 new[tuple(out)] = c wl = new return merges, wl corpus = {"low": 5, "lower": 2, "newest": 6, "widest": 3} merges, wl = bpe_train(corpus, 10) print("merges:", merges) for k in sorted(wl, key=lambda t: (-wl[t], t)): print(wl[k], " ".join(k))

Verified output of that block on CPython 3.12:

merges: [('t', '</w>'), ('s', 't</w>'), ('e', 'st</w>'), ('o', 'w'), ('l', 'ow'), ('w', 'est</w>'), ('n', 'e'), ('ne', 'west</w>'), ('low', '</w>'), ('w', 'i')] 6 newest</w> 5 low</w> 3 wi d est</w> 2 low e r </w>

Read that output carefully, because it is the whole lesson in four lines. Nothing merged in "lower" except nothing at all — it stays low e r, three tokens, because frequency 2 loses every tie against "newest" (frequency 6). A domain word that appears rarely never gets a cheap token. That is the "audit identifiers fragment" problem in miniature: BPE buys efficiency in proportion to how often text appeared, so the long tail pays full character price.

Encoding: apply merges in trained order, not in any order

Encoding must replay the merge list in the exact order it was learned. Applying (w,est) before (e,st) gives a different segmentation for the same string. This is merge order determinism — it is why a tokenizer is a file, not a flag.

encode(s) = fold over merges: ids ← replace first occurrence of (a, b) with ab, in merge-rank order
decode(encode(s)) = s   ∀ s ∈ byte* The second line is the round-trip invariant. It must hold byte-for-byte. If it does not, your vocabulary has a hole and any non-ASCII or control character can be silently destroyed.

The cost model you should memorise

cost(USD) ≈ ∑requests [ Tin · pin + Tout · pout ]    where T = #tokens, p = price/token
Tin ≈ ∑words (1 + εword)    with ε from 0.14 (common words) to >2 (hashes, non-Latin, base64) Tin is not a function of characters. It is a function of how well your text matches the tokenizer's training distribution. A URL, a JSON blob and a PEM key are the expensive cases.

Context windows are in tokens too, so the same 1 MB of logs that are "fine" as English are 10× too many tokens as hex dumps. And because attention cost grows as O(n2) in prefill, the token count is squared into your latency budget (see L06).

4 · Your hands #

Experiment 1 — Round-trip or it did not happen

A tokenizer that cannot round-trip is a data-corruption bug, not a nuance. This test is diagnostic because it fails on every byte sequence the vocabulary claimed to cover but does not.

import random random.seed(0) # Toy byte-level vocabulary: ids 0..255 are bytes, ids 256+ are merged pairs. class ToyBPE: def __init__(s, merges): s.vocab = {i: bytes([i]) for i in range(256)} s.ranks = {} for rank, pair in enumerate(merges): a, b = pair new_id = 256 + rank s.vocab[new_id] = s.vocab[a] + s.vocab[b] s.ranks[pair] = (rank, new_id) def encode(s, text): ids = list(text.encode("utf-8")) # byte fallback: always representable while len(ids) > 1: cand = [(s.ranks[p], i) for i, p in enumerate(zip(ids, ids[1:])) if p in s.ranks] if not cand: break (rank, new_id), i = min(cand) # lowest merge rank wins = trained order ids[i:i+2] = [new_id] return ids def decode(s, ids): return b"".join(s.vocab[i] for i in ids).decode("utf-8", errors="replace") # one merge for the byte pair "th" (0x74, 0x68 -> id 256 here stands for b'th') tb = ToyBPE([(116, 104)]) tests = ["hello", "the theme", "très tôt", "日本語", "\\x00\\x01\\xfe control", "🙂 emoji"] for t in tests: ids = tb.encode(t) back = tb.decode(ids) print(repr(t), "->", len(ids), "ids", "roundtrip" if back == t else "MISMATCH " + repr(back))

Every line prints roundtrip, with counts 5, 7, 10, 9, 12, 10 — verified on CPython 3.12 with PYTHONIOENCODING=utf-8 (on a Windows console without that variable the print itself raises UnicodeEncodeError, which is its own demonstration that the text interface is bytes end-to-end). Read the counts: "très tôt" is 8 chars but 10 bytes because two accents cost 2 bytes each; "日本語" is 9 bytes for 3 characters; the emoji line is 10 bytes for 7 characters. Token count tracks bytes, not characters. Falsifier: any MISMATCH means your decode is not the inverse of encode, i.e. the vocabulary has holes. Note that errors="replace" would hide truncation mid-codepoint — production streaming tokenizers must buffer partial UTF-8 sequences instead.

Experiment 2 — Build the cost meter before you sign the invoice

You cannot optimise prompt cost without knowing your own tokens-per-word ratio. This meter is the smallest version of the calculator every serving team keeps in a notebook.

python -c "import re; t='The auditor reconciled the ledger. CMS-2024-0042 hash 9f3a1c77e0b4d5a6'; w=re.findall(r'\\w+|[^\\w\\s]', t); print('chars', len(t)); print('whitespace chunks', len(w)); print('est. tokens at 1.3x', round(1.3*len(w)))"

Observed: chars 70 words 13 tokens(word-split) 13, estimate 17 tokens, and $0.00473 for 1,000 prompts — i.e. the whole exercise is five-tenths of a cent until you multiply by a real request volume. The word-regex count is a floor, not the truth: real tokenizers split CMS-2024-0042 into more pieces than the whitespace chunks. The diagnostic value is the ratio between your regex count and the tokenizer's actual count (use the model's tokenizer endpoint or a local tokenizer library). If the ratio for your corpus is above ~1.5, your prompts are structurally expensive and you should measure it on 100 real samples before optimising anything else.

Experiment 3 — The frequency trap

Prove to yourself that BPE's price is frequency, not importance. Take the trainer from section 3 and feed it a corpus where one high-value string is rare.

# paste bpe_train from section 3 first corpus = {"audit": 40, "auditor": 12, "ledger": 30, "qzx": 1} merges, wl = bpe_train(corpus, 8) for k in sorted(wl, key=lambda t: (-wl[t], t)): print(wl[k], " ".join(k))

Verified output: 40 audit</w>, 30 led g e r</w>, 12 audit o r</w>, 1 q z x </w>. Two things to notice. First, "qzx" is preserved at 4 symbols because its frequency is 1 — it can always be encoded, it is just expensive. Second, and more instructive: "audit" collapsed to one token only because its final pair closed at the end-of-word sentinel. "auditor" inherits the audit merge (12 merges of a+u), which is exactly why the sentinel exists: without it, auditor's continuation would have polluted audit's statistics and neither word would get a clean token. Falsifier: if qzx had merged, your count weighting is wrong (you forgot to multiply by frequency).

5 · Failure modes #

  • Cross-tokenizer comparison. You compare model A's loss or cost with model B's, but they used different vocabularies. Perplexity is not comparable across tokenizers at all — only bits-per-byte is (see L16). Symptom: a "cheaper" model wins on cost per token but loses on cost per request.
  • Truncation mid-structure. You truncate by character count and the cut lands inside a JSON object or a code fence. Symptom: the model receives unbalanced brackets and starts hallucinating the missing closing brace.
  • Whitespace sensitivity. Trailing spaces and newlines are absorbed into tokens (" the" ≠ "the"). Symptom: two nominally identical prompts score differently; fixing one space flips a benchmark result.
  • Numeric arithmetic failure. Digits are grouped arbitrarily by the tokenizer, so 1749 may be "174"+"9". Symptom: errors concentrated on carry operations and digit alignment; the model "knows" the rule but miscarries. Mitigation is tool use, not prompting (see L77).
  • Silent byte fallback loss. A tokenizer without full byte coverage turns unknown characters into a single unknown id. Symptom: emoji and CJK in user input vanish from the model's view but remain in your logs — non-reproducible evaluations.
  • Tokenizer drift across versions. Upgrading a tokenizer library changes merges or normalisation. Symptom: identical prompts produce different ids, cached prefixes stop hitting (see L45), and a "no-op" upgrade moves your eval numbers.

7 · Self-check #

Q1. Why is character-level tokenization quadratic-cost while byte-level BPE is not, when both are "lossless"?

Reveal answer

Both are lossless, so the difference is sequence length n: attention prefill costs O(n2). Character-level is ~1 unit per character; BPE collapses frequent substrings into single ids, typically 3–5 characters per token on English, so n shrinks by that factor and attention work by its square. Losslessness is not the axis — length is.

Q2. A document is 2,000 English words. Under a 1.3 tok/word tokenizer it costs how much per 1,000 such documents at $0.28 per million input tokens? And by how much does the bill change for a corpus that runs 2.0 tok/word?

Reveal answer

2,000 × 1.3 = 2,600 tokens/doc × 1,000 = 2.6M tokens. At $0.28/M = $0.728. At 2.0 tok/word: 4.0M tokens = $1.12, a +54% bill for the same document count. Cost scales linearly in tok/word while scope stayed flat — exactly the failure mode of comparing vendors by price per token.

Q3. Diagnostic: your eval accuracy dropped 3 points after a "no-op" library upgrade. What do you check first and what is the signature?

Reveal answer

Hash the vocab file and the merge list, and re-encode a fixed eval split. If the token-id sequences changed (even though the text is identical), the tokenizer drifted; regenerate logits/probabilities accordingly. Signature: identical text, different len(ids) or different ids; cached prefix hit-rate collapses at the same time.

Q4. In the trainer output above, "lower" stays low e r while "newest" becomes one token. State the rule that predicts this without running the code.

Reveal answer

Merge priority is frequency-weighted count, not word importance. The pair e+r in "lower" has count 2 (the word's frequency) and loses to n+e/ne+w/w+est at frequency 6. General rule: a substring merges only if its corpus-wide pair count beats all competitors in the same greedy round, so rare words pay character price.

Q5. Why can you not swap a better tokenizer into an already-trained model?

Reveal answer

The embedding matrix and the output projection are indexed by token id; id k has a learned vector and a learned output direction. A new vocabulary has no correspondence to those ids, so every input would look like noise and the output head would sample from an unrelated basis. Changing the tokenizer requires retraining the embedding rows (at minimum) and usually the whole model — which is why tokenizers are versioned artefacts, not config.
