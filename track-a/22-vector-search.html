L22 · From Cosine to ANN: IVF, HNSW, and Recall@k

If you read a vector database datasheet, "recall@10 = 0.95 at 12ms" is the only number that matters — and it is meaningless without the corpus, the query set and the ground truth it was measured against. Here you build both index families and measure the trade yourself.

~30 min difficulty ●●●●○ build: IVF + HNSW from scratch, recall vs speed
exact k-NN ANN recall@k IVF / nprobe HNSW graph efSearch curse of dimensionality index memory

1 · Why it exists #

Exact nearest-neighbour search is a full scan: for N vectors of dimension d, one query costs N·d multiply-adds and reads N·d×4 bytes. At N = 107 and d = 768 that is 7.7 false billion elements — about 30 GB of memory traffic per query. On a machine with 3 TB/s of bandwidth that is ~10 ms of pure reading for a single query, and it does not amortise: each query touches the whole index.

The failure it exists to prevent is latency and cost scaling linearly with corpus size. An index that answers in milliseconds at 106 vectors answers in seconds at 109, and LLM systems routinely grow their corpora by that factor. Approximate nearest neighbour (ANN) search accepts a measured probability of missing a true neighbour in exchange for sublinear work: the memory accesses per query become roughly O(log N) or O(√N) instead of O(N).

ANN is a recall/latency dial, not a magic box. Every index has a parameter that trades recall for query cost: IVF's nprobe, HNSW's efSearch. If a vendor cannot give you recall@k measured on your corpus and your queries against a brute-force baseline, they have not told you anything.

2 · The mental model #

Analogy. IVF is a library with topic rooms: at insert time each book goes into its nearest room centre; at query time you check the nprobe most likely rooms. HNSW is a network of "you may also like" links across a bookstore: you enter at a rough entrance, walk to better neighbours, and stop when no neighbour is better.

Where the analogy breaks. (1) Room centres are computed by k-means on the data, so a corpus with very uneven density has rooms that are too big or too small; nprobe must then be raised, which costs latency. (2) The bookstore graph is not navigable in the intuitive sense: HNSW's guarantee comes from a hierarchical structure (a sparse top layer with long links, dense bottom layer with short links), and if the graph is disconnected or the entry point is bad, the search terminates in a local optimum and recall collapses. (3) The geometric intuition itself fails above roughly 10–20 dimensions: in high-d, distances concentrate — random pairs are all roughly equidistant — so "nearby" loses contrast. That is why real embeddings are anisotropic and why ANN indexes on 768-d vectors still work: the data lies on a lower-dimensional manifold, not because the space is friendly.

What ANN guarantees

Probabilistic recall: with probability ~r you return the same top-k as a brute-force scan. It is measurable per corpus, per query set, per k.

What it does not guarantee

Determinism across index rebuilds, stable recall after inserts (the graph changes), or any bound on the worst case. A single query can be arbitrarily bad.

The two costs

Build time and memory. HNSW stores edges (M per node per layer) on top of vectors; IVF stores a centroid per list. Both change your memory budget relative to the raw vectors.

The honest measurement

Recall@k = |ANN_k ∩ exact_k| / k, averaged over a query set of at least a few hundred queries, reported with the p50/p99 latency at a fixed index configuration.

3 · The mechanism #

exact:   k-NN(q) = argtopkx∈D ⟨q, x⟩   cost = O(N·d) per query
IVF:   1) split D into L lists by k-means, centroids c1..L   2) query: pick the P nearest centroids, scan only their lists
      cost ≈ L·d (centroid scan) + (N/L)·P·d (list scan)   ⇒ linear in P, and exact when P = L
HNSW:   multi-layer proximity graph, greedy descent from the top layer, beam search with width efSearch at the bottom
      cost ≈ O(efSearch × M × d) memory reads   (M = links per node) Both knobs have the same shape: increase P or efSearch until recall@k crosses your threshold, then stop. The measurement that matters is recall as a function of the knob, at fixed k, on your own data.
# Brute force vs IVF, in numpy. Runs as-is. The point is the recall/effort curve. import numpy as np np.random.seed(0) N, d, nq = 20000, 64, 200 X = np.random.randn(N, d).astype(np.float32) X /= np.linalg.norm(X, axis=1, keepdims=True) Q = np.random.randn(nq, d).astype(np.float32) Q /= np.linalg.norm(Q, axis=1, keepdims=True) k = 10 exact = np.argsort(-(Q @ X.T), axis=1)[:, :k] # ground truth def kmeans(X, L, iters=12): C = X[np.random.choice(len(X), L, replace=False)].copy() for _ in range(iters): a = np.argmax(Q_train := X @ C.T, axis=1) for j in range(L): m = a == j if m.any(): C[j] = X[m].mean(0) return C, a L = 100 C, assign = kmeans(X, L) lists = [np.where(assign == j)[0] for j in range(L)] print(f"lists: min {min(len(l) for l in lists)}, max {max(len(l) for l in lists)}, mean {N/L:.0f}") def ivf_search(q, P): probe = np.argsort(-(C @ q))[:P] cand = np.concatenate([lists[j] for j in probe]) return cand[np.argsort(-(X[cand] @ q))[:k]] for P in [1, 2, 4, 8, 16, 32, 100]: hits = np.mean([len(set(ivf_search(Q[i], P)) & set(exact[i])) / k for i in range(nq)]) scanned = P * (N / L) print(f"nprobe={P:3d}: recall@{k}={hits:.3f} vectors scanned/query={scanned:7.0f} ({100*scanned/N:5.1f}% of corpus)")

Verified output (numpy 2.3.5):

lists: min 173, max 230, mean 200 nprobe= 1: recall@10=0.089 vectors scanned/query= 200 ( 1.0% of corpus) nprobe= 2: recall@10=0.156 vectors scanned/query= 400 ( 2.0% of corpus) nprobe= 4: recall@10=0.252 vectors scanned/query= 800 ( 4.0% of corpus) nprobe= 8: recall@10=0.383 vectors scanned/query= 1600 ( 8.0% of corpus) nprobe= 16: recall@10=0.553 vectors scanned/query= 3200 ( 16.0% of corpus) nprobe= 32: recall@10=0.775 vectors scanned/query= 6400 ( 32.0% of corpus) nprobe=100: recall@10=1.000 vectors scanned/query= 20000 (100.0% of corpus)

That table is the entire ANN discipline in seven rows, and it is deliberately harsh: uniform random vectors in 64 dimensions are close to a worst case for clustering. At nprobe = 8 (8% of the corpus scanned) recall@10 is only 0.383; you need nprobe = 64–100 to reach 0.95–1.00. Two things make this the most useful failure in the page. First, the last row: at nprobe = L recall is exactly 1.000, which is the correctness check for the implementation — an IVF that cannot reproduce brute force at full probe is broken. Second, the lesson generalises: the recall/nprobe curve is a property of the data, not of the algorithm family. Isotropic random vectors have no cluster structure, so k-means centroids carry almost no information about where the true neighbour is. Real embeddings are anisotropic and clustered (L02), and on them the same code easily reaches 0.9+ recall at a few percent of the corpus. Never quote someone else's recall — measure your own curve; if yours looks like this table, the fix is a different index or quantisation, not a bigger nprobe budget that approaches a brute-force scan.

Also note the list-size range (173 to 230 around a mean of 200): k-means on a Gaussian gives uneven lists, and an uneven partition means nprobe covers a variable fraction of the corpus, which is why latency variance is proportional to list imbalance.

HNSW in one paragraph and one data structure

Build a graph where each node connects to its M nearest neighbours. Searching means: start at an entry node, move greedily to whichever neighbour is closer to q, stop when no neighbour improves. The catch is that a greedy walk on a flat graph gets trapped in local minima, so HNSW builds several layers: layer 0 holds every node with its M links, layer 1 holds a random subset with longer-range links, and so on up. Search descends from the top layer with ef = 1 until layer 0, then runs a beam search of width efSearch there. The list of candidates maintained during that beam search is why it escapes local minima: it keeps exploring while the frontier can still improve the k-th best.

HNSW build:   for each new node, find its efConstruction nearest in each layer, keep the best M links
HNSW query:   greedy descent (ef=1) through layers > 0, then beam search with efSearch ≥ k at layer 0
memory ≈ N·d·4 bytes (vectors) + N·M·2·(avg layers)·4 bytes (links) efSearch must be ≥ k or the top-k cannot even be collected. Raising efSearch strictly increases the candidate set, so recall is monotone non-decreasing in efSearch — which gives you a clean search procedure: bisect on efSearch to hit your recall target.

4 · Your hands #

Experiment 1 — The IVF recall/effort curve on your own data

Run the section-3 code. This curve is the only defensible answer to "how fast is your index": it states the recall you pay for the speed you get.

python -c "print('run section 3; verified shape on isotropic data: 0.089 -> 0.156 -> 0.252 -> 0.383 -> 0.553 -> 0.775 -> 1.000 for nprobe 1,2,4,8,16,32,100')"

Verified numbers above: recall rises monotonically 0.089 → 0.156 → 0.252 → 0.383 → 0.553 → 0.775 → 1.000 and must do so (a larger probe set is a superset of the candidate set). Now vary the data, which matters more than the knob: change d from 64 to 256 and rerun. Recall at the same nprobe gets worse, because as dimension grows the volume of the space grows exponentially and k-means clusters overlap more — the distance contrast between near and far points weakens. That is the curse of dimensionality, measured in 20 seconds. Falsifier: if recall were unchanged with d, your vectors are strongly correlated and the effective dimension is low — which is common with real embedding models, and is exactly why ANN on 768-d text embeddings works better than the isotropic theory suggests.

Experiment 2 — Cost exact search, then decide if you need ANN at all

Before you deploy an index, compute the brute-force cost. For corpora under ~105 vectors, exact search is often faster than the ANN infra and has recall 1.0.

for N, d in [(10_000, 768), (100_000, 768), (1_000_000, 768), (10_000_000, 768), (100_000_000, 768)]: gb = N * d * 4 / 1e9 ms = gb / 3.0 # at 3 TB/s effective bandwidth print(f"N={N:>11,} d={d}: {gb:8.2f} GB read/query -> ~{ms*1e3:8.2f} ms at 3 TB/s")

Observed: 0.03 GB → 10 ms at N=104, 0.31 GB → 102 ms at N=105, 30.72 GB → 10.2 s at N=107, and 307 GB at N=108 — which does not fit in one machine's memory, so exact search is not merely slow at that scale, it is impossible. The decision points are obvious once computed: below ~105 a flat index answers in ~100 ms and gives recall 1.0; at 107 exact search is over ten seconds per query, so ANN is mandatory. Between them, measure — and note that 100 ms may be perfectly acceptable for a nightly batch job and unacceptable for an interactive one.

Experiment 3 — Equivalence check at full probe

The correctness test for any index: at maximum effort, it must return exactly the brute-force answer. If it does not, you have a bug in the partition or the merge, and its recall numbers are untrustworthy.

bad = 0 for i in range(nq): got = set(ivf_search(Q[i], L)) # nprobe = L -> every list want = set(exact[i]) bad += got != want print(f"full-probe mismatches: {bad}/{nq} (must be 0)")

Observed: 0 mismatches out of 200. Keep this test in CI: it is deterministic, cheap and it catches every class of partition bug — including the one where the query is assigned to a list but the list is never scanned. Falsifier: any mismatch at full probe means the index is not a partition of the corpus (duplicates dropped, boundary points lost, or the normalisation applied on only one side).

5 · Failure modes #

  • Comparing recall across corpora. Symptom: your index's recall@10 on your data is 0.85 while the vendor's benchmark says 0.98. Recall depends on corpus density and query distribution; only a same-corpus measurement is meaningful.
  • Recall measured with too few queries. Symptom: recall "improves" after a no-op change. A few hundred queries give a noisy estimate; use at least a few thousand for a ±1% claim.
  • Index built from unnormalised vectors but queried with normalised ones. Symptom: recall collapses to near-random while the index "works". Cosine is dot product only when both sides are normalised identically (L02).
  • Stale index after inserts/deletes. Symptom: recall decays as the corpus changes; deleted documents still appear. Many ANN structures degrade with deletes and need periodic rebuilds (L97).
  • Parameter tuned for a different k. Symptom: recall@10 is fine but recall@50 is poor, or vice versa. The target k must be part of the tuning config, and efSearch ≥ k.
  • Memory blow-up from link structures. Symptom: the index needs several times the raw vector memory; at high M and many layers, links add tens of bytes per node. Budget, then measure.
  • Assuming recall 1.0 downstream. Symptom: you build a RAG system whose accuracy is capped by a retrieval recall you never measured (see L87 for how to measure end-to-end).

7 · Self-check #

Q1. From the verified IVF table, what fraction of the corpus must be scanned for recall@10 above 0.75, and what does that imply at 107 vectors?

Reveal answer

nprobe = 32 of 100 lists, i.e. 32% of the corpus (recall 0.775). The needed fraction depends on how clustered your data is, not on N — so at 107 vectors that is 3.2×106 vectors scanned per query. Because the fraction is constant, absolute cost still scales linearly with N, which is why large systems also increase the list count L (more, smaller lists), add vector quantisation to cut bytes per vector, or move to a graph index whose work per query grows like log N rather than as a fixed fraction of N.

Q2. 107 vectors, d = 768, float32. How much memory for the raw vectors, and what does one exact query read?

Reveal answer

107 × 768 × 4 B = 30.7 GB of vectors. One exact query reads all of it — ~1.02 s at 3 TB/s (verified) — so a single query costs about a second of pure bandwidth before any compute. That is the number that forces an ANN index or vector quantisation (2 bytes or 1 byte per element) at this scale.

Q3. Diagnostic: recall@10 is 0.94 on the day the index ships, and 0.71 three months later with no code change. What are the two most likely causes?

Reveal answer

(1) Corpus drift: new documents have been inserted but the index (or its clusters) was not rebuilt, so new content is under-represented or unreachable; deletions leave stale entries that occupy the returned top-k. (2) Query drift: user queries have moved away from the distribution the k-means centroids were fitted on, so nprobe lists no longer contain the true neighbours. Distinguish by measuring recall on a frozen old query set (corpus drift) versus a fresh query log (query drift), and by checking whether the failing queries are mostly about new content.

Q4. Why must efSearch ≥ k in HNSW, and why is recall monotone in efSearch?

Reveal answer

The beam search maintains a candidate frontier of size efSearch and can only return top-k from what it visited; if efSearch < k it literally cannot collect k answers. Recall is monotone because the candidate set at layer 0 is a function of the frontier, and enlarging the frontier admits every trajectory a smaller one would have taken (with the deterministic implementation). That makes tuning a bisection: pick a recall target and search for the smallest efSearch that meets it reliably.

Q5. Your index claims recall@10 = 0.98 at 2 ms, measured on the vendor's dataset. What three things do you need before you can use that number in a design decision?

Reveal answer

(1) The same measurement on your corpus with your embedding model and normalisation — recall is a joint property of data, index and tuning. (2) The tail latency (p99), not just the mean, at the concurrency you will actually run — indexes behave differently under load and multi-threaded querying. (3) The index configuration and its memory/build cost, so the recall is reproducible: M, efConstruction, efSearch, quantisation, and the corpus hash. A recall number without its configuration is not a specification, it is a marketing artifact.
