L07 · Multi-Head Attention: Why Heads, and What They Cost

One attention head produces one convex combination per token — a single "average of what I looked at". Language needs several different lookups at once: previous token, matching bracket, subject, delimiter. Multi-head attention is that fan-out, and its whole implementation risk lives in four transpose calls.

~28 min difficulty ●●●○○ build: head-slicing experiment + shape-correct multi-head attention
head splitting d_head = d_model / H reshape vs transpose concat + W_O per-head scaling specialised heads head redundancy

1 · Why it exists #

Single-head attention computes softmax(QKT/√d)A·V — one distribution over keys per query, hence one weighted average of values. That is a severe bottleneck for exactly the cases that matter in code and contracts. A token inside a JSON object wants to attend to its matching opening brace and to the key name and to the previous token. Averaging those three lookups into one vector destroys the distinction: the output is a blend that a linear layer cannot un-blend, because the averaging happens before any nonlinearity.

Multi-head attention fixes this by splitting the representation space: run H independent attention operations on H disjoint slices of the model dimension, then concatenate. Each head has its own Q/K/V projections, therefore its own similarity metric, therefore its own attention pattern. This is the mechanism that lets a trained model contain a "previous token head", a "syntactic head" and a "copy head" simultaneously — and it is why interpretability work (induction heads, head ablation, attribution patching) addresses heads individually rather than a monolithic attention block.

Multi-head does not increase the FLOPs or the parameter count much: dmodel × dmodel for Q, K, V each, regardless of H. It increases capacity to express multiple distinct attention patterns at the same cost per token, and it multiplies the KV-cache size by H unless you compress — the tradeoff that drives every architecture in Track B.

2 · The mental model #

Analogy. A committee of H specialists reads the same sentence. Each writes its own summary of "what I looked at", and a final editor (the output projection WO) merges the H memos into one document. A syntax specialist and a coreference specialist can disagree without destroying each other's work.

Where the analogy breaks. The specialists do not read the same input — they read disjoint slices of each token's vector. Head h only ever sees coordinates [h·dhead : (h+1)·dhead] after its own projection, so the split is a hard partition of the width, not a soft mixture of experts. And the merge is a single learned linear map shared by all positions, not an editor with judgement: WO is the only place heads can interact, and its rank is dmodel. A second place it breaks: with a small dhead, a head cannot represent an arbitrary similarity function — its capacity is bounded by dhead-dimensional geometry, which is exactly why the number of heads has an optimum rather than "more is better".

Cost is per-head, not per-model

Q,K,V,O are four dmodel×dmodel matrices no matter the split. Attention FLOPs are 4·n2·dmodel per layer regardless of H. Splitting is nearly free.

What costs is dhead

The scaling factor becomes 1/√dhead, not 1/√dmodel. Using dmodel under-scales logits by √H — a silent bug that makes attention too flat.

Heads are not independent

Many heads turn out to be prunable at inference (identified in the literature as a large fraction being removable), but they must be trained as redundancy — pruning before convergence is destructive.

The KV-cache multiplier

Memory for K and V is 2·H·dhead·L per token — the full dmodel width, twice. That is the number GQA/MQA/MLA attack (L09, L10, L33).

3 · The mechanism #

dhead = dmodel / H   (must divide evenly)
For h = 1..H:   Qh = XWQ,h,   Kh = XWK,h,   Vh = XWV,h   where each Wh ∈ Rdmodel×dhead
Oh = softmax(QhKhT/√dhead + mask) Vh ∈ Rn×dhead
out = [O1 ; O2 ; … ; OH] WO   (concat on the feature axis, WO ∈ Rdmodel×dmodel) In practice WQ, WK, WV are stored as single dmodel×dmodel matrices and the head split is a reshape. It is algebraically identical to H separate matrices — and it is why the reshape must be view(n, H, d_head) then transpose(1, 0, 2), not a bare reshape of the (n, H, d_head) output.
import numpy as np np.set_printoptions(precision=3, suppress=True) def softmax(x, axis=-1): x = x - x.max(axis=axis, keepdims=True); e = np.exp(x); return e / e.sum(axis=axis, keepdims=True) rng = np.random.default_rng(1) n, d_model, H = 6, 16, 4 d_head = d_model // H X = rng.normal(size=(n, d_model)) Wq, Wk, Wv, Wo = (rng.normal(size=(d_model, d_model)) / np.sqrt(d_model) for _ in range(4)) def split(z): return z.reshape(n, H, d_head).transpose(1, 0, 2) # (H, n, d_head) Q, K, V = split(X @ Wq), split(X @ Wk), split(X @ Wv) S = Q @ K.transpose(0, 2, 1) / np.sqrt(d_head) # (H, n, n) -- scale by d_head! S = S + np.triu(np.full((n, n), -np.inf), k=1) # causal, broadcast over heads A = softmax(S, -1) O = A @ V # (H, n, d_head) Y = O.transpose(1, 0, 2).reshape(n, d_model) @ Wo # concat heads, then project print("Y[1][:4]:", Y[1][:4]) for h in range(H): ent = -(A[h] * np.log(A[h] + 1e-12)).sum(-1) print(f"head {h} attention entropy at last token: {ent[-1]:.3f} nats")

Verified output (numpy 2.3.5):

Y[1][:4]: [-0.138 -0.032 -0.081 0.535] head 0 attention entropy at last token: 1.759 nats head 1 attention entropy at last token: 1.490 nats head 2 attention entropy at last token: 1.783 nats head 3 attention entropy at last token: 1.633 nats

With random weights the heads are near-uniform, so entropy is close to ln(6) = 1.79 for all four — they do not yet differ. That is the correct expectation at initialisation, and it tells you how to detect a real problem: if all heads share entropy and attention patterns after training, the split is not being used (typical cause: the head-axis transpose is missing, so all "heads" are attending over the same feature block).

Is multi-head just one wide head?

No, and it is worth being precise about why, because people often claim it is "equivalent for linear attention". With one head of width dmodel, the row-stochastic matrix Asingle is shared across all feature dimensions: every output coordinate is a mixture of the values with the same weights, so the output at a position lies in the span of the values weighted by a single distribution. With H heads, each block of dhead output coordinates has its own distribution Ah. Formally, the concatenated output is a block-diagonal mixture: H independent convex combinations. A single head cannot represent that unless all heads agree. Verified numerically in Experiment 1: the two outputs differ by max |single-head - multihead| = 0.6697 on identical inputs.

The four transpose bugs

LineWrong versionSymptom
view(n, H, d_head)view(n, d_head, H)Heads are interleaved across features; attention still runs, quality quietly drops
transpose(1, 0, 2)missing transposeBatch/head axes swapped: heads 1..H-1 silently share head 0's statistics; often no crash when n == H
S / sqrt(d_head)S / sqrt(d_model)Logits too flat by √H; attention never sharpens, model underfits
concat transpose(1,0,2).reshape(n, d_model)reshape(n, d_model) on the (H, n, d_head) tensorHead contents are scrambled into wrong output coordinates; trains but badly, with no error

The last one is the worst kind of bug because shapes all agree. The invariant that catches it: after the reshape, Y[:, h*d_head:(h+1)*d_head] must equal O[h] exactly. Assert that in a unit test.

4 · Your hands #

Experiment 1 — Prove that H heads ≠ one wide head

Build both on identical weights and compare. If they match, either your split is degenerate or your "multi-head" is secretly averaging.

# paste the section-3 setup first, then: Qs = X @ Wq; Ks = X @ Wk; Vs = X @ Wv Ss = Qs @ Ks.T / np.sqrt(d_model) + np.triu(np.full((n, n), -np.inf), k=1) out_single = (np.exp(Ss - Ss.max(-1, keepdims=True)) @ Vs) @ Wo # normalise_single above == softmax(Ss); compare with multi-head Y print("max |single - multi| =", float(np.abs(out_single - Y).max()))

Verified: 0.6697 — a large difference, not floating point noise. The reason is structural: the single head applies one attention distribution to all 16 coordinates, while the multi-head version applies four different distributions to four blocks of 4. Falsifier: if the difference were ~1e-15, the head axis is not being used. This experiment is the cheapest possible check on a rewritten attention kernel.

Experiment 2 — The concat invariant

The assertion that catches the scrambled-concat bug, which produces valid shapes and broken semantics.

O = A @ V # (H, n, d_head) from section 3 concat = O.transpose(1, 0, 2).reshape(n, d_model) ok = all(np.allclose(concat[:, h*d_head:(h+1)*d_head], O[h]) for h in range(H)) print("concat invariant holds:", ok) print("head0 block equals O[0]:", np.allclose(concat[:, :d_head], O[0]))

Both print True. Now remove the transpose (O.reshape(n, d_model)) and rerun: shapes still match, but the invariant fails. That is the exact signature to look for in a code review — correct shape, wrong layout, no exception.

Experiment 3 — Price the head count

Head count is nearly free in compute and in parameters, but it is linear in KV-cache memory and in the size of the attention matrix you must store. Compute all three for a realistic block.

def cost(d_model=4096, n=2048, H=32, bpe=2, layers=32): d_head = d_model // H params = 4 * d_model * d_model # Q, K, V, O flops_attn = 4 * n * n * d_model # QK^T and AV scores = H * n * n * bpe kv = 2 * H * d_head * bpe # bytes per token per layer return d_head, params, flops_attn, scores / 1e6, kv, kv * layers for H in [8, 16, 32, 64, 128]: dh, p, f, sc, kv, kvl = cost(H=H) print(f"H={H:3d} d_head={dh:4d} params={p/1e6:6.1f}M attn_FLOPs={f/1e9:7.1f}G scores={sc:8.2f}MB KV/token/layer={kv:6d}B KV/token(all)={kvl:6d}B")

Parameters and FLOPs are identical across every head count; only dhead and the score-matrix size change, and the score matrix scales as H×n2×2 bytes while KV per token stays fixed at 2·dmodel bytes because H·dhead = dmodel. That last equality is important: naive MHA's KV cache does not depend on head count at all — it depends on dmodel and layers. GQA/MQA break that equality deliberately (L10).

5 · Failure modes #

  • Scaling by d_model instead of d_head. Symptom: attention entropy stays near maximum (uniform) even after many steps; loss decreases but plateaus above target. Check: log mean row entropy per head; healthy trained heads are much sharper than ln(n).
  • Scrambled concat (missing transpose before reshape). Symptom: no crash, quality lower than expected, head ablations show every head matters equally — a sign the layout is mixed. Caught by the concat invariant test.
  • Head transpose applied to the wrong axis after batching. Symptom: works with n == H or batch == 1 and breaks otherwise; classic in code moved from a single-example notebook. Test with batch ≠ heads ≠ n.
  • d_model not divisible by H. Symptom: reshape error, or worse, silent truncation when using //. Assert d_model % H == 0 at construction.
  • Per-head dropout with the wrong probability. Symptom: attention entropy at eval is much sharper than at train, and validation loss is worse than train — the classic unresolved dropout-vs-eval scaling mistake.
  • Head pruning without accounting for KV groups. Symptom: after removing heads you gain little because the KV cache is unchanged (removing a query head that shares a KV head saves compute, not memory). This is why GQA is a design-time choice, not a post-hoc prune (L10).

7 · Self-check #

Q1. With d_model = 768 and H = 12, what is d_head, and what number goes under the square root?

Reveal answer

d_head = 768/12 = 64, so the scaling is 1/√64 = 1/8. Using 1/√768 would make logits √12 ≈ 3.46× too small, i.e. attention too flat. The general statement: the scaling must match the width of the vectors being dotted together, which is d_head in each head.

Q2. Does increasing H from 16 to 64 (fixed d_model = 4096) change parameter count, attention FLOPs, or KV-cache size? Answer each.

Reveal answer

(a) Parameters: unchanged — four dmodel2 matrices either way. (b) Attention FLOPs: unchanged — 4·n2·dmodel for the QKT+AV pair, since H·d_head = dmodel. (c) KV-cache size: unchanged — 2·H·d_head = 2·dmodel bytes per token per layer. (d) Changed: the score matrix count grows with H (each head materialises its own n×n block), and the per-head geometric capacity shrinks. So H trades "how many distinct patterns" against "how much geometry per pattern", at constant compute.

Q3. Diagnostic: a rewritten attention kernel passes every shape check and loss decreases, but the model is 4 points behind a reference run. Name the two most likely causes and the test for each.

Reveal answer

(1) Scrambled concat / missing head transpose — test with the concat invariant concat[:, h*d:(h+1)*d] == O[h]. (2) Wrong scaling factor (d_model instead of d_head) — test by logging per-head attention entropy after a few hundred steps; uniformly high entropy indicates under-scaling. A third candidate: masks broadcast on the wrong axis (test: sequence alone vs in a padded batch). All three are silently wrong, none crashes, which is why the three assertions belong in the kernel's test file.

Q4. Explain precisely why H=4 heads with d_head=4 is not equivalent to H=1 head with d_head=16, even ignoring the output projection.

Reveal answer

Because the attention mixture is applied per head: the output block of coordinates 0..3 is (A1V1), coordinates 4..7 is (A2V2), and so on. A single 16-wide head applies one A to all coordinates. Four heads can express a block-diagonal family of mixtures (4 distinct distributions), a single head can only express rank-one-along-features mixtures. The measured difference on random weights was 0.67 in max-abs, not numerical noise. Only if all four Ah happened to be equal would the two be equivalent.

Q5. Why does removing a query head save compute but not KV memory, and why does that shape the KV-cache optimisations?

Reveal answer

The KV cache stores keys and values per KV head. A query head carries no stored state — it is computed fresh for the current token. Removing one reduces the QKT work for that head only, while K and V must still be kept. Memory is governed by the number of KV heads, which is exactly why GQA/MQA share KV across query heads and MLA stores a compressed latent: the only ways to shrink the cache are to store fewer distinct K/V tensors or fewer bytes per entry.
