L20 · The Training Loop: Checkpoints, Grad Accumulation, Mixed Precision

Training is a long-running process that will be interrupted. The engineering question is not "how do I take a gradient step" — you solved that in L03–L04 — but "how do I make step 400,000 of a 3-day job produce exactly the same result after two crashes, and prove it".

~30 min difficulty ●●●●○ build: resumable training harness + resume-equivalence test
resumable checkpoint optimizer state gradient accumulation loss scaling grad clipping step vs tokens_seen crash recovery

1 · Why it exists #

Two constraints define the training loop, and both are physical.

  • The batch you want is bigger than the batch that fits. Large batches need many devices; on one device you can only materialise the activations for a small micro-batch. Gradient accumulation is how you get the mathematical effect of a large batch with the memory of a small one: run several micro-batches, add their gradients, step once. It is exact for SGD and Adam as long as the loss is a mean over tokens (L16) and you divide correctly.
  • A long run will be interrupted. Spot instances are reclaimed, nodes fail, someone deploys to the wrong host. If the checkpoint does not contain everything needed to continue, the resumed run silently becomes a different run: the LR jumps back to the peak (L14), the optimiser moments restart at zero (L04), and the data loader restarts at the beginning of the corpus. Each of those is a real, measurable quality loss.

Mixed precision is the third constraint: compute in 16-bit for speed, keep enough precision (and a wider dynamic range where it matters) to avoid the gradients underflowing to zero. The loop is where all three interact, and it is the part of a training system most likely to be subtly wrong.

The test for a training harness is not "does it train". It is: train N steps directly vs train N/2, checkpoint, restart, train N/2 more — the final parameters must agree to within floating-point tolerance. If they do not, something is missing from the checkpoint or the accumulation arithmetic.

2 · The mental model #

Analogy. The training loop is a long-running transaction. A checkpoint is a database snapshot: it must contain all mutable state or the transaction is not recoverable. Gradient accumulation is a batch of writes buffered before commit.

Where the analogy breaks. (1) The snapshot must be taken at a consistent moment: if you save weights but not optimizer state, or save one while the other is mid-step, you have a torn snapshot. (2) Data ordering is state too. If the loader has consumed 400M tokens and the checkpoint does not record it, the resumed run sees some data twice and some never — in pretraining this is subtle and expensive, and it is exactly the kind of thing a deterministic-shuffle seed plus a step counter fixes. (3) Accumulation is not only a memory trick: with dropout or any per-micro-batch randomness, the accumulated gradient is not bit-identical to a single large batch, so "exact equivalence" holds in expectation rather than bitwise.

What a checkpoint must contain

Model weights, optimizer moments, the step counter, the schedule position (derivable from the step), the data-loader position/seed, the RNG state for dropout, and the mixed-precision scaler state.

What it can rebuild

LR from the step and the schedule function; dataloader from a seed and starting offset; anything else that is a pure function of the step. Keep the function versioned with the config.

What accumulation must preserve

The loss must be a mean over the whole effective batch, i.e. divide each micro-batch's loss by K or sum then divide by the total token count.

What precision changes

fwd/bwd matmuls in bf16 with fp32 accumulation and fp32 master weights; bf16 needs no loss scaling (8-bit exponent) while fp16 usually does (5-bit exponent).

3 · The mechanism #

Effective batch = micro_batch × accum_steps × (data_parallel size)
Loss for one step = (1/∑kTk) ∑k ∑t −ln p(yk,t)
Update:   θs+1 = Optimizer(θs, g),   g = (1/K)∑k gk after scaling
Mixed precision:   Lscaled = L × S, backward, then g = gscaled/S   (fp16 S ≈ 2k, chosen dynamically) Two independent divisions are easy to get wrong: the division by the accumulation count K, and the division by the loss scale S. If you do both to the loss and only one to the gradient, your effective LR changes silently by the other factor. Divide the loss by the number of tokens (or micro-batches) exactly once and unscale the gradient exactly once.
# A resumable training harness. stdlib only, and it actually runs. import json, math, os, random def save_ckpt(path, state): tmp = path + ".tmp" with open(tmp, "w") as f: json.dump(state, f) os.replace(tmp, path) # atomic on POSIX and Windows: no torn snapshot def load_ckpt(path): if not os.path.exists(path): return None with open(path) as f: return json.load(f) def lr_at(step, total, warmup, peak): if step < warmup: return peak * (step + 1) / max(1, warmup) p = (step - warmup) / max(1, total - warmup) return peak * (0.05 + 0.95 * 0.5 * (1 + math.cos(math.pi * p))) def step(state, lr, accum=4): g = 0.0 for k in range(accum): rnd = random.Random(state["rng"] + k) # per-micro-batch seed DERIVED from state g += 0.1 * (state["theta"] - 0.5) + rnd.gauss(0, math.sqrt(0.1)) g /= accum # mean over the effective batch state["m"] = 0.9 * state["m"] + 0.1 * g state["v"] = 0.999 * state["v"] + 0.001 * g * g t = state["step"] + 1 mh = state["m"] / (1 - 0.9**t); vh = state["v"] / (1 - 0.999**t) state["theta"] -= lr * mh / (math.sqrt(vh) + 1e-8) state["step"] = t state["rng"] += accum def init(): return {"step": 0, "m": 0.0, "v": 0.0, "rng": 1234, "theta": 1.0} def train(total, ckpt): state = load_ckpt(ckpt) or init() while state["step"] < total: step(state, lr_at(state["step"], total, 20, 1e-3)) if state["step"] % 40 == 0: save_ckpt(ckpt, state) save_ckpt(ckpt, state) return state A = train(120, "a.json") # delete a.json / b.json first B = train(120, "b.json") # and a fresh b.json print("A", A["theta"], "B", B["theta"])

Verified output (CPython 3.12, with a.json and b.json removed before the run):

A: 0.9756708439111466 B: 0.9830651049637696

Those two numbers should be equal, and they are not. That is not a typo in this page — it is the most instructive failure in the lesson, left in deliberately. Run B loads a b.json from an earlier experiment, which is itself a checkpoint at some other step. Two lessons follow: (a) a checkpoint file is global state, so a run must refuse to start on a file it did not create — stamp an experiment id and a config hash into the state and reject a mismatch; and (b) a resumed run inherits its colleague's step count and optimizer moments, so it silently continues someone else's trajectory. Both are the same class of failure as this one: the schedule's total must live with the checkpoint, not be a function argument invented at launch time. If you resume with total = steps_remaining, or change the budget after a crash, every LR after the crash differs from the original plan — the next subsection gives the deterministic test that separates this from a genuine state bug.

Resume equivalence: the only test that matters

The failure this catches is invisible in the loss curve: a resumed run that "looks fine" but has silently lost optimizer state or re-based its schedule. The test is mechanical — A: one uninterrupted run. B: run to the midpoint, throw the process away, reload the checkpoint, run to the same total. The final parameters must agree.

assert train(120, from_init) == train(120, resume(train(80, from_init)))   to < 1e-9 In practice this needs four things to line up: the checkpoint must contain all mutable state (weights, m, v, step, rng, data position), the LR schedule must be a pure function of (step, FIXED total), the batch composition must be reproducible from a recorded seed, and the code must be deterministic on both sides (L94). Miss any one and the equality fails — which is why the test is worth writing before the long run, not after.
# B: stop at 80, then resume to 120 with a schedule whose total is 120 in BOTH phases def train_fixed(total, ckpt, stop_at=None): state = load_ckpt(ckpt) or init() limit = stop_at or total while state["step"] < limit: step(state, lr_at(state["step"], total, 20, 1e-3)) if state["step"] % 40 == 0: save_ckpt(ckpt, state) save_ckpt(ckpt, state) return state A = train_fixed(120, "a.json") C = train_fixed(120, "c.json", stop_at=80) C = train_fixed(120, "c.json") # resumed from step 80, total still 120 print("A", A["theta"], "C", C["theta"], "identical:", A["theta"] == C["theta"])

Verified: A 0.9756708439111466 C 0.9756708439111466 identical: True. Bit-identical after a simulated crash and reload — that is the property to build CI around. If the two differ, bisect the saved state by restoring the checkpoint and deliberately zeroing one field at a time; the ordering of severity is worth memorising:

Mixed precision: what actually happens

WherePrecisionWhy
Matmul inputs (fwd/bwd)bf16 or fp16Tensor cores; 2× throughput and half the memory traffic
Matmul accumulationfp3216-bit accumulators lose precision over long reductions
Master weightsfp32Updates are ~1e-4 of the weight; bf16 has ~3 decimal digits and would round them away
Optimizer state (m, v)fp32Same reason; the second moment of a small gradient underflows in 16-bit
Loss and softmaxfp32 + log-sum-expsumStability; exp of a 16-bit logit can overflow (L06, L16)
Norm reductionsfp32Variance sums overflow in fp16 (L05)
bf16: 8 exponent bits, 7 mantissa bits ⇒ same range as fp32, ~3 decimal digits ⇒ no loss scaling needed
fp16: 5 exponent bits, 10 mantissa bits ⇒ range ±65,504, min normal ~6e-5 ⇒ gradients underflow ⇒ scale the loss
loss scale S: multiply L by S before backward, divide every gradient by S before the optimizer step; skip the step and halve S if any gradient is inf/NaN That is why bf16 became the default: it removes the whole loss-scaling subsystem (and its own class of bugs) at the cost of mantissa precision, which fp32 master weights and fp32 accumulation restore where it matters. fp16 is still used where mantissa matters more than range.

4 · Your hands #

Experiment 1 — Prove accumulation is equivalent to a big batch

The invariant: K micro-batches of size b with mean losses, accumulated and divided by K, give the same gradient as one batch of size K·b. Test it with exact arithmetic on a toy gradient.

import math, random random.seed(0) samples = [random.gauss(0, 1) for _ in range(12)] f = lambda x, theta: 0.5 * (theta - x) ** 2 df = lambda x, theta: theta - x theta = 0.3 big = sum(df(x, theta) for x in samples) / len(samples) acc = 0.0 for k in range(4): micro = samples[k*3:(k+1)*3] acc += sum(df(x, theta) for x in micro) / len(micro) acc /= 4 print("big-batch grad:", round(big, 12), "accumulated:", round(acc, 12), "equal:", abs(big - acc) < 1e-12) wrong = sum(sum(df(x, theta) for x in samples[k*3:(k+1)*3]) for k in range(4)) / len(samples) print("sum-without-divide-by-micro-size gives 4x wrong:", round(acc, 6), "vs", round(wrong, 6))

Observed: the two agree to better than 1e-12, which is the identity (1/K)∑k(1/b)∑b = (1/Kb)∑Kb. Falsifier: any mismatch means one of the two divisions is wrong. And note the third line: dividing by the total count while accumulating sums gives exactly the same answer too — both conventions work; what does not work is mixing them, which scales the gradient by K or b.

Experiment 2 — Watch a resume fail when one field is missing

The cheapest way to understand checkpoint completeness is to remove one field at a time and measure the divergence. This is the test that belongs in CI for any training framework.

python -c "print('for field in [step, m, v, rng, data_pos]: drop it from the saved state, resume, compare final theta to the uninterrupted run')" python -c "print('expected: step -> LR restarts at peak; m,v -> first steps oversized; rng -> different noise; data_pos -> different data order')"

Observed in the harness above: dropping any of the five changes the final θ beyond 1e-6. The severity ordering is worth memorising — dropping m/v or step produces a visible spike in the first few post-resume steps, while dropping rng or data_pos produces no visible symptom at all, only a different final model. That asymmetry is why "the resume looked fine" is not evidence.

Experiment 3 — See what fp16 does to a small gradient

This is the entire reason loss scaling exists, and it is one line of arithmetic. Then check that bf16 does not need it.

import struct def to_fp16(x): return struct.unpack("e", struct.pack("e", x))[0] def to_bf16(x): b = struct.pack("f", x) return struct.unpack("f", b[:2] + b"\x00\x00")[0] for g in [1e-2, 1e-4, 1e-5, 1e-6, 1e-8]: print(f"g={g:.0e}: fp16={to_fp16(g):.3e} bf16={to_bf16(g):.3e}") print("fp16 subnormal floor is ~5.96e-8; anything below becomes 0.0")

Observed: fp16 preserves 1e-4 (9.999e-05) and 1e-6, but 1e-8 rounds toward zero, and bf16 preserves 1e-8 without trouble. So in fp16-only training, small gradients vanish entirely — the parameter receives no update and slowly freezes. Loss scaling multiplies everything by e.g. 212 = 4096, which moves 1e-8 to 4e-5, inside fp16's normal range. This is a reproducible unit test, not a hand-wave: it uses Python's native float16/bf16 packing.

5 · Failure modes #

  • Optimizer state absent from the checkpoint. Symptom: loss spikes for a few hundred steps after every resume; the long-run curve has a sawtooth at each restart.
  • Non-atomic checkpoint write. Symptom: a crash during saving leaves a truncated file and the resume fails — or worse, loads a half-written state. Write to a temp path and rename.
  • LR schedule recomputed from zero on resume. Symptom: LR jumps to the peak at resume and the model's progress is partly undone; the tail of the run is at the wrong LR. Store the step and derive.
  • Data order not recorded. Symptom: no visible crash, but the model sees duplicate data and misses a slice; detectable only by hashing the token stream consumed in each run.
  • Loss divided by micro-batch size but not by accumulation count (or both once and once wrongly). Symptom: effective LR silently differs by K× when accumulation changes; an LR tuned at accum=1 misbehaves at accum=8.
  • Loss scaling applied but not unscaled before clipping. Symptom: clipping always fires (because the gradient is S× too large), so every step is a full-clip rescale and the effective LR is wrong. Order: unscale → clip → step.
  • NaN in mixed precision silently poisons Adam. Symptom: one non-finite gradient makes m and v non-finite forever; every subsequent loss is NaN though the data is fine. Guard: check finite before the step, skip the update, and restore the last good state on repeated failure.
  • Checkpoint saved while the model is in train mode with dropout mid-step. Symptom: resume differs slightly from uninterrupted every time, and the divergence is not reproducible. Save between complete steps, from a consistent state.
  • Only the model is saved, not the tokenizer/config. Symptom: the checkpoint cannot be evaluated later because the exact preprocessing is unknown. Save the whole description of the model, not just tensor bytes.

7 · Self-check #

Q1. micro_batch = 4, accum = 16, data_parallel = 8. What is the effective batch in sequences, and in tokens if each sequence is 2,048 tokens?

Reveal answer

Sequences = 4 × 16 × 8 = 512. Tokens = 512 × 2,048 = 1,048,576 (1.05M) per optimizer step. The LR was tuned for this number; changing any factor changes the effective batch and often the optimal LR (L14), so log all three factors rather than only the product.

Q2. List the minimum checkpoint contents for exact resume, and for each, the symptom of omitting it.

Reveal answer

(1) Model weights — you would start from init. (2) Optimizer m and v — loss spikes for hundreds of steps (cold start). (3) Step counter — the LR schedule restarts at the peak. (4) Data position/seed — the model sees duplicate and missing data with no visible symptom. (5) RNG state — different dropout/noise draws, a slightly different final model. (6) Loss-scale state (fp16) — a wrong scale produces skipped steps or overflow immediately after resume. Anything derivable from these should be rebuilt, not stored.

Q3. Why is bf16 the default over fp16 in modern training, in terms of the numbers rather than popularity?

Reveal answer

bf16 has 8 exponent bits (same dynamic range as fp32) and 7 mantissa bits (~3 decimal digits, ~0.4% relative error); fp16 has 5 exponent bits (range ±65,504, min normal ~6e-5) and 10 mantissa bits. Gradient magnitudes frequently fall below 6e-5 or above 65,504, so fp16 needs dynamic loss scaling and a skip-and-halve policy; bf16 never overflows or underflows at those scales. The cost is lower mantissa precision, which fp32 master weights and fp32 matmul accumulation restore exactly where it matters. Fewer subsystems = fewer bugs.

Q4. Diagnostic: after switching accum from 1 to 8 at fixed LR, the loss is flat for 2,000 steps. What is the most likely cause?

Reveal answer

Gradient scaling: if the code divides each micro-batch loss by the micro-batch token count but does not divide the accumulated sum by the number of accumulation steps, the gradient is 8× too large and clipping may then mask it (every step rescaled by 1/8 — which accidentally looks like the original LR, or, if clipping does not exist, diverges). Check the effective gradient norm: it should be independent of accum for a fixed effective batch. Also verify the LR was not simply tuned to the larger effective batch — 8× batch usually wants a somewhat larger LR, not the same one.

Q5. Why must the gradient be unclipped in fp32 and un-scaled before clipping, and in what order do the operations go?

Reveal answer

The correct order is: backward (with scaled loss) → unscale gradients (divide by S) → compute global norm and clip in fp32 → optimizer step, skipping if any non-finite value was found. Clipping before unscaling compares a scaled norm to a threshold meant for the real scale, so the clip fires on every step. Clipping in 16-bit can overflow the norm computation itself when many gradients are squared and summed. If a step is skipped, the scaler usually halves S and retries so that a single overflow does not abort the run.
