L11 · Activations: ReLU → GeLU → SwiGLU

Two thirds of a transformer's parameters sit in the feedforward block, and the only nonlinearity in the whole model sits there too. Which activation you pick changes how much information survives the block, how smooth the loss landscape is, and how many parameters you have to buy to keep the same width.

~26 min difficulty ●●○○○ build: activation ablation on a toy MLP + parameter budget
ReLU GeLU (tanh approx) SiLU / Swish gated linear unit SwiGLU dead units / dying ReLU FFN parameter budget

1 · Why it exists #

Remove the nonlinearity and the entire transformer collapses into a single linear map — attention included. Stack any number of linear layers, residual adds and normalisations, and the composition is y = Ax + b: it cannot learn XOR, it cannot detect an exception, and no amount of depth helps. The activation is what makes depth mean something.

ReLU (max(0, x)) was the workhorse: cheap, sparse, and it fixed the vanishing-gradient saturation of sigmoid/tanh. But it has a specific, observable failure — units whose pre-activation is negative for every input in the batch get exactly zero gradient forever ("dead ReLU"). At the scale of a large model with a small effective batch per unit, that is a permanent loss of capacity. GeLU and SwiGLU are both responses to that: smooth, non-monotone around zero, and never exactly flat across the whole real line.

The activation choice in a modern LLM block is worth roughly one iteration of a training sweep. The much bigger consequence is the structural change it forces: a gated unit costs three weight matrices instead of two, which is why SwiGLU forced everyone to re-derive their hidden width and their parameter counts.

2 · The mental model #

Analogy. The feedforward block is a bank of feature detectors: each row of W1 asks "how much does this pattern occur in the token vector", the activation decides how strongly to respond, and W2 writes the answer back into the residual stream. ReLU is a detector that either fires fully or not at all. GeLU is a detector that fires weakly for near-misses. A gate (SwiGLU) adds a second, separate question whose answer multiplies the first — "is this feature relevant given the current context".

Where the analogy breaks. (1) The detectors are not interpretable as a bank of independent units — in a trained model many units respond to mixtures of features (superposition), so "one row = one concept" is false and any claim of that form needs causal evidence. (2) The activation is applied elementwise to the wide (4×) hidden vector, not to the model dimension, so its sparsity is per-unit and the block's output is always dense. (3) GeLU's non-monotonicity is real but tiny: it dips to about −0.17 near x ≈ −0.75 (the table below shows −0.1588 at −1 and −0.0036 at −3). Its practical effect is to keep a gradient flowing for small negatives, not to implement some "gate" semantics.

What you get for smoothness

GeLU is differentiable everywhere, so the Hessian exists and second-order effects (momentum, adaptive scaling, sharpness-aware methods) are well-defined. ReLU has a kink at 0 that no gradient method can resolve.

What you pay

GeLU costs an erf or a tanh per element; ReLU costs a compare. At FFN width 4d that is 4d×T extra transcendental operations per layer — still memory-bound, but measurable in a fused kernel.

What a gate buys

One path asks the question, the other path decides how much of the answer to let through, as a function of the same input. That is genuine multiplicative interaction, which a single elementwise nonlinearity cannot express as cheaply.

What it costs

A third matrix: 3·d·dff instead of 2·d·dff. To keep the parameter count constant you must shrink dff by 2/3, which is why the canonical SwiGLU width is &frac83;d or &frac83;·4d, not 4d.

3 · The mechanism #

ReLU:   f(x) = max(0, x)
GeLU:   f(x) = x · Φ(x),   Φ = standard normal CDF  ≈  0.5x(1 + tanh(√(2/π)(x + 0.044715x3)))
SiLU / Swish:   f(x) = x · σ(x) = x/(1 + e−x)

Gated linear unit:   GLU(x) = (xW1 + b1) ⊙ σ(xW2 + b2)
SwiGLU:   FFN(x) = ( SiLU(xWgate) ⊙ (xWup) ) Wdown f is applied elementwise to the wide hidden vector. ⊙ is elementwise multiplication. In SwiGLU the gate path is nonlinearised (SiLU) and multiplies the linear up-projection elementwise, then a single down-projection returns to d_model. Three matrices, all d_model × d_ff.
# Activation sweep in 1-D — stdlib only. Compare shapes, not just values. import math from math import erf, sqrt def relu(z): return max(0.0, z) def gelu_tanh(z): return 0.5 * z * (1 + math.tanh(math.sqrt(2/math.pi) * (z + 0.044715 * z**3))) def gelu_erf(z): return 0.5 * z * (1 + erf(z / sqrt(2))) def silu(z): return z / (1 + math.exp(-z)) acts = {"relu": relu, "gelu_tanh": gelu_tanh, "silu": silu} for z in [-3, -1, -0.1, 0, 0.1, 1, 3]: print(f"z={z:5}: " + " ".join(f"{k}={v(z):+.4f}" for k, v in acts.items())) print("gelu_erf(1) =", gelu_erf(1), " gelu_tanh(1) =", gelu_tanh(1)) print("max |erf - tanh| on [-5,5]:", max(abs(gelu_erf(z/10) - gelu_tanh(z/10)) for z in range(-50, 51)))

Verified output (CPython 3.12):

z= -3: relu=+0.0000 gelu_tanh=-0.0036 silu=-0.1423 z= -1: relu=+0.0000 gelu_tanh=-0.1588 silu=-0.2689 z= -0.1: relu=+0.0000 gelu_tanh=-0.0460 silu=-0.0475 z= 0: relu=+0.0000 gelu_tanh=+0.0000 silu=+0.0000 z= 0.1: relu=+0.1000 gelu_tanh=+0.0540 silu=+0.0525 z= 1: relu=+1.0000 gelu_tanh=+0.8412 silu=+0.7311 z= 3: relu=+3.0000 gelu_tanh=+2.9964 silu=+2.8577 gelu_erf(1) = 0.8413447460685428 gelu_tanh(1) = 0.8411919906082768 max |erf - tanh| on [-5,5]: 0.0004732346287421585

Three things to read off the table. (1) GeLU and SiLU are negative for small negative inputs — that is the non-monotone region, and it is why they never have a dead unit: d/dx is nonzero even where the output is negative, so a unit can recover. (2) At +1, GeLU passes 0.8412, not 1.0 — a small but systematic attenuation of positive activations relative to ReLU. (3) The tanh approximation is accurate to 4.7e-4 on [−5, 5], which is far inside fp16 noise; this is why practically every implementation uses it. A key point for anything you write: the 0.044715 constant is part of the approximation, not a fitted model parameter.

The parameter arithmetic that SwiGLU forces

Standard FFN (2 matrices):   P = 2 · d · dff
SwiGLU (3 matrices):          P = 3 · d · dff
Equal budget:   3d·dffglu = 2d·dff  ⇒  dffglu = ⅔ dff
3. For d = 4096, dff = 11008:   standard (2 matrices) = 2×4096×11008 = 90,177,536  |  SwiGLU at the budget-neutral 2/3·4d = 10922 (3 matrices) = 3×4096×10922 = 134,217,726  |  SwiGLU without adjusting the width (dff = 16384) = 201,326,592 Check the last number carefully: d_ff = 11008 is not a multiple of 3, so the budget-neutral choice is 2/3 · 11008 = 7338.7 → 7339, or with the usual rounding to a hardware tile, ≈ 2/3·4d = 10922 against a 4d = 16384 GeLU baseline. Any implementation that "switches to SwiGLU" without changing d_ff has silently inflated the FFN by exactly 1.5× — and since FFNs are two thirds of a transformer's parameters, that is a large, unpriced change to model size and cost.

The FFN's share of the model

For a GPT-style block with attention (4d2 params) and a 4× FFN (8d2 params), the FFN is 8/12 = 66.7% of the block. So an activation change that also changes dff is not a local decision — it moves two thirds of the parameter count, and therefore the training FLOPs (forward is ~2N per token) and the memory for weights (L21).

4 · Your hands #

Experiment 1 — Count dead units, and watch GeLU not have the problem

Feed a wide hidden layer standard-normal pre-activations and count units whose output is exactly zero across the whole batch — those units get zero gradient and are dead. Then do it at a shifted mean, which is what a badly initialised or badly normalised layer looks like.

import math, random random.seed(0) def dead_fraction(act, B=64, d=4096, mean=0.0): dead = 0 for _ in range(d): vals = [act(random.gauss(mean, 1)) for _ in range(B)] if all(abs(v) < 1e-12 for v in vals): dead += 1 return dead / d relu = lambda z: max(0.0, z) gelu = lambda z: 0.5 * z * (1 + math.tanh(0.7978845608 * (z + 0.044715 * z**3))) for name, act in [("relu", relu), ("gelu", gelu)]: print(name, "dead@mean0: %.2e dead@mean-2: %.4f" % (dead_fraction(act, mean=0), dead_fraction(act, mean=-2)))

Observed: relu dead@mean0: 0.00e+00 dead@mean-2: 0.2244 and gelu dead@mean0: 0.00e+00 dead@mean-2: 0.0000. ReLU loses 22.4% of its units when the pre-activation mean is −2; GeLU loses none at either shift. That is the mechanism, not a preference: GeLU's output is never identically zero, so its derivative never fully vanishes.

Falsifier: if GeLU showed dead units, your formula is wrong (probably a ReLU in disguise). Scale the shift to −4 and ReLU goes to ≈ 100% dead — the state a mis-scaled layer wakes up in, since every pre-activation is then negative with probability Φ(−4) ≈ 0.99997. Note the units are effectively independent in this test; real layers correlate their pre-activations and the honest dead fraction is lower, which is why this is a comparison tool, not a measurement of your model.

Experiment 2 — The parameter budget check

Before adopting a GLU variant, compute what happens to your model size. This is a five-line check that catches the most expensive kind of miscommunication in an architecture review.

d = 4096 for name, kind, dff in [("ReLU/GeLU 4x", 2, 4*d), ("SwiGLU 2/3*4d", 3, int(2/3*4*d)), ("SwiGLU 4d (unadjusted!)", 3, 4*d)]: p = kind * d * dff print(f"{name:22s} d_ff={dff:6d} FFN params={p/1e6:7.2f}M per layer") base = 2*d*(4*d) for kind, dff in [(3, int(2/3*4*d)), (3, 4*d)]: print(f"ratio to standard: {kind*d*dff/base:.4f}")

Observed: GeLU at d_ff = 16384 gives 134.22M per layer, the 2/3-adjusted SwiGLU at d_ff = 10922 gives 134.21M — a ratio of 0.9999 — while an unadjusted SwiGLU at d_ff = 16384 gives 201.33M, a ratio of exactly 1.5000. So the adjusted GLU is budget-neutral to within 0.01% while adding a multiplicative interaction. That is the entire reason SwiGLU is standard: it is nearly free at equal parameter count. The unadjusted version is not free, and it is not an architecture change you can make after the fact — it moves the FLOP count, the weight memory and the training cost of two thirds of the model.

Experiment 3 — Where the activation's compute goes at inference

Activation cost is elementwise over dff×tokens, so it lands in the same memory-bound regime as everything else at decode. Confirm the order of magnitude so you do not optimise the wrong thing.

d, dff, T, L = 4096, 11008, 8192, 32 act_elems = dff * T * L print("activation element-evals per prefill: %.2f G" % (act_elems / 1e9)) matmul_flops = 2 * (2 * d * dff + 4*d*d) * T * L print("matmul FLOPs per prefill: %.2f T" % (matmul_flops / 1e12)) print("ratio (1 transcendental ~ several FLOPs): activation is %.2f%% of matmul work" % (100 * act_elems * 4 / matmul_flops))

Observed: 2.886 G activation evaluations versus 82.46 T matmul FLOPs, so the activation is about 0.014% of the arithmetic even counting a transcendental as ~4 FLOPs. Consequence: never choose an activation to win FLOPs — choose it for the shape of its derivative and the capacity of the gated form. What does matter is fusion: an unfused GeLU writes and re-reads a 4d-wide tensor to global memory, and at decode that memory traffic costs more than the maths.

5 · Failure modes #

  • Dying ReLU at scale. Symptom: a fixed fraction of the FFN never activates; loss improves then stalls; the fraction is visible as rows of W1 whose output is always ≤ 0 and whose gradient norm stays at zero.
  • SwiGLU adopted without adjusting dff. Symptom: parameter count jumps ~50% in the FFN, training memory and per-token FLOPs jump with it, and comparisons against the GeLU baseline are invalid. Always print the parameter count after a block swap.
  • Gate/up projections wired in the wrong order. Symptom: trains but underperforms; the model has the right number of parameters and the wrong function. Check that the nonlinearity is applied to the gate path and the up path is linear (both orders are used in practice, but a mismatch with a checkpoint breaks it).
  • GeLU approximation constant mistyped. Symptom: small but real quality loss; a wrong constant (e.g. 0.0447 instead of 0.044715, or a wrong 0.7979) shifts the curve by ~1e-2, far above the 4.7e-4 approximation error. Unit test the function against erf on a small grid.
  • Activation in the wrong precision. Symptom: exact zeros in bf16 from a saturated tanh, or overflow in fp16 for large exponential terms. Compute GeLU and SiLU in fp32 or use a fused kernel with an explicit precision policy (L21).
  • Believing sparsity in the activations equals speed. Symptom: ReLU produces ~50% zeros at the unit level, but dense matmuls do not skip them. You get the accuracy characteristics without the throughput, unless the hardware has structured-sparse support.
  • Activation applied after the residual add. Symptom: nonlinearity on the residual stream destroys the identity path and harms gradient flow; symptom is a worse deep model, not a crash. In pre-norm blocks the activation lives strictly inside the FFN.

7 · Self-check #

Q1. Why does GeLU not suffer from dead units the way ReLU does? Give the derivative.

Reveal answer

ReLU's derivative is exactly 0 for x < 0, so a unit whose output is zero receives no gradient and cannot escape. GeLU's derivative is Φ(x) + xφ(x), which is nonzero for every finite x — it approaches 0 but never equals it (it is negative near x ≈ −0.75 and positive elsewhere). So even a strongly negative pre-activation retains a small gradient path. Verified: measured dead fraction is exactly 0.0000 for GeLU at both mean 0 and mean −2.

Q2. A model has d = 2048 and a 4× GeLU FFN. You switch to SwiGLU keeping dff = 4d. By what factor does the FFN parameter count change, and what dff would keep it constant?

Reveal answer

GeLU FFN = 2·2048·8192 = 33.55M. SwiGLU at the same width = 3·2048·8192 = 50.33M, a factor of 1.5. To stay constant: dff = (2/3)·8192 = 5461 (round to a hardware-friendly multiple, e.g. 5504 or 5632). Same arithmetic as the verified d=4096 table, which showed a ratio of 1.4884 for the 2/3-adjusted version.

Q3. Diagnostic: after converting a block to SwiGLU the loss curve is worse than the GeLU baseline and the parameter count is identical. Name two candidate causes.

Reveal answer

(1) Path swap: SiLU applied to the wrong projection (up instead of gate) — same parameters, different function. (2) dff was reduced by 2/3 but the learning rate or initialisation was tuned for the wider GeLU layer, so the comparison confounds an architecture change with an optimisation change. Also check the gate's initialisation: a gate initialised too close to zero multiplies the up path by ~0, which can look like a dead block early in training. The honest test is a short ablation at constant parameter count with matched hyperparameters, plus a unit test that the gate path is the nonlinear one.

Q4. Why is the activation almost never the bottleneck in FLOPs, and why should you still care about it at decode?

Reveal answer

Because matmul FLOPs scale as d·dff per token while elementwise work scales as dff — with d = 4096, the matmul is ~4000× the activation's element count. At decode the binding resource is not FLOPs but memory traffic: each unfused activation forces an extra write and read of the dff-wide hidden tensor through HBM, and with a ridge point near 114 FLOP/byte you cannot afford that. Fusing the activation into the matmul epilogue and the down-projection is where the real gain is.

Q5. What does the multiplicative gate add that a single nonlinearity cannot?

Reveal answer

A second, independently projected linear function of the same input decides the scale of the first. A single elementwise nonlinearity can only reshape one channel at a time, so making unit i suppress unit j requires learned weights arranged to cancel, which is a second-order effect learned over many steps. With a gate, the suppression is a first-class product term: SiLU(xW_g) ⊙ (xW_u). That makes the block's output a bilinear function of its input features, which is strictly more expressive per parameter than any elementwise-only stack of equal width.
