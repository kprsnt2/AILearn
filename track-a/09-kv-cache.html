L09 · KV Cache: The True Cost of Memory

Generation is not one expensive computation, it is thousands of cheap ones, and each one re-reads every weight plus the whole conversation so far. The KV cache is what makes that affordable — and it is also what limits your batch size, your context window, and therefore your gross margin per GPU.

~30 min difficulty ●●●○○ build: prefill vs decode throughput model
prefill vs decode KV cache bytes/token arithmetic intensity memory-bound decoding batch size ceiling time-to-first-token context-cost model

1 · Why it exists #

Autoregressive generation emits one token at a time. Without any caching, generating token number t means running the full forward pass over t tokens — and attention over t tokens already costs O(t2) — so generating a 4,000-token answer would reprocess 1+2+…+4000 ≈ 8 million token-positions of attention work. Almost all of that work is recomputation of keys and values that did not change.

There is nothing in the causal transformer that requires recomputation: token j's key and value depend only on token j and everything before it, so once computed they are fixed forever. The KV cache stores them. At step t you compute K and V for the one new token and concatenate, then attend against the stored matrix. Generation goes from O(n2) total to O(n) per step and O(n2) in aggregate only for the attention part, with the weight matmuls done once per token instead of once per token per prefix.

The KV cache is a memory-for-compute trade with a brutal exchange rate: for a 32-layer, 4096-wide model in fp16 it is 512 KiB per token. At 128k context, one request needs 68.7 GB of cache before you have loaded a single weight. That number, not the parameter count, usually decides your server configuration.

2 · The mental model #

Analogy. Prefill is reading a whole document into notes (one expensive pass). Decode is annotating one new line at a time while consulting the notes you already took. The notes are the cache: you never re-read the document, but the notes grow with every line and you must keep them on a desk that has a fixed area.

Where the analogy breaks. Two ways. (1) The notes are not a summary — they are exact and double the model's per-token memory footprint, so they grow linearly and never compress by themselves. (2) The bottleneck is not reading speed but arithmetic intensity: at decode, each token's forward pass does only ~2·N FLOPs while touching ~2·N bytes of weights, an intensity near 1 FLOP/byte, far below the several-hundred FLOP/byte a modern accelerator delivers per byte of HBM bandwidth. So decode runs at a small fraction of peak compute, and batching is the only way to raise intensity: 32 concurrent requests read the same weights once for 32 tokens' worth of work.

Prefill: compute-bound

All n prompt tokens at once. FLOPs ≈ 2·N·n. The GPU is busy; latency is set by FLOPs/peak. This is the time-to-first-token (TTFT) phase.

Decode: memory-bound

One token at a time, FLOPs ≈ 2·N. Time per step is set by reading weights plus KV cache. This is the inter-token latency phase, and it governs tokens/second.

What the cache buys

Per decode step, attention reads only the new token's K,V plus the stored ones (O(n) bytes) instead of recomputing all n projections (O(n·d2) FLOPs).

What the cache costs

2·L·H·dhead·bytes per token, contiguous and unbounded. It is the reason "long context" is a memory product, not just a model capability.

3 · The mechanism #

KV bytes per token = 2  (K and V)  × L  (layers)  × Hkv  (KV heads)  × dhead × bytes_per_element

cache bytes per request = tokens × KV bytes per token    (grows every step)
cache bytes for a batch = batch_size × tokens × KV bytes per token

weight bytes ≈ Nparams × bytes_per_element   (read once per decode step) For naive multi-head attention Hkv·dhead = dmodel, so the cache is 2·L·dmodel elements per token regardless of head count (verified in L07). L10 replaces Hkv with a smaller number; L33 replaces the whole thing with a latent.
# KV cache and decode cost model — stdlib only, runs as-is. n, H, dh, L = 8192, 32, 128, 32 bpe = 2 # fp16 kv_per_tok = 2 * H * dh * bpe * L print("KV bytes/token:", kv_per_tok, "=", kv_per_tok / 1024, "KiB") print("8k ctx, batch 1 : %.2f GB" % (kv_per_tok * 8192 / 1e9)) print("128k ctx, batch 1: %.2f GB" % (kv_per_tok * 131072 / 1e9)) print("128k ctx, batch 8: %.2f GB" % (kv_per_tok * 131072 * 8 / 1e9)) d_model = H * dh params_layer = 3*d_model*d_model + d_model*d_model + 8*d_model*d_model + 2*d_model P = params_layer * L print("approx params:", round(P / 1e6), "M", "weight bytes fp16: %.2f GB" % (P * 2 / 1e9)) print("prefill n=8192 FLOPs: %.3e" % (2 * P * 8192)) print("decode one token FLOPs: %.3e" % (2 * P)) attn_prefill = 4 * 8192**2 * d_model * L print("attention share of prefill: %.1f%%" % (100 * attn_prefill / (2 * P * 8192))) print("decode tokens/s at 3.5 TB/s, tile 256: %.0f" % (3.5e12 / (P * 2 / 256))) print("prefill tokens/s at 400 TFLOP/s fp16, 50%% MFU: %.0f" % (400e12 * 0.5 / (2 * P)))

Verified output (CPython 3.12):

KV bytes/token: 524288 = 512.0 KiB 8k ctx, batch 1 : 4.29 GB 128k ctx, batch 1: 68.72 GB 128k ctx, batch 8: 549.76 GB approx params: 6443 M weight bytes fp16: 12.89 GB prefill n=8192 FLOPs: 1.056e+14 decode one token FLOPs: 1.289e+10 attention share of prefill: 33.3% decode tokens/s at 3.5 TB/s, tile 256: 69536 prefill tokens/s at 400 TFLOP/s fp16, 50% MFU: 15521

Five readings, each with a decision attached:

  1. 512 KiB/token. A 100k-token conversation is 51.2 GB of cache for one user. This is why long-context pricing is not linear in tokens — the provider is paying rent on a growing resident buffer.
  2. 128k × batch 8 = 549.76 GB of cache. No single accelerator holds that. Concurrency at long context is a cluster-level, not device-level, question (L44).
  3. Attention is 33.3% of prefill FLOPs at n=8192. Not the majority, but far from negligible: at n=32768 it becomes the dominant term (the 4n2dmodel term grows quadratically while the 2Pn term grows linearly). Compute that crossover before choosing a tile size.
  4. Decode is one twelfth of prefill per token at n=8192 (1.29e10 vs 1.06e14 FLOPs) — yet it is often slower per token, because its arithmetic intensity is ~256× lower.
  5. 69,536 vs 15,521 tokens/s for decode-when-bandwidth-bound versus prefill-when-compute-bound (both optimistic, with a tile factor of 256 folded into the weight read). These are the same order of magnitude only by construction; the real point is that decode's ceiling is set by HBM bandwidth, so a faster GPU with more FLOPs but the same bandwidth will not make generation faster.

Why batching is the only lever on decode throughput

intensity(prefill) ≈ 2·N·n / (2·N) = n FLOP/byte    (amortised over the whole weight read)
intensity(decode, batch B) ≈ B FLOP/byte per byte of weights read
time per decode step ≈ max( bytes_read / bandwidth , FLOPs / peak )  →  read-bound when B < peak/bandwidth With peak ≈ 400 TFLOP/s and bandwidth ≈ 3.5 TB/s, the ridge point is ≈ 114 FLOP/byte. Decode with batch B has intensity B, so you need B ≈ 114 to become compute-bound. Below that, every extra request in the batch is nearly free throughput-wise — until the KV cache fills memory.

That gives the two-sided constraint every serving system lives inside:

Bmax ≈ (HBM − weights − activations) / (context_length × KV bytes/token)
throughput ≈ min( Bmax, Bridge ) / time_per_step Raise Bmax and throughput rises until you hit Bridge; past that, more concurrency only adds latency. Cutting KV bytes per token (GQA, MLA, quantised cache) raises Bmax directly — that is the economic case for L10 and L33.

4 · Your hands #

Experiment 1 — Fit your own GPU: how many concurrent 8k requests?

The number an infrastructure conversation should start from. Change the constants to your actual deployment.

def fits(hbm_gb, params_b, bytes_per_param, L, Hkv, dh, ctx, bpe=2, overhead=0.15): weights = params_b * 1e9 * bytes_per_param kv_tok = 2 * L * Hkv * dh * bpe free = hbm_gb * 1e9 * (1 - overhead) - weights return weights / 1e9, kv_tok / 1024, free / (ctx * kv_tok) for name, kw in {"MHA H_kv=32": dict(L=32, Hkv=32, dh=128), "GQA H_kv=8": dict(L=32, Hkv=8, dh=128)}.items(): w, kv, n_req = fits(hbm_gb=80, params_b=7, bytes_per_param=2, ctx=8192, **kw) print(f"{name}: weights {w:5.2f} GB, KV {kv:6.1f} KiB/token -> {n_req:5.1f} concurrent 8k requests")

Observed: MHA H_kv=32: weights 14.00 GB, KV 512.0 KiB/token -> 12.6 concurrent 8k requests and GQA H_kv=8: weights 14.00 GB, KV 128.0 KiB/token -> 50.3 concurrent 8k requests. The decisive result is the ratio — 50.3 / 12.6 ≈ 4.0, exactly the group size, because nothing in the weights changed. Falsifier: if the two rows came out equal you used H instead of Hkv, which is the commonest bookkeeping error in capacity planning. Note also that 12.6 concurrent long requests is a small number for an 80 GB device — this is the real shape of the problem.

Experiment 2 — Costs the same, latency does not

Two requests, 8,000 prompt tokens and 200 output tokens. Compare how the time splits, and note which term you cannot fix with a bigger GPU but with a smaller cached prefix.

n, P, bw, peak, mfu = 8000, 6443e6, 3.5e12, 400e12, 0.5 ttft = 2 * P * n / (peak * mfu) per_tok = (P * 2) / bw # read all weights once per decode step print("TTFT %.1f ms" % (ttft * 1e3)) print("per decode token %.2f ms -> 200 tokens = %.2f s" % (per_tok * 1e3, per_tok * 200)) print("if 90%% of the prompt is a cached prefix: prefill FLOPs drop to %.2f%% of full" % (100 * (n * 0.1) / n))

Observed: TTFT 515.4 ms and 200 decode steps 0.74 s — decode is 58.8% of total latency, and it is a function of weight bytes, not of the prompt. That is why prefix caching (L45) attacks TTFT while KV-compression (L10) attacks memory and concurrency, and why neither makes the weights read any faster. Both figures ignore attention reads over the growing cache; at 128k context the cache-read term is the one that starts to dominate decode latency.

Experiment 3 — The cost of a context window in dollars

Convert the memory model into money. Pick a price per token from your current provider and see which share of it is plausibly KV-cache rent.

kv_tok_bytes = 524288 ctx = 131072 gpu_hour = 2.0 # your own number, not a fact req_per_gpu_hour = 0.5 # a full-length request takes 2 h of occupancy gb_needed = kv_tok_bytes * ctx / 1e9 print("GB of cache for one 128k request: %.1f" % gb_needed) print("cache bytes per output-100 token completion: %.1f MB" % (kv_tok_bytes * 100 / 1e6)) print("rent per 1M cached tokens at that occupancy: $%.2f" % (gpu_hour / (req_per_gpu_hour * ctx / 1e6)))

The exact outputs depend on your inputs, and that is the point: the model makes the dependency explicit. The OBSERVE that matters is structural — cache cost is proportional to context length × concurrency × bytes/token, so a provider that halves bytes/token can serve the same traffic on half the memory, which is exactly the DeepSeek-V4.1-Flash claim of KV cache at 1/4 HBM and 1/8 SSD versus the prior generation state as of 2026-09. Treat your own numbers as a hypothesis to measure, never as a quote.

5 · Failure modes #

  • Unbounded cache growth per session. Symptom: a chat server is fast for the first minute and OOMs requests after an hour; memory correlates with session age, not with load. Fix: hard context cap plus summarisation/compaction (L79).
  • KV cache undercounted in capacity planning. Symptom: "we fit 7B in 16 GB" is true for weights alone (14 GB fp16) but leaves 2 GB for cache — two 4k requests. Always compute cache, not just weights.
  • Cache not invalidated when the prompt changes. Symptom: editing the system prompt mid-conversation produces answers that ignore the edit. Any token change invalidates the suffix after it (L45).
  • Head-count assumption in the cache layout. Symptom: correct with MHA, wrong after switching to GQA — concurrency silently drops or rises. The layout must be derived from Hkv, never hard-coded from dmodel.
  • Fragmentation across varying lengths. Symptom: utilisation below 60% while requests are rejected; per-request contiguous allocations waste memory at the tail. This is precisely what paged allocation solves (L44).
  • Cache in the wrong precision. Symptom: storing fp32 doubles memory for no measurable quality gain, or storing fp8 without per-channel scales degrades long-context recall. Quantise the cache deliberately and evaluate (L40).
  • Prefill and decode mixed in the same batch at long context. Symptom: TTFT spikes when a long prompt arrives while streaming requests are in flight (head-of-line blocking). Needs chunked prefill or separate pools (L44).

7 · Self-check #

Q1. Compute the KV cache size per token for a 40-layer model with dmodel = 5120 in fp16, under MHA and under MQA.

Reveal answer

MHA: 2 (K,V) × 40 layers × 5120 elements × 2 bytes = 819,200 bytes = 800 KiB/token. MQA (Hkv = 1, dhead = 5120 with one head, or 1 shared head): the KV side is 2 × 40 × dhead. Under the standard MQA formulation Hkv·dhead = dmodel/H only if you keep the head dim; the clean statement is that MQA stores one K and one V head of width dhead — with dhead = 128 and H = 40, that is 2 × 40 × 1 × 128 × 2 = 20,480 bytes = 20 KiB/token, a 40× reduction.

Q2. A 14 GB-weight model runs on an 80 GB GPU with 15% overhead for activations and framework. How many concurrent 32k-token requests fit if the cache is 512 KiB/token?

Reveal answer

Usable = 80 × 0.85 = 68 GB. Minus 14 GB weights = 54 GB for cache. Per request: 32,768 × 512 KiB = 32,768 × 524,288 B = 1.72 × 1010 B = 17.18 GB. 54 / 17.18 = 3.1, so 3 concurrent requests (and the third is tight). This is why long context forces either smaller batches, more GPUs, or KV compression.

Q3. Diagnostic: tokens/second drops by 4× when average prompt length goes from 1k to 40k, while GPU utilisation stays near 100% and batch size stays constant. What is happening?

Reveal answer

Decode is reading the KV cache in addition to the weights. At 512 KiB/token, a 40k-token context means ~21 GB of cache read per decode step versus ~13 GB of weights — more than doubling bytes moved, and worse once batching means N different caches. The bandwidth is saturated, hence ~100% utilisation with low FLOP efficiency. Confirm by measuring achieved HBM bandwidth and by computing predicted bytes/step = weights + batch×ctx×KV/token. The fix is KV compression, shorter context, or paged/quantised cache.

Q4. Why does prefix caching reduce TTFT but barely change inter-token latency?

Reveal answer

TTFT is dominated by prefill: 2·N·n FLOPs over the prompt. If a k-token prefix is already cached, prefill only processes n − k new tokens, so FLOPs and TTFT fall roughly proportionally. Inter-token latency is set by reading weights plus the full KV cache each step — and the cache now includes the cached prefix, so the bytes read per step are unchanged (or slightly larger). Prefix caching buys latency-to-first-token and some compute, not steady-state throughput.

Q5. What exactly is "arithmetic intensity" here, and why does it decide whether more batching helps?

Reveal answer

Arithmetic intensity = FLOPs performed per byte of memory traffic. A machine has a ridge point = peak FLOP/s ÷ bandwidth — about 114 FLOP/byte for 400 TFLOP/s and 3.5 TB/s. If a kernel's intensity is below the ridge, it is bandwidth-bound and extra FLOPs are wasted; above it, compute-bound. Decode with batch B reads the weights ~once and does ~B tokens of work, so its intensity is ~B. Increasing B from 1 toward 114 converts wasted bandwidth into throughput; past 114 the batch is compute-bound and additional requests strictly add latency. That is the entire rationale for continuous batching.
