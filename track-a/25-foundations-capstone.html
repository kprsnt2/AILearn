TRACK A · FOUNDATIONS

L25 · Capstone: A GPT-2-Scale Truth Check

Track A ends with the discipline the rest of the course depends on: predict first, then measure. You will state a loss curve and a compute budget from arithmetic alone, run a small model, and report the gap between prediction and reality as a number instead of an opinion.

~40 min difficulty ●●●●● build: a reproducible, budgeted training run + truth check
prediction before measurement 6N FLOPs rule MFU bits-per-byte comparison tokens/param curve fingerprint falsifiable run report

1 · Why it exists #

Every claim about a training run is either a measurement or a guess, and the two are indistinguishable in conversation. "A 124M model should reach loss around 3 on character-level data" is a guess until you write down an arithmetic prediction, run the thing, and show both. The failure this capstone exists to prevent is the expensive one: spending GPU budget on a run whose outcome you could have predicted, and therefore learned nothing from.

Here is the discipline, and it is the same discipline the audit background already uses: a prediction committed to before the measurement is falsifiable; a prediction formed afterwards is not. So the capstone has one rule — the predicted numbers are written into a report file before the run starts, and the report is only accepted when the measured numbers sit beside them.

The deliverable is not a trained model. It is a one-page run report containing: predicted parameters, predicted FLOPs, predicted time at a stated MFU, measured values for all three, and one sentence on the largest discrepancy and why. That document is the only thing that proves you can do this.

2 · The mental model #

Analogy. A structural engineer sizes a beam with arithmetic and then the load test confirms it. The arithmetic is not optional and the test is not optional; the value is in the agreement or the explained disagreement.

Where the analogy breaks. (1) The prediction here has three parts of very different reliability: parameter count (exact arithmetic, should match to the tensor), FLOPs (exact given the forward/backward convention, within a few percent of the runtime's implementation), and wall-clock time (a guess, because MFU depends on the hardware, batch size, sequence length and kernel quality). Record them separately, or a large time error will mask a real parameter error. (2) The loss prediction is not derived here — that is Track B's scaling law (L26). In this capstone you predict loss only by a stated, fallible heuristic and mark it as such; the point is to practice committing to a number, not to pretend you have a law. (3) A curve that matches your prediction can still be a wrong implementation — the structural tests from L06/L15/L19 are a separate gate.

Predict: parameters

From the config, with the L19/L24 formula, including biases, norms, positions and tying. This one is exact and must match the checkpoint.

Predict: FLOPs

6·N per token for training (plus the attention n² term if sequences are long). Multiply by tokens; report in PF-days or GPU-hours.

Predict: time

FLOPs / (peak FLOPs × MFU) with MFU stated explicitly. Use a conservative MFU, then say so.

Measure: everything

Parameter sum from the state dict, tokens×6N, wall clock, tokens/s, and the loss curve sampled at fixed token counts (not fixed steps, since step size varies).

3 · The mechanism #

1. N — from the config (exact).   2. FLOPs = 6·N·D (training, D = tokens)
3. wall-clock ≈ FLOPs / (peak × MFU)  ⇒  GPU-hours = FLOPs / (peak × MFU × 3600)
4. tokens/param = D / N   (compare against L27's compute-optimal ratio)
5. bits/byte = (nats/token) / (ln2 × bytes/token)   (the only cross-tokenizer loss unit, L16) Report the three predictions independently. The one you will get most wrong is time, because MFU is not a property of the model but of the kernel, the batch shape and the hardware. Anything within a factor of 2 is a useful prediction; claiming a factor of 2 without stating the MFU is not.
# The prediction sheet. Fill it in BEFORE the run and commit the file. import math cfg = {"V": 65, "L": 4, "d": 128, "H": 4, "d_ff": 4*128, "tied": True, "ctx": 256, "batch": 32, "steps": 5000} def params(c): per = 4*c["d"]**2 + 2*c["d"]*c["d_ff"] + 2*c["d"] + 4*c["d"] # attention + FFN + norms + biases emb = c["V"] * c["d"] head = 0 if c["tied"] else c["V"] * c["d"] return c["L"] * per + emb + head + 2*c["d"] # + final norm N = params(cfg) D = cfg["batch"] * cfg["ctx"] * cfg["steps"] flops = 6 * N * D peak, mfu = 150e12, 0.30 # STATE YOUR DEVICE AND YOUR MFU ASSUMPTION hours = flops / (peak * mfu) / 3600 print(f"predicted N = {N:,} parameters") print(f"tokens D = {D:,} ({D/N:.0f} tokens/param)") print(f"predicted FLOPs = {flops:.3e} ({flops/3600/(peak*mfu):.2f} GPU-hours on one device at MFU {mfu})") print(f"predicted train time = {hours:.2f} h") print(f"predicted loss (heuristic, MARK AS A GUESS): ln(V)={math.log(cfg['V']):.3f} at init; expect 1.5-2.2 nats/token after {D/N:.0f} tokens/param")

Verified output (CPython 3.12):

predicted N = 798,080 parameters tokens D = 40,960,000 (51 tokens/param) predicted FLOPs = 1.961e+14 (0.00 GPU-hours on one device at MFU 0.3) predicted train time = 0.00 h

Look at the two absurdities. 798,080 parameters is dominated by the embedding: 65 × 128 = 8,320 of the total, with the trunk at 197,376 × 4 = 789,504 — so this is a model whose FFN and attention are almost entirely in the name of predicting 65 token types. And 51 tokens per parameter is a very short run by any scaling reference (L27), which is exactly the point: at this budget the experiment cannot demonstrate scaling, only that the machinery works. The FLOPs figure 1.961e14 is right for these numbers; the formatted GPU-hours and hours columns print 0.00 because 1.961e14 / (150e12 × 0.3) = 4.36 seconds, i.e. 0.0012 hours. That formatting is itself the lesson: a report that rounds a quantity to two decimals across four orders of magnitude hides the real number, so always print the raw value next to the formatted one.

The correct reading of the sheet is therefore: N = 798,080, D = 40.96M tokens (51 tokens/param), 1.961e14 FLOPs, and a single-device compute time of about 4.4 s if the kernels ran at 30% MFU. A real run of this size takes far longer — minutes, not seconds — because data loading, optimizer bookkeeping and per-step launch overhead dominate at this scale. That gap is the discrepancy your report must explain rather than hide, and it is a demonstration of the 6N rule's scope: it models matmul FLOPs only, not the surrounding system.

4 · Your hands #

Experiment 1 — Commit the prediction, then reconcile it

Write the prediction sheet to a file with the config, the N/FLOPs/time predictions and the MFU assumption. Then build the model, sum its actual parameters, and diff.

python -c "import json; print(json.load(open('prediction.json')))" python -c "import torch; m=build_model(cfg); print(sum(p.numel() for p in m.parameters()), sum(p.numel() for p in m.parameters() if p.requires_grad))"

Observe the parameter diff first: with biases included, a tied head and one final norm the count should match to the integer. Any diff decomposes into named terms (L24). Only then look at the time diff, and attribute it to one of: framework overhead at small scale, data-loading stalls, MFU far from your assumption, or a unit error. Falsifier for "the implementation is right": if the parameter count matches but the loss at step 1 is not close to ln(V) (for a zero-initialised or small head), the head or the loss is wrong.

Experiment 2 — The curve report: loss at fixed token counts

The curve is only comparable across runs if it is sampled at fixed tokens seen, not at a fixed number of steps — because batch size and sequence length differ between runs (L14, L16). Produce the report the capstone asks for.

report = { "config": {"V": 65, "L": 4, "d": 128, "H": 4, "d_ff": 512, "tied": True, "ctx": 256, "batch": 32}, "predicted": {"N": 798_080, "D": 40_960_000, "flops": 1.961e14, "gpu_hours": 0.0012}, "measured": {"N": "?", "wall_clock_s": "?", "tokens_per_s": "?"}, "curve_nats_per_token": {"1M": "?", "5M": "?", "10M": "?", "20M": "?", "41M": "?"}, "baseline_uniform": "ln(V) = 4.174 nats/token", "largest_discrepancy": "? and why", } for k, v in report.items(): print(k, "->", v)

The report is the deliverable. The two acceptance criteria are: (a) the curve falls well below the uniform baseline of ln(65) = 4.174 nats/token — a model that cannot beat uniform has not learned anything; (b) every "?" is filled with a measured number and the largest discrepancy is explained in one sentence. A report with an unexplained discrepancy is an honest report; a report with no discrepancy at 39 tokens/param is a measurement bug. Report bits-per-byte alongside nats/token if your data has bytes (L16), because that is the number that survives a tokenizer change.

Experiment 3 — Scale the truth check: is the curve where it should be?

Track B opens with scaling laws. Do the crude version now: run the same config at 2× and 4× the token budget and check that loss decreases monotonically with a shrinking improvement — the shape a power law predicts.

def epr(a, b, c): # three token budgets, three measured losses return (a, (a - b) / (b - c)) # a, b, c are losses at D, 2D, 4D. A power law implies the ratio (L(D)-L(2D))/(L(2D)-L(4D)) > 1 print(epr(3.10, 2.85, 2.72), "ratio 1.92 -> consistent with a smooth power law") print("ratio near 1.0 or below -> you have hit an irreducible floor or a data wall; report it")

The illustrative numbers above show the shape to look for: each doubling helps less. If your measured ratio is near 1.0, you are at the noise floor of a tiny model and the honest report says so. If it is below 1, something is wrong (a bug, a broken schedule, or evaluation noise). This experiment is the bridge to L26, where the exponent gets fitted properly instead of eyeballed.

5 · Failure modes #

  • Prediction written after the run. Symptom: the report is always right. Post-hoc predictions are not predictions; commit the file first, with a timestamp or a git hash.
  • Unit errors in the time column. Symptom: GPU-hours that are off by 3600× — exactly the one caught in section 3. Carry units explicitly and sanity-check against a known run.
  • Comparing curves at fixed steps. Symptom: two runs disagree in a way that vanishes when you plot against tokens. Always x-axis tokens seen.
  • Loss not compared to the uniform baseline. Symptom: a "converged" model that is worse than predicting uniformly. Print ln(V) as a horizontal line on every loss plot a base model produces.
  • Perplexity compared across tokenizers. Symptom: a change in tokenizer looks like a model improvement. Convert to bits/byte (L16).
  • Claiming a scale result from one seed. Symptom: the "power law" changes shape with a different seed. At small scale, seed variance can be larger than the effect you are measuring; run at least two or three.
  • No data card with the curve. Symptom: the loss cannot be attributed to the model because the corpus changed. Pin the shard hashes (L23).

7 · Self-check #

Q1. Why are parameters, FLOPs and wall-clock reported separately rather than as one "cost" number?

Reveal answer

Because their error sources differ. Parameters are exact arithmetic from the config and must match the checkpoint exactly — a mismatch is a real bug. FLOPs follows from N and tokens by convention and is accurate to a few percent, catching implementation mistakes (wrong token count, missing backward). Wall clock includes MFU, kernel quality, data loading and framework overhead, so it can be off by a factor of 2–10 legitimately. Combining them lets a large time error hide a small parameter error; separating them localises the discrepancy to the right layer.

Q2. Verify the section-3 arithmetic: 6×798,080×40,960,000 FLOPs at 150 TFLOP/s peak and MFU 0.30. What is the wall clock, and why did the sheet print 0.00 hours?

Reveal answer

FLOPs = 6 × 798,080 × 40,960,000 = 1.961 × 1014. Time = 1.961e14 / (150e12 × 0.30) = 1.961e14 / 4.5e13 = 4.36 seconds = 0.0012 hours. The sheet printed 0.00 h because two-decimal formatting of 0.0012 rounds to zero — not a units error, a reporting error, which is worse in practice because it silently hides the answer. Print the raw value beside the formatted one. Numeric check: 6 × 798,080 × 40.96e6 = 1.961e14. Well done if you also notice that 4.4 s is the matmul-only model: real wall clock is dominated by data loading and per-step overhead at this size.

Q3. Diagnostic: your 800K-parameter model reaches 3.8 nats/token with V = 65 and you call it converged. What is wrong and what does the correct baseline tell you?

Reveal answer

The uniform-prediction baseline is ln(65) = 4.174 nats/token. 3.8 is only 0.374 nats below uniform — roughly 9% better than random — which for a 51-tokens/param run indicates a bug (loss mask, label shift, wrong window), a severely undertrained run, or a data problem. Always plot ln(V) as a horizontal line; "converged" is meaningless without it. A model that cannot clearly beat uniform has not learned a distribution, and no amount of further steps will fix a masking bug.

Q4. Why sample the curve at fixed tokens rather than fixed steps, and why does this matter for a capstone report?

Reveal answer

Learning is a function of data seen and compute spent, not of optimizer steps. A step processes batch × context tokens, so two runs with different batch or context sizes reach the same loss at different step numbers. Plotting against steps makes a run with a bigger batch look "faster-learning" when it is only seeing more tokens per step. The capstone report must be comparable to other runs — and to Track B's scaling fits — so the x-axis is tokens seen and the metric is nats/token (or bits/byte).

Q5. What makes this capstone falsifiable, and what would count as a failed capstone?

Reveal answer

Falsifiable because the predictions are committed to a file before the run and the measured values are reported against them: a prediction that is off by 10× and explained is still a successful capstone, because the model of the system was explicit and its error is attributable. A failed capstone is one where no prediction was written first, or where a discrepancy is left unexplained, or where the loss curve has no uniform baseline and no data card — i.e. a report that could be produced without having learned anything.
