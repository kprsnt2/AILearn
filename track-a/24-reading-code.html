L24 · Reading a Real Model Repo: nanoGPT to HF Transformers

You will spend more time reading model code than writing it. The difference between a slow reader and a fast one is not speed — it is having a fixed protocol that turns an unfamiliar repository into a parameter table and a verified forward pass in under an hour.

~28 min difficulty ●●●○○ build: an annotated source walkthrough + a reading checklist
config → weights contract state_dict keys block read order shape trace tied vs untied fused vs eager kernels checkpoint fingerprint

1 · Why it exists #

Every downstream decision — can I fine-tune this, where does it cache KV, what does "context length" mean, why is this loss different from the paper — is a question about the implementation, not the architecture diagram. And implementations diverge from diagrams in ways that matter: a config flag changes the normalisation placement, a different d_ff changes the parameter count, a fused attention path changes the mask semantics, a conversion script renames every tensor.

The failure this causes is concrete: you load a checkpoint, it loads without error, and the model behaves worse than the reported benchmark — because the config you used was the released config but your code's default attention implementation differs, or because the head was untied and you initialised it randomly, or because positions are added at the input but your fork assumed RoPE. All of those are silent. The protocol below is designed to make them loud.

You have understood a model repo when you can state its parameter count from the config, list every tensor in the state dict, and predict the shape of every intermediate. If you cannot do those three things, you have read the README, not the model.

2 · The mental model #

Analogy. Reading a model repo is auditing a filing system. First find the index (config, which declares what should exist), then reconcile it against the actual files (state dict, which declares what does exist), then audit one folder in detail (one block), then spot-check the output. Any mismatch between the index and the files is a finding.

Where the analogy breaks. (1) The config does not fully specify the model: many repos have code defaults that the config omits, and a checkpoint can be trained with settings not recorded in the config JSON. That is why the state dict is the ground truth for shapes. (2) The "files" are not independent: a fused kernel can be numerically equivalent to eager code for the same weights but produce different floating-point results, so fingerprinting must distinguish "as implemented" from "as intended". (3) Reading is not enough for correctness: you only know the code is right when a test passes — causal-mask test, parameter count, and a logit fingerprint against a reference.

Layer 1: the contract

Config fields → expected tensors → parameter count. Ten minutes of arithmetic that catches a surprising number of config mistakes.

Layer 2: the block

Read the forward in execution order: norm, attention, residual, norm, FFN, residual. Write the shape at each step. If you cannot, you do not yet understand it.

Layer 3: the kernels

Which path is actually executed (eager vs fused, dtype, KV layout)? This is where "same model" stops being true.

Layer 4: the proof

Parameter count matches, causal mask test passes, and a fixed input produces the same logits as the reference. Anything less is an impression.

3 · The mechanism #

The reading protocol, in order

  1. Read config.json and find the architecture class. Note: vocab size, d_model, n_layers, n_heads, n_kv_heads (if present), intermediate_size, activation, norm type, position type, tie_word_embeddings, max_position_embeddings, dtype.
  2. List the state dict keys and shapes from the checkpoint (without loading weights if it is huge). Reconcile against the config: does wte exist once or twice, is there a lm_head, are there bias tensors?
  3. Compute the parameter count from the config with the L19 formula and compare. A mismatch means the repo has extra parameters (biases, separate head, position table) you have not accounted for.
  4. Read the block forward pass and write the shape trace. This is where norm placement, residual scaling, and GQA mapping become visible.
  5. Find the attention dispatch: which implementation runs by default, and does the mask semantics match your assumptions (L06, L15)?
  6. Fingerprint: run a fixed input and record the first-token logits (or their sum) to 6 decimals. This is the artefact you compare against after any refactor.
# Layer 1: the config → parameter contract, and the checklist that goes with it. import json config = { "vocab_size": 50257, "n_embd": 768, "n_layer": 12, "n_head": 12, "n_inner": None, "activation_function": "gelu_new", "tie_word_embeddings": True, "layer_norm_epsilon": 1e-5, "n_positions": 1024 } def contract(c): d, L, V = c["n_embd"], c["n_layer"], c["vocab_size"] dff = c["n_inner"] or 4 * d attn = 4*d*d + 4*d + 3*d # qkv bias (3d) + out bias (d); final bias is d in ffn ffn = 2*d*dff + dff + d norms = 2*(2*d) # 2 LayerNorms per block, gamma + beta per_block = attn + ffn + norms emb = V*d + (V*d if not c["tie_word_embeddings"] else 0) pos = c["n_positions"] * d # learned position table (this config has one) final_ln = 2*d return {"per_block": per_block, "trunk": per_block*L, "emb": emb, "pos": pos, "final_ln": final_ln, "total": per_block*L + emb + pos + final_ln} r = contract(config) for k, v in r.items(): print(f"{k:10s} {v:>12,}")

Verified output (CPython 3.12):

per_block 7,090,176 trunk 85,082,112 emb 38,597,376 pos 786,432 final_ln 1,536 total 124,467,456

This is the arithmetic that catches config mistakes before you load a 124M-parameter checkpoint. Note what changed versus L19's count of 123.55M: attention and FFN biases, a learned position table (786,432), and the final LayerNorm — about 0.9M parameters that an architecture diagram does not show. Those are exactly the terms a diagram of "a transformer block" omits and an implementation includes. When your count disagrees with the checkpoint's actual tensor sum, the difference tells you which term you missed.

4 · Your hands #

Experiment 1 — Reconcile a config against a real state dict

Run the contract function on a model you actually have, then sum the real tensors. The difference, decomposed, is your understanding of the repo.

python -c "from safetensors.torch import load_file; sd=load_file('model.safetensors'); print(len(sd)); print(sum(t.numel() for t in sd.values())); [print(k, tuple(v.shape)) for k,v in list(sd.items())[:12]]"

Expect three findings: (1) the tensor sum matches your contract once you add the terms you missed; (2) if there is both wte.weight and lm_head.weight, the head is untied and the model is ~V×d larger than you thought; (3) if there is a wpe.weight (or position_embeddings), positions are learned-and-absolute, not RoPE, which changes the long-context story entirely (L08). Falsifier: if the sum matches exactly on the first try, you have read the block code already — verify by predicting one intermediate shape.

Experiment 2 — The fingerprint test after a refactor

The only cheap way to prove a rewrite is behaviour-preserving. Record before, refactor, compare after.

import hashlib def fingerprint(logits, k=8): return tuple(round(float(v), 6) for v in logits[0][-1][:k]) before = (-12.034512, -11.998701, 0.881203, -3.440012, 2.117650, -0.003291, 4.550091, -1.221004) def h(t): return hashlib.sha256(repr(t).encode()).hexdigest()[:16] print("fingerprint hash:", h(before)) print("after refactor: recompute and compare the tuple, then hash it; equal hash == numerically identical forward")

The hash is a convenience, not the proof — store the tuple. Two caveats: floating-point results depend on kernel and reduction order, so the fingerprint is only valid within one environment; and a refactor that changes dtype or fuses a kernel can legitimately change the last digits. Compare to ~1e-5 relative, not to the last bit, and record the environment with the fingerprint.

Experiment 3 — Find the mask semantics in the attention dispatch

The highest-value single read in any repo. Different implementations disagree about how padding and causality combine, and about the meaning of the attention mask's values.

python -c "import inspect, transformers.models.llama.modeling_llama as m; print([n for n in dir(m) if 'attention' in n.lower()]); print(inspect.getsource(m.LlamaAttention.forward)[:1500])"

Read for three things: whether the mask is added as a float bias or applied as a boolean (and what convention: True = keep or True = mask); whether positions are applied inside attention (RoPE) or added before; and which backend is dispatched by default. Write down one sentence per item. Those three sentences are the difference between code that works under batching and packing and code that leaks across documents (L15).

5 · Failure modes #

  • Trusting the config to be complete. Symptom: the parameter count does not match the checkpoint and nobody knows why. Enumerate state-dict keys; the config is a summary.
  • Missing a tied/untied distinction. Symptom: after a "small" fine-tune, the model degrades on rare tokens; the head was untied and initialised randomly instead of loaded.
  • Assuming RoPE where absolute positions are used. Symptom: long-context behaviour does not match expectations; slicing or extending context fails in a way the architecture diagram would not predict.
  • Reading the class but not the dispatch. Symptom: the model is correct in one environment and worse in another; the fused kernel path was selected and its mask/dtype semantics differ.
  • A refactor with no fingerprint. Symptom: a mysterious small quality regression after "a cleanup" that changed the normalisation epsilon or the residual scale. No test would catch it.
  • Copying a block without its masks. Symptom: works in inference on single sequences, breaks under padding or packing. The mask is not part of the block class in many repos; it lives outside.
  • Reading a conversion script as documentation. Symptom: tensor names differ between the original and the converted repo, and you chase a renaming that is cosmetic. Read the script's mapping table instead of the model.

7 · Self-check #

Q1. Your config-derived count is 84.95M for the trunk (the L19 formula, no biases) but the checkpoint trunk sums to 85.08M. What explains the 130,048 difference?

Reveal answer

Biases, plus the difference in d_ff. Per block the bias terms are qkv bias 3d = 2,304, out-projection bias d = 768 and FFN biases d_ff + d = 3,072 → 6,912 per block, 82,944 over 12 layers. LayerNorm already has beta in both counts. The remaining gap comes from the second cause: L19 used the SwiGLU-style d_ff = int(8d/3) = 2,048 while this contract uses 3,072 (the ReLU convention), and 12 × 3 × 768 × (3,072 − 2,048) = 28.3M — which is why the two trunk figures differ by ~28.3M, not by 0.13M. The lesson: the config's n_inner: None means a code default decides the FFN width, so the formula is only as correct as the default you assumed. Exactly the failure this protocol exists to catch.

Q2. What is the first thing you check in the state dict after "does it load"?

Reveal answer

Whether the output head is tied to the input embedding. If lm_head.weight exists as a separate tensor and is identical to wte.weight, tying was used and the config flag is informational; if it differs, the head is untied, the parameter count is larger by V×d, and re-initialising the head destroys the model's output distribution. This single check changes both the parameter budget and the fine-tuning recipe.

Q3. Diagnostic: your reimplementation matches the reference for sequence length 1 but diverges for length 8. Where do you look?

Reveal answer

The attention mask and the positional mechanism — both are no-ops at length 1. At length 1, causal masking is trivial and positions are all zero, so a wrong mask convention (True = keep vs True = mask), a missing causal mask, an off-by-one in the mask, or a position encoding applied in the wrong place all look identical to the reference. Test: feed a length-8 sequence and compare the attention matrix of layer 1 against the reference; then compare position embeddings. This is by far the most common "it works on my one example" failure.

Q4. Why is a fingerprint not a full correctness proof, and what should it be paired with?

Reveal answer

It fixes one input and compares one slice of output, so it cannot detect behaviours that are not exercised — masking, padding, long context, GQA mapping or positional handling beyond the length tested. Pair it with structural tests: the parameter count, the causal-mask test from L06/L15 (row 0 equals V[0], rows sum to 1, packed invariance), a padding-invariance test, and a length sweep. The fingerprint catches silent refactor regressions; the structural tests catch wrong implementations.

Q5. You must explain in one paragraph how to answer "is this checkpoint actually the model it claims to be?"

Reveal answer

Reconcile three independent artefacts: (1) the config, expanded into a parameter contract and checked against the actual tensor sum and the state-dict key list; (2) the source, read in execution order for norm placement, position mechanism, activation/FFN structure and head tying; and (3) a runtime fingerprint on a fixed input within a pinned environment, plus structural tests (causal mask, padding invariance). Agreement across all three makes the claim auditable; any single one alone is a hope.
