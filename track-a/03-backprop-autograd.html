L03 · Backprop & Autograd: Credit Assignment

A model with 109 parameters computes one scalar loss. Deciding which of the billion numbers caused the error, using one forward pass and one backward pass, is the algorithm that makes deep learning affordable. If you cannot hand-write it for a scalar graph, you cannot debug a wrong gradient.

~30 min difficulty ●●●○○ build: 60-line micro autodiff + finite-difference oracle
computational graph reverse-mode AD local derivative topological order gradient accumulation finite-difference check backward cost = 2x forward

1 · Why it exists #

The problem is credit assignment under a huge parameter count. Training makes one scalar decision — "this batch had loss 2.71, adjust the weights" — but loss depends on every parameter through dozens of composed layers. The naive way to compute ∂L/∂θi is numerical: perturb θi by ε, rerun the forward pass, divide. For N parameters that costs N+1 forward passes. At N = 108 (a modest model) with a 10 ms forward pass, one gradient step takes 106 seconds ≈ 11 days. Training is not slow, it is impossible.

Backpropagation fixes this with a single structural fact: every layer exposes a cheap local derivative, and the chain rule lets you multiply them. One forward pass caches intermediate values; one backward pass sweeps the same graph in reverse and delivers all N partial derivatives for roughly the cost of two to three forward passes. This is reverse-mode automatic differentiation.

Reverse mode computes "sensitivity of one output to N inputs" in O(1) passes regardless of N. Forward mode computes "sensitivity of M outputs to one input" in O(1) passes. Deep learning has N ≫ M=1, so it must be reverse mode — a fact worth stating explicitly in any review of a hand-rolled training loop.

The failure it exists to stop is not only speed. Hand-derived gradients are wrong in practice more often than people admit: a forgotten transpose, a sign error in the sigmoid derivative, a mean over the wrong axis. A silent wrong gradient still trains — it just trains worse, and you discover it after spending GPU weeks. So every gradient implementation needs an oracle, and section 4 makes the finite-difference oracle into a unit test.

2 · The mental model #

Analogy. The forward pass is a factory line: each station takes parts and produces a new part. The backward pass is a complaint travelling up the line: "your output was off by this much". Every station converts the complaint about its output into complaints about its inputs, using only local knowledge — how sensitive my output was to each of my inputs. Two stations that both fed the same downstream part each get a share of the complaint.

Where the analogy breaks. A real factory worker cannot be blamed twice; a tensor can. If a value is used in two places (the residual stream does this in every transformer block: a value is added into the residual, then again used inside the layer), the complaint must be summed, not averaged or overwritten. The most common autograd bug is an = where a += belongs. The second place it breaks: a station cannot report sensitivity to an earlier station without knowing the intermediate output it produced — which is why the forward pass must cache activations, and why memory scales with depth, not with the number of parameters.

The one-line rule

∂L/∂x = ∑children y (∂L/∂y) · (∂y/∂x). Sum over every path from x to L. Nothing else.

The order matters

Process nodes only after every consumer of their output has contributed its gradient. That is a reverse topological order; getting it wrong silently zeroes gradients.

Cost

Reverse mode costs about 2–3× a forward pass, independent of parameter count. The 6N FLOPs/token training convention in L43 is forward 2N + backward 4N.

Where it stops being easy

Control flow (conditionals, loops) and in-place mutation break the cached graph. Real frameworks either record a dynamic tape (PyTorch eager) or compile it (JAX); both are the same math you write below.

3 · The mechanism #

The chain rule, written for graphs

Let x be a node feeding outputs y1…yk. Define δ = ∂L/∂x (the "adjoint").
δ = ∑j (∂L/∂yj) · (∂yj/∂x)     then recurse with δ as the incoming adjoint.
Seed: ∂L/∂L = 1. ∂L/∂yj is the adjoint that has already arrived at yj. ∂yj/∂x is the local derivative, known at graph-construction time. Nobody ever differentiates the whole composed function symbolically.

Local rules you need for a transformer

A micro autodiff engine, complete and runnable

This is the whole idea in 55 lines. Every real framework is this, plus arrays instead of scalars, plus kernel fusion.

import math class T: def __init__(s, v, parents=(), op=""): s.v, s.parents, s.op, s.g = float(v), parents, op, 0.0 def __add__(s, o): o = T(o) if not isinstance(o, T) else o y = T(s.v + o.v, (s, o), "+") def b(g): s.g += g; o.g += g # += because a value can have many consumers y._b = b; return y def __mul__(s, o): o = T(o) if not isinstance(o, T) else o y = T(s.v * o.v, (s, o), "*") def b(g): s.g += g * o.v; o.g += g * s.v y._b = b; return y def __pow__(s, n): y = T(s.v ** n, (s,), "**") def b(g): s.g += g * n * s.v ** (n - 1) y._b = b; return y def __neg__(s): return s * -1.0 def __sub__(s, o): return s + (-o if isinstance(o, T) else T(-o)) _b = staticmethod(lambda g: None) def tanh_(s): t = math.tanh(s.v); y = T(t, (s,), "tanh") def b(g): s.g += g * (1 - t * t) # cached t: no recompute y._b = b; return y def backward(y): order, seen = [], set() def visit(n): # post-order DFS = reverse topological order if id(n) in seen: return seen.add(id(n)) for p in n.parents: visit(p) order.append(n) visit(y) y.g = 1.0 # seed dL/dL = 1 for n in reversed(order): if n.g: n._b(n.g) def numgrad(f, xs, i, h=1e-6): # central finite difference = the oracle a, b = list(xs), list(xs); a[i] += h; b[i] -= h return (f(*[T(x) for x in a]).v - f(*[T(x) for x in b]).v) / (2 * h) # --- test 1: a composed expression with reuse (the residual pattern) --- f1 = lambda a, b: (a * b + a) * tanh_(b) xs = [0.7, -1.3] ts = [T(x) for x in xs]; y = f1(*ts); backward(y) print("f1", round(y.v, 6), [round(t.g, 6) for t in ts], [round(numgrad(f1, xs, i), 6) for i in range(2)]) # --- test 2: one neuron y = tanh(w.x + b), checked against the hand formula --- w = [T(0.3), T(-0.9)]; bb = T(0.1); x = [1.7, 0.4] y = tanh_(w[0]*x[0] + w[1]*x[1] + bb); backward(y) print("autograd", round(y.v, 6), [round(t.g, 6) for t in w], round(bb.g, 6)) t = math.tanh(0.3*1.7 - 0.9*0.4 + 0.1) print("analytic", round(t, 6), [round((1-t*t)*1.7, 6), round((1-t*t)*0.4, 6)], round(1-t*t, 6))

Verified output (CPython 3.12):

f1 0.180962 [0.258517, -0.657267] [0.258517, -0.657267] autograd 0.244919 [1.598025, 0.376006] 0.940015 analytic 0.244919 [1.598025, 0.376006] 0.940015

Three things are proven by those two lines, and they are the whole point of the engine:

  1. Autograd equals the analytic formula exactly on the neuron test, to six decimals. Your local rules are right.
  2. Autograd equals the finite difference exactly on the composed test. The graph machinery (topological sort, additive adjoints) is right.
  3. Reuse works. In f1, the value b feeds both a*b and tanh_(b). Its gradient is the sum of two paths. If the engine used = instead of +=, the finite-difference column would disagree and you would see a mismatch in the second component — exactly the bug that kills residual networks if hand-written.

Why the finite difference matches to 1e-6 and not better: forward error is O(h) from floating-point cancellation and O(h2) from truncation; the two balance near h ≈ √εmach ≈ 3×10-8, but in practice h = 1e-6 is the safe default because below it you are subtracting two nearly equal floats. A relative error around 1e-6 is a pass; 1e-3 usually means a real bug.

4 · Your hands #

Experiment 1 — Break the accumulation and watch the oracle catch it

Take the engine above and change one character: in __add__, replace s.g += g with s.g = g. Then rerun test 1. This is the exact bug that a hand-written residual block has, and the finite-difference oracle localises it to a single component.

python -c "import math; print('change += to = in the add rule, rerun test 1, compare to 0.258517 / -0.657267')"

Observe: the second gradient no longer matches -0.657267. Diagnosis: a value consumed twice received only one contribution. The counterfactual is clean — with += restored, the numbers match to six decimals. Any gradient you cannot reproduce this way is not a gradient, it is a guess.

Experiment 2 — Differentiate a softmax cross-entropy by hand

This is the gradient the language-model head actually uses, and the one most often implemented with a sign error. Loss L = −log softmax(z)target. Write it directly, then check it.

# forward: stable log-softmax, and its exact gradient import math def log_softmax(z): m = max(z); s = m + math.log(sum(math.exp(v - m) for v in z)) return [v - s for v in z] def loss(z, t): return -log_softmax(z)[t] def grad(z, t): lp = log_softmax(z); p = [math.exp(v) for v in lp] d = list(p); d[t] -= 1.0 # dL/dz = softmax(z) - onehot(target) return [v / 1.0 for v in d] z = [2.0, 0.5, -1.0, 3.0]; t = 1 g = grad(z, t) fd = [] for i in range(4): a, b = list(z), list(z); a[i] += 1e-6; b[i] -= 1e-6 fd.append((loss(a, t) - loss(b, t)) / 2e-6) print("loss", round(loss(z, t), 6)) print("grad ", [round(v, 6) for v in g]) print("numeric", [round(v, 6) for v in fd]) print("sum(grad) must be 0:", sum(g))

Verified output: loss 2.884092, grad [0.250551, -0.944094, 0.012474, 0.681069], numeric identical to six decimals, and sum(grad) = -2.220446049250313e-16, i.e. zero up to float64 rounding (L16 computes 2.88409 by a different route — same number, different arithmetic path). The match proves the rule dL/dz = softmax(z) − onehot(t). The zero sum is a structural invariant: because softmax logits are shift-invariant (adding a constant to every z changes nothing), the gradient must sum to zero or your implementation is wrong. That single check catches most head bugs without any oracle.

Experiment 3 — Measure reverse mode's independence from parameter count

Prove the claim in section 1 empirically: forward time grows linearly in N, backward time also grows linearly, but the ratio backward/forward stays roughly constant.

import time def bench(n): def f(*xs): acc = xs[0] * xs[0] for v in xs[1:]: acc = acc + v * v return tanh_(acc) xs = [T(0.01 * (i % 7)) for i in range(n)] t0 = time.perf_counter(); y = f(*xs); t1 = time.perf_counter() backward(y); t2 = time.perf_counter() return (t1 - t0) * 1e3, (t2 - t1) * 1e3 for n in [10, 100, 1000]: fw, bw = bench(n) print(f"n={n:5d} forward {fw:7.3f} ms backward {bw:7.3f} ms ratio {bw/fw:4.2f}")

Ratio stays near 1–3 rather than growing with n. That is the entire economic argument for backpropagation. Falsifier: if the ratio grew linearly with n, you would have re-run the forward pass for each parameter (that is numeric differentiation, not reverse mode). Note the scalar Python engine is 100× slower than a tensor library — correctness first, then vectorise.

5 · Failure modes #

  • Overwrite instead of accumulate. Symptom: tensors used in multiple branches (residual, attention + skip) get too-small gradients; loss plateaus at a value the model should beat; finite-difference check on a reused variable fails while single-use variables pass.
  • Missing .detach() or wrong no_grad scope. Symptom: VRAM grows every step because the eval loop kept the graph alive; nvidia-smi shows steady climb then OOM.
  • Graph retained across the optimizer step. Symptom: "backward through the graph a second time" error, or silently doubled gradients when the same graph is reused in gradient accumulation without re-zeroing.
  • Wrong scaling in the mean. Symptom: gradient magnitude scales with batch size or sequence length; an LR tuned on one config diverges on another. Check sum(loss)/T versus mean(loss) explicitly (L16).
  • NaN from an unguarded log/sqrt. Symptom: loss becomes NaN first at the last layer or at a specific token; gradient arrives as inf, then the Adam state is poisoned permanently. Guard with log(x + eps) and clip.
  • In-place mutation of a cached tensor. Symptom: gradients correct on step 1 and wrong afterwards; happens when you reuse a buffer the graph still references (classic in a hand-rolled normalization layer).

7 · Self-check #

Q1. Why must adjoints be accumulated with +=? Give the graph that exposes the bug.

Reveal answer

Because L can depend on a node through several paths, and the chain rule for a multivariate function sums over paths. In f(a,b) = (a*b + a) * tanh(b), b reaches L via a*b and via tanh(b). With overwrite you keep only whichever backward closure ran last. The finite-difference check on that example fails in the b component (expected -0.657267) while a single-path expression would still pass — which is why oracles need a reused variable.

Q2. A model has 108 parameters and a forward pass takes 10 ms. Estimate the cost of one gradient step by numeric differentiation versus reverse mode, and the ratio.

Reveal answer

Numeric: (N+1) forwards ≈ 108 × 10 ms = 106 s ≈ 11.6 days per step. Reverse: forward 10 ms + backward at ~2× forward = 30 ms total, i.e. 0.03 s. Ratio = 106/0.03 ≈ 3.3×107. The independence from N is the whole design.

Q3. Diagnostic: your loss is fine for 100 steps, then becomes NaN, and every checkpoint after that is NaN. Where do you look first?

Reveal answer

First at the last layer's normalization/softmax: an inf or NaN gradient appears there and propagates into the optimizer state. Since Adam keeps running moments, one bad step poisons every later update — "NaN persists" is the signature. Check log of zero or negative probability, division by a zero variance, an unclipped exploding gradient, and whether mixed precision overflowed in fp16. Mitigations: eps guards, gradient clipping, loss scaling, and a step-level NaN guard that restores the last good checkpoint.

Q4. The softmax cross-entropy gradient sums to zero. Why must it, and what does a non-zero sum tell you?

Reveal answer

Softmax is invariant to adding a constant c to all logits: softmax(z + c1) = softmax(z). So L(z + c1) = L(z) for all c, and differentiating along 1 gives 1T∇L = 0. A non-zero sum therefore means the gradient does not correspond to the function you think you are differentiating — typically a missing stabilizer term (forgot to subtract the running max), a target index error, or a missing normaliser. It is a free structural test that needs no oracle.

Q5. Your custom layer passes a finite-difference check for h = 1e-3 but fails for h = 1e-8. Is the layer wrong?

Reveal answer

Probably not. Central differences have truncation error O(h2) and rounding/cancellation error O(ε/h). At h = 1e-3 truncation dominates (~1e-6 relative) and both columns agree loosely; at h = 1e-8 the numerator is the difference of two numbers that agree to ~7 digits, so cancellation destroys the estimate and the "mismatch" is numerical noise. Use h ≈ 1e-6 and compare relative error, not absolute; also prefer float64 for the oracle. If a mismatch persists at several h values, then the analytic gradient is wrong.
