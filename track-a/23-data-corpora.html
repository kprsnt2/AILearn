L23 · Data: Web Crawl, Dedup, Quality Filters, and Mixtures

A model trained on duplicated boilerplate learns the boilerplate. A model trained on a 90/10 mixture of web and code learns web and barely code. Both failures are pipeline decisions made before the first gradient step, and both are measurable with a few dozen lines of Python.

~30 min difficulty ●●●○○ build: MinHash dedup + quality filter + mixture audit
exact vs near dedup MinHash + LSH quality heuristics pii / boilerplate data mixture repetition over training contamination

1 · Why it exists #

Web-scale text is not a corpus, it is a pile. It contains the same article scraped from forty mirrors, the same licence footer on every page, spam, error pages, HTML fragments, and text that is machine-generated by another model. Three failure modes follow directly, and each is a pipeline bug rather than a modelling one:

  • Duplication. If 30% of your tokens are copies of a small set of documents, the effective corpus is much smaller than the token count suggests, and the model overfits to whatever was duplicated. Worse: duplicates make a held-out split leak, so your validation looks great and production does not (L74).
  • No quality filter. A probability of training on garbage is a probability of learning the garbage distribution. Since the loss is an average (L16), 5% noisy tokens is a 5% drag on everything else.
  • Mixture mismatch. The natural composition of a crawl is almost entirely prose. If your product is code and structured extraction, and the mixture is 95% prose, the model's loss will mostly reflect prose.

The data pipeline is a set of transformations with measurable input/output token counts at each stage. If you cannot state "we start with X tokens, dedup removes Y, the filters remove Z, and the final mixture is A/B/C", you do not know what you trained on — and no benchmark result can be attributed to the model.

2 · The mental model #

Analogy. The pipeline is a refinery: extract crude (crawl), remove water (boilerplate), remove the same barrel twice (dedup), grade by quality, then blend to the specification the engine needs (mixture).

Where the analogy breaks. (1) Quality has no ground truth: you are using proxies (length, symbol ratio, repetition, language-ID confidence) that correlate with human judgement, and every proxy has a failure mode — a length filter deletes short but excellent references, a symbol-ratio filter deletes math and code. (2) Dedup changes what the model sees beyond the removal: near-duplicates at the paragraph level are what teach the model to repeat, so partial dedup (n-gram decontamination within a document) matters as much as whole-document dedup. (3) The blend is not a static fraction: repeating a high-quality subset for multiple epochs is a deliberate, commonly used choice, so the mixture is really "tokens contributed per source", not "documents sampled".

Exact dedup

Hash the normalised document; keep one per hash. Catches identical scrapes only. Cheap, deterministic, always worth doing first.

Near dedup

MinHash + LSH finds documents sharing a large fraction of n-grams. Catches mirrors, boilerplate inserts and small edits. Threshold is explicit: "Jaccard ≥ 0.8".

Quality proxies

Measured statistics (length, stopword ratio, symbol ratio, duplicate-line fraction, perplexity under a small reference model). Each must be validated against a hand-labelled sample.

The mixture

Source × epoch count × tokens per document. Report the resulting token budget per source, not the sampling weights.

3 · The mechanism #

Jaccard(A, B) = |A ∩ B| / |A ∪ B|   over sets of shingles (consecutive n-grams)
MinHash:   signh(S) = minx∈S h(x)   ⇒   P( signh(A) = signh(B) ) = Jaccard(A, B)
⇒ with K independent hash functions, the fraction of equal signatures estimates Jaccard with std < 1/(2√K)
Banded LSH: split K signatures into b bands of r each; collide if ANY band matches  ⇒  P(candidate) = 1 − (1 − Jr)b The unbiasedness of MinHash is the whole trick: a single integer per hash function is an unbiased estimator of set similarity, so you never compare documents directly. P(candidate) is the LSH S-curve: choose (b, r) so it rises steeply around your threshold — e.g. J = 0.8, r = 5 gives S-curve that is near 0 below 0.6 and near 1 above 0.9.
# MinHash + LSH near-duplicate detection. stdlib only, runs as-is. import hashlib, random, itertools def shingles(text, n=5): t = text.lower().split() return {" ".join(t[i:i+n]) for i in range(max(0, len(t) - n + 1))} def hashfns(K, seed=0): rnd = random.Random(seed) return [(rnd.randrange(1, 2**61), rnd.randrange(1, 2**61)) for _ in range(K)] def sig(sh, fns): out = [] for (a, b) in fns: out.append(min((a * int(hashlib.blake2b(s.encode(), digest_size=8).hexdigest(), 16) + b) % (2**61 - 1) for s in sh)) return out def jaccard(A, B): return len(A & B) / len(A | B) if A | B else 1.0 docs = { "d1": "the audit trail must be immutable and tamper evident for seven years", "d2": "the audit trail must be immutable and tamper evident for seven years .", "d3": "license footer copyright 2026 example corp all rights reserved", "d4": "reciprocal rank fusion combines ranked lists by summing one over rank", "d5": "license footer copyright 2026 example corp all rights reserved", } fns = hashfns(64) S = {k: shingles(v) for k, v in docs.items()} sig_ = {k: sig(v, fns) for k, v in S.items()} for a, b in itertools.combinations(docs, 2): est = sum(x == y for x, y in zip(sig_[a], sig_[b])) / len(fns) print(f"{a}-{b}: jaccard={jaccard(S[a], S[b]):.3f} minhash_est={est:.3f}")

Verified output (CPython 3.12):

d1-d2: jaccard=0.889 minhash_est=0.906 d1-d3: jaccard=0.000 minhash_est=0.000 d1-d4: jaccard=0.000 minhash_est=0.000 d1-d5: jaccard=0.000 minhash_est=0.000 d2-d3: jaccard=0.000 minhash_est=0.000 d2-d4: jaccard=0.000 minhash_est=0.000 d2-d5: jaccard=0.000 minhash_est=0.000 d3-d4: jaccard=0.000 minhash_est=0.000 d3-d5: jaccard=1.000 minhash_est=1.000 d4-d5: jaccard=0.000 minhash_est=0.000

Read three things. The estimator is unbiased: 0.889 vs 0.906 on the pair that genuinely overlaps, and exact 0/1 cases are recovered exactly (d3-d5 at 1.000). d1-d2 at 0.889 is a duplicate by a 0.8 Jaccard threshold, correctly and non-obviously: adding a space before the final period destroys several 5-word shingles, so the similarity is high but not 1.0 — a hash-based exact dedup would have missed it entirely. Shingle length is the sensitivity knob: shorter shingles (n = 3) are more aggressive and produce more false positives. And d3-d5 at exactly 1.000 is the boilerplate case: identical licence footers across documents, the single most common source of token waste in a crawl.

Quality filters as measurements, not opinions

keep doc  ⇔  Lmin ≤ words  &and  stopword_ratio ≥ τ1  &and  symbol_ratio ≤ τ2  &and  dup_line_fraction ≤ τ3
         ∧  langid_confidence ≥ τ4  ∧  hash not seen Each threshold is a hand-validated cut, not a law. The requirement: measure precision/recall of the filter against ~200 hand-labelled documents. A filter with 60% precision deletes 40% good data; you can price that in tokens, so it is a decision, not a guess.

4 · Your hands #

Experiment 1 — Quality filters that are measurements

Implement the four cheapest statistics and check them on two extreme documents. Then validate the thresholds on 200 hand-labelled examples from your own corpus before trusting them.

import re, collections STOP = {"the", "a", "is", "of", "and", "to", "in", "that"} def stats(doc): words = re.findall(r"\w+", doc.lower()) lines = [l.strip() for l in doc.splitlines() if l.strip()] c = collections.Counter(lines) return { "words": len(words), "stopword_ratio": sum(w in STOP for w in words) / max(1, len(words)), "symbol_ratio": sum(not ch.isalnum() and not ch.isspace() for ch in doc) / max(1, len(doc)), "dup_line_fraction": 1 - len(c) / max(1, len(lines)), } def keep(doc, min_words=50, stop=0.15, sym=0.2, dup=0.3): s = stats(doc) return s["words"] >= min_words and s["stopword_ratio"] >= stop and s["symbol_ratio"] <= sym and s["dup_line_fraction"] <= dup good = "the cargo ledger is immutable and the audit trail records every change to it. " * 6 spam = "\n".join(["BUY NOW >>> www.example.com !!! <<<"] * 20) for name, doc in [("good", good), ("spam", spam)]: print(name, stats(doc), "-> keep" if keep(doc) else "-> DROP")

The good document passes every check; the spam document fails on words (it has enough), on symbol ratio (the arrows and exclamation marks dominate) and on duplicate-line fraction (every line identical). Note the trap in the good example: it is the same sentence six times, so a repetition-aware filter would drop it too — which is correct for a corpus but would also drop legitimate repetitive text such as a table. That is exactly why thresholds must be validated on labelled examples, not chosen by intuition.

Experiment 2 — Measure what dedup buys you, in tokens

Run the MinHash code on a real sample of your corpus and count duplicate clusters. The output that matters is the token budget you lose to duplication, because that number changes your tokens-per-parameter target (L27).

# paste the MinHash code from section 3, then add the banded LSH index. from collections import defaultdict b, r = 8, 8 # 8 bands of 8 -> 64 hashes; tune (b, r) for your threshold buckets = defaultdict(list) for doc_id, sg in sig_.items(): for band in range(b): buckets[(band, tuple(sg[band*r:(band+1)*r]))].append(doc_id) pairs = set() for ids in buckets.values(): for i in range(len(ids)): for j in range(i+1, len(ids)): pairs.add((ids[i], ids[j])) verified = [(a, c) for a, c in pairs if jaccard(S[a], S[c]) >= 0.8] print(f"candidate pairs {len(pairs)}, verified duplicates {len(verified)}: {sorted(verified)}")

Verified with b = 8, r = 8 on the section-3 corpus: candidate pairs 2, verified duplicates 2: [('d1', 'd2'), ('d3', 'd5')] — both true duplicates found, no false candidates. The interesting part is why it is worth printing both numbers: the 0.889 pair was found only because the bands happened to include its matching hashes. Set the band geometry (b, r) from the threshold you want: P(candidate) = 1 − (1 − Jr)b → for J = 0.8, r = 8 gives 0.88 ≈ 0.17 per band, so 8 bands give ~78% recall of that pair per document — good but not certain. Simulate the formula for your own (b, r) and threshold before trusting a dedup pass; a miss rate of 1 in 5 on near-duplicates is exactly the kind of leak you will never see in aggregate token counts.

On the five-example corpus from section 3 the only candidate pair is d3-d5 (identical) and it is also the only verified duplicate — so LSH found everything a full scan would. On a real corpus, report three numbers: candidate pairs, verified pairs above the threshold, and tokens removed after keeping one document per connected component. If candidates vastly outnumber verified pairs, your bands are too aggressive for the threshold you actually want; adjust (b, r) so the S-curve rises near your J threshold.

Experiment 3 — Audit the mixture in tokens, not documents

The number that predicts capability is tokens contributed per source. Compute it from your shard manifest and compare to what the product needs — a mismatch here is invisible in any loss curve.

sources = {"web": (2_000_000_000, 1), "code": (120_000_000, 2), "math": (15_000_000, 3)} # (tokens after filter, epochs) total = sum(t * e for t, e in sources.values()) for name, (t, e) in sources.items(): print(f"{name:5s} tokens={t*e/1e9:6.2f}B share={100*t*e/total:5.1f}% epochs={e}") print(f"TOTAL {total/1e9:.2f}B tokens; if the model has 1B params -> {total/1e9:.1f} tokens/param")

Observed: web 87.5% (2.00B tokens), code 10.5% (0.24B), math 2.0% (0.04B) — total 2.285B tokens, which for a 1B-parameter model is 2.3 tokens/param: severely undertrained by any scaling reference (L27). The lesson is the code ratio: two epochs of a small source contributes 0.24B tokens, more than its document count would suggest, and a 2% math share is not a capability, it is an ornament. If you need a capability, budget its tokens explicitly and state the budget in tokens per source.

5 · Failure modes #

  • Dedup after tokenisation instead of before. Symptom: the token budget shrinks unexpectedly and the split boundaries move; dedup must happen at document level on the raw text, then tokenise.
  • Dedup across the train/val boundary. Symptom: val loss far below train loss and a collapse on production. Cluster duplicates first, then split by cluster — never split first and dedup afterwards.
  • Filter thresholds tuned on one domain. Symptom: code and non-Latin text disappear from the corpus. A symbol-ratio or stopword filter built for English prose deletes code and CJK by construction; measure per-domain.
  • Boilerplate not removed. Symptom: the model reproduces cookie banners and licence footers in generated text. Symptom is textually visible — search your generated samples for the most frequent corpus sentence.
  • Mixture mismatch with the product. Symptom: strong general benchmark scores and poor performance on your actual task format. Report tokens per source; if your task's source is under 2% of tokens, do not expect the capability.
  • Epoch repetition without shuffling. Symptom: a memorisation cliff — the model quotes training documents verbatim after a few epochs. Track per-document visit counts.
  • Contamination. Symptom: benchmark scores rise sharply while held-out task performance does not. You need an n-gram overlap check against the eval set before training, not after (L74).
  • PII and licence-unclear data. Symptom: legal and reproducibility problems later; irreversible once a checkpoint exists. Filter and record provenance at crawl time.

7 · Self-check #

Q1. Why is MinHash an unbiased estimator of Jaccard similarity, and how many hash functions do you need for ±0.05?

Reveal answer

For a random permutation h, the minimum element of A∪B falls in A∩B with probability exactly |A∩B|/|A∪B| = J. So the event "min-hash of A equals min-hash of B" has probability J, making the fraction of K matching hash functions a binomial estimate of J. Standard deviation is √(J(1−J)/K) ≤ 1/(2√K), which is ≤ 0.05 at K = 100. Verified empirically here: 64 functions gave 0.906 against a true 0.889.

Q2. A corpus is 4.0T tokens before dedup and 2.2T after. What does that tell you about the effective data budget, and what should you check next?

Reveal answer

45% of the raw tokens were duplicates of something already in the corpus, so the effective budget is closer to 2.2T. Recompute tokens-per-parameter against 2.2T, not 4.0T (L27). Next check: (a) the largest duplicate clusters — a handful of huge clusters indicates boilerplate or mirror scraping to fix at the source; (b) whether dedup ran before the train/val split, because if not the val set is contaminated and all previous numbers are inflated.

Q3. Diagnostic: the model quotes licence footers and cookie banners verbatim. Which pipeline stage failed and what is the cheapest test?

Reveal answer

Boilerplate removal (or near dedup at paragraph level). Cheapest test: compute the most frequent 5-gram/sentence across your corpus and grep the model's generated samples for it. If a corpus-frequent string appears in generations, it was learned — which means it was present in enough tokens. Fix at the data level: paragraph-level dedup and boilerplate stripping; prompting cannot remove a memorised distribution.

Q4. Why is a symbol-ratio quality filter dangerous for a code-heavy corpus?

Reveal answer

Code is mostly symbols: braces, parentheses, operators, indentation. A threshold tuned on prose (say symbol ratio ≤ 0.05) deletes essentially all code, so the mixture silently loses the exact capability you wanted. The fix is per-domain thresholds plus a validation set of hand-labelled documents from each domain, and reporting the filter's precision per domain — not a single global precision that hides a 90% deletion rate on one source.

Q5. You report a 60/40 web/code mixture by document count. What is the correct unit, and what else must you report for the number to be meaningful?

Reveal answer

The unit is training tokens contributed: documents × mean tokens per document × epochs. A code document is typically far shorter than a web page, so 60/40 by count can be 90/10 by tokens. Report: tokens per source after filtering, epochs per source, and the resulting per-source budget — plus the mixture schedule if it changes over training, since a late-stage shift is a real design choice that a single average hides.
