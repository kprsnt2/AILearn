L18 · Beam Search, Speculative Decoding, Constrained Decoding

Left-to-right sampling is greedy in the wrong sense: it commits to a token before it knows what that token makes possible. Three strategies fix different parts of that: beam search explores several hypotheses, speculative decoding makes the expensive model do less work, constrained decoding removes invalid tokens before they can be chosen.

~30 min difficulty ●●●●○ build: speculative-decode gain model + exactness proof
beam search length normalisation draft & verify acceptance rate distribution exactness constrained decoding logit mask / FSM

1 · Why it exists #

Three separate production failures, three separate answers.

  • Local decisions with global consequences. A token with high probability now can lead into a dead end three tokens later. Sampling never revisits; beam search keeps several partial hypotheses alive so a locally-worse token can still be explored. It matters where the metric is exact — a translation, a structured extraction, a shortest-program problem — not where creativity is the point.
  • Decoding is memory-bound and wasteful. Generating one token requires reading every weight. A cheaper draft model can propose several tokens, and the expensive model verifies them all in one forward pass — because that pass can score many positions in parallel. If the proposals are good, you get several tokens per expensive pass.
  • Valid output is a constraint, not a preference. A JSON response, an enum value, a date, a tool-call schema: a single invalid token invalidates the whole output. Sampling cannot guarantee validity; a mask computed from a grammar can, at the cost of the mask machinery and a real risk of allocating probability mass to nowhere if the grammar is wrong.

These are not competing options. Production stacks combine them: constrained decoding to make the output machine-parseable, speculative decoding to make it cheap, and ordinary sampling inside the constraint. Beam search is the odd one out — it optimises sequence probability, which is not the same as output quality.

2 · The mental model #

Analogy. Beam search is a chess engine keeping k candidate lines. Speculative decoding is a junior associate drafting an email while the partner checks it — the partner's read is cheap because the draft exists, and every sentence the partner accepts is a sentence not written twice. Constrained decoding is a legal-department filter: any sentence that violates the rules never reaches the page.

Where the analogy breaks. (1) A chess engine can evaluate a line; beam search cannot — it scores hypotheses by the model's own likelihood, and the model's likelihood is not the metric you care about. Beam search is famous for returning higher-probability, more generic, shorter text. (2) The verification pass in speculative decoding is not free, and it is only amortised if the draft's acceptance rate is high: below some threshold it is strictly slower than plain decoding. (3) A grammar filter can create a distribution that is not the model's conditional distribution — if the model wanted to emit an invalid token with high probability, constraining it changes the relative order of the valid ones too, because renormalisation redistributes mass.

Beam search

Keeps b hypotheses, expands each step, prunes to b by summed log-prob. Cost: b× the per-step compute (or b× memory for the cache). No quality guarantee.

Speculative decoding

Draft γ tokens cheaply, verify in one pass, accept the longest correct prefix. Output distribution is exactly the target model's, up to floating point — that is the point, and it is provable by enumeration.

Constrained decoding

At each step, compute the set of next tokens that keep a valid completion possible; set all others to −∞. Exactly correct if the set is exact, catastrophically slow if computed naively per step.

What they share

All three are ways to spend compute to make the output deterministic-correct or cheaper. All three interact with batching: a per-request mask or per-request draft breaks the uniform-batch assumption (L44).

3 · The mechanism #

Beam search and why the score must be length-normalised

score(sequence) = ∑t log p(yt | y<t, x)   (sum, always ≤ 0)
length-normalised:   score / |y|α   (R = α, 0 < α ≤ 1)
prune after each step:   keep the top-b prefixes over all b × V expansions A longer sequence has more (negative) terms, so raw log-prob always prefers shorter outputs and beats longer, higher-quality ones on the score. The length penalty is not an optional cosmetic; it is what stops beam search from emitting terse garbage. It also means the chosen sequence is the argmax under a modified objective, not the true one.
import math def logsoftmax(z): m = max(z); s = m + math.log(sum(math.exp(v - m) for v in z)) return [v - s for v in z] steps = [logsoftmax([2.0, 0.5, -0.5]), logsoftmax([0.0, 3.0, 0.0]), logsoftmax([0.0, 0.0, 4.0])] beam = {(0,): 0.0} for t, lp in enumerate(steps): cand = sorted(((sc + l, seq + (i,)) for seq, sc in beam.items() for i, l in enumerate(lp)), key=lambda z: -z[0]) beam = dict(cand[:3]) print(f"step {t+1} beams:", {k: round(v, 4) for k, v in beam.items()}) for k, v in beam.items(): print(f"raw={v:.4f} normalised(a=0.6)={v/len(k)**0.6:.4f} seq={k}")

Verified output:

step 1 beams: {(0,): -0.6931, (1,): -2.0986, (2,): -3.0986} step 2 beams: {(0, 1): -0.6936, (0, 0): -2.1255, (1, 1): -2.2966} step 3 beams: {(0, 1, 2): -0.6936, (1, 1, 2): -2.2971} raw=-0.6936 normalised(a=0.6)=0.4074 seq=(0, 1, 2) raw=-2.2971 normalised(a=0.6)=0.5214 seq=(1, 1, 2)

That last block is the length-penalty lesson in one line: the raw-score winner (0,1,2) is ranked below (1,1,2) once you normalise by length0.6, because the loser is much shorter — 0.6936/1.8 = 0.4074 vs 2.2971/2.4 = 0.5214 and higher is better. Change α and you change the answer, which is why "beam search" without a stated length penalty is an under-specified decoder.

Speculative decoding: the arithmetic, and why it is exact

Tokens per verification round = 1 + (1 + α + α2 + … + αγ−1) accepted on average
Cost per round = 1 target pass + c draft passes
Speedup ≈ [∑i=0..γ αi] / (1 + c) α = per-token acceptance probability of the draft, γ = draft length, c = cost of drafting γ tokens relative to one target pass. The +1 in the numerator is the token the target model emits when it rejects, or the bonus token when it accepts everything.
def spec_speedup(alpha, gamma, c): accepts = sum(alpha ** i for i in range(1, gamma + 1)) return (accepts + 1) / (1 + c) for alpha in [0.5, 0.7, 0.9]: for gamma in [1, 3, 5]: print(f"alpha={alpha} gamma={gamma}: E[accepts]={sum(alpha**i for i in range(1,gamma+1)):.2f} speedup c=0.1 {spec_speedup(alpha,gamma,0.1):.2f} c=0.3 {spec_speedup(alpha,gamma,0.3):.2f}")

Verified output (abridged, c = 0.1 / 0.3):

alpha=0.5 gamma=1: E[accepts]=0.50 speedup c=0.1 1.36 c=0.3 1.15 alpha=0.5 gamma=5: E[accepts]=0.97 speedup c=0.1 1.79 c=0.3 1.51 alpha=0.7 gamma=3: E[accepts]=1.53 speedup c=0.1 2.30 c=0.3 1.95 alpha=0.8 gamma=4: E[accepts]=2.36 speedup c=0.1 3.06 c=0.2 2.80 c=0.3 2.59 alpha=0.9 gamma=3: E[accepts]=2.44 speedup c=0.1 3.13 c=0.3 2.65 alpha=0.9 gamma=5: E[accepts]=3.69 speedup c=0.1 4.26 c=0.3 3.60

Two things to read. Acceptance dominates draft length: at α = 0.5 even γ = 5 gives only 1.79×, while α = 0.9 with γ = 3 gives 3.13×. So the drafting model's agreement with the target is the whole game — which is why production drafts are chosen from the same family/model version, not just any small model. And the cost ratio c matters at the margin: at α = 0.8, γ = 4 the speedup falls from 3.06× (c=0.1) to 2.80× (c=0.2) to 2.59× (c=0.3) — about a 15% loss for a tripling of draft cost. Aim for a draft that is much cheaper per token than the target, or the round-trip overhead eats the win.

Why the output distribution is exactly the target's. This is the part that makes speculative decoding safe. For each drafted token evaluated at its position, with target probability p and draft probability q:

accept with probability min(1, p/q); if rejected, resample from the residual r = normalize(max(0, p−q))
⇒ P(output = x) = q(x)·min(1, p(x)/q(x)) + P(reject)·r(x) = p(x) The first term is q(x) when q(x) ≤ p(x) and p(x) when q(x) > p(x); the second term supplies exactly the deficit p(x) − q(x) for the tokens where the draft under-proposed. So the total is p(x), for every x. Verified by 200,000-sample enumeration in Experiment 2.

Constrained decoding: a mask from a state machine

valid(state, token) = ∃ a continuation of token that is a complete output from state
z′i = zi if i ∈ valid(state) else −∞
state ← transition(state, chosen_token) The set of valid next tokens is computable from a finite-state machine or parser for the output grammar (JSON, a regex, an enum list). The mask must be applied BEFORE truncation and sampling, and the state must advance with the chosen token exactly. If the set ever becomes empty, the grammar and the model's prefix have diverged — retry from the last valid state rather than emitting garbage.
import math def softmax(z): m = max(z); e = [math.exp(v - m) for v in z]; s = sum(e); return [v / s for v in e] V = ["{", "}", "\"key\"", "\"val\"", ":", ",", "junk"] logits = [0.1, 0.2, 3.0, 2.0, 0.5, 0.4, 5.0] # model loves "junk" allowed = [False, False, True, False, False, False, False] print("raw p(junk) =", round(softmax(logits)[6], 4)) masked = [v if a else -1e9 for v, a in zip(logits, allowed)] print("constrained argmax:", V[max(range(7), key=lambda i: masked[i])], "p(inside mask)=", round(softmax(masked)[2], 6))

Verified output: raw p(junk) = 0.8184 and constrained argmax: "key" p(inside mask)= 1.0. The model's preferred token was invalid with 82% probability, and the mask reduces the choice to the single legal token. Note what that means for quality: when the model's mass is concentrated on an invalid token, the surviving valid token may be one the model ranked almost last, so the text after the constraint can be poor. That trade is audible in production: constraints guarantee validity, not quality, and the right fix for the quality half is training or prompting, not a looser mask.

4 · Your hands #

Experiment 1 — Size a speculative setup before you build it

Measure the acceptance rate on your own traffic; then the formula tells you the speedup. If the projected gain is under ~1.3×, do not build it — the complexity and the mask interactions are not worth it.

def project(alpha, gamma, c): return (sum(alpha ** i for i in range(1, gamma + 1)) + 1) / (1 + c) for alpha in [0.4, 0.6, 0.8, 0.95]: row = [project(alpha, g, 0.15) for g in [1, 2, 4, 6, 8]] print(f"alpha={alpha:.2f} c=0.15: " + " ".join(f"g={g}:{s:.2f}x" for g, s in zip([1, 2, 4, 6, 8], row)))

The row structure is the decision rule: for α < 0.5 the gain saturates below 1.6× no matter how long the draft, so a poorly-matched draft model cannot be rescued by drafting more tokens. Measure α as (number of draft tokens accepted) / (number drafted) over a few thousand steps, not on one example. Falsifier: if your measured speedup is far below the model's prediction, the verification pass is not actually amortising the draft — check that you batch the verify and that c is what you think it is.

Experiment 2 — Prove speculative decoding is exact, by enumeration

This is the strongest possible test: run the accept/reject/resample procedure several hundred thousand times and confirm the empirical output distribution equals the target distribution p, not the draft's or some mixture.

import random p = [0.5, 0.3, 0.1, 0.1] # target distribution q = [0.2, 0.5, 0.2, 0.1] # draft distribution (deliberately different) rng = random.Random(0); counts = [0] * 4 for _ in range(200000): d = rng.choices(range(4), weights=q)[0] if rng.random() < min(1.0, p[d]/q[d]): t = d else: resid = [max(0.0, pi - qi) for pi, qi in zip(p, q)] s = sum(resid); c = rng.random() * s; t = 3 for i, v in enumerate(resid): c -= v if c <= 0: t = i; break counts[t] += 1 tot = sum(counts) print("target p: ", p) print("empirical:", [round(c/tot, 4) for c in counts])

Verified: target p: [0.5, 0.3, 0.1, 0.1] and empirical: [0.5007, 0.2998, 0.0997, 0.0999] — the target, not the draft. That is the guarantee: speculative decoding changes speed, not output distribution, so it is safe to enable behind an existing product without re-tuning evals. Falsifier: any systematic skew toward the draft's distribution means the implementation skips the residual resampling (a common shortcut that does change the distribution).

Experiment 3 — Cost the constraint

Constrained decoding adds a per-token mask computation. Decide up front whether it is negligible or dominant, by measuring the ratio of mask work to the decode step.

V, steps = 128000, 1000 mask_ops_per_step = V # a mask must touch every logit model_flops_per_step = 2 * 7e9 print("mask element-ops per step: %.0f vs model FLOPs per step: %.3e -> ratio %.1e" % (mask_ops_per_step, model_flops_per_step, mask_ops_per_step / model_flops_per_step)) print("state-machine transitions per step (typical): 1") print("the mask is free; the FSM / parser is the cost, and it must be O(1) per step, not O(grammar size)")

The mask itself is 0.0009% of the FLOPs — free. The real cost is the state machine: an FSM that recomputes the valid-token set by scanning the whole grammar per step turns a 1 ms decode step into a multi-millisecond one. Use incremental transition tables (one per state, precomputed as a bitset over the vocabulary). Falsifier: if your constrained throughput is 2× worse than unconstrained, the mask is not the problem — the state machine is.

5 · Failure modes #

  • Beam search for open-ended generation. Symptom: monotonous, short, high-probability text; a model that "has no personality". Beam maximises likelihood, and likelihood-maximal text is generic. Use it for exact-match tasks only.
  • Beam search without a length penalty. Symptom: outputs are systematically too short and end abruptly. The penalty parameter must be chosen per task family.
  • Speculative decoding with a poorly-matched draft model. Symptom: slower than baseline; acceptance rate below ~0.5. Measure α per domain — it varies by prompt type, so a global average can mislead.
  • Speculative decoding that skips the residual resample on rejection. Symptom: quality subtly off in a way evals only catch with distribution-sensitive metrics; the output is no longer the target model's. The enumeration test catches it immediately.
  • Constrained decoding with an approximate grammar. Symptom: occasionally invalid output, or a state where no token is allowed and the decoder emits a fallback. Validate the grammar against a real parser, and handle the empty-valid-set case by backtracking.
  • Constraint applied after sampling or after top-p. Symptom: allowed tokens get truncated away, so the model emits an invalid token anyway or the sampler has zero mass. Mask first, then truncate.
  • Per-request masks/drafts in a batched server. Symptom: throughput collapses or requests block each other; the batching logic assumed uniform state. Needs continuous batching with per-sequence state (L44).

7 · Self-check #

Q1. Why does raw log-probability always prefer shorter sequences, and what does the length penalty actually change?

Reveal answer

Each token contributes a log-probability ≤ 0, so a longer sequence accumulates more negative terms and has a lower (worse) raw score. The penalty divides by |y|α so longer sequences are no longer automatically penalised; it changes the ranking to one that trades length against per-token likelihood. It does not restore the true conditional probability — the selected sequence is optimal for the modified objective. In the verified example, the raw winner (0,1,2) at -0.6936 ranks below (1,1,2) at -2.2971 after normalising with α = 0.6.

Q2. Draft acceptance rate α = 0.8, draft length γ = 4, draft cost c = 0.2. What is the expected speedup, and how many tokens per target pass?

Reveal answer

E[accepted draft tokens] = 0.8 + 0.64 + 0.512 + 0.4096 = 2.3616. Tokens per round = 2.3616 + 1 = 3.3616. Cost per round = 1.2 target passes. Speedup = 3.3616 / 1.2 = 2.80×. So you emit about 3.36 tokens for each 1.2 units of target-model work.

Q3. Prove in one line why speculative decoding preserves the target distribution.

Reveal answer

For a drafted token x with target p(x) and draft q(x): the accept branch contributes q(x)·min(1, p(x)/q(x)) = min(q(x), p(x)), and the reject branch resamples from the normalised residual r(x) ∝ max(0, p(x)−q(x)) with total reject probability equal to the residual mass, contributing exactly max(0, p(x)−q(x)). The sum is min(p,q) + max(0, p−q) = p(x). Verified empirically: target [0.5, 0.3, 0.1, 0.1] reproduced as [0.5007, 0.2998, 0.0997, 0.0999] over 200,000 samples.

Q4. Diagnostic: constrained decoding produces valid JSON in 99.9% of cases but the extraction accuracy is worse than free-form + a repair pass. What is the likely cause?

Reveal answer

The model's preferred tokens were frequently invalid, so the mask forced it onto low-probability valid tokens, and the content after the constraint is semantically poor even though the syntax is right. The verified toy case shows the model putting 0.64 of its mass on the invalid token: the surviving token then carries almost none of the model's belief. Options: (a) prompt/schema design that makes the valid continuation likely (order fields to match the model's preferred output order, keep the schema simple), (b) a repair pass anyway, (c) train the model on schema-valid targets (L52/L70). Constraint guarantees syntax, never semantics.

Q5. What is the hidden cost of beam search that people forget when comparing it to sampling?

Reveal answer

Memory and batching. Each beam needs its own KV cache (L09), so beam width b multiplies cache footprint by b and shrinks the number of concurrent requests per GPU by b — the throughput cost is not just b× compute, it is b× cache plus fewer batches. Also, beams diverge so the per-step work is not perfectly shared, and the final selection needs all beams' scores. That is why beam search is rare in high-throughput serving and common only in offline, latency-tolerant, exact-match workloads.
