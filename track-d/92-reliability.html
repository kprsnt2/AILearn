L92 · Reliability: retries, idempotency, degradation, queueing

Retries are the most common reliability feature and the most common cause of cascading failure: at a 30% backend failure rate with 5 retries, each logical call becomes 1.43 attempts, making the failing backend fail harder. And a key generated inside the retry loop turns one mutation into three.

~35 min difficulty ●●●●○ build: failure-injection test suite
retry amplification idempotency key placement duplicate mutations degradation ladder Little's Law utilisation knee circuit breaker failure injection

1 · Why it exists #

The failure: retry logic turned a partial outage into a total one. A provider degrades to a 30% error rate. Every client retries up to five times with no jitter. Each logical call now generates a mean of 1.428 attempts against a service already struggling, so effective load rises by 42.8% at exactly the moment capacity is lowest. The service goes from degraded to unavailable, and the retries keep it saturated.

The second failure is quieter and more expensive: duplicate side effects. A tool call times out. Your retry fires. The first call had already applied its effect — the response was slow, not the write. Now there are two rows, two comments, two charges. At a 5% timeout rate with 90% of effects applied before timeout, 4.5% of mutations are duplicated. Applied to a 15,317-tool-call run that is roughly 689 duplicate mutations, and none of them raise an error.

The third failure is the absence of a degradation policy. When the system cannot serve at full quality it either serves broken at full quality, or it hangs. There is no designed intermediate state, so the failure mode is whatever the timeout happens to produce.

Three mechanisms that must be designed rather than inherited: (1) bounded retries with backoff and jitter, whose amplification is computable from the failure rate; (2) idempotency, with the key derived from the logical operation once, before any attempt; (3) a declared degradation ladder specifying what is served at each level of impairment, including honest refusal.

2 · The mental model #

Reliability is a budget of attempts, and every retry spends it on the assumption that the failure is transient. When failure is persistent — overload, quota exhaustion, a broken deploy — retries convert a bounded problem into an unbounded one.

Analogy: a circuit breaker in a house

A breaker trips to protect the wiring, not the appliance. In a distributed system the breaker protects the caller from a dead dependency and the dependency from the caller's load. Both directions matter: half of a retry storm is you hurting the provider, half is the provider hurting you.

Where it breaks

A house breaker trips on current and resets by hand. A software breaker must decide when to probe, and each probe sends real traffic to a service you believe is down. The half-open state is where most breaker bugs live: loops that never probe (permanent outage after a transient), or every client probing at once (a thundering herd at recovery).

Real attempts form a geometric sum. For independent failures at rate p with r retries, expected attempts per logical call is ∑i=0r pi, which converges to 1/(1−p). Compute that before choosing the retry count.

3 · The mechanism #

Retry amplification, exactly:

E[attempts] = ∑i=0r pi   →   1/(1−p) as r→∞      excess load = E[attempts] − 1 p = per-attempt failure probability, r = retries. At p=0.30, r=5: 1+0.3+0.09+0.027+0.0081+0.00243 = 1.428 → +42.8% load on an already-failing backend. At p=0.50, r=5: 1.969 → +96.9%. This is why retries need a budget shared across the whole run rather than a per-call count.

Duplication without idempotency, and the queueing relation that makes overload nonlinear:

P(duplicate) = P(timeout) · P(effect applied | timeout)      L = λ · W   →   W = 1/(μ−λ) at util ρ=λ/μ Left: 0.05 × 0.90 = 0.045. Right: Little's Law says in-flight work equals arrival rate times time-in-system, so a latency increase multiplies concurrency linearly, which is how one slow dependency exhausts a connection pool. At ρ=0.95 time-in-system is 10× the service time at ρ=0.50's 1.11× — the curve is not linear near saturation.

The implementation: shared retry budget, caller-supplied idempotency key, circuit breaker.

import random, time class RetryBudget: """Shared across a whole agent run: caps TOTAL extra attempts, not per-call retries.""" def __init__(self, extra=10): self.extra, self.used = extra, 0 def take(self): if self.used >= self.extra: return False self.used += 1 return True class Breaker: def __init__(self, threshold=5, cooldown_s=30): self.threshold, self.cooldown_s = threshold, cooldown_s self.fails, self.opened_at = 0, None def allowed(self, now): if self.opened_at is None: return True if now - self.opened_at > self.cooldown_s: self.opened_at, self.fails = None, 0 # half-open: allow ONE probe return True return False def record(self, ok, now): if ok: self.fails = 0 else: self.fails += 1 if self.fails >= self.threshold: self.opened_at = now def call_with_retries(op, idem_key, budget, breaker, clock, attempts=3, base_s=0.2, jitter=0.5, rng=None): """idem_key comes FROM THE CALLER, derived once from the logical operation. Generating it here is the bug: every retry would get a fresh key and the server-side dedupe would never fire.""" rng = rng or random.Random() for i in range(attempts): now = clock() if not breaker.allowed(now): raise CircuitOpen(idem_key) try: out = op(idem_key) # server dedupes on key breaker.record(True, now) return out except (TransientError, TimeoutError): breaker.record(False, now) if i == attempts - 1 or not budget.take(): raise sleep = base_s * (2**i) * (1 + jitter*(2*rng.random()-1)) time.sleep(sleep) # exponential backoff + jitter

Four decisions, all load-bearing. (1) The idempotency key is a parameter, not a generated value — the single most common bug. (2) The budget is shared across the run, so a run cannot generate unbounded retries through many calls each retrying. (3) The breaker opens on persistent failure and probes after a cooldown, so a dead dependency stops receiving retry traffic. (4) Backoff is exponential with jitter — without jitter, clients retry in lockstep and the retry wave is itself a spike.

Reliability claims are testable only by injection. The audit question: for each row of the degradation ladder, is there a test that forces the trigger and asserts the served behaviour? If the "refuse" level has never been exercised, you do not know whether it refuses or crashes — and that path runs for the first time during your worst incident.

4 · Your hands #

Experiment 1 — Retries amplify load on a failing backend

Expected attempts per logical call across failure rates and retry counts. Watch the right-hand column as p rises.

def amplification(p_fail, retries): return sum(p_fail**i for i in range(retries + 1)) print("p_fail r=0 r=2 r=5") for pf in (0.01, 0.05, 0.10, 0.30, 0.50): row = [amplification(pf, r) for r in (0, 2, 5)] print(f"{pf:5.2f} " + " ".join(f"{x:.3f}" for x in row)")

Observed output: 0.01 → 1.000 1.010 1.010 · 0.05 → 1.000 1.052 1.053 · 0.10 → 1.000 1.110 1.111 · 0.30 → 1.000 1.390 1.428 · 0.50 → 1.000 1.750 1.969. Two readings. Retries are nearly free when p is small (1.010× at 1% failure) — the regime they were designed for. They are devastating when p is large: at 50% failure with 5 retries you nearly double the load on a service already at half capacity, which drives p toward 1, which raises attempts further. That positive feedback is the mechanism behind most retry-induced outages. Falsifier: if your service survives a 50% failure with 5 retries, you have genuine headroom — verify that with Experiment 3's utilisation numbers rather than assuming it, because the loop only bites near saturation.

Experiment 2 — Duplicates depend on where one line of code lives

Timeout-then-retry with and without a key that survives the retry loop.

def duplicate_rate(p_timeout, p_applied_given_timeout): return p_timeout * p_applied_given_timeout for p_to, p_ap in ((0.01, 0.5), (0.05, 0.5), (0.05, 0.9), (0.10, 0.9)): print(f"P(timeout)={p_to:.2f} P(applied|timeout)={p_ap:.1f} " f"-> P(duplicate)={duplicate_rate(p_to,p_ap):.4f}") print(f"15317 tool calls at 4.5% -> {int(15317*0.045)} duplicate mutations") def apply_with_dedupe(attempts, seen): applied = 0 for k in attempts: if k in seen: continue # dedupe hit - no side effect seen.add(k) applied += 1 return applied print("same key x3 -> applied", apply_with_dedupe(["k1"]*3, set()), "(correct)") print("new key each -> applied", apply_with_dedupe(["k1","k2","k3"], set()), "(BUG: 3 mutations)")

Observed output: 0.01 / 0.5 → 0.0050 · 0.05 / 0.5 → 0.0250 · 0.05 / 0.9 → 0.0450 · 0.10 / 0.9 → 0.0900; then 15317 tool calls at 4.5% -> 689 duplicate mutations; then same key x3 -> applied 1 (correct) and new key each -> applied 3 (BUG: 3 mutations). The last two lines are the lesson compressed: whether your system duplicates depends on where one line of code lives. Generating the key inside the retry function is a one-line difference between one mutation and three. Falsifier: if your dedupe store has a TTL shorter than your longest retry chain, the window closes and duplicates return — check TTL against sum(backoff) + timeout.

Experiment 3 — The utilisation knee, where retries land

Mean time in system for an M/M/1 queue as utilisation rises. This is the headroom that absorbs retries instead of amplifying them.

def time_in_system(lam, mu): return 1 / (mu - lam) # seconds, valid for lam < mu mu = 10.0 # 10 requests/sec service capacity for util in (0.5, 0.7, 0.8, 0.9, 0.95): lam = util * mu print(f"util={util:.2f} -> time in system {time_in_system(lam,mu):.2f}s " f"(service {1/mu:.2f}s, ratio {time_in_system(lam,mu)*mu:.1f}x)")

Observed output: util=0.50 → 0.20s (service 0.10s, ratio 2.0x) · 0.70 → 0.33s (3.3x) · 0.80 → 0.50s (5.0x) · 0.90 → 1.00s (10.0x) · 0.95 → 2.00s (20.0x). At 95% utilisation a request waits 20× its service time — and a 42.8% load increase from retries (Experiment 1 at p=0.30) pushes utilisation from 0.70 to 0.99, where the queue explodes. The retry policy must be designed against the utilisation curve, not against the error rate. Falsifier: if your latency is flat at high utilisation you have concurrency or batching hiding the queue — that is real headroom; find its limit with a load test rather than trusting the M/M/1 numbers.

5 · Failure modes #

  • Retry storm. Unbounded or unjittered retries on a degraded backend. Symptom: effective load rises above capacity precisely during an incident; utilisation pinned near 1.0.
  • Key generated inside the retry loop. Symptom: duplicate rows/comments/charges with no error; duplicate count tracks timeout rate.
  • Retry on non-idempotent, non-retryable errors. Retrying a 400 or a validation error. Symptom: identical error strings repeated in the trace; wasted spend with zero chance of success.
  • Timeout shorter than p99 of the operation. Healthy slow requests are killed and retried, adding load. Symptom: retry rate exceeds true error rate; retried calls often succeed on the second attempt for no reason.
  • Breaker with no probe. Opens and never closes. Symptom: a dependency recovers but traffic never returns; permanent degradation after a transient.
  • Breaker probe storm. All clients probe simultaneously on cooldown expiry. Symptom: periodic latency spikes at exactly the cooldown interval.
  • Unbounded queue. Backlog grows without shedding. Symptom: queue depth grows monotonically; latency measured in queue-age, not work time; memory climbs.
  • Undesigned degradation. No ladder. Symptom: at 20% error rate users get partial or truncated answers with no warning; support cannot distinguish "degraded" from "broken".

7 · Self-check #

Q1. Backend failure rate 0.20, 4 retries. Compute the load multiplier and say what it does to a backend running at 80% utilisation.

Reveal answer

∑i=04 0.2i = 1 + 0.2 + 0.04 + 0.008 + 0.0016 = 1.2496 → +25% load. A backend at 80% utilisation receiving 1.25× load goes to 0.80 × 1.2496 = 0.9997 — effectively 100%, where queue time diverges and latency blows up. So a 20% error rate plus retries does not merely persist the error rate; it removes the remaining headroom and turns a degradation into an outage. The fix is a shared retry budget plus a breaker, so total attempt inflation is bounded rather than per-call.

Q2. You observe 4% duplicate comments. Timeout rate is 4%, and effects apply before timeout 95% of the time. Is the math consistent, and what is the bug?

Reveal answer

Predicted duplicate rate = 0.04 × 0.95 = 0.038, i.e. 3.8% — consistent with the observed 4%. So the mechanism is confirmed: the retry fired after the effect had already been applied, and the second application succeeded because it was not deduplicated. The bug is the absence of an idempotency key, or a key generated per attempt rather than per logical operation. Fix: derive the key from (logical_op, target, request_id) at the call site before entering the retry loop, and require the server to dedupe on it. Verify by asserting the mutation count equals the logical-op count in a test that injects timeouts.

Q3. Why does jitter matter, quantitatively?

Reveal answer

Without jitter, clients that fail at the same moment retry at the same moment: an outage produces a synchronized retry wave at t+backoff, which hits the recovering service as a spike and can re-trigger the outage. With full jitter, retries spread uniformly over the backoff window, so the peak load from retries is roughly 1/(number of retry cohorts) of the no-jitter peak. Practically: exponential backoff sets the total wait budget; jitter spreads arrivals within it. The standard implementation is sleep = base × 2^i × (1 + jitter×(2r−1)) with jitter near 0.5, which disperses each cohort over a 2× window.

Q4. Diagnostic: a dependency recovered 20 minutes ago but your error rate is unchanged. What is the likely cause and the test that proves it?

Reveal answer

A circuit breaker with no working probe — it opened and never entered half-open, so no traffic reaches the recovered dependency. Prove it by inspecting the breaker state in the trace (CircuitOpen errors with no attempted call underneath), then force a probe manually and watch the error rate drop. The fix is an explicit half-open state with a single permitted probe and jitter on the cooldown, and a test that simulates recovery and asserts traffic resumes. Without this, a transient failure becomes a permanent one — the failure mode a breaker is supposed to prevent.

Q5. Which operations must never be auto-retried, and what does that imply for the architecture?

Reveal answer

Irreversible or externally visible mutations without a reliable idempotency guarantee: deploys, payments, deletions, sends to third parties, and anything with side effects outside your transaction boundary. Retrying them risks an un-undoable duplicate (L84). Implication: the retryable/non-retryable distinction is a property of the tool or capability, not a global policy — so it belongs in the tool contract (L77) alongside the irreversibility flag, and the retry wrapper must consult it. For non-retryable operations, the correct behaviour is to surface the ambiguity ("we do not know whether it applied") and require an out-of-band check, not to guess by retrying.
