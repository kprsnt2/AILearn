L95 · The RAKE reporting harness

Reporting And Knowledge Evaluation: the harness that turns "the agent did well" into a bundle a stranger can verify. Six components — manifest, immutable artifact bundle, hash-chained log outside the workspace, AND-gated promotion, independent oracle, cost attribution — each specified to the field.

~45 min difficulty ●●●●● build: full RAKE harness spec + reference implementation
run manifest immutable artifact bundle hash-chained event log AND-gated promotion independent oracle cost & latency attribution report format reproducibility class

1 · Why it exists #

The failure RAKE exists to stop: a run reports success and nobody can check it. The agent finished, the logs show tool calls, the summary says the task is complete, and the person reading it has no way to distinguish that from a run that asserted completion and did nothing. Every claim is a claim about a transcript that no longer exists in a form anyone can replay.

Your existing systems already contain the pieces. BugAgents' 4-point promotion gate is an AND-gate. AgentSwarm's hash-chained ledger is the immutability primitive. JobAgents' zero-LLM scoring path is an oracle that does not depend on the model being right. What is missing is the assembly: one bundle per run, produced by a harness that will not emit a report it cannot back with evidence, and a promotion decision that is a function of that bundle alone.

RAKE is that assembly. The name is deliberate: rake as in raking a ledger — sweeping every run into a single auditable record — and Reporting And Knowledge Evaluation as the two outputs: a report per run, and the accumulated knowledge (golden sets, calibration records, gate history) that makes the next report comparable to the last.

RAKE's single design rule: the harness refuses to produce a report it cannot substantiate. A missing manifest field, a broken hash chain, a claim with no oracle event, or an undeclared reproducibility class makes the report say so — it does not default to pass. Everything else in the spec follows from that rule.

2 · The mental model #

Six components, each with one job, arranged so that no component trusts another's assertion:

#ComponentSingle jobRefuses when
1Run manifestfreeze everything that could change the resulta required field is missing
2Artifact bundlehold the run's outputs, content-addressed and immutablean artifact's hash does not match its recorded address
3Event logrecord every action in a hash chain outside the workspacethe chain does not verify from genesis
4Promotion gatesdecide go/no-go as an AND over named gatesany single gate fails
5Independent oraclemint credit for a claimno oracle event exists for the claim
6Cost & latency attributionprice the run per event kind and per toola spend event has no cost estimate

Analogy: a laboratory notebook with a notary

A lab notebook records what was done, with page numbers so a removed page is obvious. A notary, periodically, seals the state of the book. RAKE is the notebook (event log), the page numbering (hash chain), the seals (artifact hashes), and the protocol for deciding whether an experiment is publishable (gates). The analogy holds because the value is in the protocol, not in the paper quality.

Where it breaks

A notebook records an experiment once; a RAKE run produces a bundle intended to be compared with prior bundles. That adds a constraint the analogy lacks: comparability. A bundle is only useful if the next one is comparable, which forces the manifest to pin the golden set, the judge calibration, and the index version — otherwise two reports have different meanings and the gate history is meaningless. This is why the manifest has 18 fields rather than 4.

Component 2 — the immutable artifact bundle

Layout, addressed by content hash so the bundle is self-verifying:

bundle/<run_id>/ manifest.json immutable; written once, then chmod 0444 events.jsonl the hash-chained log (append-only) head one line: final chain hash artifacts/ <sha256>/<name> every output file, addressed by its own hash report.json generated LAST, references only hashes SEAL sha256 over (manifest, head, sorted artifact hashes)

The SEAL is what makes the bundle immutable in practice: it is a single hash over the manifest, the chain head, and every artifact hash. Recompute it and you know whether anything in the bundle changed. This is the same construction as your AgentSwarm ledger's integrity check, applied to the whole run rather than to a single event stream.

Component 3 — the hash-chained event log, outside the writable workspace

hi = SHA256( hi−1 ‖ canonical_json(eventi) )      SEAL = SHA256( manifest_hash ‖ hn ‖ sort(artifact hashes) ) The log directory must be on storage the agent cannot write (L84) — otherwise the agent can edit and re-chain. Event kinds: run_start, tool_call, claim, oracle, llm, error, denial, run_end.

Component 4 — promotion gates (AND, not majority)

Every gate reads a derived value — a recomputation from the log — never a stored pass flag. A gate that reads a boolean written by the agent is not a gate.

Component 5 — the independent oracle

"Independent" is a testable property, not an aspiration. An oracle is admissible only if it satisfies all four:

RequirementTestFails when
Cannot be edited by the agentoracle code + tests hash recorded; agent has no write capability to themthe agent can modify what judges it (L84 self-modification pair)
Deterministic or calibratedsame input → same verdict; or a calibration report with TPR/FPR (L89)an uncalibrated judge is the oracle
Adversarially testeda suite of known-bad inputs that the oracle rejectsno one has tried to make it pass wrongly
Reproducible from the bundlere-running the oracle on bundle artifacts reproduces the verdictthe oracle depends on live state not captured in the bundle

Component 6 — cost and latency attribution

import hashlib, json, time def canon(o): return json.dumps(o, sort_keys=True, separators=(",", ":")) class EventLog: def __init__(self): self.prev, self.events = "0"*64, [] def emit(self, kind, payload): ev = {"seq": len(self.events), "kind": kind, "ts": round(time.time(), 3), "payload": payload, "h_prev": self.prev} ev["h"] = hashlib.sha256((self.prev + canon(ev)).encode()).hexdigest() self.prev = ev["h"] self.events.append(ev) def verify(self): prev = "0"*64 for i, ev in enumerate(self.events): stored = ev["h"] body = {k: v for k, v in ev.items() if k != "h"} if body["h_prev"] != prev: return False, i, "chain" if hashlib.sha256((prev + canon(body)).encode()).hexdigest() != stored: return False, i, "hash" prev = stored return True, len(self.events), prev[:12] # ---- gates derive from the log; none reads a stored pass flag ---- def g_ledger(log): return log.verify()[0] def g_tests(log): return any(e["kind"]=="oracle" and e["payload"].get("pass") for e in log.events) def g_no_overclaim(log): claims = {e["seq"] for e in log.events if e["kind"] == "claim"} covered = {e["payload"].get("claim_seq") for e in log.events if e["kind"] == "oracle"} return claims <= covered def g_repro(manifest): return manifest.get("repro_class") in ("BYTE_REPRODUCIBLE", "TOLERANT_REPRODUCIBLE") def attribute(log): out = {} for e in log.events: if e["kind"] == "llm": c = (e["payload"].get("tokens_in", 0)*0.28 + e["payload"].get("tokens_out", 0)*1.10) / 1e6 out["llm"] = out.get("llm", 0.0) + c elif e["kind"] == "tool": out["tool"] = out.get("tool", 0.0) + e["payload"].get("cost_usd", 0.0) return {k: round(v, 8) for k, v in out.items()}

The report format

{ "rake_version": "1.0", "manifest_hash": "<12 hex>", "ledger": { "n_events": 6, "verified": true, "head": "<12 hex>" }, "seal": "<sha256>", "gates": [ {"gate":"ledger_intact","pass":true}, ... ], "promoted": true, "oracle": { "name": "pytest", "pass": true, "calibration_id": "..." }, "cost": { "by_kind": {"llm":0.00268,"tool":0.001}, "total": 0.00368 }, "latency": { "p50_ms": ..., "p95_ms": ... }, "repro_class": "TOLERANT_REPRODUCIBLE", "artifacts": [ {"name":"diff.patch","sha256":"..."} ], "report_hash": "<sha256 over all of the above, excluding this field>" }

RAKE's review test: given only the bundle, can a stranger reproduce the report hash and the promotion decision? If yes, the run is evidence. If any step requires a dashboard, a database, or your memory, the bundle is a summary — and a summary of an agent run is exactly the artifact that overclaims.

4 · Your hands #

Experiment 1 — A working harness, three run outcomes

Manifest validation, hash-chained log, real gates, and report generation. Run it and observe that a tampered log and an undeclared repro class each block promotion for a different reason.

import hashlib, json, time def canon(o): return json.dumps(o, sort_keys=True, separators=(",",":")) def sha12(o): return hashlib.sha256(canon(o).encode()).hexdigest()[:12] REQUIRED = ["run_id","task_id","code_commit","agent_config_hash","model_id", "model_revision","temperature","top_p","seed","system_prompt_hash", "tools_schema_hash","golden_set_id","golden_set_hash","judge_id", "judge_calibration_id","budget_cap","index_version","created_at"] class Log: def __init__(self): self.prev, self.ev = "0"*64, [] def emit(self, k, p): e = {"seq": len(self.ev), "kind": k, "payload": p, "h_prev": self.prev} e["h"] = hashlib.sha256((self.prev + canon(e)).encode()).hexdigest() self.prev = e["h"]; Observed output: clean promoted=True failing=[] · tampered promoted=False failing=['ledger_intact'] · no repro class promoted=False failing=['repro_declared']. Three runs, three verdicts, each traceable to a specific gate reading a specific derived value. Note that the tampered run still has oracle_passed=True and no_overclaim=True — the edit changed a tool name, not the verdicts — and it is blocked anyway, because the ledger gate noticed the edit. That is the AND-gate working as designed: one failure is enough. Falsifier: if tampering with an event does not fail ledger_intact, your verifier is not recomputing the hash from content (L90, Experiment 2).

Experiment 2 — Reproduce the report hash independently

The review test in executable form: a second party recomputes the report hash from the bundle's own contents and confirms it matches.

import hashlib, json def canon(o): return json.dumps(o, sort_keys=True, separators=(",",":")) def report_hash(rep): body = {k: v for k, v in rep.items() if k != "report_hash"} return hashlib.sha256(canon(body).encode()).hexdigest() def seal(manifest_hash, head, artifact_hashes): return hashlib.sha256(canon([manifest_hash, head, sorted(artifact_hashes)]).encode()).hexdigest() rep = {"rake_version": "1.0", "manifest_hash": "abc123", "ledger": {"n_events": 6, "verified": True, "head": "def456"}, "promoted": True, "repro_class": "TOLERANT_REPRODUCIBLE"} r1 = report_hash(rep) rep2 = dict(rep); rep2["promoted"] = False r2 = report_hash(rep2) print("report hash ", r1[:16]) print("after flipping promoted", r2[:16], "-> matches:", r1 == r2) print("seal ", seal("abc123", "def456", ["h1", "h2"])[:16]) print("seal with one artifact changed", seal("abc123", "def456", ["h1", "hX"])[:16])

The report hash changes when a single verdict field flips, and the seal changes when a single artifact hash changes. Together they give the reviewer two checks: was the report altered? (report hash) and were the inputs it references altered? (seal). A reviewer recomputes both from the bundle and either both match or the run is rejected — no trust required, no access to your systems required. Falsifier: if your report hash is computed over a canonical form that omits fields (e.g. only the summary line), flipping promoted will not change it — hash the whole report body minus the hash field.

Experiment 3 — Cost attribution by kind and by tool (copy-paste)

The attribution component, on a realistic event stream. The output is what a report's cost section contains.

PRICE_IN, PRICE_OUT = 0.28/1e6, 1.10/1e6 events = [ {"kind": "llm", "payload": {"tokens_in": 2000, "tokens_out": 400}}, {"kind": "tool", "payload": {"tool": "search", "cost_usd": 0.001}}, {"kind": "llm", "payload": {"tokens_in": 8000, "tokens_out": 300}}, {"kind": "tool", "payload": {"tool": "pytest", "cost_usd": 0.0}}, {"kind": "llm", "payload": {"tokens_in": 14000, "tokens_out": 250}}, ] def attribute(events): by_kind, by_tool = {}, {} for e in events: p = e["payload"] if e["kind"] == "llm": c = p["tokens_in"]*PRICE_IN + p["tokens_out"]*PRICE_OUT by_kind["llm"] = by_kind.get("llm", 0) + c elif e["kind"] == "tool": c = p["cost_usd"] by_kind["tool"] = by_kind.get("tool", 0) + c by_tool[p["tool"]] = by_tool.get(p["tool"], 0) + c return by_kind, by_tool k, t = attribute(events) print("by_kind", {a: round(b, 6) for a, b in k.items()}) print("by_tool", {a: round(b, 6) for a, b in t.items()}) print("total $%.6f" % sum(k.values()))

Observed output: by_kind {'llm': 0.007765, 'tool': 0.001}, by_tool {'search': 0.001, 'pytest': 0.0}, total $0.008765. The last LLM call (14,000 input tokens) costs $0.004195 — more than the first call's entire cost, because context grows (L90, L79). LLM spend is 88.6% of the run, and 54% of that LLM cost is the single final call. Attribution per event is what turns "the run cost $0.0088" into "the run cost $0.0088 and 88.6% of it was three LLM calls with a growing context, of which the last was half". That is the sentence a reviewer can act on. Falsifier: if by_kind has no tool key, your tool events carry no cost_usd and the tool bill is invisible — a harness that silently under-reports tool cost will approve runs that are not cheap.

5 · Failure modes #

  • Gate reads a stored boolean. The agent (or its framework) writes passed: true. Symptom: every run promotes; tampering has no effect on the decision.
  • Log inside the workspace. Symptom: the chain verifies but events contradict artifacts — the agent re-chained its own edits (L84).
  • Manifest written after the run. Values filled from what actually happened. Symptom: the manifest always matches the run, and can never detect a config drift.
  • Majority-gate. "5 of 7 gates passed." Symptom: promotions with a broken ledger or a failed oracle, because the failing gate was outvoted.
  • Oracle not independent. The oracle is the same model that produced the work. Symptom: oracle_passed correlates perfectly with the agent's own claims; zero true negatives.
  • Unsealed artifacts. Artifacts referenced by path, not hash. Symptom: two bundles point at the same mutable path; the diff a reviewer sees is not the diff the run produced.
  • Cost from a dashboard. Attribution pulled from a provider console. Symptom: totals disagree with the events; retries and failed calls missing from the report.
  • Comparability broken. Golden set or judge calibration changed between runs. Symptom: report scores are not comparable; gate history shows improvement that reverses when re-scored (L88).

7 · Self-check #

Q1. Why must the SEAL cover artifact hashes in addition to the manifest and the chain head?

Reveal answer

Because the manifest pins the configuration and the chain pins the events, but neither pins the outputs. An attacker (or a careless process) could leave the manifest and the chain untouched while replacing a produced file — a diff that passes review but is not the diff the run made. Including the sorted set of artifact hashes in the seal makes the outputs part of the sealed state, so replacing one artifact changes the seal. Notice it must be sorted so that the seal is independent of listing order, otherwise the same bundle produces different seals.

Q2. A run has oracle_passed=true, no_overclaim=true, cost_within_cap=true, and ledger_intact=false. What is the promotion decision, and why is that the right rule?

Reveal answer

Not promoted. ledger_intact=false means the record of what happened was altered, which invalidates the evidence for every other gate — the oracle_passed event could be one of the altered ones. An AND gate is correct because gates are not independent evidence of different qualities; they are a conjunction where the ledger gate is the precondition for trusting the rest. A majority rule would let four "passes" outvote a broken record, which is precisely the overclaim RAKE exists to prevent.

Q3. Name the four tests that make an oracle "independent", and say which one is most often skipped.

Reveal answer

(1) The agent cannot edit it (no write capability to oracle code or tests). (2) It is deterministic or has a calibration report with TPR/FPR. (3) It has been adversarially tested with known-bad inputs. (4) It is reproducible from the bundle alone. The most-skipped is adversarial testing — teams check that the oracle passes good work but rarely construct inputs designed to make it pass bad work, so its false-positive rate is unmeasured until production measures it for them (L89 calibration is the same gap in judge form).

Q4. Diagnostic: a RAKE report shows cost.total = $0.0085, but the provider invoice attributes $0.014 to the run. Give three checks in order.

Reveal answer

(1) Cached tokens — if the trace prices all input at the standard rate while the invoice bills cache writes at a different rate, totals diverge; check for a cached_in field on LLM events. (2) Error and timeout events — a timed-out call that carried a large prompt is often billed; if error events carry no tokens_in, their cost is missing from attribution. (3) Missing event kinds — embedding calls, reranker calls, and subagent calls that were not instrumented. A persistent gap should be treated as a missing span kind, not a pricing error, because the harness's job is to make every billable action an event.

Q5. Why does the spec require the manifest to be written before the run, when writing it afterwards would be more accurate?

Reveal answer

Because a manifest written afterwards is a description of what happened, not a commitment to what was intended — and it can therefore never detect the failure it exists to detect: configuration drift between what you believed you ran and what actually ran. A pre-run manifest that mismatches the observed events is a finding (the run used a different model revision, temperature, or prompt than declared). A post-run manifest always matches and has zero diagnostic power. The mutable fields (end time, actual spend, verdicts) live in the report, not the manifest.
