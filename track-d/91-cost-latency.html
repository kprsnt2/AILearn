L91 · Cost & latency budgets: caching, routing, model cascades

A 12× price ratio makes a cascade look free: at a 20% escalation rate you save 71.7%. But escalated requests pay the cheap model and the expensive one serially, so p95 latency goes up relative to the direct path — 1,800 ms becomes more than 1,800 ms. Cost and latency are separate budgets and you optimise them separately.

1 · Why it exists #

The failure: the average user is happy and the p95 user is furious. You route every request to the strong model. Mean latency 1,800 ms, cost $0.006/request, no surprises. You add a cascade — cheap model first, escalate when unsure — and your dashboard's mean drops to 760 ms and cost falls 72%. Ship it. Then the support tickets arrive from the 20% whose requests hit both models in sequence: their latency is now the cheap model's time plus the expensive model's time, which is structurally worse than just calling the expensive model.

The second failure is a cascade without a usable confidence signal. If escalation fires at random, you pay both models for the escalated share and gain accuracy only in proportion to the expensive model's advantage over a random sample — measured below at 0.775 accuracy for a 30% random escalation rate, versus 0.8407 for a signal that escalates 50% when the cheap model is wrong and only 5% when it is right. Same escalation rate, +6.6 accuracy points, pure signal quality.

The third failure is optimising the wrong metric entirely. Cost per request is not cost per verified task. A cheap path that fails 20% of the time and requires a retry costs more than an expensive path that succeeds first time — and the retry cost lives in a different allocation bucket, so nobody sees it.

Cost and latency are two separate budgets with different objectives: cost minimises expected dollars per verified task; latency constrains a tail percentile (p95/p99), not the mean. A cascade is a cost instrument that usually worsens the latency tail. Decide which budget binds before choosing the instrument, and gate each on its own declared SLO.

2 · The mental model #

Three levers, in order of how much they change the economics and how little they change behaviour:

LeverMechanismCost effectLatency effectQuality effect
Caching (prefix, exact-match, semantic)reuse a previous computationlarge, multiplicative on hit ratelarge, only on hitsnone if the cache key is right; stale if it is wrong (L97)
Cascade / routingcheap model first, escalate on signalc_cheap + p·c_expmean improves, tail worsensdepends entirely on escalation signal
Cascade by task classroute by task type rulessame as above but deterministicdeterministic per class; tail predictableset by rule accuracy, debuggable

The ordering matters: caching is first because it reduces work rather than redistributing it. A cascade that saves 72% is impressive until you notice a 40% cache hit rate saves 40% with zero quality risk and improves latency on every hit. Do the cheap, safe thing first.

Analogy: a triage nurse and a specialist

Cascade routing is triage. Nearly everyone sees the nurse; a signal sends some patients to the specialist. Cheap, and effective — but the patients who see both wait for both, so their total wait is longer than going straight to the specialist. Triage improves the average only because most patients never see the specialist.

Where it breaks

A triage nurse's signal is based on patient presentation, and a missed case is caught later by a human. A model's confidence signal is generated by the same model that may be wrong, so the missed cases are exactly the ones the model is confidently wrong about — the escalation signal has a blind spot that correlates with the error. That is why an independent verifier (L76, L89) is a better escalation signal than self-reported confidence.

3 · The mechanism #

Expected cost of a two-tier cascade, and the escalation rate at which it stops paying:

Ccascade = ccheap + pesc·cexp      pesc* = (cexp − ccheap) / cexp With c_cheap/$0.0005 and c_exp/$0.0060, p_esc* = 0.917: the cascade is cheaper than going direct until 91.7% of requests escalate. That is a very forgiving break-even — which is why cascades are popular — but it says nothing about latency or quality.

Latency, which is where the trap is:

E[L] = tcheap + pesc·texp      p95[L] = tcheap + texp   (if pesc > 5%) Escalated requests are serial, so their latency is the sum. With t_cheap=400, t_exp=1800: mean 760 ms at p_esc=0.2 (a 58% mean improvement) but p95 = 2,200 ms, worse than the 1,800 ms direct path. A mean-based SLO passes; a p95 SLO fails.

Quality given an escalation signal with different rates on wrong vs right answers:

pesc = pcheap·qesc|right + (1−pcheap)·qesc|wrong      Acascade = pcheap(1−qesc|right) + pesc·Aexp qesc|wrong − qesc|right is the separation of the signal, and it is the whole game. At p_cheap=0.70, A_exp=0.95: separation 0.75 (0.80 on wrong, 0.05 on right) gives 0.9262 accuracy at $0.00215; separation 0.30 gives 0.8407 at $0.00161; random escalation (separation 0) gives 0.7750 at $0.00230.

The router, with the SLO gates as code rather than as a dashboard.

class Router: def __init__(self, tiers, slo): self.tiers = tiers # [(name, cost, latency_ms, accuracy), ...] cheapest first self.slo = slo # {"p95_ms": ..., "cost_per_task": ..., "min_accuracy": ...} self.stats = {"n": 0, "cost": 0.0, "lat": [], "correct": 0} def route(self, task, verifier): # Escalate on a VERIFIER result, not on model self-confidence. lat = 0.0 for name, cost, ms, acc in self.tiers: lat += ms out = call(name, task) # cost is charged whether or not we escalate self.stats["cost"] += cost ok = verifier(task, out) # independent oracle if ok: break if lat + self.tiers[-1][2] > self.slo["p95_ms"]: break # SLO gate: stop before blowing the tail self.stats["n"] += 1 self.stats["lat"].append(lat) self.stats["correct"] += ok return out, ok def report(self): lat = sorted(self.stats["lat"]) n = max(1, self.stats["n"]) p95 = lat[min(len(lat)-1, int(0.95*len(lat)))] if lat else 0 return { "mean_cost": self.stats["cost"]/n, "p95_latency": p95, "accuracy": self.stats["correct"]/n, "slo_ok": (p95 <= self.slo["p95_ms"] and self.stats["cost"]/n <= self.slo["cost_per_task"] and self.stats["correct"]/n >= self.slo["min_accuracy"]), } # ---- the correct unit: cost per VERIFIED task, including retries ---- def cost_per_verified(p_success_first_try, cost_per_attempt, max_retries=3): # geometric: expected attempts before success expected_attempts = min(1 / p_success_first_try, max_retries) return expected_attempts * cost_per_attempt / 1

Three decisions in that code are the page. (1) Escalation is driven by a verifier, not by self-confidence — the model that is wrong is the model that says it is right, so its confidence has poor separation on exactly the items that matter. (2) The SLO gate can stop the cascade early: if escalating would blow the p95 budget, answer with the cheap result and flag it, which is a degradation decision made explicitly rather than by timeout. (3) cost_per_verified divides by success, which is the only cost metric that is comparable across architectures.

The reviewer's question for any routing change: what is the p95 latency and the cost per verified task for each route, and which SLO binds? A change that improves mean cost while worsening p95 is not an optimisation; it is a trade, and it needs to be recorded as one with both numbers attached.

4 · Your hands #

Experiment 1 — The cascade's cost win and its latency tail

12× price ratio, 4.5× latency ratio. Sweep the escalation rate and watch mean and p95 diverge.

C_CHEAP, C_EXP = 0.0005, 0.0060 # 12x price ratio T_CHEAP, T_EXP = 400, 1800 # ms def cascade(p_esc): return C_CHEAP + p_esc*C_EXP, T_CHEAP + p_esc*T_EXP print("p_esc cost saving mean_ms p95_ms") for p in (0.1, 0.2, 0.3, 0.5, 0.9, 1.0): c, l = cascade(p) p95 = T_CHEAP + T_EXP if p > 0.05 else T_CHEAP print(f"{p:4.1f} ${c:.5f} {1-c/C_EXP:6.1%} {l:7.0f} {p95:6.0f}") print(f"\ndirect: ${C_EXP:.5f} mean={T_EXP}ms p95={T_EXP}ms") print(f"break-even p_esc = {(C_EXP-C_CHEAP)/C_EXP:.3f}")

Observed output: p_esc=0.1 cost=$0.00110 saving 81.7% mean=580ms p95=2200ms · 0.2 $0.00170 71.7% 760ms 2200ms · 0.3 $0.00230 61.7% 940ms 2200ms · 0.5 $0.00350 41.7% 1300ms 2200ms · 0.9 $0.00590 1.7% 2020ms 2200ms · 1.0 $0.00650 −8.3% 2200ms 2200ms. The headline: at every escalation rate above 5%, p95 is 2,200 ms — strictly worse than the 1,800 ms direct path, while mean cost is 62–82% lower. If your SLO is on the mean you will ship this; if it is on p95 you must not, or you must bound escalation differently (e.g. escalate asynchronously, or route high-complexity classes directly to the expensive tier). Falsifier: if your measured p95 did not worsen, your escalated requests are running concurrently or the cheap tier is nearly free in latency — measure the two durations separately before concluding the model is wrong.

Experiment 2 — Signal quality is worth more than the routing policy

Same cheap/expensive models, same cost structure; only the escalation signal changes. The last row is random escalation.

C_CHEAP, C_EXP = 0.0005, 0.0060 def cascade_quality(p_cheap, p_exp, q_esc_wrong, q_esc_right): p_esc = p_cheap*q_esc_right + (1-p_cheap)*q_esc_wrong acc = p_cheap*(1-q_esc_right) + p_esc*p_exp return C_CHEAP + p_esc*C_EXP, p_esc, acc print("cheap acc=0.70, exp acc=0.95") print("q_wrong q_right cost p_esc accuracy") for qw, qr in ((0.2,0.05), (0.5,0.05), (0.8,0.05), (1.0,0.05), (0.8,0.30), (0.3,0.30)): c, pe, a = cascade_quality(0.70, 0.95, qw, qr) print(f" {qw:.2f} {qr:.2f} ${c:.5f} {pe:.2f} {a:.4f}")

Compare the last two: same 30% escalation rate, but the signal-quality version (0.8/0.05) costs $0.00320 and gets 0.9262, while random costs $0.00230 and gets 0.7750. Random escalation buys 7.5 accuracy points for a 12× cheaper model — because escalating at random means you re-roll a model that was already right 70% of the time. Experiment 3 — Cache before you cascade (copy-paste)

The same query mix, three architectures. Caching is applied first because it removes work rather than redistributing it.

C_EXP, T_EXP = 0.0060, 1800 def with_cache(hit): # hits cost ~0 and return in ~0 ms; misses go straight to the expensive model return (1-hit)*C_EXP, (1-hit)*T_EXP def cascade_with_cache(hit, p_esc): mc = 1-hit cost = mc*(0.0005 + p_esc*C_EXP) mean = mc*(400 + p_esc*T_EXP) p95 = mc*(400 + T_EXP) if p_esc > 0.05 else mc*400 return cost, mean, p95 print("arch cost mean_ms p95_ms") c, m, p = with_cache(0.0) print(f"direct, no cache ${c:.5f} {m:7.0f} {p:6.0f}") c, m, p = with_cache(0.4) print(f"direct, 40% cache ${c:.5f} {m:7.0f} {p:6.0f}") c, m, p = cascade_with_cache(0.0, 0.2) print(f"cascade(0.2), no cache ${c:.5f} {m:7.0f} {p:6.0f}") c, m, p = cascade_with_cache(0.4, 0.2) print(f"cascade(0.2) + 40% cache${c:.5f} {m:7.0f} {p:6.0f}")

Observed output: direct, no cache $0.00600 1800 1800 · direct, 40% cache $0.00360 1080 1080 · cascade(0.2), no cache $0.00170 760 2200 · cascade(0.2) + 40% cache $0.00102 456 1320. The reading is a decision: 40% cache alone gives cost at 60% of direct and mean latency at 60% of direct with zero quality change, because a hit returns the identical answer. The cascade alone gives the largest cost cut but a p95 of 2,200 ms that exceeds the direct path's 1,800 ms. Cascade + cache wins on every column, and its p95 (1,320 ms) is lower than direct — because 40% of traffic never enters the cascade. The ordering rule: cache first (free, safe), then route (a cost-for-quality trade), then optimise the tail. Falsifier: if your cache hit rate is near zero, none of this applies — investigate why before architecting around a lever you do not have.

5 · Failure modes #

  • Mean-SLO cascade. p95 regresses while the dashboard improves. Symptom: average latency down, support tickets up; the p95 series was never on the dashboard.
  • Self-confidence escalation. The model's own confidence gates escalation. Symptom: accuracy on escalated items ≈ accuracy on non-escalated — the signal has no separation, so the cascade is random escalation with extra cost.
  • Cascade on a cheap-first-strategy with low base accuracy. Cheap model at 0.60 accuracy escalates constantly. Symptom: p_esc near 1.0, cascade cost approaches or exceeds direct (the 0.917 break-even).
  • Cost per request. Optimising the wrong denominator. Symptom: per-request cost falls while cost per successful task rises because retries increased.
  • Cache poisoning / staleness. Semantic cache returns a near-match for a different question. Symptom: confidently wrong answers on a small subset; traceable to a cache hit with a similarity just below threshold (L97).
  • Cache key instability. Timestamps or unordered tool lists in the cached prefix. Symptom: hit rate near zero despite repeated identical queries.
  • Timeout as the implicit SLO. No explicit latency gate, so slow paths truncate. Symptom: a spike in timeout status spans precisely at the provider's limit; partial outputs downstream.
  • Router drift. Task-class rules tuned on old data. Symptom: escalation rate creeps up over weeks with no deploy; cost rises silently.

7 · Self-check #

Q1. Cheap tier $0.0004 / 300 ms, expensive $0.0080 / 2000 ms, escalation rate 25%. Give cost, saving, mean and p95 latency, and say whether to ship if the SLO is p95 < 2,000 ms.

Reveal answer

Cost = 0.0004 + 0.25×0.0080 = $0.00240, saving 1 − 0.0024/0.0080 = 70%. Mean latency = 300 + 0.25×2000 = 800 ms (a 60% improvement over 2,000). p95 = 300 + 2000 = 2,300 ms — exceeds the 2,000 ms SLO. Do not ship as configured. Options: route predictably-hard classes straight to the expensive tier (they skip the cheap model, so their latency is 2,000 not 2,300); escalate asynchronously and return the cheap answer immediately; or reduce the escalation rate below 5% so p95 stays on the cheap path.

Q2. Derive the break-even escalation rate and explain why it is so high.

Reveal answer

Set c_cheap + p·c_exp = c_exp, giving p* = (c_exp − c_cheap)/c_exp = 1 − c_cheap/c_exp. It is high because the cheap model's cost is a small fraction of the expensive one: at a 12× ratio, p* = 1 − 1/12 = 0.917. Intuition: even if you almost always escalate, you only pay an extra 1/12 of a request, because most of the money was going to the expensive model anyway. This is also why the break-even is a trap — it guarantees the cascade is cheaper at almost any escalation rate, so cost analysis alone will always endorse a cascade, and the real constraint is p95 latency and accuracy per unit cost.

Q3. Your cascade escalates 40% of requests. Accuracy on escalated items is 0.91 and on non-escalated items is 0.88. What does that mean?

Reveal answer

The escalation signal has almost no separation — escalated items are only 3 points harder than non-escalated ones, so escalation is nearly random. Expected random-escalation accuracy at 40% would be roughly 0.40×0.95 + 0.60×(cheap accuracy) — check by computing it. Implication: the confidence signal is not working. Replace it: use a verifier result, a schema check, or a small classification model trained on labelled hard/easy items, and re-measure the gap. A useful signal typically shows a large gap (e.g. 0.55 on escalated vs 0.97 on retained) because it is supposed to concentrate failures.

Q4. Diagnostic: per-request cost fell 60%, but monthly spend is flat. What happened?

Reveal answer

Volume rose, or retries rose. The most common cause in a cascade deployment is that the cheap tier's answers fail verification more often, so the system retries — and retries are separate requests that each look cheap, so per-request cost improves while total spend does not. Measure cost per verified task (expected_attempts × cost_per_attempt) rather than cost per request, and break the trace down by whether the request was a retry. Flat monthly spend with falling per-request cost is an architecture that is failing and refunding.

Q5. Why does caching come before cascading in the optimisation order?

Reveal answer

Because caching removes work while cascading redistributes it. A cache hit costs approximately nothing, returns fast, and produces the identical answer — so it improves cost and latency with zero accuracy risk (provided the key is correct). A cascade trades accuracy and latency for cost, which is a decision that needs evaluation. Optimising in the wrong order wastes effort: a 40% cache hit rate delivers 40% savings before you touch the router, and it also shrinks the cascade's p95 problem, because 40% of traffic never enters the cascade at all.
