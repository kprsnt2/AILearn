L96 · Production checklist for an autonomous agent system

A checklist whose items do not name their evidence is a ritual. This one has 20 items, 48 points of weight, and 18 blocking gates — and it will refuse to go even at a 93.8% weighted score if the ledger verification evidence is absent.

~30 min difficulty ●●●●○ build: computable go/no-go gate
evidence-required checklist blocking vs advisory weighted score vs gate ship criterion on CI lower bound capability inventory failure injection evidence rollback drill anti-ritual rules

1 · Why it exists #

The failure: the checklist was completed and the system still failed in a way the checklist never covered. Every box was ticked. "Error handling: yes." "Monitoring: yes." "Testing: yes." Each of those is unfalsifiable — the reviewer asks "yes, but where is it?" and the answer is a conversation rather than an artifact.

The second failure is the opposite: a checklist so long that the gate is never actually run. Forty items with soft judgments means the ceremony is skipped and the decision is made by whoever is most confident. Length does not produce rigour; a short list of computable gates does.

The third failure is a weighted score used as a gate. "We scored 87% — ship it" is how a system goes live with an unverified ledger, because that item happened to be worth 2 points out of 48 and the rest carried it. Weights measure effort; blocking flags measure admissibility. Confusing them is the structural bug in most production-readiness checklists.

The design rule: every item names the artifact that proves it, and every artifact is machine-checkable from the RAKE bundle (L95) or a repository path. Go requires all blocking items present and a weighted score above threshold. The score cannot rescue a missing blocking item, and a complete blocking set does not excuse a low score.

2 · The mental model #

Two axes, and they are independent. Blocking = without this artifact the system is not admissible, regardless of everything else. Weight = how much of the design is represented, used to catch "all the gates passed but the system is half-built".

Analogy: a pre-flight checklist

Pre-flight lists are short, physical, and every item has an observable state — fuel quantity, control surface movement, altimeter reading. Nothing says "flight readiness: good". An agent production checklist should have the same property: every line reads a value, not an opinion.

Where it breaks

A pre-flight check is performed once per flight on a deterministic machine. An agent system changes under you — a model revision, an index rebuild, a prompt edit — so the checklist must be re-run on a schedule or on every change to a pinned artifact (L94 manifest). A checklist run once at launch is a pre-flight check performed for an aircraft that has since been rebuilt.

3 · The mechanism #

The decision rule, stated precisely:

GO  ⇐  ( ∀ blocking item : evidence present )  ∧  ∑wpresent / ∑wtotal ≥ θ Conjunction over blocking items, then a weighted threshold θ (0.80 here). The score is computed over all items including blocking ones, so a system missing one blocking item gets (48−3)/48 = 0.938 and still fails — the score never rescues the absence. Both conditions must hold.

The full list. Blocking items carry 45 of 48 total weight (94%), which is the intended shape: the advisory items are genuinely optional refinements, not disguised gates.

The gate, as code you can run in CI.

# (id, category, item, weight, evidence_kind, blocking) ITEMS = [ ("M1", "measurement", "Golden set versioned, >=150, stratified", 3, "golden_set_hash", True), ("M2", "measurement", "Baseline with CI on same set", 3, "baseline_report", True), ("M3", "measurement", "Ship criterion uses CI lower bound", 2, "gate_config", True), ("R1", "rag", "recall@served_k measured", 2, "rag_report", True), ("R2", "rag", "Faithfulness separate from recall", 2, "rag_report", True), ("A1", "agents", "Every claim has an oracle event", 3, "rake_report", True), ("A2", "agents", "Budget cap + spend attribution", 3, "rake_report", True), ("A3", "agents", "Four termination predicates", 2, "code_review", True), ("S1", "safety", "Capability inventory; irreversible gated", 3, "capability_inventory", True), ("S2", "safety", "Taint rule + injection tests", 3, "taint_test_report", True), ("S3", "safety", "Blast radius computed + accepted", 2, "blast_radius_doc", True), ("O1", "ops", "Trace schema with cost + hashes", 2, "trace_sample", True), ("O2", "ops", "p95 + cost per verified task", 3, "slo_report", True), ("O3", "ops", "Bounded jittered retries + idem keys", 2, "failure_injection_report", True), ("O4", "ops", "Degradation ladder exercised", 3, "failure_injection_report", True), ("P1", "integrity", "Chained ledger outside workspace", 3, "ledger_verify_output", True), ("P2", "integrity", "Reproducibility class declared", 2, "seed_audit", True), ("P3", "integrity", "Judge calibrated", 2, "judge_calibration", False), ("X1", "docs", "Rollback drilled", 2, "rollback_drill", True), ("X2", "docs", "Runbook names failure modes", 1, "runbook", False), ] def evaluate(evidence, items=ITEMS, theta=0.80): total = sum(i[3] for i in items) earned = sum(i[3] for i in items if i[4] in evidence) missing = [i[0] for i in items if i[5] and i[4] not in evidence] score = earned / total return {"go": (not missing) and score >= theta, "score": round(score, 3), "missing_blocking": missing}

Three properties of that code matter. (1) Evidence is a set membership test, not a prose review — the gate cannot be satisfied by a persuasive description. (2) The score and the blocking set are computed from the same table, so there is no separate tally to drift. (3) theta = 0.80 is a parameter, not a constant, so a higher-risk system can raise it without editing the list.

The audit test for the checklist itself: delete one blocking evidence artifact and confirm the gate flips to NO-GO. If the decision does not change, that item was not a gate — it was decoration, and the checklist has a hole where a reviewer believes there is a wall. Run this mutation test on the checklist in CI, not on the system.

4 · Your hands #

Experiment 1 — The gate refuses at 93.8%

Four scenarios against the 20-item table. Watch the score-vs-blocking separation.

def evaluate(evidence, items=ITEMS, theta=0.80): total = sum(i[3] for i in items) earned = sum(i[3] for i in items if i[4] in evidence) missing = [i[0] for i in items if i[5] and i[4] not in evidence] return {"go": (not missing) and earned/total >= theta, "score": round(earned/total, 3), "missing": missing} ALL = {i[4] for i in ITEMS} scenarios = { "everything": ALL, "all but judge calibration": ALL - {"judge_calibration"}, "all but failure injection": ALL - {"failure_injection_report"}, "all but ledger verify": ALL - {"ledger_verify_output"}, "all but measurement": ALL - {"golden_set_hash", "baseline_report", "gate_config"}, } for name, ev in scenarios.items(): r = evaluate(ev) print(f"{name:28s} go={str(r['go']):5s} score={r['score']:.3f} missing={r['missing']}")

Observed output: everything go=True score=1.000 missing=[] · all but judge calibration go=True score=0.958 missing=[] · all but failure injection go=False score=0.896 missing=['O3','O4'] · all but ledger verify go=False score=0.938 missing=['P1'] · all but measurement go=False score=0.896 missing=['M1','M2','M3']. Two readings. First, the advisory item is the only one whose absence does not block — that is what "advisory" should mean, and it is worth 2 of 48 points. Second, the 93.8% row is the point of the page: a system that would score "A" on any weighted rubric is refused because the one missing artifact is the ledger verification. A weighted score without blocking flags would have shipped it. Falsifier: if deleting an artifact never changes the verdict, that artifact is not gating anything — audit the list, not just the system.

Experiment 2 — Mutate the checklist, not the system

The meta-test: for each blocking item, remove only its evidence and confirm the gate flips. Any item whose removal leaves the verdict unchanged is decoration.

def mutation_audit(items=ITEMS, theta=0.80): ALL = {i[4] for i in items} decorations, live = [], [] for iid, cat, item, w, ev, blk in items: if not blk: continue r = evaluate(ALL - {ev}, items=items, theta=theta) (live if not r["go"] else decorations).append(iid) return {"live_gates": len(live), "decorations": decorations} print(mutation_audit()) print(mutation_audit(theta=0.60)) # low threshold: blocking flags still hold

With theta=0.80, all 18 blocking items are live gates — every one of them, removed, flips the verdict. With theta=0.60 the blocking conjunction still holds, so all 18 remain live: the blocking flags are not a function of the threshold, which is exactly the intended independence. If any item shows up in decorations, either its evidence kind is duplicated with another item (so removing it removes nothing unique) or it was mistakenly marked non-blocking. Falsifier: duplicated evidence kinds are a real defect — O3 and O4 share failure_injection_report, so removing that artifact flags two items. If you want independent gates, give each item its own artifact; sharing an artifact means one missing document fails two gates, which is fine but should be deliberate.

Experiment 3 — Report the gate as an artifact (browser console)

The output a CI job should produce: not "pass", but which evidence was present and which items it satisfied.

const evidence = [ "golden_set_hash", "baseline_report", "gate_config", "rag_report", "rake_report", "capability_inventory", "taint_test_report", "blast_radius_doc", "trace_sample", "slo_report", "failure_injection_report", "seed_audit", "rollback_drill", "runbook", ]; // NOTE: "code_review", "ledger_verify_output", "judge_calibration" deliberately absent. const ITEMS = [ ["M1",3,"golden_set_hash",true], ["M2",3,"baseline_report",true], ["M3",2,"gate_config",true], ["R1",2,"rag_report",true], ["R2",2,"rag_report",true], ["A1",3,"rake_report",true], ["A2",3,"rake_report",true], ["A3",2,"code_review",true], ["S1",3,"capability_inventory",true], ["S2",3,"taint_test_report",true], ["S3",2,"blast_radius_doc",true], ["O1",2,"trace_sample",true], ["O2",3,"slo_report",true], ["O3",2,"failure_injection_report",true], ["O4",3,"failure_injection_report",true], ["P1",3,"ledger_verify_output",true], ["P2",2,"seed_audit",true], ["P3",2,"judge_calibration",false], ["X1",2,"rollback_drill",true], ["X2",1,"runbook",false], ]; const have = new Set(evidence); const total = ITEMS.reduce((a,i) => a + i[1], 0); const earned = ITEMS.filter(i => have.has(i[2])).reduce((a,i) => a + i[1], 0); const missingBlocking = ITEMS.filter(i => i[3] && !have.has(i[2])).map(i => i[0]); console.log({ score: +(earned/total).toFixed(3), go: missingBlocking.length===0 && earned/total>=0.8, missingBlocking, advisoryMissing: ITEMS.filter(i => !i[3] && !have.has(i[2])).map(i => i[0]) });

Expect {score: 0.854, go: false, missingBlocking: ['A3','P1'], advisoryMissing: ['P3']} (41/48 earned). The report separates blocking from advisory gaps so the reader knows what must be fixed versus what could be fixed, and it names item ids rather than describing the system as "not ready". That is what makes the gate actionable in a three-line CI log. Falsifier: if the score is above 0.8 and the team asks to ship anyway, the missing-blocking list is the answer — and if nobody accepts that answer, the checklist is not the mechanism, the culture is, and you should say so explicitly rather than weakening the gate.

5 · Failure modes #

  • Evidence-free items. "Error handling: yes." Symptom: every checklist passes; the gate provides no discrimination between systems.
  • Weighted score used as the gate. Symptom: launches with 87% score and an unverified ledger; the specific missing artifact is never named.
  • Advisory items that are actually essential. Judge calibration marked advisory while a judge gates the release. Symptom: an uncalibrated judge decides promotions.
  • Run once at launch. Symptom: the checklist is green from six months ago while the model revision, index, and prompts all changed (L94).
  • Self-attested evidence. The artifact is a document the team wrote saying it is done. Symptom: the ledger verification artifact is a paragraph, not a verifier output.
  • Checklist doesn't match the architecture. Items about components that do not exist; no items about the ones that do. Symptom: the gate is green and an entire subsystem (e.g. reranking) is unmeasured.
  • Threshold as a knob. θ lowered when it blocks a launch. Symptom: the threshold history shows a step change per release; the gate is a negotiation.
  • No owner per item. Symptom: at review time nobody knows who can produce a given artifact; the review stalls and then ships without it.

7 · Self-check #

Q1. Why is a weighted score alone not a sufficient gate?

Reveal answer

Because weights are additive and auditable properties are often conjunctive. A system missing its ledger verification scores (48−3)/48 = 0.938 — an "A" — and ships. But the ledger gate is not a quality contribution, it is a precondition for trusting every other gate's evidence: if the record can be altered, then the artifacts proving M1, M2, and A1 are themselves unverified. Blocking flags encode "without this, nothing else counts"; weights encode "how much design this represents". They answer different questions and both are needed.

Q2. You have 44 of 48 points and no failure_injection_report. Give the verdict and the two specific items that fail.

Reveal answer

Score 44/48 = 0.917, above the 0.80 threshold, but the verdict is NO-GO because two blocking items share that evidence kind: O3 (retries bounded, jittered, idempotency keys) and O4 (degradation ladder exercised). Both are blocking, so the missing artifact fails two gates. The reviewer's action is concrete: produce the injection report, which is a test suite run — force each failure class (timeout, 500, circuit open, quota exhausted) and record the served behaviour per degradation level.

Q3. Which items would you add for a system that mutates production data unattended, and why are they not already covered?

Reveal answer

Add: (a) irreversible-action inventory with a named approver per action — S1 says irreversible actions are gated, but not that the gate has an owner and a timeout; (b) restore drill from backup with measured RTO — X1 covers rollback of code, not restoration of mutated data; (c) kill switch tested — the ability to halt the agent mid-run within a stated time, verified by injection; (d) quarterly re-certification — the checklist expires. These are not covered because the base list assumes reversible mutations, which is the wrong assumption for unattended production writes; that mismatch between checklist and architecture is itself one of the listed failure modes.

Q4. Diagnostic: the gate passes at launch and has passed every quarter since, but incidents keep occurring. What are the two most likely explanations?

Reveal answer

(1) Self-attested or stale evidence — the artifacts are documents written once, not outputs regenerated on each run, so the checklist is green about a system that no longer exists (model revision, index version, prompts changed). (2) The checklist does not match the architecture — the incidents occur in subsystems with no corresponding item (e.g. reranking, memory writes, subagent merge). The fix for both is the same: make the gate regenerate every artifact from the current RAKE bundle on every run, and run the mutation audit (Experiment 2) — any incident class that maps to no failing item identifies a missing item, and that mapping should be a required part of the post-incident review.

Q5. What does it mean that 18 of 20 items are blocking, and is that the right ratio?

Reveal answer

It means the gate is dominated by conjunctive requirements — 45 of 48 weight points sit behind "must have evidence". That is deliberate for an autonomous agent system where a missing artifact is usually a missing control rather than a missing nicety, and where the consequence of a false GO is an incident you cannot reconstruct. The right ratio depends on the scrutiny level: an internal tool could move several items to advisory (e.g. X1 rollback, X2 runbook) and still be safe because a human is watching. A ratio where everything is blocking is as broken as one where nothing is — it makes the gate unpassable and therefore ignored, which is how checklists die.
