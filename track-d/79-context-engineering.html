L79 · Context engineering: window budgets, compaction, summarization

Conversation history is 66% of your context budget and the first thing eviction drops — so the agent forgets exactly what it just learned. Every compaction round multiplies a fact's survival by a factor below 1, which gives memory a measurable half-life.

~30 min difficulty ●●●○○ build: context budget planner
context as a budget value-density allocation compaction summarization half-life quadratic prefill pin decisions vs summarize turns context poisoning output reserve

1 · Why it exists #

The failure: an agent that gets worse the longer it works. Turn 8 is sharp. Turn 60 confidently contradicts a decision it made at turn 12, because turn 12 was compacted out. The transcript reads as coherent — the model is fluent about whatever it remembers — and the summarizer that replaced the memory had no idea which facts would matter later.

This is not a capacity problem you can buy your way out of, because three costs rise with length simultaneously: money (every token is billed every turn), latency (the attention term in prefill is roughly quadratic in sequence length), and accuracy (long-context retrieval is uneven; the widely reported "lost in the middle" pattern should be measured on your model, not assumed). On top of that, the same 3.2k tokens of tool schemas are re-sent on a turn that writes one line of code and on a turn that uses all 26 tools.

Context is a fixed-capacity store with a lossy eviction policy you wrote by accident. Every design decision — what lives in the system prompt, whether history is verbatim or summarized, whether a tool result is echoed back — is an eviction-policy decision. The engineering question is never "does it fit" but "what is each item's value density, and what is silently destroyed when the budget forces a choice".

2 · The mental model #

The window is a knapsack. Items have sizes (tokens) and values (how much the next action depends on them). The design work is the ranking — and the ranking changes as the task progresses, which is why static allocation fails.

Analogy: an L1 cache with a policy you write

Context is an L1 cache — fast, tiny, expensive on miss. Unlike a CPU cache, the replacement policy is yours and the "miss" is not slow, it is silent: the model reasons confidently from whatever replaced the truth.

Where it breaks

A CPU evicts by address and the program cannot observe it. Here the program is the model, and it has no way to know an eviction happened. So the cache analogy hides the real failure: not a miss but a silent cache poisoning where a lossy summary stands in for ground truth with no provenance marker attached.

The design rule that follows: anything that must survive compaction belongs in structured state, not in the transcript. Decisions, plan state, file paths, and open questions live in a small object outside the conversation and are re-rendered every turn. The transcript then becomes a narrative that can be summarized safely, because nothing load-bearing is stored only in it.

3 · The mechanism #

Allocation by value density. Greedy is optimal for the fractional knapsack and near-optimal here because item sizes are small relative to the budget.

ρi = vi / ti      take in descending ρ while ∑ ti ≤ W − R vi = item priority (1–5), ti = tokens, W = window, R = reserve for the next output plus tool-call JSON. Agents that fill the window to 100% cannot emit a reply at all.

The compaction rule. Do not compact when full — compact when growth predicts you will hit the reserve mid-step, because compacting during a verification step deletes exactly the evidence that step needs.

compact when   Ct + Δavg · n̂ > W − R Ct = current context tokens, Δavg = mean tokens added per turn, n̂ = expected turns left in the current plan step. Triggering one step early is always cheaper than triggering in the middle of proving something.

The planner and the compaction policy together. The critical detail is that decision turns and pinned turns are never summarized — they are re-rendered verbatim from structured state.

# items: (name, tokens, priority 1..5). Greedy value-density allocation. def plan_budget(window, reserve, items, pinned=frozenset()): cap = window - reserve ranked = sorted(items, key=lambda x: -(x[2] / x[1])) used, keep, drop = 0, [], [] for name, tok, pri in ranked: if name in pinned or used + tok <= cap: used += tok; keep.append((name, tok, pri)) else: drop.append((name, tok, pri)) return used, keep, drop def render_context(state, history, keep_recent=6): # 1. Structured state is authoritative and always rendered verbatim. parts = [render_state(state)] # plan, decisions, open questions, file paths # 2. Tool outputs are truncated head+tail with an explicit marker the model can see. # 3. Old non-decision turns are dropped entirely; the summary lives in `state`. rendered = [] for i, turn in enumerate(history): age = len(history) - i if turn.kind == "decision": rendered.append(f"[DECISION {turn.id}] {turn.text}") # verbatim elif age <= keep_recent: rendered.append(turn.text) elif turn.kind == "tool_output": rendered.append(head_tail(turn.text, 200, 400, marker="[elided {n} tokens]")) # other old turns: omitted. Their content must already be in `state` or it is lost. parts.append("\n".join(rendered)) return "\n\n".join(parts)

Now the part almost nobody models: summarization is lossy and applied repeatedly. If each compaction preserves a given fact with probability a, then after r rounds its survival is ar, and the number of rounds until it is more likely gone than present is:

survival(r) = ar       r1/2 = ln(0.5) / ln(a) a = per-compaction retention. With a = 0.85 (15% of detail lost per round) the half-life is ln(0.5)/ln(0.85) = 4.27 rounds. Four compaction rounds — a normal long agent session — and an unpinned fact is already a coin flip.

The conclusion is not "write a better summarizer". Even at 0.95 retention you lose half of an unpinned fact in 13 rounds. The conclusion is that facts which must survive must not be in the summarized channel at all. Pin them. The table is the argument for structural state over better prose.

Audit test for a context system: take any fact the agent asserted at turn 10, then ask at turn 80 whether it still holds. If your context builder cannot answer that from the rendered prompt alone, you do not know what the model knows. Log the rendered prompt hash per turn (L90) — without it, "the agent forgot" is an unfalsifiable claim.

4 · Your hands #

Experiment 1 — See which item eviction kills first

Nine realistic context items, three window sizes. The ranking is computed, not assumed.

ITEMS = [ ("system_prompt", 900, 5), ("tool_schemas_26", 3224, 3), ("retrieved_chunks_top8", 6400, 4), ("conversation_history", 21000, 3), ("plan_state", 1200, 5), ("file_under_edit", 4300, 5), ("test_output_tail", 2800, 4), ("memory_summary", 1500, 3), ("subagent_reports", 5200, 2), ] def plan_budget(window, reserve, items): cap = window - reserve ranked = sorted(items, key=lambda x: -(x[2] / x[1])) used, keep, drop = 0, [], [] for name, tok, pri in ranked: if used + tok <= cap: used += tok; keep.append((name, tok, pri)) else: drop.append((name, tok, pri)) return used, keep, drop for w, r in ((32_000, 4_000), (128_000, 8_000), (1_000_000, 16_000)): used, keep, drop = plan_budget(w, r, ITEMS) kept = sum(t for _, t, _ in keep) print(f"W={w:>9,} kept={kept:>7,} ({kept/(w-r):5.1%}) dropped={[d[0] for d in drop]}")

Observed output: W=32,000 kept=25,524 (91.2%) dropped=['conversation_history'] · W=128,000 kept=46,524 (38.8%) dropped=[] · W=1,000,000 kept=46,524 (4.7%) dropped=[]. The item list totals 46,524 tokens, so at 32k exactly one item fails to fit — and because history is the largest it has the lowest value density (21000 tokens at priority 3 = 0.000143), so it is the one dropped. That is the system working correctly and the agent getting dumber at the same time. Falsifier: if your priorities put history at 5, nothing is ever dropped and you will hit the reserve mid-step instead — test by running a long session and watching for hard truncation errors rather than graceful drops.

Experiment 2 — Measure the half-life of a summary

Multiplicative decay with per-round noise. The point of the noise is realism: retention is not constant, it is N(1−α, σ), so survival is a random walk in log space with negative drift.

import math, random def drift(alpha=0.15, variance=0.05, rounds=12, seed=7): rng = random.Random(seed) fid, curve = 1.0, [1.0] for _ in range(rounds): fid *= max(0.0, rng.gauss(1 - alpha, variance)) curve.append(fid) return curve c = drift() for r in range(0, len(c), 2): print(f"round {r:2d}: fidelity {c[r]:.4f}") for a in (0.05, 0.10, 0.15, 0.25): print(f"alpha={a:.2f} half-life = {math.log(0.5)/math.log(1-a):5.2f} rounds")

Observed output: for alpha=0.15, seed=7 the sampled curve reads round 0: 1.0000, round 2: 0.7330, round 4: 0.5129, round 6: 0.3459, round 8: 0.2729, round 10: 0.2123, round 12: 0.1586. The analytic half-lives are alpha=0.05 → 13.51, 0.10 → 6.58, 0.15 → 4.27, 0.25 → 2.41 rounds. The sampled curve crosses 0.5 between rounds 4 and 6, matching the predicted 4.27. Falsifier: if you measure per-fact retention empirically and find the curve is not multiplicative (e.g. facts disappear all at once at round 3 because the summarizer has a budget cliff), then model it as a cliff, not decay — and the fix is a bigger summarizer reserve, not pinning.

Experiment 3 — Prove the quadratic prefill term is real (browser console)

Rough FLOP model: 2NT for the linear layers plus 2L T² d for attention. At 100k to 1M tokens with L=60, d=5120, the ratio tells you what "1M context" actually costs.

const N = 13e9, L = 60, d = 5120; const flops = T => 2*N*T + 2*L*T*T*d; const s = [1e4, 1e5, 3e5, 1e6]; for (let i = 1; i < s.length; i++) { console.log(`${s[i-1]/1e3}k -> ${s[i]/1e3}k : ${(flops(s[i])/flops(s[i-1])).toFixed(2)}x FLOPs`, `attn share at ${s[i]/1e3}k: ${(2*L*s[i]*s[i]*d/flops(s[i])*100).toFixed(1)}%`); }

Observed output: 10k -> 100k : 27.20x FLOPs attn share at 100k: 70.3% · 100k -> 300k : 7.22x FLOPs attn share at 300k: 87.6% · 300k -> 1M : 10.15x FLOPs attn share at 1M: 95.9%. Every multiplier exceeds its token multiplier (10×, 3×, 3.33×) because the quadratic term takes over: by 1M tokens attention is 95.9% of prefill FLOPs. Going 300k→1M is 3.33× the tokens for 10.15× the prefill compute. That is the quantitative case for compaction even when the window technically fits. Falsifier: if your serving stack uses a sparse or linear attention variant (DSA, L34), the quadratic term is suppressed — rerun with the real attention pattern before quoting this ratio.

5 · Failure modes #

  • Silent decision loss. A design decision was made at turn 12, compacted out at turn 30, and reversed at turn 45. Symptom: the agent re-litigates settled questions; the plan's "decided" list grows and shrinks.
  • Summary-of-summary drift. Each compaction summarizes the previous summary. Symptom: fidelity decays as ar; late-session answers reference details that were never in the original (confabulated specifics are the tell).
  • Context poisoning. A wrong tool output or injected instruction sits in history forever and is re-read every turn. Symptom: the same wrong fact appears in outputs 20 turns later, traceable to one bad tool call. Fix: results carry provenance and a taint flag; tainted items are evicted, not summarized.
  • Accumulating retrieval. Each query appends chunks instead of replacing them. Symptom: context grows monotonically across turns while answer quality drops; duplicate chunks from the same document.
  • Full-window deadlock. No output reserve. Symptom: context_length_exceeded on the response, immediately after a successful call — or truncated JSON in a tool call.
  • Prefix-cache invalidation. A timestamp or reordered system prompt at the top of the context. Symptom: cache hit rate near zero; cost per turn flat instead of declining with a warm cache.
  • Compaction mid-verification. Triggered by token count rather than by step boundary. Symptom: test output is truncated exactly on the turn the agent needs it to diagnose a failure.

7 · Self-check #

Q1. Why does priority-3 conversation history lose to a priority-2 subagent report in Experiment 1's ranking?

Reveal answer

Value density, not priority. History: 3/21000 = 0.000143. Subagent reports: 2/5200 = 0.000385 — 2.7× higher. But notice history did get dropped while subagent reports were kept, which exposes the flaw: a coarse priority cannot represent "the last 3 turns are critical and turns 1–40 are worthless". The fix is to split history into segments before ranking (recent turns high, decisions pinned, rest low) rather than ranking the whole bucket as one item.

Q2. A summarizer retains 88% of details per round. How many compaction rounds until an unpinned fact is more likely lost than present, and what should you do about a fact you absolutely need?

Reveal answer

r1/2 = ln(0.5)/ln(0.88) = 5.42 rounds. So after ~5 compactions, an unpinned fact is a coin flip. Do not try to raise 0.88 to 0.99 — even 0.99 gives a half-life of only 69 rounds and you pay more summarizer tokens on every compaction. Instead move the fact out of the summarized channel: store it in structured state and re-render it verbatim each turn. The correct engineering response to a lossy channel is to stop routing critical data through it.

Q3. Your context is 40k tokens, window 128k, mean growth 2.5k/turn, expected 30 turns left in the step. Do you compact now? Show the arithmetic.

Reveal answer

Take R = 8k for output + tool JSON. Projected: 40k + 2.5k × 30 = 115k. Cap: 128k − 8k = 120k. 115k < 120k, so you do not compact now — the step fits. But the headroom is only 120k − 115k = 5k, about two turns of growth, so compaction must land between steps: schedule it at the end of turn 28 so it never fires mid-verification. The reusable rule is that compaction is scheduled at step boundaries using the projection, never triggered by a token threshold inside a step.

Q4. Diagnostic: token usage per turn is flat at ~45k and never declines, and your bill is 3× your estimate. What is the most likely cause?

Reveal answer

Prefix-cache invalidation, plus possibly accumulating retrieval. Flat usage means the prefix is being rebuilt every turn, so the cached portion is never reused — the usual causes are a timestamp, session id, or a re-sorted tool list at the top of the prompt. Check the cache-hit metric before touching the context; if the hit rate is near zero, the fix is making the first N tokens byte-identical across turns, which typically cuts cost far more than any compaction work.

Q5. Why is "just use the 1M-token window and stop compacting" a bad answer even when the bill is acceptable?

Reveal answer

Because prefill FLOPs grow quadratically (Experiment 3: 300k→1M is 3.33× tokens but 10.15× prefill FLOPs, and attention is 95.9% of the work at 1M), so latency and cost per turn rise much faster than the token count suggests; because a longer context makes retrieval less reliable at the middle; and because it makes every failure harder to attribute — you cannot tell whether the model ignored a fact or the fact was evicted, since nothing is ever evicted. A bounded, deliberately-built context is auditable; an unbounded one is merely large.
