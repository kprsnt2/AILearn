L81 · Subagents and orchestration: fan-out, merge, conflicts

A subagent is a context compressor, and compression has a break-even turn count. Get that wrong and fanning out six agents at 9k tokens each makes the parent context larger (0.83×), not smaller — and the whole fan-out loses money on a one-shot task.

~30 min difficulty ●●●●○ build: orchestrator with disjoint scopes
subagent as context compressor break-even turn count disjoint write scopes merge conflict probability fan-out union bound orchestrator vs worker scope as a lock report schema

1 · Why it exists #

The failure: you fanned out five agents, they all finished, and the merged result is worse than not having split the work. Three causes, all arithmetic, none of them model quality:

(1) The compression is fake. If each child reads 9,000 tokens and returns a 400-token report, the parent sees 2,400 tokens instead of 45,000 — a real 18× win. But the children each paid 9,000 tokens plus a setup overhead, so total spend can be higher than the parent reading everything once. At one turn of parent use, six children at 9k raw cost 65,400 tokens versus 54,000 for the direct path. Fan-out lost.

(2) Fan-out multiplies failure. Six children that each succeed at 90% give a whole-fan-out success rate of 0.96 = 0.531. Half your orchestrations have at least one broken input.

(3) Merge conflicts are quadratic in overlap. Two agents each writing to 5 random units of a 200-unit workspace still collide with probability 0.85 over six agents. Disjoint scopes are not tidiness — they are the only thing that makes merging a concatenation instead of a reconciliation.

A subagent buys context isolation, not parallelism. Its value is exactly the tokens it keeps out of the parent, minus what it spent to produce its report, minus the merge cost. All three terms are computable before you design the fan-out. Parallelism is a latency bonus that only pays if the children are actually independent.

2 · The mental model #

An orchestrator is a process and a subagent is a message-passing thread with an isolated heap. The heap is the child's context; the message is its report. The thread cannot see the parent's heap and the parent cannot see the thread's — that isolation is the entire product.

Analogy: map-reduce with a human-as-reducer obligation

Fan-out is map, merge is reduce. The analogy is useful because it forces the right question: what is the reducer's associative operation? If you cannot name it (concatenate lists? union findings? pick max confidence?), you have not designed the merge and the fan-out will produce a pile, not a result.

Where it breaks

Map-reduce assumes map outputs are comparable and the reduce operation is associative and commutative. Subagent reports are neither: they overlap, contradict, and have different confidence. And a child can produce a syntactically valid report that is semantically wrong with no error signal. So the reduce step needs an oracle or arbiter (L89), not just a fold. Reduce is where the hard part lives, and it is the part people skip.

The consequence for design: make children return facts with provenance, not conclusions. A child reporting "the bug is in the retry logic" is unmergeable. A child reporting {"file": "...", "line": 212, "evidence": "...", "confidence": 0.7} is mergeable, deduplicable, and checkable — and the orchestrator can apply an oracle to each claim before composing them.

3 · The mechanism #

The economics, exactly. Let n children each read r tokens, return a report of s tokens, and pay o tokens of setup overhead. The parent would otherwise read all n·r directly and reuse that context for T turns.

D(T) = n · r · T      S(T) = n (r + o) + n · s · T Delegation wins when S(T) < D(T). Solving: r T = r + o + s T, so T* = (r + o) / (r − s). Note s (report size) barely affects the break-even because it appears on both sides — the binding constraint is the overhead o relative to r.

Substitute the realistic numbers (r=9000, s=400, o=1500): T* = (9000+1500)/(9000−400) = 1.22 turns. So the rule is: delegate only when the parent will reuse the summary for two or more turns. For a one-shot lookup, inline it.

Then the merge. The probability that two agents with write footprints of size a and b in a workspace of N units touch at least one common unit:

P(overlap) = 1 − ∏j=0b−1 (N − a − j)/(N − j) This is the hypergeometric "no shared element" probability, exact for uniformly random footprints. For N=200, a=b=5: P = 0.121 per pair, and over 15 pairs (6 agents) the chance of at least one conflict is 0.85. Disjoint-by-assignment scopes have P=0 by construction, which is why scope assignment is the orchestrator's first duty, not the last.

The orchestrator, with scope as an enforced lock rather than a convention.

import itertools, math # ---- 1. Should this be a subagent at all? ---- def breakeven_turns(raw, summary, overhead): return (raw + overhead) / (raw - summary) if raw > summary else math.inf def spend(n, raw, summary, overhead, turns): return (n * raw * turns, # direct n * (raw + overhead) + n * summary * turns) # delegated (total) # ---- 2. Conflict probability (exact, hypergeometric) ---- def p_overlap(total, a, b): p_no = 1.0 for j in range(b): p_no *= max(0.0, total - a - j) / max(1e-9, total - j) return 1 - p_no def p_any_conflict(total, scopes): p = 0.0 for a, b in itertools.combinations(scopes, 2): p = 1 - (1 - p) * (1 - p_overlap(total, a, b)) return p # ---- 3. The scope lock: an assignment the orchestrator enforces ---- class ScopeRegistry: def __init__(self): self.owner = {} def claim(self, agent, paths): for p in paths: if p in self.owner and self.owner[p] != agent: raise ScopeConflict(f"{agent} and {self.owner[p]} both claim {p}") self.owner[p] = agent def guard_write(self, agent, path): if self.owner.get(path) != agent: raise ScopeViolation(f"{agent} may not write {path}")

Three things in that code carry the lesson. (1) The scope registry is a pre-claim system: conflicts are rejected before any work starts, so a conflict is a planning error rather than a merge problem. (2) guard_write is enforced at the tool boundary (L84), so a child that ignores its scope fails loudly instead of silently corrupting a sibling's file. (3) The break-even formula sits before the orchestration code, because the first question is whether to fan out at all.

The audit question an orchestrator must answer: for each merged claim, which child produced it, with what evidence, and was any conflicting claim suppressed? If suppression happened, by what rule. A merge that cannot name its suppressed alternatives is indistinguishable from a merge that ignored them, and that is exactly where the zero-false-positive property of a gate gets lost.

4 · Your hands #

Experiment 1 — Find the turn at which fan-out starts paying

Six children, 9,000 raw tokens each, 400-token reports, 1,500 tokens of per-child overhead. The parent reuse count is the only free variable.

import math N, RAW, SUM, OVER = 6, 9000, 400, 1500 def totals(turns): return N * RAW * turns, N * (RAW + OVER) + N * SUM * turns def breakeven(raw, summ, over): return (raw + over) / (raw - summ) if raw > summ else math.inf for t in range(1, 6): d, s = totals(t) print(f"turns={t} direct={d:>8,} delegated={s:>8,} " f"ratio={d/s:.2f}x {'WIN' if s < d else 'LOSE'}") print(f"\nbreak-even turns = {breakeven(RAW, SUM, OVER):.2f}")

Observed output: turns=1 direct=54,000 delegated=65,400 ratio=0.83x LOSE · turns=2 108,000 67,800 1.59x WIN · turns=3 162,000 70,200 2.31x WIN · turns=4 216,000 72,600 2.98x WIN · turns=5 270,000 75,000 3.60x WIN — break-even 1.22 turns. So fan-out at these parameters is loss-making for one-shot work and increasingly profitable for reused work. In dollars per 1M input at $0.28: turns=1 loses $0.00319; turns=5 saves $0.05460. Falsifier: if your children do not actually cost r + o — e.g. they read the file before the parent ever would have, so r is not avoidable — the direct arm is over-counted and the break-even moves toward 1. Measure the real per-child token total from your trace before trusting T*.

Experiment 2 — The two ways fan-out multiplies failure

Union bound on child failures, and the exact conflict probability for overlapping write scopes.

import itertools def p_overlap(total, a, b): p_no = 1.0 for j in range(b): p_no *= max(0.0, total - a - j) / max(1e-9, total - j) return 1 - p_no def p_any(total, scopes): p = 0.0 for a, b in itertools.combinations(scopes, 2): p = 1 - (1 - p) * (1 - p_overlap(total, a, b)) return p print("child success p -> P(at least one of 6 fails)") for p in (0.99, 0.95, 0.90, 0.85): print(f" p={p:.2f} -> {1-p**6:.4f}") print("\n6 agents, 200-unit workspace, scope = k units each") for k in (1, 2, 5, 10, 20): print(f" scope={k:2d} -> P(any conflict) = {p_any(200, [k]*6):.4f}")

Observed output: p=0.99 → 0.0585, 0.95 → 0.2649, 0.90 → 0.4686, 0.85 → 0.6229. Even at 95% child reliability more than a quarter of orchestrations have at least one broken child. And on conflicts: scope=1 → 0.0724, 2 → 0.2609, 5 → 0.8532, 10 → 0.9996, 20 → 1.0000. Five units each out of 200 — 2.5% of the workspace — and you are at an 85% chance of a conflict. The two curves are the argument for (a) fewer, larger children and (b) assigned scopes. Falsifier: if your children write to genuinely partitioned directories, P=0 by construction and this model does not apply — verify by checking that no two children's write logs share a path.

Experiment 3 — Assert scope disjointness in CI (copy-paste)

The property to enforce mechanically: a child's declared scope and its actual writes must be identical sets.

class ScopeViolation(Exception): pass class ScopeConflict(Exception): pass class ScopeRegistry: def __init__(self): self.owner = {} def claim(self, agent, paths): for p in paths: if p in self.owner and self.owner[p] != agent: raise ScopeConflict(f"{agent} and {self.owner[p]} both claim {p}") self.owner[p] = agent def guard_write(self, agent, path): if self.owner.get(path) != agent: raise ScopeViolation(f"{agent} may not write {path}") def test_scopes(): r = ScopeRegistry() r.claim("a", ["src/retry.py", "tests/test_retry.py"]) r.claim("b", ["src/queue.py"]) try: r.claim("b", ["src/retry.py"]) raise AssertionError("duplicate claim must be rejected") except ScopeConflict: pass try: r.guard_write("b", "src/retry.py") raise AssertionError("cross-scope write must be blocked") except ScopeViolation: pass r.guard_write("a", "src/retry.py") # in scope: allowed print("PASS: scope lock holds") test_scopes()

Prints PASS: scope lock holds. Run the equivalent in your orchestrator before dispatching any child: if claim does not raise on a duplicate, two agents will edit the same file and your merge is a race, not a merge. If guard_write does not raise, your children are trusted by convention — and one child that "helpfully" fixes an out-of-scope file silently invalidates a sibling's verified result. Falsifier: if your children run in separate worktrees with a real VCS merge, you can allow overlap — but then measure merge-conflict rate, and expect it to track the hypergeometric model above (~85% at 5 units of 200).

5 · Failure modes #

  • Fan-out for a one-shot task. Six children assembled for work the parent reuses once. Symptom: total token spend up 21% with no quality change — exactly the 0.83× row in Experiment 1.
  • Correlated children. All six children get the same full context and produce six versions of the same answer. Symptom: reports are near-duplicates; voting adds confidence without information; the fan-out has the isolation of one agent at 6× the cost.
  • Unmergeable reports. Children return prose. Symptom: the orchestrator's synthesis step is another LLM call whose output cannot be traced to any child; duplicate and contradictory findings both appear.
  • Silent scope creep. A child writes outside its declared scope. Symptom: a sibling's verified change is reverted or corrupted; the audit shows a write with no matching claim.
  • Lost child. A child times out or crashes and the orchestrator proceeds with n−1 reports. Symptom: merged output is subtly incomplete; nothing in the log says a child was missing. Fix: the merge counts expected vs received reports and hard-fails on mismatch.
  • Arbiter shares the blind spot. Conflicts are resolved by the same model with the same context. Symptom: conflict resolution is confidently wrong and consistent across runs — a systematic bias, not noise.
  • Merge without suppression record. Two conflicting claims, one silently wins. Symptom: you cannot tell later why a claim was dropped; this is where a gate's audit trail is lost.

7 · Self-check #

Q1. Derive T* and explain why the report size s matters less than people think.

Reveal answer

Set n·r·T = n(r+o) + n·s·T, divide by n, collect terms: T(r−s) = r+o, so T* = (r+o)/(r−s). s appears in the denominator (which is nearly r) and in the numerator's implicit place — shrinking it from 400 to 200 changes the break-even from 1.22 to 1.19 turns. What actually moves the needle is o/r: the child's setup overhead relative to the material it processes. This is why "make reports shorter" is a weak optimization and "don't waste 1,500 tokens re-deriving what the parent knows" is a strong one.

Q2. Six children at 96% individual success. What is the probability the fan-out is fully clean, and what should the orchestrator do about the remainder?

Reveal answer

0.966 = 0.7828, so ~22% of orchestrations have at least one failed child. The orchestrator must (a) track expected vs received child reports and refuse to merge an incomplete set, (b) retry the failed child with a fresh context rather than patching its partial output, and (c) record the retry in the ledger so the n is honest. Silently merging n−1 is the bug — the merged result looks complete and is missing a scope.

Q3. You have a 500-unit workspace and 6 agents. What scope size keeps the expected number of conflicts below 1? Show the arithmetic.

Reveal answer

Expected conflicting pairs = 15 × P(pair), and you want that below 1. At N=500: scope=1 gives P(pair)=0.00200 → 0.030 expected pairs; scope=2 → 0.120; scope=5 gives P(pair)=0.04920 → 0.738 expected pairs (under 1, P(any)=0.531); scope=10 gives P(pair)=0.18445 → 2.767 expected pairs, already over. So scope ≤ 5 units per agent at N=500 keeps expected conflicts below one. Compare N=200, where scope=5 already gives 1.80 expected pairs — the same scope size is safe in one workspace and unsafe in another, which is why the rule must be computed, not remembered.

Q4. Diagnostic: orchestration is 3× slower than a single agent on the same tasks, with unchanged token spend. What is happening?

Reveal answer

Fan-out traded latency for tokens but the children are running sequentially or contending on a shared resource — most often a single rate-limited API key or one thread pool. Token spend unchanged means the economics are as designed, and the extra wall clock is purely scheduling. Check: child start/end timestamps in the trace. If they are non-overlapping, you have serialization, not parallelism, and you're paying the orchestration coordination cost for nothing.

Q5. Why is "ask six agents and take the majority" worthless if all six receive the same full context?

Reveal answer

Because majority voting only adds information when errors are independent. Children given identical context see identical evidence and run the same model, so their errors are strongly correlated — six correlated voters behave like one voter with extra cost. Independence must be engineered: different retrieval, different temperatures or seeds, different tools, or genuinely different roles/expertise. The test is measurable: compare the disagreement rate between two children against the error rate of one. If disagreement << error rate, the children are correlated and voting cannot help.
