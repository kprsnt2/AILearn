L78 · Planning: decomposition, plan-then-act, replanning

A plan is not a to-do list the agent reads — it is a commitment about what survives a failure. The difference between re-planning from scratch and repairing the failed subtree is the difference between 27% and 88% completion on a 20-step task, at 62% of the cost.

~30 min difficulty ●●●○○ build: plan executor with replan triggers
plan as DAG plan-linearization tax plan-repair replan triggers irreversible steps commitment horizon step granularity plan validity budget

1 · Why it exists #

The failure: the agent planned correctly, executed eleven of thirteen steps, hit a recoverable error, and threw it all away. A plan-then-act loop that treats any deviation as "re-plan" restarts from step one. If each step fails with probability p, a k-step plan with restart-on-failure has completion probability (1−p)k only if it gets exactly one attempt. Give it r restarts and it is 1 − (1 − (1−p)k)r. With p=0.15, k=20: one attempt is 3.9%. That is the number that makes long-horizon agents look impossible, and it is an artefact of the restart policy, not of the model.

The second failure is subtler: the plan itself goes stale. Step 4's output changes an assumption that step 9 depended on, and no step in the plan is responsible for noticing. The agent executes a valid plan against an invalid world and produces a confident, wrong result.

Two orthogonal decisions make up "planning": (1) decomposition granularity — how many steps and where the commit points are; (2) replan scope — on failure, what is invalidated. Get (2) wrong and long plans are hopeless regardless of model quality. Get (1) right and you get fewer failures and cheaper repairs, because a small failed step has a small blast radius.

2 · The mental model #

A plan is a DAG G = (V, E) where an edge u → v means v's preconditions are satisfied by u's postconditions. The edges are the only thing that tells you what a failure invalidates: when u fails, everything reachable from u is suspect; everything not reachable is untouched.

Which makes the key design quantity explicit: for each step, its descendant cone Desc(v). Repairing v has to redo only Desc(v) — unless the step is irreversible, in which case redoing it is impossible and you do not have a repair, you have an incident.

Analogy: database transactions with savepoints

A plan with explicit checkpoints is a transaction with savepoints. A step failure rolls back to the nearest savepoint, not to the start of the transaction. A step that has already committed (an irreversible side effect) cannot be rolled back — that is exactly the difference between a savepoint and a real commit.

Where it breaks

A database knows the dependency graph exactly, and rollback is free. An agent's dependency graph is guessed by the planner and is frequently wrong — a step's output may depend on something the planner never drew an edge to. So plan-repair can "succeed" while operating on a stale assumption. The correction is not a better rollback, it is re-validating the edges, which is what a replan trigger is for.

3 · The mechanism #

The clean result first. Let a k-step serial plan have per-step failure probability p and give it r retries. Under plan-repair, a failure costs you one step back; under plan-linear, it costs you all of them.

Plinear(success) ≈ 1 − (1 − (1−p)k)r       Prepair(success) ≈ [1 − pr]k p = per-step failure probability, k = steps, r = retry allowance per step. The repair form is a lower bound (it assumes each step gets r independent shots, which overstates success slightly when retries deplete a global budget) — good enough for design. Note the structural difference: linear has the whole plan inside the retry exponent, repair has a single step there.

Plug in p = 0.15, k = 20, r = 8 retries: linear gives 1 − (1 − 0.8520)8 = 1 − (1 − 0.0388)8 = 1 − 0.7286 = 0.271. Repair gives (1 − 0.158)20 = (1 − 2.56e-7)20 ≈ 0.999995 as an upper bound; the exact recursion below is lower because retries share a budget.

The executor, with the replan triggers made explicit as data rather than as prose in a prompt.

from functools import lru_cache # A plan is a list of steps; a step declares its deps and whether it is reversible. # Triggers are predicates over (step, result, world) -> None | "repair" | "replan" | "abort" def execute(plan, run_step, triggers, budget, max_restarts=8): done = {} # step_id -> result, the surviving prefix restarts = 0 audit = [] # append-only; hash-chain this (L90, L94) pending = [s for s in plan] while pending: step = pending.pop(0) if not all(d in done for d in step.deps): pending.append(step); continue # deps not ready, requeue budget.debit(step.cost) # L76 pre-debit res = run_step(step, done) audit.append((step.id, res.status, res.detail)) action = fire(triggers, step, res, done) # REPLAN TRIGGERS if action == "abort": return "aborted", done, audit if action == "replan": restarts += 1 if restarts > max_restarts: return "gave_up", done, audit plan = replan(done, res) # keep `done` -> this is the repair pending = [s for s in plan if s.id not in done] continue if action == "repair": pending = [step] + pending # retry THIS step only continue if res.status == "ok": done[step.id] = res return "complete", done, audit def fire(triggers, step, res, done): for t in triggers: if t.matches(step, res, done): return t.action return "repair" if res.status != "ok" else None

The four triggers that actually matter in production. Note that only the first is about the step failing; the other three are about the world failing, which is what agents usually cannot see.

TriggerFires whenActionWhy you need it
STEP_ERRORstep returned non-okrepairdefault; cheap, local
PRECONDITION_DRIFTre-reading a step's declared input disagrees with what the plan assumedreplanthe world changed under you; the plan's edges are stale
ORACLE_REGRESSIONa previously-green invariant went redreplanthis step broke something upstream — the bug is earlier than the failure
IRREVERSIBLE_AHEADthe next step is irreversible and its preconditions are not all verifiedabortthe one trigger whose job is to stop, not to recover
BUDGET_THRESHOLDremaining budget < estimated cost of the rest of the planreplan with a reduced goaldegrades gracefully instead of dying mid-step (L92)

The audit question for a plan executor is not "did it finish". It is "can you reconstruct, from the log alone, which steps were invalidated by which failure, and whether every irreversible step had its preconditions verified at the moment it fired?" That requires the audit row to contain the trigger that fired and the step set it invalidated — not just a status code.

4 · Your hands #

Experiment 1 — Price plan-linearization

Exact recursion over states (steps_completed, retries_left), comparing both regimes with an identical retry allowance of 8. This is the number that decides whether your orchestrator may re-plan from scratch.

from functools import lru_cache def solve(k, p=0.15, c=1.0, rework=0.5, regime="repair", R=8): @lru_cache(maxsize=None) def P(i, r): if i == k: return 1.0 if r <= 0: return 0.0 back = 0 if regime == "linear" else max(0, i - 1) return (1-p) * P(i+1, r) + p * P(back, r-1) @lru_cache(maxsize=None) def EC(i, r): if i == k or r <= 0: return 0.0 extra = (rework * c) if regime == "repair" else 0.0 back = 0 if regime == "linear" else max(0, i - 1) return (1-p) * (c + EC(i+1, r)) + p * (c + extra + EC(back, r-1)) return P(0, R), EC(0, R) for k in (4, 8, 12, 20, 30): for regime in ("linear", "repair"): prob, cost = solve(k, regime=regime) print(f"k={k:2d} {regime:7s} P={prob:.3f} E[cost]={cost:6.2f}")

Observed output: k=4 linear P=0.997 E[cost]=6.09 / repair P=0.999 E=5.81 · k=8 linear P=0.922 E=16.40 / repair P=0.993 E=11.91 · k=12 linear P=0.707 E=28.42 / repair P=0.975 E=17.90 · k=20 linear P=0.271 E=44.83 / repair P=0.884 E=29.14 · k=30 linear P=0.059 E=51.53 / repair P=0.674 E=40.63. The crossover is around k=6: below it, the choice barely matters; above it, plan-linear is a deliberate decision to fail. At k=20 repair is 3.3× more likely to finish at 65% of the cost. Falsifier: if your steps are genuinely independent and idempotent, plan-linear is fine — test by re-running the whole plan after a forced failure and checking whether recompleted steps cost anything. If they do (they usually do: migrations, API quotas, wall clock), repair wins.

Experiment 2 — Find your granularity from a failure log

Step granularity is a measurable trade-off, not taste. Small steps: more steps (k up) but smaller cones. Large steps: fewer retries needed but each failure is catastrophic. Compute expected cost from your own step durations and failure rates.

# Each row: (step, p_fail, cost, cone_size_in_steps). Fill from your trace store. rows = [ ("migrate-schema", 0.10, 3.0, 6), ("backfill-rows", 0.25, 8.0, 3), ("swap-reads", 0.05, 1.0, 4), ("drop-old-column", 0.02, 0.5, 0), ] def expected_cost(rows, mean_step_cost): total = 0.0 for name, p, c, cone in rows: total += c + p * (mean_step_cost * cone) # failure -> redo the cone return total mean_c = sum(r[2] for r in rows) / len(rows) print(f"mean step cost {mean_c:.2f}", f"E[cost] {expected_cost(rows, mean_c):.2f}") for name, p, c, cone in sorted(rows, key=lambda r: -r[1] * r[3]): print(f"{name:16s} p={p:.2f} cone={cone} risk={p*cone:.2f} step-units")

Observed output with these four rows: mean step cost 3.12 E[cost] 17.34, then the risk ranking backfill-rows risk=0.75, migrate-schema risk=0.60, swap-reads risk=0.20, drop-old-column risk=0.00. Note the rows swap order against their step cost: migrate-schema is the second-cheapest step (3.0) but the second-riskiest, because its cone is 6. The diagnostic is the ranking of p × cone. The top row is where to split (reduce its cone by moving downstream steps behind a verified checkpoint) or where to add a savepoint (so a failure rolls back to just before it, not before the whole cone). Note drop-old-column has cone=0: it is terminal, so its failure costs nothing downstream — terminal steps should always be last and cheap, which is a free design win. Falsifier: if backfill-rows fails on data rather than on code, splitting won't help — the fix is a pre-flight validation step, which is a new step with its own row here.

Experiment 3 — Test the triggers, not the happy path (copy-paste)

The only way to know a replan trigger works is to force the condition it watches. This harness injects each failure class and asserts the executor's response.

def test_executor(execute): class Step: def __init__(s, id, deps=(), rev=False): s.id, s.deps, s.reversible = id, deps, rev class Budget: def debit(s, n): pass plan = [Step("a"), Step("b", deps=("a",)), Step("c", deps=("b",))] class Res: def __init__(s, status, detail=""): s.status, s.detail = status, detail # inject: 'b' fails once, then never again seen = [] def run_step(step, done): seen.append(step.id) if step.id == "b" and seen.count("b") == 1: return Res("fail", "transient") return Res("ok") status, done, audit = execute(plan, run_step, triggers=[], budget=Budget()) assert status == "complete", status assert seen.count("a") == 1, "step a must NOT be re-executed on repair" assert set(done) == {"a", "b", "c"} print("PASS: repair kept the prefix; exec order =", seen) test_executor(execute)

Prints PASS: repair kept the prefix; exec order = ['a', 'b', 'b', 'c']. The assertion that matters is seen.count("a") == 1: if your executor re-runs a, you have plan-linearization hiding inside a loop that claims to replan. Run this test against every orchestrator you ship — it is three lines and catches the most expensive bug in the class. Falsifier: if you cannot write this test because run_step has side effects you cannot undo in a test harness, that is itself the finding — your steps are not isolatable and you cannot test triggers at all.

5 · Failure modes #

  • Hidden plan-linearization. The code says "replan", but re-planning regenerates the whole plan including completed steps, which get re-executed. Symptom: completed-step execution count > 1; cost grows superlinearly with k.
  • Stale-edge execution. A completed step's output invalidates an assumption downstream, but no trigger watches for it. Symptom: plan "completes" and the final artifact is wrong; every individual step reported success. This is the highest-severity mode because it looks like success.
  • Unverified irreversible step. A destructive step runs while a precondition is still being retried. Symptom: no error, no rollback possible, incident. Prevent with the IRREVERSIBLE_AHEAD trigger as a hard gate, not a heuristic.
  • Granularity too coarse. A 40-minute step fails at minute 39. Symptom: high variance in cost-per-attempt; p99 duration >> p50; retries that reproducibly fail at the same point.
  • Granularity too fine. 60 steps for a simple task. Symptom: planning tokens exceed execution tokens; the plan itself consumes the budget (L76).
  • Unbounded replanning. No max_restarts. Symptom: agents oscillating between two incompatible plans forever — the plan-history log shows alternating A/B/A/B.
  • Plan narrated but not executed. The model emits a plan as text and then acts reactively. Symptom: done set does not match the plan's step ids; no audit row per planned step.

7 · Self-check #

Q1. Per-step failure probability is 0.12, the plan has 15 steps, and you allow 3 retries total. Give both completion estimates and say which assumption each makes.

Reveal answer

Plan-linear: single-attempt success is 0.8815 = 0.1472; with 3 restarts, 1 − (1 − 0.1472)3 = 1 − 0.85283 = 1 − 0.6203 = 0.380. Plan-repair (upper bound, per-step retries): (1 − 0.123)15 = (1 − 0.001728)15 = 0.9744. Assumptions: linear assumes all work is discarded on failure; repair assumes each step independently gets enough retries, which overstates when retries come from one shared pool — so the truth is between 0.380 and 0.974, and the exact recursion (Experiment 1) settles it for your specific budget.

Q2. From Experiment 1: at k=20, repair is 3.3× more likely to finish. What's the mechanism, stated in one sentence about exponents?

Reveal answer

Under plan-linear the entire plan's failure probability sits inside the retry exponent — you need all 20 steps to succeed before you can bank anything — whereas under plan-repair only a single step's failure probability sits there, so the exponent multiplies 20 small quantities instead of one very small one. Concretely: 0.8520 = 0.0388 versus 0.158 = 2.6e-7. That's the whole argument for savepoints.

Q3. Your executor passes the happy-path test and fails one step in five, yet users report the final artifact is wrong while every step logged ok. Name the failure mode and the log field you are missing.

Reveal answer

Stale-edge execution. Every step succeeded against the inputs it was given, but an earlier step's output invalidated a downstream assumption the plan never drew an edge for. Missing field: the input snapshot hash per step (what the step actually read), plus a post-completion oracle re-check of the end-state invariant. With input hashes you can diff "what step 9 believed" against "what step 4 produced" and find the missing edge. Without them, every step is individually blameless and the bug is unfindable.

Q4. Why must IRREVERSIBLE_AHEAD be an abort and not a repair or replan?

Reveal answer

Because by the time you detect the problem, the correct response is not to continue — any further automated action is operating on a state you have not verified. Repair and replan both assume the world is recoverable; an irreversible step's precondition failure means the recoverable set is unknown, so the only safe action is to stop and escalate to a human. It is the one trigger whose failure mode is designed to be loud rather than cheap, and it is the reason your 4-point promotion gate works: irreversible actions are the ones that need the most evidence, not the least.

Q5. A colleague argues planning is unnecessary: "just let the model take the next best action each turn, like ReAct". Give the quantitative counterexample.

Reveal answer

Reactive control works when the local best action is globally best — true for short, low-branching tasks. It fails when the task has ordering constraints with irreversible steps: the locally attractive action (e.g. "drop the old column, it's unused") is globally catastrophic if a downstream migration still reads it, and no amount of local lookahead fixes it because the cost is non-local. Measure it: run the same task family reactive vs plan-then-act and compare failure rate at k > 8. The honest result is usually a hybrid — plan for ordering and commit points, act reactively within each step — which is what the executor above does.
