L80 · Memory: working / episodic / semantic / procedural

Memory systems fail by retrieving the wrong thing, not by storing too little. The recency weight you pick silently decides whether a superseded fact outranks its replacement — and with the weight at zero it's a tie that sorting resolves in favour of whichever was written first.

~30 min difficulty ●●●○○ build: memory store with decay & retrieval
working / episodic / semantic / procedural decay half-life recency-relevance tradeoff supersession interference consolidation provenance & taint retrieval scoring function

1 · Why it exists #

The failure: the agent confidently uses a fact it should have known was obsolete. At session 1 it learned "the database is Postgres 14". At session 40 the team upgraded to Postgres 16 and it learned that too. Now both are in the store, both match the query "database version", and the retrieval function returns whichever scores slightly higher. There is no error. There is a wrong migration script.

Note what this is not. It is not a storage-capacity failure, not an embedding-quality failure, and not a context-window failure. It is a ranking failure between two true-at-different-times statements, and the only structural fix is to record that one supersedes the other. Memory systems that store facts as flat text are append-only by construction, and append-only stores cannot express "this replaced that".

The second failure is subtler and more expensive: memory that makes the agent worse. An agent that retrieves a plausible but irrelevant past episode for every new task spends context and attention on noise. Because retrieval always returns k results, a bag of low-value memories degrades every query rather than returning nothing.

Memory is not a database with a search box. It is a ranking function over competing explanations of the present, where recency, relevance, importance, and provenance are in tension and the weights are yours. The audit question is not "is the fact stored" but "given the store at time T, would the retriever have returned the fact that was true at time T?"

2 · The mental model #

Four stores with different write paths, different lifetimes, and different retrieval rules. Treating them as one store is the original sin.

Analogy: a library where books are never withdrawn

Semantic memory as a library: you shelve a new edition next to the old one, and the retrieval system returns whichever is closer to the hand. Without a withdrawal process the library becomes steadily less useful as it grows — which matches the observed behaviour of memory-augmented agents over long deployments.

Where it breaks

A library has a single authoritative edition per title. Memory has no natural "title" — two statements about the database version are different strings with different embeddings, and "these are about the same fact" is a judgement that must be made explicitly (a key, a subject, an entity) rather than inferred from text similarity. Embedding similarity cannot detect contradiction; it only detects topical proximity.

So semantic memory needs a subject key (the thing the fact is about) and a validity interval, not just a vector. With a subject key, supersession is a single indexed update. Without one, supersession is a research problem you are solving at retrieval time with cosine similarity, badly.

3 · The mechanism #

Three mechanisms, in order: decay, scoring, supersession. Decay first, because it sets the scale for everything else. An exponential retention curve with a half-life proportional to importance:

R(t) = exp( −(t − taccess) / τ ),   τ = τ0 · importance      t1/2 = τ · ln 2 τ0 = base time constant (e.g. 8 hours), importance in 1–5 multiplies it. At τ0=8h: importance 1 → half-life 5.55h, importance 5 → half-life 27.7h. Decay is a ranking device, not a deletion device — low-retention items should rank lower, not vanish, so they stay auditable.

Then the score. The weights are the design, and the recency weight in particular has a cliff at zero.

score = wrel·rel(q,m) + wrec·R(m) + wimp·(importance/5) rel = query-item relevance (lexical or embedding cosine), R = retention above, wrec = 0 means the ranking is blind to when a fact was learned — and ties between a fact and its replacement break arbitrarily.

The store. Note the three fields that make it auditable: subject (supersession key), supersedes (a pointer, not an inference), and provenance (which tool/human produced it).

import math, time class MemoryStore: def __init__(self, tau0=8.0): self.tau0 = tau0 self.items = {} # id -> item self.by_subject = {} # subject -> current item id (supersession index) def write(self, text, subject, importance=3, provenance="unknown", now=None): now = now or time.time() mid = f"m{len(self.items)+1}" prev = self.by_subject.get(subject) self.items[mid] = {"text": text, "subject": subject, "importance": importance, "t0": now, "t_access": now, "provenance": provenance, "supersedes": prev, "valid_to": None} if prev: self.items[prev]["valid_to"] = now # EXPLICIT supersession self.by_subject[subject] = mid return mid def retention(self, it, now): tau = self.tau0 * it["importance"] dt = max(0.0, now - it["t_access"]) # clock-skew guard return math.exp(-dt / tau) def search(self, q_terms, now=None, k=3, w_rel=1.0, w_rec=1.0, w_imp=0.5, include_superseded=False): now = now or time.time() scored = [] for mid, it in self.items.items(): if it["valid_to"] is not None and not include_superseded: continue # hard filter, not a soft penalty toks = set(it["text"].lower().split()) rel = len(toks & q_terms) / max(1, len(q_terms)) s = w_rel*rel + w_rec*self.retention(it, now) + w_imp*(it["importance"]/5) scored.append((s, mid)) scored.sort(reverse=True) return scored[:k]

The single most important line is the hard filter valid_to is not None → skip. Superseded facts must be excluded by a filter, not out-competed by a recency bonus, because a bonus is a continuous quantity competing with relevance — and a sufficiently relevant stale fact will beat a less topically similar fresh one. Filter first, rank second. That ordering is the invariant.

Retention-based ranking makes a specific audit promise testable: replay the store as of time T and confirm the retriever returns the fact that was valid at T. This is only possible if writes are timestamped in a tamper-evident log (L90/L94) and supersession is recorded as a pointer. If supersession is inferred at query time by similarity, the store cannot be replayed to a historical state at all, and the audit is impossible by construction.

4 · Your hands #

Experiment 1 — Reproduce the stale-fact resurrection

Five memories, one superseding pair. Sweep the recency weight and watch the top result change. The interesting row is w_rec = 0.0.

import math def ret(t0, imp, now, tau0=8.0): return math.exp(-(now - t0) / (tau0 * imp)) def score(text, t0, imp, q, now, w_rel=1.0, w_rec=1.0, w_imp=0.5): toks = set(text.lower().split()) rel = len(toks & q) / max(1, len(q)) return w_rel*rel + w_rec*ret(t0, imp, now) + w_imp*(imp/5) NOW, Q = 100.0, {"database", "postgres"} MEM = [("m1", "database uses postgres 14", 0, 5), ("m6", "database uses postgres 16", 90, 5), ("m4", "migration must be reversible", 0, 5)] for wr in (0.0, 0.5, 1.0, 2.0, 4.0): r = sorted(MEM, key=lambda x: -score(x[1], x[2], x[3], Q, NOW, w_rec=wr)) print(f"w_rec={wr:.1f} top1={r[0][0]} ({score(r[0][1],r[0][2],r[0][3],Q,NOW,w_rec=wr):.3f})" f" top2={r[1][0]} ({score(r[1][1],r[1][2],r[1][3],Q,NOW,w_rec=wr):.3f})")

Observed output: w_rec=0.0 top1=m1 (1.500) top2=m6 (1.500) — an exact tie, resolved against the newer fact. Then w_rec=0.5 → m6 (1.889), 1.0 → m6 (2.279), 2.0 → m6 (3.058), 4.0 → m6 (4.615). The scores for m1 stay near 1.5–1.8 throughout. The lesson: with w_rec = 0 you have no signal at all distinguishing a fact from its replacement, and whether the bug manifests depends on dictionary iteration order — which means it manifests intermittently and looks like flakiness. And notice that even at w_rec = 0.5 the recency term is doing the entire job of supersession, which is fragile: raise relevance (make the stale fact more topically similar) and it wins again. Falsifier: if your store returns m6 at w_rec = 0, you got lucky on ordering — rerun with the items inserted in the opposite order.

Experiment 2 — Half-lives, and why decay must not delete

With τ0 = 8h and importance 1–5, compute how fast each class of memory goes stale as a ranking signal.

import math TAU0 = 8.0 for imp in (1, 2, 3, 4, 5): tau = TAU0 * imp print(f"importance={imp} tau={tau:4.1f}h half-life={tau*math.log(2):5.2f}h") print() # after 48h, what is retention? for imp in (1, 3, 5): print(f"imp={imp} at 48h: R={math.exp(-48/(TAU0*imp)):.5f}")

Observed output: half-lives imp=1 → 5.55h, 2 → 11.09h, 3 → 16.64h, 4 → 22.18h, 5 → 27.73h. After 48h: imp=1 R=0.00248, imp=3 R=0.13534, imp=5 R=0.38674. The design conclusion: importance must multiply τ linearly, or a low-importance memory decays so fast it can never be retrieved. But even R=0.0025 is not zero — the item still exists and is still auditable, which is the property you want. If decay deleted items, you could not reconstruct why a past run behaved as it did. Falsifier: if retrieval quality improves when you delete low-retention items, your scoring function is letting low-relevance items through via the importance term — fix the weights, don't delete evidence.

Experiment 3 — Assert the supersession invariant (copy-paste test)

The property that must hold in every memory store: after a superseding write, the old fact is unreachable by any weight setting.

def test_supersession(store): now = time.time() # realistic offsets; huge dt overflows exp() store.write("database uses postgres 14", subject="db.version", importance=5, provenance="tool:pg_read", now=now - 48*3600) store.write("database uses postgres 16", subject="db.version", importance=5, provenance="tool:pg_read", now=now - 10*3600) q = {"database", "postgres"} # invariant: for ANY weight vector, the superseded item never wins for wr in (0.0, 0.1, 1.0, 10.0): for wi in (0.0, 0.5, 2.0): hits = store.search(q, now=now, k=5, w_rec=wr, w_imp=wi) texts = [store.items[m]["text"] for _, m in hits] assert "postgres 14" not in " ".join(texts), f"STALE LEAK wr={wr} wi={wi}" assert "postgres 16" in " ".join(texts), f"MISSING CURRENT wr={wr}" # and the old fact is still retrievable for forensics hits = store.search(q, now=now, k=5, include_superseded=True) assert len(hits) == 2, "history must remain available" print("PASS: supersession invariant holds across all weights") test_supersession(MemoryStore())

Prints PASS: supersession invariant holds across all weights. The two assertions encode the whole design: no weight combination may surface a superseded fact in normal retrieval, and the fact must still be retrievable with include_superseded=True for forensics. If your store fails this test at even one weight combination, your "memory" cannot distinguish current from historical and every downstream eval is contaminated. Falsifier: if the assertion fails only at w_imp = 2.0, the importance term is overpowering everything — which means importance is being used as a relevance proxy, a bug worth fixing on its own.

5 · Failure modes #

  • Append-only semantics. No subject key, no supersession. Symptom: contradictory facts co-exist; the answer flips between runs on the same question — classic non-reproducibility (L94) misattributed to sampling.
  • Recency-as-supersession. No hard filter; the new fact wins only because it scores higher. Symptom: raising relevance of the old fact (a slightly better keyword match) resurrects it. Detect: the supersession invariant test above.
  • Provenance laundering. A model-generated guess is stored with the same authority as a tool-verified read. Symptom: memory says "the API returns X" and X was never returned by anything; traced to an inference that got written back. Fix: provenance is mandatory and tainted items are excluded from authoritative answers (L97).
  • Episodic contamination. Failed attempts stored as facts. Symptom: the agent "remembers" that an approach doesn't work when it was the environment that was broken. Episodes need outcome labels (failed_because), not just text.
  • Unbounded growth with no ranking calibration. 50k items, k=5 always returned. Symptom: retrieval returns topically related but useless items; precision drops as the store grows while recall looks fine.
  • Consolidation collapse. Periodic consolidation rewrites everything into a summary. Symptom: same half-life decay as summarization (L79), but now it is the only copy. Consolidation must write a new derived item, never overwrite sources.

7 · Self-check #

Q1. Why is a hard valid_to filter strictly better than a recency bonus for supersession?

Reveal answer

Because a bonus is a continuous term competing against relevance and importance, so there always exists a fact stale enough to be penalised but relevant enough to win — the ranking is only correct within a weight regime, and your weights are also tuned for retrieval quality, so the two objectives fight. A filter is an invariant: superseded facts are excluded before scoring, for every weight vector. That is exactly what Experiment 3 tests. Filters encode "this is not a candidate"; bonuses encode "this candidate is slightly less good" — supersession is the former.

Q2. With τ0=8h, what is the retention of an importance-4 memory after 36 hours, and after 120 hours? Show the arithmetic.

Reveal answer

τ = 8 × 4 = 32h. At 36h: exp(−36/32) = exp(−1.125) = 0.3247. At 120h: exp(−120/32) = exp(−3.75) = 0.0235. Half-life is 32 × ln2 = 22.18h. If your retrieval threshold is retention > 0.3, that memory is a ranking candidate for about a day and a half regardless of how important it is — which is why importance must multiply τ, and why a fact you need indefinitely must be re-accessed (which resets t_access) or stored in procedural memory instead of relying on decay.

Q3. Diagnostic: for the same question, the agent answers correctly on Monday and incorrectly on Wednesday, same model, temperature 0. What do you check first?

Reveal answer

Memory contents, not sampling. At temperature 0 the model is nearly deterministic on a fixed prompt (L94), so a different answer implies a different prompt — and the most likely differing component is retrieved memory. Check the trace: what did retrieval return on each day? Look for a superseding write between Monday and Wednesday, or for a new item that outranked the correct one. The Monday-correct/Wednesday-wrong pattern with no deploy is the signature of a store that changed underneath a stable model.

Q4. Why must consolidation write a new derived item rather than overwrite the sources it summarized?

Reveal answer

Two reasons. First, lossy: consolidation has the same ar decay as summarization (L79), so an overwrite is irreversible information loss with no way to detect it later. Second, auditability: if the derived item is wrong, a reviewer must be able to walk back to the sources that produced it and see where the error entered. Overwriting destroys the evidence needed to do that. Store derived_from: [ids] on the new item and leave sources intact with valid_to set if they are truly retired — the distinction between "retired from ranking" and "deleted from existence" is the whole point.

Q5. Your store has 2,000 memories, retrieval always returns k=5, and users say the agent "brings up irrelevant old episodes". Give the two candidate root causes and the measurement that separates them.

Reveal answer

(a) Scoring miscalibration: the importance or recency terms dominate so old high-importance episodes outrank genuinely relevant current material; (b) episodic contamination: the episodes are topically relevant but their outcomes are unlabelled, so "I tried X and it failed" is retrieved and treated as guidance. Measurement: label a sample of 100 retrieved sets for whether the top-1 item was useful to the response, then break the error rate down by item store (episodic vs semantic) and by score component. If failures concentrate in episodic items, it is (b) — add outcome labels and a store-type filter. If they spread evenly across both, it is (a) — recalibrate weights against the usefulness labels rather than against similarity, which is what you can already measure.
