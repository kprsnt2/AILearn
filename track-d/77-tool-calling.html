L77 · Tool calling & MCP: schemas as the product

Your 26 tools in MyLocalCLI are 26 prompts the model must obey without seeing an example. A schema is not documentation for humans — it is the entire specification the model gets, and every ambiguity in it converts directly into a failed or wrong tool call.

~30 min difficulty ●●●○○ build: tool schema linter
schema as specification tool boundary token tax per tool required-field brittleness enum over free text MCP transport vs semantics idempotency keys error returns as context

1 · Why it exists #

The failure that made tool schemas a first-class artifact: a tool that works perfectly but is called wrong. A function named update with a required id, a free-text body, and an implicit "you must read before you write" rule is a function that a human teammate reads once and gets right, and a model gets right 70% of the time. The 30% is not a model deficiency — it is an underspecified interface. The model has no type checker, no IDE hover, no compile error. It has your description string and nothing else.

Once agents call each other's tools (MCP turns every server into a tool provider), the schema stops being documentation and becomes a wire contract between two stochastic parties. Nobody reviews it as a contract. A typo in required ships to production and shows up as a 4% tool-call failure rate that nobody attributes to the schema, because it presents as "the model is dumb today".

Determine the tool boundary before the prompt. Every tool call is a typed transaction across a trust boundary between the model and your process. An underspecified schema is not a prompt-engineering problem; it is a missing validation layer. And a large tool catalogue is a per-turn token tax paid on every single turn of every conversation, whether the tool is used or not.

2 · The mental model #

Four layers, and the model only ever sees the first:

LayerLives whereWho validatesWhat the model sees
1. Schema — name, description, JSON Schema paramsprompt / tools arraynobodyall of it
2. Argument validationyour handlerJSON Schema validatorerror string only, after the fact
3. Precondition check — "does this row exist / am I allowed"your handlerbusiness logicerror string only, after the fact
4. Effect — the mutationyour handlertransaction / idempotency keynothing

Schemas are a compression of layers 1–3 into prose. Every fact in layers 2 and 3 that you do not put in layer 1 has to be discovered by the model through a failed call, which costs a turn (L76's debit) and a context slot.

The analogy that works: a strongly-typed RPC IDL, written for a blind compiler

Think of a schema as a protobuf .proto file whose only reader is a compiler that cannot ask questions and cannot read the implementation. Good IDLs bound types, enumerate variants, and state preconditions in comments. Good schemas do exactly that.

Where the analogy breaks

A protobuf compiler is deterministic and rejects illegal input, so an underspecified field is still typed. A model fills unspecified fields plausibly. Absence of constraint is not treated as "use your judgement" — it is treated as licence to invent. So looseness in a schema does not just cause failures; it causes silently wrong successes, which are worse and which the analogy has no word for.

3 · The mechanism #

The two quantities worth modelling. First, token tax: the tools array is serialised into the prompt every turn.

Ttools = n · t̄      and      costturn ⊇ (Ttools + Tctx + Tout) · pin/106 n = number of registered tools, t̄ = mean tokens per schema, Tctx = conversation, pin = input price per 1M tokens. Ttools is paid on turn 1 and on every turn after unless the provider caches the prefix (L45). It is pure overhead when a turn does not use a tool — which in a long agent loop is most turns.

Second, call validity. If a tool has k required fields and the per-field probability of the model getting each one right on the first attempt is q, first-attempt validity is qk. This is why six required fields is a smell, not a style preference.

P(valid call) ≈ qk     →    q=0.97, k=2 ⇒ 94.1%    k=6 ⇒ 83.3%    k=10 ⇒ 73.7% Treat q as measurable per field, not as a guess: count first-attempt field errors in your logs. The formula tells you that reducing k by making fields optional-with-defaults beats any prompt tweak, because it removes a multiplicative factor rather than improving one.

The linter. Twenty lines that predict real failures, written as a review gate you can run in CI.

import re VAGUE = re.compile(r"\b(do|handle|process|manage|thing|stuff|data|info|some|various|optionally)\b", re.I) def lint_desc(s): out = [] if len(s) < 40: out.append(("DESC_SHORT", f"{len(s)} chars; cannot be told apart from siblings")) if len(s) > 400: out.append(("DESC_LONG", f"{len(s)} chars; taxed on every turn")) if VAGUE.search(s): out.append(("DESC_VAGUE", f"vague words: {VAGUE.findall(s)[:3]}")) if not re.search(r"\b(use when|call when|when the|if the)\b", s, re.I): out.append(("DESC_NO_TRIGGER", "no explicit trigger clause")) if not re.search(r"\breturns?\b|\bresult\b|\blist\b", s, re.I): out.append(("DESC_NO_RETURN", "does not say what comes back")) return out def lint_params(p): props, out = p.get("properties", {}), [] if p.get("additionalProperties", True) is not False: out.append(("PARAMS_OPEN", "additionalProperties not False; model may invent fields")) for k, v in props.items(): if "description" not in v: out.append(("PARAM_NO_DESC", k)) if v.get("type") == "string" and not ({"enum","pattern","maxLength"} & v.keys()): out.append(("PARAM_UNBOUNDED_STRING", k)) if v.get("type") == "integer" and ({"minimum","maximum"} > v.keys()): out.append(("PARAM_UNBOUNDED_INT", k)) if v.get("type") == "array" and "maxItems" not in v: out.append(("PARAM_UNBOUNDED_ARRAY", k)) req = set(p.get("required", [])) for k in req - props.keys(): out.append(("REQUIRED_MISSING", k)) if len(req) > 6: out.append(("REQUIRED_TOO_MANY", f"{len(req)} required: q^k decay")) return out

Run on a realistic first draft, it fires four findings — and each one maps to a specific production symptom:

FindingDraft toolSymptom in productionFix

PARAM_UNBOUNDED_STRINGqueryModel pastes a 4k-char spec into the query field; search times outmaxLength: 200 + a pattern

PARAMS_OPEN(fired on the original)Model adds sort: "relevance"; handler ignores it silentlyadditionalProperties: false

MCP in one paragraph. MCP standardises the transport and discovery of tools (a JSON-RPC surface where a server advertises tools/list and executes tools/call). It does not standardise semantics: it will happily ship a wildly underspecified tool schema across a process boundary. The consequence is that schema quality becomes a supply-chain property — you are now trusting a third party's descriptions to steer your model. Lint third-party schemas on ingest and log the schema hash with every call, so that when a tool starts behaving differently you can prove the schema changed.

4 · Your hands #

Experiment 1 — Price your tool catalogue

Count what 26 tools actually cost per turn. This is the number that makes you delete tools instead of adding them.

import json def schema_tokens_est(schema): # crude: ~4 chars/token on compact JSON. Deliberately labelled an estimate - # the point is scaling in n, not the constant. return len(json.dumps(schema, separators=(",", ":"))) / 4.0 tool = {"name": "search_issues", "description": "Search issues by full text. Use when the user asks about existing tickets. Returns a list of issue summaries.", "parameters": {"type": "object", "properties": { "query": {"type": "string", "maxLength": 200}, "state": {"type": "string", "enum": ["open", "closed", "any"]}, "limit": {"type": "integer", "minimum": 1, "maximum": 50}}, "required": ["query"], "additionalProperties": False}} per = schema_tokens_est(tool) print(f"one schema ~= {per:.0f} tokens") for n in (5, 10, 20, 26, 50, 100): t = per * n print(f"{n:4d} tools -> {t:6.0f} tok/turn -> {t*30:8.0f} tok / 30 turns")

Observed output: one schema ~= 124 tokens, then 5 → 619 tok/turn → 18,562 over 30 turns; 10 → 1,238 → 37,125; 20 → 2,475 → 74,250; 26 → 3,218 → 96,525; 50 → 6,188 → 185,625; 100 → 12,375 → 371,250. At a hypothetical $0.28/1M input tokens, 26 tools over 30 turns is $0.027 — small in absolute terms, but it is paid on every conversation and it scales linearly with a number you control. In a 400-turn loop the same 26 tools cost 1.29M tokens of pure schema. Falsifier: if your provider caches the tools prefix (L45), the marginal cost after turn 1 is near zero — then the real cost of a bloated catalogue is attention, not money, and you must measure selection accuracy instead. The test: hold the task fixed, add 20 distractor tools, measure wrong-tool-selection rate.

Experiment 2 — The qk decay is measurable in your own logs

Instead of assuming q, estimate it. This is the single statistic that tells you whether to refactor a tool.

from collections import Counter # shape of a real log row; replace with your own event store (L90) calls = [ {"tool": "update_issue", "ok": False, "err": "missing id"}, {"tool": "update_issue", "ok": True, "err": None}, {"tool": "search_issues", "ok": True, "err": None}, {"tool": "update_issue", "ok": False, "err": "body too long"}, ] def first_attempt_validity(calls): seen, stats = set(), {} for c in calls: key = (c["tool"], c.get("turn", 0)) if key in seen: continue # only first attempt per turn counts seen.add(key) s = stats.setdefault(c["tool"], {"n": 0, "ok": 0, "errs": Counter()}) s["n"] += 1; s["ok"] += c["ok"] if not c["ok"]: s["errs"][c["err"]] += 1 for tool, s in stats.items(): q = s["ok"] / s["n"] print(f"{tool:14s} n={s['n']:4d} q={q:.3f} top_err={s['errs'].most_common(1)}") return stats first_attempt_validity(calls)

With this 4-row sample you get update_issue n=3 q=0.333 top_err=[('missing id', 1)] and search_issues n=1 q=1.000. The intent is not the number — 3 samples is not an estimate — it is the shape: a per-turn first-attempt validity rate per tool, with the dominant error string attached. Run it over 2,000 rows and you have q. If a tool sits below ~0.95, the fix is schema, not prompt. Falsifier: if the dominant error is a runtime error (timeout, rate limited), the schema is fine and you have a reliability problem (L92) — do not "fix" the description.

Experiment 3 — Mutation-test the schema (browser console)

Delete one character class at a time from a valid argument object and confirm your handler rejects every mutation. If it accepts any of them, that field is unconstrained in practice regardless of what the schema claims.

const args = {query:"ledger hash mismatch", state:"open", limit:20}; const muts = { wrong_type_limit: {...args, limit:"20"}, bad_enum: {...args, state:"opened"}, over_max: {...args, limit:9000}, extra_field: {...args, sort:"newest"}, missing_required: {state:"open"}, null_query: {...args, query:null}, empty_query: {...args, query:""}, }; function validate(a) { const e = []; if (typeof a.query !== "string" || !a.query || a.query.length > 200) e.push("query"); if (!["open","closed","any"].includes(a.state)) e.push("state"); if (!Number.isInteger(a.limit) || a.limit < 1 || a.limit > 50) e.push("limit"); const allowed = ["query","state","limit"]; for (const k of Object.keys(a)) if (!allowed.includes(k)) e.push("extra:"+k); return e; } for (const [name, a] of Object.entries(muts)) { const e = validate(a); console.log(name.padEnd(18), e.length ? "REJECT " + e.join(",") : "ACCEPTED <-- GAP"); }

All seven mutations print REJECT. If any prints ACCEPTED <-- GAP, that is a live injection surface: extra_field is the dangerous one, because it is how a model (or a prompt injection forwarded through a tool result) adds a parameter your handler never intended to read. Falsifier: if null_query is accepted with no error, your handler is coercing null to "" somewhere — check for String(x) or default-argument coercion.

5 · Failure modes #

  • Adjacent-tool confusion. Two tools whose descriptions differ only in wording (get_issue vs fetch_issue). Symptom: wrong-tool-selection rate rises when you add tools, not when you change the model. Detect: log the chosen tool name against the expected tool for a golden set; the confusion matrix shows the pair.
  • Retry storm from a required-field mistake. Model omits a required field, gets a validation error, retries with the same omission. Symptom: 3× the intended call count for one tool, with identical error strings. Fix: make the error message prescriptive ("missing id; call search_issues first and pass issue_id").
  • Silent extra-field drop. additionalProperties open and the handler ignores unknown keys. Symptom: zero errors, wrong results — the model believes it applied a filter that was discarded. This is the worst class because it produces no signal.
  • Unbounded parameter blowup. No maxLength/maxItems. Symptom: p99 latency spikes correlated with user input length; occasional context-window overflow when a tool echoes back what it was given.
  • MCP schema drift. Third-party server updates a description or an enum without a version bump. Symptom: tool selection degrades at a fixed timestamp with no deploy on your side. Fix: log the schema hash per call and alert on change.
  • Non-idempotent mutation retried. The tool has no idempotency key and the loop retries after a timeout. Symptom: duplicate rows, duplicate comments, duplicate charges — count > 1 per logical action.

  • L17 · Samplers — constrained/structured decoding enforces the schema at the logit level, which is the only way to get P(valid call) = 1 rather than qk.

7 · Self-check #

Q1. Your update_issue tool has 7 required fields. First-attempt per-field accuracy is 0.96. Estimate first-call validity and name the single highest-leverage change.

Reveal answer

0.967 = 0.751, so ~25% of first attempts fail. Highest leverage: reduce k, not improve q. Moving 3 fields to optional-with-server-default takes you to 0.964 = 0.849 — a +10 pt jump. Getting q from 0.96 to 0.99 with the same k=7 yields 0.997 = 0.932, a +18 pt jump but requires prompt-and-model work with no guarantee. Do both; do the k reduction first because it is a one-line schema change with a closed-form effect.

Q2. 26 tools, 124 tokens each, 40 turns per session, 500 sessions/day, $0.28 per 1M input tokens. What is the daily schema bill, and what fraction of a 30k-token session context is schema?

Reveal answer

Schema per turn = 26 × 124 = 3,224 tokens. Per session = 3,224 × 40 = 128,960. Per day = 128,960 × 500 = 64.48M tokens → 64.48 × 0.28 = $18.05/day. As a share of context: 3,224 / 30,000 = 10.7% of every turn's context is tool descriptions. That 10.7% is the number to attack, because context is the scarcer resource (L79).

Q3. Diagnostic: tool-call errors are zero, but users report filters "not working". Which failure mode, and what instrument proves it?

Reveal answer

Silent extra-field drop. The model passes a field the handler does not read, validation passes because additionalProperties is open, and the query runs unfiltered. Prove it by logging the received argument object alongside the executed query and diffing them: any key present in the arguments and absent from the executed query is a dropped field. Fixed by additionalProperties: false (turning drops into loud errors) plus per-field descriptions.

Q4. Why does an MCP server need its schema hash logged per tool call, when the call arguments are already logged?

Reveal answer

Because the arguments are produced from the schema. If the remote server silently changes a description or narrows an enum, your model's outputs change while your arguments look normal — the causal input is the schema, not the arguments. With a per-call schema hash you can bisect: "selection accuracy dropped at 14:20; schema hash changed at 14:19". Without it, you will blame the model and lose a day. It also makes the third-party dependency auditable at all, which is the same property your hash-chained ledger provides for your own actions.

Q5. A teammate proposes solving tool confusion by writing a very long decision tree in the system prompt ("if X then use A, if Y then use B..."). Give the token arithmetic and the better fix.

Reveal answer

A 2,000-token routing preamble is cheaper than 26 schemas on turn 1 but is also paid every turn and is not cache-friendly when task state changes. Worse, it duplicates information already in the schemas, creating two sources of truth that drift. The better fix is structural: (a) prune to the ~8 tools the task family needs, selected by a cheap classifier or by task type at session start; (b) make each description start with its trigger clause so the model's own routing is accurate. Turn selection into a small, measurable classification problem with a golden set (L88) instead of an unmeasured prose artefact.
