L88 · Evals: golden sets, statistical power, pass@k vs pass^k

A pass rate is an estimate from a finite sample, and most eval claims are unsupported by their own arithmetic. Detecting a 3-point lift at 60% baseline needs 4,129 items per arm. Detecting an 8-point lift on a paired set needs 150. The design, not the model, decides whether you can see the effect.

1 · Why it exists #

The failure that makes evals worthless: "we improved pass rate from 71% to 74%" is a claim about 100 coin flips, not about the system. With 100 items and p=0.72, the 95% Wilson interval is [0.625, 0.799] — 17.3 points wide. A 3-point measured "improvement" is inside the noise of a single re-run. Teams ship on this, then the next run reverses it, then they stop trusting evals and go back to vibes.

The second failure is a category error that infects agent evaluation specifically. pass@k and pass^k look like the same metric and answer opposite questions. pass@k is "will at least one of k attempts succeed" — the right question for a coding assistant where the user rerolls. pass^k is "will all k attempts succeed" — the right question for an autonomous agent that runs unattended once. At p=0.70: pass@5 = 0.969 but pass^5 = 0.031. A system optimised for the first is actively bad for the second, and vendor tables usually quote the first.

The third failure is the sample-size estimator. pass@k computed from n samples is only valid when n ≥ k, and when n−c < k the estimator saturates at exactly 1.0. With 10 samples and 7 correct, pass@5 = 1.000 — not because the system is perfect but because it is mathematically impossible to draw 5 failures from 3 failures.

An eval number is a confidence interval plus a declaration of what was measured. The interval comes from the item count; the declaration must say whether it is pass@1, pass@k, or pass^k, and at what n. Ship criteria should be stated on the lower bound of the interval, not the point estimate — that is the number that would survive a rerun.

2 · The mental model #

An eval set is a measuring instrument, and like any instrument it has a resolution. n items set the resolution; the item mix sets the bias. You cannot detect an effect smaller than the resolution, and no amount of statistical cleverness recovers it — you can only add items or reduce variance by pairing.

Analogy: a ruler with 1cm marks cannot measure millimetres

An eval with 100 items and p≈0.7 has ~7cm marks. You can tell 60% from 80%; you cannot tell 71% from 74%. The fix is not a better statistical method — it is a finer ruler (more items) or a smarter measurement procedure (paired comparison, which removes item-difficulty variance).

Where it breaks

A ruler is unbiased: repeated measurements scatter around the truth. An eval set is biased if its items do not match the production distribution — and no interval reveals that, because the interval only measures sampling noise within the chosen item set. A 1,000-item set of easy questions gives a beautifully narrow interval around a number that predicts nothing. Precision is not accuracy.

Which is why golden-set construction matters more than golden-set size. Sample items from the production input distribution, stratify by difficulty and by task family, and keep a held-out slice that is never used for iteration. An honest 300-item stratified set beats a lazy 3,000-item one, and it is the only version whose interval means what you think it means.

3 · The mechanism #

Three formulas carry this page. First, the interval — Wilson, because Wald fails exactly where evals live (near 0 and 1, small n):

CI95 = [ p̂ + z²/2n ± z√( p̂(1−p̂)/n + z²/4n² ) ] / (1 + z²/n),   z = 1.96 At n=100, p̂=0.72: centre 0.7118, half-width 0.0847, so [0.625, 0.799]. The interval's half-width is your measurement resolution; state it with every number you report.

Second, the sample size needed to detect an absolute difference Δ between two independent arms at power 1−β:

narm = [ zα√(2p̄(1−p̄)) + zβ√(p1(1−p1) + p2(1−p2)) ]² / Δ² p̄ = pooled rate, zα=1.96 for 95% confidence, zβ=0.8416 for 80% power. At baseline 0.60 detecting +0.05: 1,471 items per arm. Detecting +0.03: 4,129. This is why "small eval, big conclusion" is always wrong.

Third, the paired design, which is the cheapest real win available. Score both systems on the same items and test only the discordant pairs (McNemar). Item difficulty variance cancels:

χ²McNemar = (b − c)² / (b + c),    nitems ≈ (zα+zβ)² · (p01+p10) / (p10−p01)² b = items A fails and B passes, c = items A passes and B fails; p01, p10 their per-item probabilities. For a 10-point net gain with discordant rates (0.05, 0.15), only ~150 items are needed versus 356 unpaired — because the items that both systems get right (or both fail) carry no information about which is better.

And the pass@k estimator, which must be used correctly or it lies:

pass@k = 1 − C(n−c, k) / C(n, k)      pass^k = (c/n)k n = total samples per problem, c = correct samples, k = attempts. The unbiased estimator avoids the naive 1−(1−c/n)k bias. When n−c < k the estimator returns exactly 1.0 by construction — it is censored, not perfect. pass^k assumes independent runs, which fails for cached or near-deterministic serving (L94) — measure the actual run-to-run agreement rather than assuming it.

The harness. It refuses to report a number the design cannot support.

import math def wilson(p, n, z=1.96): if n == 0: return (0.0, 1.0) d = 1 + z*z/n c = (p + z*z/(2*n)) / d h = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d return (max(0.0, c-h), min(1.0, c+h)) def report(passes, n, metric="pass@1", min_resolution=0.05): p = passes / n lo, hi = wilson(p, n) width = hi - lo warn = [] if width <= min_resolution else [ f"CI width {width:.3f} > {min_resolution}: cannot resolve effects below {width/2:.3f}"] return {"metric": metric, "n": n, "p": round(p, 4), "ci95": (round(lo, 4), round(hi, 4)), "lower_bound": round(lo, 4), "warnings": warn} def n_required(p1, p2, z_alpha=1.96, z_beta=0.8416): pbar = (p1 + p2) / 2 num = (z_alpha*math.sqrt(2*pbar*(1-pbar)) + z_beta*math.sqrt(p1*(1-p1) + p2*(1-p2)))**2 return math.ceil(num / (p2-p1)**2) def mcnemar(b, c, z=1.96): # b: A fails & B passes ; c: A passes & B fails if b + c == 0: return {"verdict": "identical on this set"} stat = (b - c)**2 / (b + c) return {"b": b, "c": c, "chi2": round(stat, 3), "significant_95": stat > 3.841, "net_effect": round((b - c) / (b + c), 3)}

Three things in that code are the lesson. (1) report returns lower_bound as a first-class field — that is the number a ship gate should use, because it is the value the system is likely to beat on a rerun. (2) It warns when the interval is wider than your claimed resolution, so "no significant difference" cannot be silently reported as "same". (3) mcnemar ignores concordant items entirely, which is why the paired design is more powerful: it spends all its information where the systems actually differ.

The audit artifact is not the pass rate — it is the eval manifest: golden-set version hash, item count, per-item outcomes, the metric definition (pass@1 / pass@k with k / pass^k with k), and the computed interval. With those, a reviewer reruns the arithmetic and confirms the claim. Without them, every reported gain is a number someone typed.

4 · Your hands #

Experiment 1 — Your interval is wider than your claim

Wilson intervals across n and p. This is the sizing chart; the readings are the answer to "how many items do I need?".

import math def wilson(p, n, z=1.96): d = 1 + z*z/n c = (p + z*z/(2*n)) / d h = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d return c - h, c + h print(" n p 95% CI width") for n in (20, 50, 100, 300, 500, 1000): for p in (0.90, 0.60): lo, hi = wilson(p, n) print(f"{n:5d} {p:5.2f} [{lo:.3f}, {hi:.3f}] {hi-lo:6.3f}")

Observed output: 20 0.90 [0.699, 0.972] 0.273 · 20 0.60 [0.387, 0.781] 0.395 · 100 0.90 [0.826, 0.945] 0.119 · 100 0.60 [0.502, 0.691] 0.189 · 300 0.90 [0.861, 0.929] 0.068 · 500 0.90 [0.871, 0.923] 0.053 · 1000 0.90 [0.880, 0.917] 0.037. Notice the shape: width falls as 1/√n, so to halve the interval you need 4× the items. At n=20 the interval is 27 points wide for a 90% system — any conclusion from 20 items is unsupported. p=0.90 also gives narrower intervals than p=0.60 (variance is p(1−p)), which is why a high-accuracy agent is easier to measure than a mid-accuracy one. Falsifier: if your reported gain exceeds the interval width at your n, it is at least potentially real — but check the paired-design number before running an expensive 1,000-item eval.

Experiment 2 — The n you need, and why pairing saves you

Power analysis for independent arms, then the paired-design comparison. The gap between them is the point.

import math def n_per_arm(p1, p2, za=1.96, zb=0.8416): pb = (p1 + p2) / 2 num = (za*math.sqrt(2*pb*(1-pb)) + zb*math.sqrt(p1*(1-p1)+p2*(1-p2)))**2 return math.ceil(num / (p2-p1)**2) for base in (0.60, 0.75, 0.90): for lift in (0.10, 0.05, 0.03, 0.01): print(f"baseline={base:.2f} lift={lift:.2f} -> {n_per_arm(base, base+lift):6d} per arm") print("\nPAIRED (McNemar) vs unpaired") def paired_n(p01, p10, za=1.96, zb=0.8416): d = p10 - p01 var = p01 + p10 - d**2 return math.ceil((za+zb)**2 * var / d**2) for p01, p10 in ((0.05,0.15), (0.10,0.20)): print(f" discordant=({p01},{p10}) -> {paired_n(p01,p10)} items")

Observed output: baseline 0.60 — lift 0.10 → 356 per arm, 0.05 → 1,471, 0.03 → 4,129, 0.01 → 37,513. Baseline 0.90 — lift 0.10 → 74, 0.05 → 435, 0.03 → 1,356. Paired design with discordant rates (0.05, 0.15) → ~150 items for a 10-point net gain, versus 356 unpaired. The arithmetic is the argument: detecting a 1-point lift requires ~37,500 items per arm at 60% baseline, which is why nobody honestly detects 1-point improvements. And the paired design cuts the requirement by more than half for the same effect, because it removes the item-difficulty variance that dominates an unpaired comparison. Falsifier: if you claim a 5-point gain on 100 items, the power calculation says you had roughly a coin's chance of detecting it even if real — report the interval, or rerun paired.

Experiment 3 — pass@k diverges from pass^k, and the estimator lies

Same system, same p, two metrics that move in opposite directions — then the censoring bug.

import math def pass_at_k(n, c, k): if k > n: raise ValueError("k must be <= n samples") if n - c < k: return 1.0 # CENSORED, not perfect return 1 - math.comb(n-c, k) / math.comb(n, k) def pass_hat_k(p, k): return p**k p = 0.70 print(" k pass@k pass^k gap") for k in (1,2,3,5,10): a, b = 1-(1-p)**k, pass_hat_k(p, k) print(f"{k:3d} {a:8.4f} {b:9.4f} {a-b:7.4f}") print("\ncensoring: n=10 samples, c=7 correct") for k in (1, 5, 10): print(f" pass@{k} = {pass_at_k(10, 7, k):.4f}") print("n=10, c=3 correct:") for k in (1, 5, 10): print(f" pass@{k} = {pass_at_k(10, 3, k):.4f}")

Observed output: at p=0.70: k=1: pass@1=0.5000 pass^1=0.5000 (identical by definition), but k=2: 0.7500 vs 0.2500, k=3: 0.8750 vs 0.1250, k=5: 0.9688 vs 0.0312, k=10: 0.9990 vs 0.0010. The gap at k=5 is 0.9375 — the two metrics describe opposite systems. Censoring: with n=10, c=7: pass@1=0.7000, pass@5=1.0000, pass@10=1.0000. With n=10, c=3: pass@1=0.3000, pass@5=0.9167, pass@10=1.0000. pass@10 = 1.000 in both cases is the censoring artefact — you cannot select 10 distinct items from the failure set when it has fewer than 10 members. Reporting that number as a capability is the single most common eval error in agent benchmarks. Falsifier: if your pass@k equals exactly 1.0, check n−c > k before believing it.

5 · Failure modes #

  • Point estimate without interval. "Pass rate 74%" on 100 items. Symptom: the next run shows 68% and the team argues about model drift instead of randomness.
  • Underpowered A/B. Claiming a 3-point gain on 200 items. Symptom: wins reverse between runs; the team's confidence and the evidence diverge permanently.
  • Unpaired comparison. Two arms scored on different item sets. Symptom: large apparent differences that shrink to nothing when re-scored on the intersection.
  • Censored pass@k. k ≥ n−c, so the estimator returns 1.0. Symptom: perfect scores on hard benchmarks; the number is a sample-size artefact.
  • pass@k where pass^k was needed. Optimising for "any of k succeeds" in an unattended single-shot agent. Symptom: benchmark looks strong, production reliability is pk and collapses on long runs (L82).
  • Non-stratified golden set. Items skewed easy. Symptom: narrow interval around a number that over-predicts production; user complaints do not match the dashboard.
  • Multiple comparisons. Tuning 20 prompt variants and reporting the best. Symptom: the winner does not reproduce; with 20 comparisons at 95%, you expect ~1 false positive by chance alone.
  • Golden-set drift. Items edited between runs. Symptom: score changes you cannot reproduce; version hash absent from the manifest.
  • Train/test leak. The set used for iteration is also the set reported. Symptom: measured gain well above what the final holdout confirms.

7 · Self-check #

Q1. You have 150 items, your system passes 111. Report the result properly and state the smallest effect you could detect.

Reveal answer

p̂ = 111/150 = 0.74. Wilson: 1 + z²/n = 1 + 3.8416/150 = 1.025611; centre (0.74 + 0.012805)/1.025611 = 0.73420; half-width 1.96×√(0.74×0.26/150 + 3.8416/90000)/1.025611 = 1.96×0.036407/1.025611 = 0.06958. Interval [0.664, 0.804], width 0.139 (computed). Report pass@1 = 0.74 [0.664, 0.804], n=150. Detectable effect: an unpaired comparison needs roughly a 14-point separation to be conclusive; a paired design could see far less. Anything smaller is not measurable at this n.

Q2. Do the arithmetic: paired test with b=18 (A fails, B passes), c=6 (A passes, B fails) out of 200 items. Is B better?

Reveal answer

χ² = (18−6)²/(18+6) = 144/24 = 6.0, which exceeds 3.841 — significant at 95%. Net effect: (18−6)/24 = 0.5 of discordant items. On point estimates, A ≈ 0.91, B ≈ 0.97 overall if concordant items split evenly — but the honest statement is about the discordant pairs, because the 176 concordant items carried no information about the difference. Note also that the unpaired view (two 200-item arms) would likely have been inconclusive for this effect size.

Q3. A vendor reports pass@10 = 0.97 with n=10 samples. What exactly is being claimed, and what is wrong?

Reveal answer

They are claiming "at least one of 10 attempts succeeds 97% of the time", estimated from 10 samples per problem. Two problems. First, k=n means the estimator is fully censored: it returns exactly 1.0 whenever c ≥ 1, so a system that gets one problem right out of ten would report pass@10 = 1.000 for that problem. It says nothing beyond "at least one sample succeeded". Second, even a legitimate pass@10 is best-of-10 — a user rerolling 10 times. It tells you nothing about pass^10, which for a p=0.70 system is 0.028. Ask for n, the per-problem sample count, and whether pass^k was measured.

Q4. Diagnostic: two sprint runs of the same unchanged system gave 71% and 78% on 120 items. Is the system drifting?

Reveal answer

Almost certainly not — this is sampling noise. At n=120, p≈0.745, the Wilson interval is [0.660, 0.815] (computed), about 15.5 points wide. Two draws from the same system landing at 0.71 and 0.78 is entirely expected. The diagnostic test for real drift is to compare on matched items: which specific questions changed outcome? If the same items flip, that is system nondeterminism (L94). If different items flip with no pattern, it is sampling variance and you need a bigger n to see anything.

Q5. You need to ship only if the true pass rate exceeds 85%. How many items do you need for the lower confidence bound to be above 0.85 when the observed rate is 0.92?

Reveal answer

Solve for the smallest n where the Wilson lower bound at p=0.92 exceeds 0.85. Computed values: n=50 → 0.8116 (fails), n=60 → 0.8235 (fails), n=100 → 0.850 (exactly at the line), n=200 → 0.874 (passes), n=300 → 0.8837. So you need roughly 150–200 items to have the lower bound comfortably above 0.85 — 100 puts you exactly on the boundary, which is not a gate you can defend. The general principle: gate on the lower bound, and derive n from the decision rule rather than choosing n first and setting the rule afterwards.
