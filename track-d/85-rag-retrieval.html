L85 · Retrieval: hybrid search, chunking, embedding choice

Hybrid retrieval is not "two retrievers are better than one". It works because their failure sets are different — and when both fail on the same query, reciprocal rank fusion hands you a tie that a sort order resolves. The chunker is where most RAG quality is actually decided.

~30 min difficulty ●●●○○ build: chunker + hybrid retriever
BM25 dense retrieval reciprocal rank fusion divergent failure sets chunking strategies tokenizer as hidden variable recall@k ceiling rank ties

1 · Why it exists #

The failure: the answer is in the corpus and retrieval returns nothing useful. A user asks "how do we prove nothing was edited" and the document says "tamper-evident append-only log". Zero shared words. BM25 — a genuinely excellent lexical ranker — scores every document 0.000 and returns an arbitrary ordering. The model then answers from its priors, confidently, with a citation that does not support it.

The mirror failure: the answer has a unique identifier and dense retrieval fuzzes it. A query for "Postgres 14" or an error code or a ticket number should be found by exact match. Embeddings compress specific tokens into a neighbourhood, so PROD-4417 lands near PROD-4427 and the retriever returns the wrong incident report with high cosine similarity and no warning.

These two failures are complementary, which is the entire argument for hybrid. But the complementary argument does not say "fuse the scores" — it says fuse the rankings, because BM25 scores and cosine similarities live on incomparable scales and any weighted sum requires a calibration you do not have.

Retrieval quality is decided at three layers and they are not equally important: chunking (is the answer entirely inside one retrievable unit?), the lexical/semantic split (does at least one retriever score it highly?), and fusion (does the fused ranking preserve the individual wins?). Most teams tune layer three first because it is the most fun and the least important.

2 · The mental model #

Two retrievers with different inductive biases over the same index. BM25 asks "which documents contain these terms, weighted by how rare those terms are". Dense asks "which documents are near the query in a learned metric space". They fail on different queries, and that is the product.

Analogy: two librarians with different search habits

One librarian searches by index terms (exact, unforgiving of synonyms). The other searches by "this feels related" (great with synonyms, unreliable with codes). You ask both and merge their shortlists. Merging positions in each list works; averaging their unrelated confidence scores does not.

Where it breaks

Librarian positions are comparable because each list is complete over the same shelves. Here, if both retrievers return all zeros for a query — as BM25 does above — the "positions" are an arbitrary tie and fusion inherits the tie. Fusion cannot create signal that neither retriever has; it can only combine signal that exists. So a measured hybrid win always comes from queries where at least one retriever ranks the gold chunk highly.

That gives the diagnostic that matters more than fusion tuning: oracle recall@k — the fraction of queries where either retriever puts the gold chunk in its top k. If that number is 0.75, no fusion strategy will get you past 0.75. Chase the missing 0.25 with chunking (is the answer split across a boundary?) before touching the ranker.

3 · The mechanism #

BM25, because every RAG engineer should be able to write it from memory:

score(q,d) = ∑t∈q IDF(t) · f(t,d)(k1+1) / [ f(t,d) + k1(1−b + b·|d|/avgdl) ]    IDF(t) = ln(1 + (N−nt+0.5)/(nt+0.5)) f(t,d) term frequency, |d| document length, avgdl mean length, N documents, nt documents containing t. k1=1.5 controls TF saturation, b=0.75 controls length normalisation. Crucially: if no query term occurs in d, the score is exactly 0.

Then fusion by rank, not by score. Reciprocal Rank Fusion needs no calibration because it discards magnitudes:

RRF(d) = ∑r∈retrievers 1 / (k + rankr(d))      k = 60 (standard) rank is 1-based, and must be competition ranking so tied scores get tied ranks. A document ranked first by one retriever and second by another scores 1/61 + 1/62 = 0.03252; first by both scores 2/61 = 0.03279. The spread between "best possible" and "one retriever missed" is only 0.00027 — tiny margins, which is why ties (and the tie-break rule) dominate the ordering when a retriever has no signal at all (Experiment 2).

The retriever. Note that it records why each chunk was retrieved — that field is what makes a bad answer debuggable.

import math, re from collections import Counter def tok(t): return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", t.lower()) # keep hyphens: "tamper-evident" def bm25(docs, query, k1=1.5, b=0.75): toks = [tok(d) for d in docs] N = len(docs); avgdl = sum(map(len, toks)) / N df = Counter(w for t in toks for w in set(t)) out = [] for t in toks: tf = Counter(t); s = 0.0 for w in tok(query): if not tf[w]: continue idf = math.log(1 + (N - df[w] + 0.5) / (df[w] + 0.5)) s += idf * tf[w] * (k1 + 1) / (tf[w] + k1 * (1 - b + b * len(t) / avgdl)) out.append(s) return out def rank(scores): order = sorted(range(len(scores)), key=lambda i: -scores[i]) r = [0] * len(scores) for pos, i in enumerate(order): r[i] = pos + 1 return r def hybrid(docs, query, dense_scores, k=60): rb, rd = rank(bm25(docs, query)), rank(dense_scores) fused = [(1/(k+rb[i]) + 1/(k+rd[i]), {"doc": i, "via": ("bm25" if rb[i] < rd[i] else "dense" if rd[i] < rb[i] else "tie")}) for i in range(len(docs))] fused.sort(key=lambda x: (-x[0], x[1]["doc"])) # deterministic tie-break return fused

Three implementation notes that are worth more than the algorithm. (1) The tokenizer is a hidden hyperparameter — a naive [a-z0-9]+ splits tamper-evident into two tokens and loses the phrase; keeping hyphens changed which documents BM25 could find at all in Experiment 1. (2) Tie-breaking must be deterministic and documented; without the explicit key=lambda x: (-x[0], doc) the fused order depends on dictionary iteration order and the same query returns different chunks across runs and processes. (3) Record provenance per result (via): when an answer is wrong you need to know whether the chunk came from lexical, semantic, or a tie.

An audit-grade retriever logs, per query: the top-k chunk ids with their source span and content hash, which retriever surfaced each, and the corpus index version. Without the content hash you cannot tell later whether the retrieved text was the text the answer was based on — and with a live index (L97), it very often was not.

4 · Your hands #

Experiment 1 — Catch BM25 returning exactly zero

Eight documents, four queries with known gold chunks. Watch the paraphrase query: BM25 scores every document zero, and the fusion then produces a tie.

import math, re from collections import Counter DOCS = [ ("d0", "SHA-256 hash chain links each event to the previous event"), ("d1", "The promotion gate runs four checks before a patch lands"), ("d2", "Backoff with jitter prevents synchronized retries"), ("d3", "Production database is Postgres 14"), ("d4", "Five deterministic factors score each job posting"), ("d5", "Deduplication drops repeated rows before insert"), ("d6", "Tamper-evident append-only log of every tool call"), ("d7", "Rate limiting caps outbound calls per minute"), ] STOP = {"the","a","an","is","of","to","and","we","do","how","on","in","each","every","before","with","per"} def content(t): return [w for w in re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", t.lower()) if w not in STOP] def bm25(docs, q, k1=1.5, b=0.75): toks = [content(t) for _, t in docs] N = len(docs); avgdl = sum(map(len, toks)) / N df = Counter(w for t in toks for w in set(t)) out = [] for t in toks: tf = Counter(t); s = 0.0 for w in content(q): if not tf[w]: continue idf = math.log(1 + (N - df[w] + 0.5) / (df[w] + 0.5)) s += idf * tf[w] * (k1 + 1) / (tf[w] + k1 * (1 - b + b * len(t) / avgdl)) out.append(s) return out q = "how do we prove nothing was edited" scores = bm25(DOCS, q) for (did, text), s in zip(DOCS, scores): print(f"{did} bm25={s:.3f} {text[:48]}") print("\nall zero?", all(s == 0 for s in scores))

Observed output: every line reads bm25=0.000, and all zero? True. This is not a bug — it is BM25 working exactly as specified, because no query content word occurs in any document ("prove", "nothing", "edited" are absent; "was" is a stopword here). The retrieval system then returns documents in index order, which happens to put d0 (“hash chain”) first — plausibly related, wrong document. This is the case dense retrieval exists for: a semantic model scores d6 (“tamper-evident append-only log”) at 1.000 on the same query. Falsifier: if your BM25 never returns all-zero, your corpus is small and lexically lucky; the failure appears as the corpus grows and vocabulary diverges from user phrasing.

Experiment 2 — RRF ties, and why the tie-break is a correctness issue

Fuse a perfect lexical retriever with the all-zero one. The gold document ties with its neighbours, and the sort order decides the answer.

def rank(scores): # COMPETITION ranking: equal scores get equal ranks. A sort-based rank hides ties. order = sorted(range(len(scores)), key=lambda i: -scores[i]) r = [0] * len(scores) r[order[0]] = 1 for pos in range(1, len(order)): i, prev = order[pos], order[pos - 1] r[i] = r[prev] if scores[i] == scores[prev] else pos + 1 return r def rrf(rl_list, k=60): return [sum(1/(k + rl[i]) for rl in rl_list) for i in range(len(rl_list[0]))] bm25 = [0.0] * 8 # lexical found nothing: everyone rank 1 dense = [0.0] * 6 + [1.0, 0.0] # d6 is the gold chunk rb, rd = rank(bm25), rank(dense) print("bm25 ranks ", rb) print("dense ranks", rd) fused = rrf([rb, rd]) for i in sorted(range(8), key=lambda i: -fused[i]): print(f"doc{i} rrf={fused[i]:.5f} rb={rb[i]} rd={rd[i]}")

Observed output: bm25 ranks [1, 1, 1, 1, 1, 1, 1, 1] and dense ranks [2, 2, 2, 2, 2, 2, 1, 2], then doc6 rrf=0.03279 rb=1 rd=1 followed by doc0 through doc7 all at rrf=0.03252 — seven documents sharing an identical fused score. Only two distinct values exist in the whole ranking. The gold chunk wins correctly (both retrievers agreed it was best), but positions 2–8 are an arbitrary permutation. The critical implementation detail: if you compute ranks with a naive sorted(range(n), key=-score) and assign pos+1, ties are silently broken by index order and you will never see this. You must use competition ranking (equal scores → equal rank) to observe the tie at all — and then you must add a documented tie-break, or the answer depends on document insertion order. Falsifier: shuffle DOCS and re-run; if the order of positions 2–8 changes, your pipeline's answer is a function of index layout, which is a reproducibility defect (L94), not a ranking.

Experiment 3 — Measure a chunker's boundary damage (copy-paste)

Fixed-size chunking splits text on a character budget. Count how often a gold answer spans two chunks — those queries are unretrievable no matter how good the ranker is.

def chunk_fixed(text, size=120, overlap=0): step = size - overlap return [text[i:i+size] for i in range(0, max(1, len(text)), step)] def boundary_damage(text, gold_spans, size=120, overlap=0): # gold_spans: list of (start, end) of the answer text chunks = chunk_fixed(text, size, overlap) # map chunk boundaries back to absolute offsets step = size - overlap starts = list(range(0, max(1, len(text)), step)) spans = [(s, s + size) for s in starts] split = 0 for gs, ge in gold_spans: inside = [sp for sp in spans if sp[0] <= gs and ge <= sp[1]] if not inside: split += 1 return split, len(gold_spans), len(chunks) doc = ("The promotion gate requires four independent checks. " * 3 + "Each check must pass before a patch is accepted for merge. " + "The checks are: build, unit tests, ledger verification, and human sign-off. " * 2) gold = [(170, 230), (290, 380), (440, 470)] for size, ov in ((120, 0), (120, 30), (256, 0), (512, 0)): split, total, nchunks = boundary_damage(doc, gold, size, ov) print(f"size={size:3d} overlap={ov:3d} chunks={nchunks:2d} split_gold={split}/{total}")

Observed output (370-character document, 3 gold spans): size=120 overlap= 0 chunks= 4 split_gold=1/3 · size=120 overlap= 30 chunks= 5 split_gold=1/3 · size=256 overlap= 0 chunks= 2 split_gold=0/3 · size=512 overlap= 0 chunks= 1 split_gold=0/3. Note that adding 25% overlap did not help at all (still 1/3) because the damaged span is longer than 30 characters — overlap only rescues spans shorter than the overlap width. Increasing chunk size fixed it (0/3), but at 512 chars a single chunk is the whole document, which defeats retrieval granularity entirely. The output gives you the retrievability ceiling before any embedding exists: with split_gold=1/3, max recall@k is 2/3 = 0.667 no matter how good the ranker is. Falsifier: if raising overlap to 50% still splits gold spans, the spans are longer than the chunk size — the answer is small-to-big indexing (index small, return parent), not more overlap.

5 · Failure modes #

  • Lexical zero-match on paraphrase. No query term occurs in the corpus. Symptom: BM25 scores all zero; results come back in index order; answers cite plausibly-related-but-wrong chunks.
  • Fuzzy identifier matching. Dense returns a neighbour of an exact code. Symptom: high similarity on wrong document; the correct document is rank 2–3 and never cited. Fix: detect identifier-shaped query tokens and route them to exact-match.
  • Score-averaging instead of rank fusion. BM25 and cosine are summed with hand-tuned weights. Symptom: the weighting changes with corpus size and query length; you re-tune after every index rebuild and never converge.
  • Boundary-split answers. The gold span crosses two chunks. Symptom: recall@k plateaus at some value below 1 no matter what you do to the ranker; both chunks rank mid-list.
  • Order-dependent ties. No deterministic tie-break. Symptom: the same query returns different chunks across runs/processes; evals are flaky (L94).
  • Overlap duplication. 50% overlap surfaces the same passage twice. Symptom: the model repeats itself or treats duplicate evidence as corroboration — effectively halving your context budget.
  • Stale embeddings after model upgrade. Query embedded with model B, index built with model A. Symptom: recall collapses from a specific deploy date; no error, just worse retrieval.
  • Chunking that destroys structure. Tables, code blocks, or YAML split mid-structure. Symptom: retrieved chunks contain syntactically broken fragments; the model hallucinates around the corruption.

7 · Self-check #

Q1. A query returns BM25 = 0 for all 8 documents. Is that a bug? What does RRF do next, and what does that tell you?

Reveal answer

Not a bug — it is BM25 working as specified: no query content term occurs in any document, so every term's contribution is zero. RRF then treats the arbitrary order as a ranking and assigns rank 1 to whatever is first, giving it 1/(60+1) = 0.01639 — the same score every other zero-score document gets from the other retriever. With both retrievers tied, the fused order is iteration order. The lesson: fusion cannot manufacture signal; if neither retriever scored the gold document highly, no fusion strategy helps, and you should be measuring oracle recall@k before tuning fusion at all.

Q2. Compute RRF for a document ranked 1st by lexical and 5th by dense, versus one ranked 4th by both, with k=60. Which wins?

Reveal answer

First: 1/61 + 1/65 = 0.016393 + 0.015385 = 0.031778. Second: 1/64 + 1/64 = 0.015625 × 2 = 0.031250 (verified above). The top-heavy document wins by 0.000528. That is the RRF property that makes it robust: one strong signal plus one weak signal beats two mediocre signals. It also shows the sensitivity — the margins are tiny, so ties and floating-point ordering matter, which is why a deterministic tie-break is mandatory.

Q3. Your recall@10 is 0.62 and oracle recall@10 (either retriever) is 0.81. What do you fix first?

Reveal answer

Fusion — there is 19 points of headroom that pure ranking work can recover, because the gold chunk is in one retriever's top 10 but not in the fused top 10. Investigate: is the fusion weighting one arm too heavily, is k wrong for your rank distributions, or is the dense arm's ANN recall@k the limit (L22)? After that is exhausted, the remaining 19 points need chunking work, since they are cases where neither retriever found the answer — which is a boundary or representation problem, not a ranking problem.

Q4. Diagnostic: retrieval quality dropped sharply at 14:20 with no code deploy. What are the three most likely causes and what field disambiguates them?

Reveal answer

(a) Index rebuild with a changed chunker, (b) embedding model/version change on one side only (query vs index), (c) corpus content change — documents edited or deleted upstream. The disambiguating field is the index version + embedding model id + document content hash, logged per query. With all three you can bisect to the exact change; with none, you are guessing. This is the retention requirement that makes RAG debuggable, and it is cheap: three strings per query.

Q5. Why is a cross-encoder rerank (L86) often a bigger win than tuning the fusion weights?

Reveal answer

Because it changes the kind of evidence rather than its weighting. Fusion only re-orders documents that one of two bi-encoders already surfaced — it cannot promote a document both scored low. A cross-encoder reads (query, document) jointly with full attention, so it can score a low-ranked candidate highly when the pair genuinely matches, recovering cases that no weighting of the two lists could. The cost is latency proportional to the number of candidates reranked, which is why the ordering is: fix chunking → ensure oracle recall → fuse → rerank the top ~50.
