L97 · RAG in production: freshness, drift, index rebuilds

Recall fell 27 points with no deploy. The cause was a query-distribution shift from 80/20 to 50/50 against an index built for the old mix. In production, an index is a versioned snapshot of a world that has since changed, and the drift is usually in the questions, not the documents.

~35 min difficulty ●●●●○ build: index lifecycle plan + drift monitor
index as versioned artifact staleness fraction incremental vs full rebuild query distribution drift eval comparability shadow indexes deletion / GDPR embedding version lock

1 · Why it exists #

The failure: retrieval degrades while every metric you have says nothing changed. Code is unchanged, the model is pinned, the golden set scores the same. But users have started asking about a product line the index barely covers, and recall for those queries is far below the average. Your aggregate recall is dominated by the 80% of queries in the well-covered topic, so it moves by a point or two while the experience for a growing segment collapses.

The second failure is stale documents served confidently. A rebuilds-every-30-days policy in a system with 10,000 daily updates means every document has changed since the last index — the index is a snapshot of a different world, and the model cites it as current.

The third failure invalidates your ability to make any of these claims: you cannot compare a score across index versions. An index rebuild changes what retrieval returns even with identical code, so a score measured before and after a rebuild is a measurement of two different systems. Teams routinely see a score move 7 points after a "routine rebuild", attribute it to variance, and then stop trusting their evals — when the actual cause was an unversioned artifact.

Treat the index like a model: versioned, pinned, and re-baselined on every change. Three numbers must be monitored separately — staleness (how much of the corpus changed since the snapshot), coverage drift (is the query mix moving away from what you indexed?), and index version (which snapshot produced this answer?). Without all three, "retrieval got worse" is unattributable.

2 · The mental model #

An index is a materialized view: a derived artifact that is always behind its source, and whose correctness is measured in time, not in logic. Three clocks are running at once, and they usually have different periods.

ClockChanges atFailure if too slowFailure if too fast
Corpusdocument updates, deletionsstale answers; deleted content still servedembedding cost, rebuild churn
Query mixuser behaviour, product changes, seasonalityrecall drops for growing segments while aggregates look fineconstant golden-set churn, incomparable evals
Embedding modelupgrades, provider changesnever — but mixing versions breaks retrievalfull re-embed cost, downtime

Analogy: a materialized view with a refresh policy

A database materialized view has an explicit refresh interval and staleness bound, and querying it is a considered trade rather than an oversight. An index with a rebuild schedule is exactly this: you are choosing REFRESH COMPLETE EVERY 1 DAY versus REFRESH FAST ON COMMIT, with the cost and staleness implications made explicit.

Where it breaks

Databases track row versions and can tell you exactly which base rows a view reflects. A vector index has no such lineage: a chunk's embedding is a function of the document at some past moment, and nothing records which moment. So staleness is not queryable unless you add a timestamp to every chunk and store it with the embedding — that field is the difference between "assume it's current" and "know it's 8 days old".

The design follows: every chunk carries (doc_id, doc_version_hash, indexed_at). Then three things become possible that otherwise are not — answering "when was this snapshot taken", detecting that a returned chunk disagrees with the live document, and deleting a document's chunks completely when the source is deleted.

3 · The mechanism #

First, staleness. The fraction of the corpus that has changed since the last rebuild is what matters, not the mean age:

stale = min(1, U · R / Ndocs)      mean index age = R / 2 U = updates per day, R = rebuild interval in days, N = corpus size. With U=1000, N=100,000: R=1 → 1.0%, R=7 → 7.0%, R=30 → 30.0%. With U=10,000 (a busy ticket system): R=7 → 70%, R=30 → 100%. The formula makes the policy decision arithmetic rather than taste.

Second, drift. Recall for a topic is capped by how much of that topic is in the index, so a shift in the query mix moves effective recall even when every underlying number is unchanged:

recalleff = ∑t wt · min(1, indext/wt) · cap wt = live query share of topic t, indext = indexed share, cap = the ceiling when coverage is adequate (0.90 here). Indexing an 80/20 mix and then serving a 50/50 mix gives 0.630 instead of 0.900 — a 27-point loss with no code change. Nothing in your system changed; the world did.

Third, rebuild economics, which is what makes the freshness policy defensible:

Cfull = Nchunks · tokens · pembed      Cincr = χ · Cfull χ = daily churn fraction. For 100,000 docs × 3 chunks × 400 tokens at $0.02/1M: C_full = $2.40. Daily full rebuilds are $72/month; daily incremental at 1% churn is $0.72/month — 100× cheaper for the same freshness. The freshness/cost tradeoff is not a tradeoff at all when incremental is available.

The lifecycle manager. Version the index, gate promotion on a shadow comparison, keep the old version warm for rollback.

import hashlib, time def doc_version(doc): return hashlib.sha256(doc.encode()).hexdigest()[:16] class IndexVersion: def __init__(self, version_id, embed_model, created_at, doc_versions): self.id = version_id self.embed_model = embed_model # pins the model; mixing versions breaks retrieval self.created_at = created_at self.doc_versions = doc_versions # doc_id -> version hash at index time self.chunks = {} # chunk_id -> {doc_id, indexed_at, text_hash} def staleness(self, live_docs): # fraction of docs whose live version differs from the indexed version changed = sum(1 for d, v in self.doc_versions.items() if d not in live_docs or doc_version(live_docs[d]) != v) deleted = sum(1 for d in self.doc_versions if d not in live_docs) return {"n_docs": len(self.doc_versions), "changed": changed, "deleted_still_indexed": deleted, "stale_fraction": round(changed / max(1, len(self.doc_versions)), 4)} class Lifecycle: def __init__(self, data_client, embed_model, slo): self.dc, self.model, self.slo = data_client, embed_model, slo self.versions = [] self.live = None def rebuild(self, incremental=True): v = IndexVersion(f"v{len(self.versions)+1}", self.model, time.time(), {}) base = self.live if (incremental and self.live) else None if base: v.doc_versions = dict(base.doc_versions) # carry forward changed = self.dc.changed_since(base.created_at if base else 0) for doc_id, text in changed.items(): v.doc_versions[doc_id] = doc_version(text) for c in chunk(text): cid = hashlib.sha256(c.encode()).hexdigest()[:20] v.chunks[cid] = {"doc_id": doc_id, "indexed_at": v.created_at} # purge chunks of deleted docs -- do not leave them retrievable live = self.dc.all_ids() v.chunks = {c: m for c, m in v.chunks.items() if m["doc_id"] in live} self.versions.append(v) return v def promote(self, candidate): # shadow eval on the SAME golden set before switching traffic shadow = eval_recall(candidate, self.slo["golden_set"]) if shadow < self.slo["min_recall"]: return {"promoted": False, "shadow_recall": shadow} self.live = candidate return {"promoted": True, "shadow_recall": shadow}

Three decisions. (1) embed_model is pinned on the version object — querying a v2 index with a v1 embedding model produces garbage silently, and the version id is what makes the mismatch detectable. (2) Deletion purges chunks: leaving chunks for deleted documents means serving content that no longer exists, and in a regulated setting it means failing a deletion obligation. (3) Promotion is a shadow eval, not a swap — the candidate is scored on the same golden set before traffic moves, and the old version stays available for rollback.

The audit requirement for production RAG: every served answer records the index version and the chunk ids plus their indexed_at timestamps. Then "the model said the wrong thing" can be resolved into: the index was 8 days old, or the chunk came from a document deleted last week, or the version was not the one the eval measured. Without those fields, every RAG incident ends in "retrieval is hard".

4 · Your hands #

Experiment 1 — Staleness is a function of rebuild interval, not of diligence

Fraction of the corpus that changed since the last snapshot, across update rates and intervals.

def stale_fraction(updates_per_day, total_docs, rebuild_days): changed = min(total_docs, updates_per_day * rebuild_days) return changed / total_docs TOTAL = 100_000 print("upd/day rebuild_d mean_age pct_stale") for rate in (10, 100, 1000, 10000): for rd in (1, 7, 30): print(f"{rate:7d} {rd:10d} {rd/2:8.1f}d {stale_fraction(rate, TOTAL, rd):9.2%}")

Observed output (excerpt): 1000 updates/day, 30-day rebuild → 30.00% stale; 10000, 7-day → 70.00%; 10000, 30-day → 100.00%; 1000, 1-day → 1.00%. The important reading is the last column: a 30-day rebuild is fine for a slow-moving corpus (0.30% at 10 updates/day) and catastrophic for a fast one (100% at 10,000). The same policy is correct in one system and wrong in another, which is why the interval must be derived from U/N rather than copied from a blog post. Falsifier: if your actual stale fraction is far below the formula's prediction, your corpus has a concentrated update pattern (a few documents change constantly) — compute it per-document rather than in aggregate, because "5% of docs changed" can still be all the docs that matter.

Experiment 2 — Query drift costs 27 recall points with no code change

Index built on an 80/20 topic mix; serve a live mix that has shifted. Nothing else changes.

INDEX_MIX = {"A": 0.80, "B": 0.20} CAP = 0.90 # recall ceiling when topic coverage is adequate def effective_recall(live_mix, index_mix=INDEX_MIX, cap=CAP): rec = 0.0 for t, w in live_mix.items(): cov = min(1.0, index_mix.get(t, 0.0) / max(1e-9, w)) rec += w * cap * cov return rec for label, mix in (("baseline", {"A":0.80,"B":0.20}), ("mild", {"A":0.65,"B":0.35}), ("even", {"A":0.50,"B":0.50}), ("reversed", {"A":0.20,"B":0.80})): print(f" {label:9s} live={mix} -> recall {effective_recall(mix):.3f}")

Observed output: baseline 0.900 · mild 0.765 · even 0.630 · reversed 0.360. A shift from 80/20 to 50/50 costs 27 points; a full reversal costs 54. And crucially, an aggregate recall metric computed on a fixed golden set would not move at all, because the golden set still reflects the old mix. That is the trap: your eval says nothing changed, and your users say it did. Falsifier: if your golden set is re-sampled from live traffic each quarter, drift does show up — at the cost of comparability across quarters (L88). The honest compromise is a fixed core set for comparability plus a rolling sample for drift detection, reported separately.

Experiment 3 — The index-version comparability trap (copy-paste)

Three scores, two changes bundled. The CIs prove the change is real; they say nothing about which change caused it.

import math def wilson(p, n, z=1.96): d = 1 + z*z/n c = (p + z*z/(2*n)) / d h = z*math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d return c-h, c+h for v, p in (("v1 old index", 0.74), ("v2 new index", 0.81), ("v2 + rerank", 0.86)): lo, hi = wilson(p, 200) print(f" {v:14s} p={p:.2f} CI=[{lo:.3f},{hi:.3f}]")

Observed output: v1 old index p=0.74 CI=[0.675,0.796] · v2 new index p=0.81 CI=[0.750,0.858] · v2 + rerank p=0.86 CI=[0.805,0.901]. The v1 and v2 intervals are disjoint, so the improvement is real. But v2 bundles a new index with unchanged code — and the next row adds a reranker, a second variable. To attribute, run: v1+no-rerank, v2+no-rerank, v2+rerank — one variable per step, each with its own interval. Version the index and treat the version as part of the experiment definition, exactly as you treat a code commit. Falsifier: if v2's interval overlaps v1's, the rebuild produced no measurable change and you should not ship it on a quality argument — ship it (or not) on freshness grounds alone.

5 · Failure modes #

  • Stale index in a fast corpus. 30-day rebuild at 10k updates/day. Symptom: 100% of documents changed since the snapshot; answers cite superseded policy.
  • Deleted content still retrievable. Chunks not purged on source deletion. Symptom: retrieval returns documents that 404; a compliance finding in a regulated setting.
  • Query drift invisible in aggregates. Fixed golden set on a shifting live mix. Symptom: eval flat, user complaints rising; recall for the growing segment far below average.
  • Embedding model mismatch. Query embedded with v2, index built with v1. Symptom: recall collapse from a specific timestamp; no error raised.
  • Unversioned index. Scores compared across rebuilds. Symptom: eval scores move 5–8 points after "routine" rebuilds; nobody can say which version produced which number.
  • Semantic cache serving stale answers. A cache hit returns an answer from before the document changed. Symptom: correct answer available but not served; a cache hit with a high similarity and a stale age.
  • Partial rebuild failure. Rebuild crashes at 60%, old index left half-replaced. Symptom: recall is fine for some topics and zero for others; index metadata shows one version with two states.
  • No rollback path. The only index is the current one. Symptom: a bad rebuild takes the system down until a full rebuild completes, with no way to serve the previous good state.
  • Chunker change bundled with index change. Symptom: recall change unattributable; the golden set had to be re-labelled because chunk ids changed, destroying longitudinal comparison.

7 · Self-check #

Q1. A 250,000-document corpus has 2,500 updates/day. What rebuild interval keeps the stale fraction at or below 5%, and what is the mean index age then?

Reveal answer

Solve U·R/N ≤ 0.05: 2500·R/250000 ≤ 0.05 → R ≤ 0.05×100 = 5 days. So rebuild at least every 5 days, and the mean index age is R/2 = 2.5 days. Check: 2500×5 = 12,500 changed docs out of 250,000 = 5.0%. Note the ratio U/N = 0.01/day means the whole corpus turns over in 100 days, so a monthly rebuild would leave 30% stale.

Q2. Incremental rebuild at 1% daily churn versus a full daily rebuild, for a $3.10 full-rebuild embedding cost. Compute the monthly difference and name the failure mode of the incremental path.

Reveal answer

Incremental: $3.10 × 0.01 = $0.031 per run, $0.93/month daily. Full: $3.10 × 30 = $93/month. Difference $92.07/month for equivalent freshness at 1% churn. The failure modes of the incremental path: (1) deleted documents are not in the change feed, so their chunks linger and get served — you must reconcile deletions explicitly; (2) drift accumulates silently if a change event is missed, so you need a periodic full reconciliation as a safety net; (3) ANN graph quality degrades under many incremental inserts, so plan periodic compaction. Incremental is right, but it needs a reconciliation job, not just a diff.

Q3. Aggregate recall on your fixed golden set is 0.86 and flat for six months, but complaints doubled. Give the diagnostic and the fix.

Reveal answer

The golden set is a fixed historical mix; live traffic has drifted. Diagnostic: segment recall by query topic (or by embedding cluster) and compare each segment's share of live traffic against its share of the golden set. If a segment's traffic share doubled while its recall stayed low, you have the drift signature — and the 0.86 aggregate is an average over the old mix, so it never moves. Fix: sample a rolling golden set from live traffic (with fresh labels) for drift detection, keep the fixed core set for longitudinal comparability, and report both. If a growing segment is under-covered in the corpus, that is a corpus problem, not a reranker problem.

Q4. Diagnostic: a retrieval query returns documents that were deleted last week. Trace the two most likely causes.

Reveal answer

(1) No deletion propagation — the rebuild is incremental and only processes updates/additions, so deleted documents' chunks were never purged. Check deleted_still_indexed from the version's staleness report. (2) Semantic or exact-match cache returning an answer citing a now-deleted chunk, even though the index is clean — check whether the answer's trace shows a cache hit and its age. Both are freshness failures with different fixes: (1) requires purge-on-delete plus a periodic full reconciliation; (2) requires cache entries to carry the index version and be invalidated on rebuild.

Q5. Why must the embedding model be pinned per index version rather than configured globally?

Reveal answer

Because a query embedded with model B against vectors from model A is a silent failure: both vectors are valid float arrays of the expected dimension (if the dimension matches), so nothing errors, but the similarity scores are meaningless. Pinning the model on the version object makes the mismatch detectable before serving — you compare the query's model id against version.embed_model and refuse. A global config cannot express this, because during a migration both models are legitimately in use: new documents with B, old ones with A, and the only safe policy is to serve queries through a matching index version until the backfill completes.
