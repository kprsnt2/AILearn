TRACK D · AGENTS, RAG, EVALS, PRODUCTION

L99 · Capstone: ship an audited autonomous agent

"Audited" is not an adjective you apply to a system; it is a bundle you produce. 16 criteria, each naming an artifact, a check, and a pass condition — and a reviewer workflow that rejects on a missing artifact without ever discussing whether the agent is good.

~45 min difficulty ●●●●● build: the acceptance bundle + reviewer script
acceptance criteria evidence bundle self-verifying SEAL one variable per change adversarial oracle suite claim–oracle join reviewer workflow reject-on-absence

1 · Why it exists #

The failure this capstone is designed to prevent: the demo was convincing and the review was a conversation. Someone watched the agent run, asked a few questions, was satisfied, and approved it. No artifact was produced that a second reviewer, six months later, could use to check the same claims. When the agent later produces a wrong answer in a way nobody predicted, there is no baseline to compare against, no trace to inspect, and no way to tell whether it was always broken.

The second failure is the inverse: the review never ends because every criterion is a judgement. "Is the eval good enough?" "Are the tests comprehensive?" These questions have no terminating condition, so approval becomes a matter of who is in the room.

A capstone is where these two problems meet, and the resolution is the same as everywhere else in this track: replace judgement with recomputation. Every criterion must name an artifact whose correctness is checkable by a script that does not trust any number the team reported. Then acceptance is: is the bundle complete, and does it verify?

Acceptance is an AND over 16 completeness checks plus a recomputation pass. The reviewer's first act is not to read the results, it is to recompute the SEAL and the ledger. If either fails, the submission is rejected regardless of how good the agent is — because the claim "the agent is good" is unsupported until the record is trustworthy. Reject-on-absence, not reject-on-disagreement.

2 · The mental model #

Five groups, arranged so that each group depends on the previous one being trustworthy. The ordering is the design:

GroupEstablishesDepends onCriteria

Analogy: a clinical trial submission

A trial submission is a bundle with a pre-registered protocol (the task spec and metric), a dataset (golden set), a statistical analysis plan (the CI rule), an independent monitoring record (the ledger), and an audit trail. The regulator does not assess whether the drug seems good; it checks whether the submission is complete and internally consistent.

Where it breaks

Trial submissions are reviewed by an institution with subpoena power and the ability to re-run analyses on raw data. An internal reviewer has neither, which is why E1 and E2 matter more here than in a trial: the bundle must be self-verifying, so that its integrity does not depend on trusting the submitter. The seal is the substitute for institutional authority.

The dependency ordering also gives the review a direction: if A fails, B through E are uninterpretable, because a measurement problem makes every downstream claim meaningless. Reviewers should work top-down and stop at the first group that fails.

The reviewer's script. This is the whole review process — note it never asks whether the agent is good.

A broken seal rejects before anything is read. if "SEAL" in bundle and not seal_recomputes(bundle): return {"accept": False, "stage": "integrity", "reason": "SEAL mismatch - bundle was modified"} missing = [cid for cid, _, art, _, _ in criteria if art not in bundle] if missing: return {"accept": False, "stage": "completeness", "missing": missing} # Step 2: re-derive every reported number from per-item artifacts. for cid, _, art, check, _ in criteria: if check.startswith(("recompute", "wilson", "mcnemar")): if not rederives(art, bundle): return {"accept": False, "stage": "recomputation", "failed": cid} # Step 3: adversarial suites must actually run and pass. for cid in ("B1", "C2", "D3"): if not run_suite(cid, bundle): return {"accept": False, "stage": "adversarial", "failed": cid} return {"accept": True, "stage": "accepted", "criteria": len(criteria)}

The ordering of the review stages is the whole mechanism. Integrity before completeness before recomputation before adversarial re-running. Checking completeness first wastes effort on a bundle that was edited; re-running suites before checking the seal wastes effort on results that may have been fabricated. Each stage is a cheaper filter than the next, and each one can only reject.

The capstone's own audit question, applied to the bundle: can a stranger re-derive every number you reported, using only files in this directory? If any number requires a dashboard, a database, or your memory, the bundle is a summary — and a summary of an autonomous agent's work is precisely the artifact that overclaims.

4 · Your hands #

Experiment 1 — Completeness is an AND, and one absence rejects

The completeness check over the 16 criteria, with one artifact removed at a time. Every removal must flip the verdict.

CRITERIA = [ ("A1","task_spec.md"), ("A2","golden_set/items.jsonl"), ("A3","baseline_report.json"), ("A4","eval_report.json"), ("B1","oracle/oracle_test_report.json"), ("B2","rake_report.json"), ("B3","seed_audit.json"), ("C1","safety/capability_inventory.json"), ("C2","safety/injection_test_report.json"), ("C3","safety/blast_radius.md"), ("D1","traces/trace_sample.jsonl"), ("D2","slo_report.json"), ("D3","failure_injection_report.json"), ("E1","ledger_verify.txt"), ("E2","SEAL"), ("E3","change_log.jsonl"), ] ALL = {a for _, a in CRITERIA} def completeness(bundle): missing = [cid for cid, art in CRITERIA if art not in bundle] return {"n": len(CRITERIA), "complete": not missing, "missing": missing} print("full bundle:", completeness(ALL)) for drop in ("SEAL", "rake_report.json", "seed_audit.json"): print(f" minus {drop:34s} -> {completeness(ALL - {drop})}")

Observed output: full bundle: {'n': 16, 'complete': True, 'missing': []}; minus SEAL → complete=False, missing=['E2']; minus rake_report.json → missing=['B2']; minus seed_audit.json → missing=['B3']. Every removal flips the verdict, which is the property that makes this a gate rather than a wish list. Note there is no weighting and no score: 15 of 16 is a rejection. That is correct for a submission whose value depends on being complete — a bundle missing its ledger verification cannot be partially trusted. Falsifier: if you find yourself arguing that a particular artifact is optional, that is the signal to either remove the criterion entirely (and say so) or restore the artifact — not to soften the check.

Experiment 2 — The reviewer's stages reject in the right order

Four bundles: one intact, one with a broken seal, one complete but with a number that does not recompute, one complete and consistent. Order matters because a cheap check should reject before an expensive one runs.

def review(bundle, seal_ok=True, rederives_ok=True, suites_ok=True): if "SEAL" in bundle and not seal_ok: return {"accept": False, "stage": "integrity"} missing = [cid for cid, art in CRITERIA if art not in bundle] if missing: return {"accept": False, "stage": "completeness", "missing": missing} if not rederives_ok: return {"accept": False, "stage": "recomputation"} if not suites_ok: return {"accept": False, "stage": "adversarial"} return {"accept": True, "stage": "accepted"} print("intact ", review(ALL)) print("seal broken ", review(ALL, seal_ok=False)) print("missing E1 ", review(ALL - {"ledger_verify.txt"})) print("bad number ", review(ALL, rederives_ok=False)) print("suite fails ", review(ALL, suites_ok=False))

Observed output: intact → {accept: True, stage: 'accepted'}; seal broken → stage 'integrity'; missing E1 → stage 'completeness', missing=['E1']; bad number → stage 'recomputation'; suite fails → stage 'adversarial'. Five dispositions, five distinct stages, each naming where the submission failed. That is the difference between "rejected" and "rejected because the ledger verification artifact is absent" — the latter is actionable in one line, the former starts a meeting. Falsifier: if a bundle with a broken seal reaches the recomputation stage, your reviewer is wasting expensive work on a record that may have been edited — the seal check must come first, always.

Experiment 3 — Recompute the SEAL over the whole bundle (copy-paste)

The integrity check a reviewer runs before reading anything. Two bundles, one with a single artifact swapped.

import hashlib, json def canon(o): return json.dumps(o, sort_keys=True, separators=(",",":")) def seal(manifest_hash, chain_head, artifact_hashes): return hashlib.sha256(canon([manifest_hash, chain_head, sorted(artifact_hashes)])).hexdigest() MANIFEST = "8f3a1c2e9b04" HEAD = "26e92581b66c" ARTIFACTS_OK = ["a1", "b2", "c3", "d1", "e1"] ARTIFACTS_BAD = ["a1", "b2", "c3", "d1", "eX"] # one swapped s_ok = seal(MANIFEST, HEAD, ARTIFACTS_OK) s_bad = seal(MANIFEST, HEAD, ARTIFACTS_BAD) print("seal (intact) ", s_ok[:20]) print("seal (1 swap) ", s_bad[:20]) print("matches ", s_ok == s_bad)

The seals differ, so a reviewer comparing the recorded SEAL against the recomputation detects the swap without reading a single report. That is the property that makes E2 cheap and decisive: one hash comparison gates the entire bundle, and it costs microseconds. Note the seal covers artifacts sorted, so listing order cannot produce a false mismatch. Falsifier: if swapping an artifact does not change the seal, the artifact hashes were not included in the input — check that the seal covers manifest_hash, chain_head, and all artifact hashes.

5 · Failure modes #

  • Review by demo. Approval granted after watching a run. Symptom: no bundle exists; the approval is unreproducible a month later.
  • Partial bundle accepted. 14 of 16 criteria. Symptom: the missing two are exactly the ones that would have caught the later incident.
  • Numbers reported, never recomputed. The reviewer reads the report and trusts it. Symptom: a baseline CI that cannot be derived from the per-item outcomes because the outcomes were discarded.
  • Adversarial suites not re-run. A test report is submitted as evidence. Symptom: the suite would fail today; it was passing when the report was generated.
  • Seal computed over a summary. Only the headline verdicts are hashed. Symptom: a report can be rewritten while the seal still matches.
  • Bundled changes. E3's one-variable rule violated. Symptom: a quality delta attributable to nothing specific (L97, L88).
  • Bundle built after the fact. Artifacts assembled retroactively from dashboards. Symptom: the ledger's timestamps do not line up with the reported run window; the manifest was written last.
  • Acceptance with a waiver. "We'll add the injection report next sprint." Symptom: the waiver list grows monotonically; the gate is decorative after the second waiver.

7 · Self-check #

Q1. Why does the reviewer check the SEAL before checking completeness?

Reveal answer

Because integrity is a precondition for the meaning of everything else. If the bundle was modified after sealing, then artifact presence is not evidence that the artifact is the one the run produced — the completeness check would be reading a possibly-edited table of contents. The seal is also the cheapest check (one hash recomputation over a small input), so putting it first is both logically correct and efficient: it rejects tampered bundles before the reviewer spends time on them. Order by (logical priority, then cost), which in this case agree.

Q2. A bundle is complete but its baseline_report.json claims p=0.74, CI=[0.66, 0.81] at n=150. Recompute and say whether the CI is plausible.

Reveal answer

Wilson at p=0.74, n=150: centre 0.7342, half-width 0.0696, so the CI should be approximately [0.664, 0.804]. The claimed [0.66, 0.81] is close and would pass a recomputation tolerance of ~1%, which is why D2's "values recompute within 1%" condition is the right test. If the claimed CI were, say, [0.70, 0.78] — much narrower than Wilson allows at that n — the reviewer would reject at the recomputation stage: the interval is inconsistent with the sample size, so either n is misreported or the interval was not computed from the outcomes.

Q3. Why is change_log.jsonl (E3) required when each individual eval report already carries its own numbers?

Reveal answer

Because a sequence of individually valid eval reports does not establish that the deltas are attributable. Two consecutive reports can both be correct and both show a 6-point gain, while the second one changed the index and the reranker (L97) — so the second 6 points belong to neither change. E3 forces each delta to touch exactly one pinned manifest field, which is what makes the history a chain of causal claims rather than a list of snapshots. Without it, a reviewer can verify every number and still be unable to say which intervention produced the improvement.

Q4. Diagnostic: your bundle passes all 16 criteria and the agent still fails in production on a class of input not in the golden set. What does that tell you about the acceptance gate?

Reveal answer

That the gate verified process completeness, not coverage. A complete bundle can be complete about the wrong distribution: A2 requires ≥150 stratified items, and if the stratification missed a whole input class, all downstream criteria are satisfied while the system is blind to that class. The fix is not to add a 17th check but to make coverage a first-class part of A1 and A2 — the task spec must enumerate the input classes, and the golden set must have items in each. Then the post-incident action is concrete: the failing input class becomes a new stratum, and the bundle's A2 hash changes, forcing a re-baseline.

Q5. Why does the reviewer re-run the adversarial suites rather than accept the submitted test report?

Reveal answer

Because a test report is an assertion about a past execution, and the bundle is meant to eliminate assertions in favour of recomputations. Three concrete reasons: the report may have been generated against a different code commit (B1 requires the oracle code hash be pinned precisely so this is checkable); the suite may have been passing then and failing now if any pinned artifact changed; and a report is the cheapest thing to fabricate. Re-running is what makes the bundle self-verifying — the same principle as recomputing the ledger instead of trusting a stored "verified: true" flag (L95).
