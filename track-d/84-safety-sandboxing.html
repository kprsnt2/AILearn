L84 · Sandboxing and permission models — the blast radius question

"Do not touch production" is not a restriction, it is a sentence. A permission model is a statement about reachable damage: what a compromised or confused agent can destroy before anything notices. Two capabilities held by one agent can be worse than both halves held separately.

~30 min difficulty ●●●●○ build: scope guard
blast radius capability set vs instruction least privilege lattice exfiltration pair separate privilege that separates irreversibility weighting action-before-decision taint tracking

1 · Why it exists #

The failure that forced sandboxing into agent architecture: the agent did exactly what it was told, and the consequences were unrecoverable. Not maliciously. It read a poisoned document (L93), followed an instruction in it, ran a script, and deleted a table. Every step was permitted by the prompt. Nothing in the system disagreed, because the only "restriction" was a sentence in a system prompt — and a sentence is not a mechanism.

The property of an instruction is that it is advice to a stochastic process. The property of a capability is that it is enforced by an interpreter that does not care what the model thinks. An agent with filesystem write access and no sandbox has, in effect, one capability: "any damage reachable from a shell". The prompt is not part of the permission model.

The second failure is subtler and lives in the composition of grants. Giving one agent "read secrets" is a bounded risk. Giving another "network egress" is a bounded risk. Giving both to agents that share a workspace produces exfiltration — a capability neither has alone. This is the classic confused-deputy / ambient-authority problem, and it means permission decisions cannot be made one grant at a time.

Design the permission model by asking a single question, and ask it before the prompt: if this agent turned fully adversarial at turn t, what is the complete set of damage reachable with its current capabilities, and how long until someone notices? Everything else — tool allow-lists, sandbox flags, approval gates — is machinery for making that set small and that latency short.

2 · The mental model #

A permission model is a pair (capability set, boundary). The capability set says what verbs over what resources are possible. The boundary says what state the agent can share with anything else. Both are required: a minimal capability set with a shared workspace is not minimal, because the workspace is itself a channel.

CapabilityReachable resources (example)Irreversible?Blast units
read:repo1,000 filesno1,000
write:repo1,000 filesno (git revert)2,000 total
fetch:net50 endpointsno2,050 total
read_secret20 secretsno, but un-undoable once leaked+20
deploy:prod_db5 prod objectsyes+50 (weighted ×10)
fullall of the aboveyes2,120

Blast units are ∑ reachable_resources × (10 if irreversible else 1). The weighting is not a measurement — it encodes the one asymmetry that matters: an irreversible action's cost is unbounded because you cannot undo it, while a reversible one's cost is bounded by the work of reverting.

Analogy: capabilities as keys, not instructions

A server room does not obey a sign saying "do not touch the power switch". It locks the door and gives out keys. The lock does not evaluate intent, cannot be argued with, and fails closed. Capability-based security is this: the agent's ability is a key it either holds or doesn't.

Where it breaks

A key grants all-or-nothing access to a room; capabilities can be composed across agents. Two agents each holding one key can, between them, open a door neither could open alone — if they can talk. An agent's output channel is a communication channel, so separate privilege only works when the boundary is real (separate filesystem, separate process, no shared writable medium). This is the one place the key analogy actively misleads.

Which gives the operational rule for separate privilege: two agents with different grants must not share a writable medium. If they do, treat them as one agent with the union of capabilities — and compute the blast radius of the union, because that is the real number.

3 · The mechanism #

Blast radius formally:

BR(A) = ∑c ∈ C(A) ∑r ∈ match(c) w(r) · ι(c) C(A) = capabilities of agent A, match(c) = resources the capability can touch, w(r) = resource weight, ι(c) = 10 if the verb is irreversible else 1. Report BR with the observation latency — damage reachable in a minute with instant detection differs from damage reachable for a day.

The composition rule, which is where naive least-privilege fails:

BR(A ∪ B) ≥ BR(A) + BR(B)      and in general   BR(A ∪ B) > BR(A) + BR(B) The union is super-additive when a capability pair creates a new action. The canonical pair is read_secret + fetch:net = exfiltration. Another is write:repo + deploy:prod_db = destruction, where the write smuggles the change past review and the deploy runs it.

The guard. Enforced at the tool boundary so the model's intent is irrelevant.

import fnmatch class Denied(Exception): pass class Capability: def __init__(self, verb, resource, irreversible=False, max_uses=None): self.verb, self.resource = verb, resource self.irreversible, self.max_uses = irreversible, max_uses self.uses = 0 class ScopeGuard: """Every tool call passes through here. Deny by default.""" def __init__(self, caps, taint_sources=()): self.caps = caps # list[Capability] - the ONLY allowed actions self.taint_sources = taint_sources # e.g. ("web:fetch",) untrusted input channels self.log = [] # append-only; hash-chain (L90/L94) def check(self, verb, resource, tainted=False): # 1. explicit deny always wins for c in self.log if False else []: pass # 2. must be in the capability set ok = None for c in self.caps: if c.verb == verb and fnmatch.fnmatch(resource, c.resource): ok = c; break if ok is None: raise Denied(f"no capability for {verb}:{resource}") # 3. taint rule: an irreversible action on tainted input is refused if tainted and ok.irreversible: raise Denied(f"irreversible {verb} on tainted input") # 4. usage budget if ok.max_uses is not None and ok.uses >= ok.max_uses: raise Denied(f"{verb}:{resource} exhausted {ok.max_uses} uses") ok.uses += 1 self.log.append((verb, resource, tainted, ok.irreversible)) return True

Four decisions inside check are the whole design. (1) Deny by default: an unlisted verb is refused, so adding a tool to the registry does not silently add a capability. (2) Glob resources, not verbs: write:repo/* is a capability; write is not. (3) The taint rule: an irreversible action whose inputs derive from an untrusted channel is refused regardless of what the model believes — this is the single highest-value rule against prompt injection, because it makes the injection unable to act even if it successfully persuades. (4) Usage budgets: irreversible capabilities get a small max_uses, so a confused agent exhausts the allowance instead of the system.

The exfiltration pair deserves its own check, because it is invisible in either grant alone:

forbidden pairs: { read_secret, fetch:net }    { write:repo*, write:net }    { write:prod*, deploy:prod* } Check the conjunction at grant time, not at call time. A pair check is one line of code and catches the composition bug that per-capability review structurally cannot see.

The audit evidence for a sandbox is not a configuration diff — configs drift. It is a capability inventory per agent per run, recorded in the ledger, plus the count of denied calls. A reviewer should be able to answer: what could this specific run have damaged? Denials are signal, not noise: a run with 40 denials is a run where the model was trying something outside its mandate, and that pattern is worth alerting on before it becomes the run with zero denials and one incident.

4 · Your hands #

Experiment 1 — Compute blast radius for real capability sets

Weighted reachable damage per grant. The interesting column is irrev, not the raw count.

RESOURCES = {"repo": 1000, "secrets": 20, "prod_db": 5, "net": 50} def blast(caps): # caps: list of (verb, resource, irreversible) return sum(RESOURCES[r] * (10 if irrev else 1) for _, r, irrev in caps) CAP_SETS = { "read_only": [("read", "repo", False)], "editor": [("read", "repo", False), ("write", "repo", False)], "editor_plus_net": [("read", "repo", False), ("write", "repo", False), ("fetch", "net", False)], "deployer": [("read", "repo", False), ("write", "repo", False), ("fetch", "net", False), ("deploy", "prod_db", True)], "auditor_only": [("read", "repo", False), ("read_secret", "secrets", False)], "full": [("read", "repo", False), ("write", "repo", False), ("fetch", "net", False), ("read_secret", "secrets", False), ("deploy", "prod_db", True)], } for name, caps in CAP_SETS.items(): print(f"{name:18s} caps={len(caps)} blast={blast(caps):5d} " f"irrev={any(c[2] for c in caps)}")

Observed output: read_only caps=1 blast=1000 irrev=False · editor caps=2 blast=2000 · editor_plus_net caps=3 blast=2050 · deployer caps=4 blast=2100 irrev=True · auditor_only caps=2 blast=1020 · full caps=5 blast=2120 irrev=True. Note editor_plus_net is only +50 over editor — network access looks cheap. It is not: the cost of network access is that it turns any other capability into an exfiltration channel, which is not visible in its own blast number. That is the lattice effect, and it is why Experiment 2 exists. Falsifier: if write:repo is genuinely irreversible in your setup (no VCS, no backups), it should be weighted ×10 and the ranking changes completely — check that before trusting these units.

Experiment 2 — Find the super-additive pairs

Every pair of capabilities; flag the conjunctions that create an action neither half has.

from itertools import combinations CAPS = [("exec", "repo", False), ("read", "repo", False), ("write", "repo", False), ("fetch", "net", False), ("read_secret", "secrets", False), ("deploy", "prod_db", True)] for a, b in combinations(CAPS, 2): va, ra = a[0], a[1] vb, rb = b[0], b[1] tag = None if {ra, rb} == {"secrets", "net"}: tag = "EXFILTRATION (secret + outbound net)" if "prod_db" in {ra, rb} and ({va, vb} & {"write", "exec"}): tag = "DESTRUCTION (write/exec + prod)" if {va, vb} >= {"read", "write"} and ra == rb == "repo": tag = "SELF-MODIFICATION (read+write repo)" if tag: print(f" {va}:{ra:9s} + {vb}:{rb:9s} -> {tag}")

Observed output (four flagged pairs): exec:repo + deploy:prod_db → DESTRUCTION · read:repo + write:repo → SELF-MODIFICATION · write:repo + deploy:prod_db → DESTRUCTION · fetch:net + read_secret:secrets → EXFILTRATION. The self-modification pair is the one people miss: read+write on the repo means the agent can edit the code that will run the next verification step, which invalidates the oracle (L76). Once an agent can modify what judges it, no downstream evidence is trustworthy. Falsifier: if your repo writes are gated by human review before any execution, self-modification is bounded — verify that the gate is on execution, not on merge, or the pair still holds.

Experiment 3 — Deny-by-default guard test (copy-paste)

Six calls against a three-capability guard. The two Denied exceptions are the product.

import fnmatch class Denied(Exception): pass class Cap: def __init__(self, verb, res, irrev=False, max_uses=None): self.verb, self.res, self.irrev = verb, res, irrev self.max_uses, self.uses = max_uses, 0 class Guard: def __init__(self, caps): self.caps, self.log = caps, [] def check(self, verb, res, tainted=False): hit = next((c for c in self.caps if c.verb == verb and fnmatch.fnmatch(res, c.res)), None) if hit is None: raise Denied(f"no cap {verb}:{res}") if tainted and hit.irrev: raise Denied(f"irrev on tainted {verb}") if hit.max_uses is not None and hit.uses >= hit.max_uses: raise Denied(f"budget exhausted {verb}:{res}") hit.uses += 1; self.log.append((verb, res, tainted)); return True g = Guard([Cap("read", "repo/*"), Cap("write", "repo/src/*"), Cap("deploy", "prod/app", irrev=True, max_uses=1)]) tests = [("read", "repo/README.md", False, "allow"), ("read", "repo/.env", False, "allow"), ("write", "repo/src/a.py", False, "allow"), ("write", "repo/ci.yml", False, "deny: scope"), ("deploy", "prod/app", True, "deny: taint"), ("deploy", "prod/app", False, "allow"), ("deploy", "prod/app", False, "deny: budget"), ("delete", "prod/app", False, "deny: no cap")] for verb, res, tainted, expect in tests: try: g.check(verb, res, tainted); got = "allow" except Denied: got = "deny" print(f"{verb:7s} {res:16s} tainted={str(tainted):5s} expect={expect:18s} got={got}")

Observed output: allow, allow, allow, deny (ci.yml outside repo/src/*), deny (irreversible on tainted), allow (clean deploy), deny (budget exhausted at 1), deny (no capability for delete). Two design points are being demonstrated: the write scope is narrower than the read scope (repo/src/* vs repo/*), so the agent cannot edit CI configuration — that is the self-modification pair being cut; and the deploy capability is single-use, which converts a confused agent into a failed call rather than a second deployment. Falsifier: if read repo/.env should be denied, the guard is correct and your resource taxonomy is wrong — secrets inside a readable repo means the secret capability boundary is fictional, and you must move secrets out of the repo path before the model means anything.

5 · Failure modes #

  • Prompt-as-permission. Restrictions live in the system prompt. Symptom: injected content (L93) produces an action outside the stated scope; the model "did what it was told" by someone else.
  • Allow-by-default registry. Tools added to a registry are callable by every agent. Symptom: capability inventory grows without any grant event; blast radius drifts upward with no config change.
  • Shared-workspace privilege merge. Two agents with different grants write to the same directory. Symptom: an action that requires the union of two grants succeeds; the ledger shows one agent's read and another's write.
  • Exfiltration pair. Secret read + network egress in one agent (or in two sharing a workspace). Symptom: outbound requests whose payload correlates with secret content; usually found after the fact.
  • Self-modification. Agent can write the file that runs its own verifier. Symptom: the oracle starts passing suspiciously; test files are modified in the same run they are used to verify.
  • Irreversible action without taint check. Deploy/delete fires on content from an untrusted source. Symptom: an irreversible event whose input trace includes a fetch from an untrusted host.
  • Silent denial. Denied calls are swallowed and the agent proceeds. Symptom: the run "succeeds" with missing work; denial counts are absent from the trace. Denials must be loud and counted.
  • Sandbox escape by tool composition. Each tool is scoped, but chaining them (write a script, then execute it) regains full capability. Symptom: exec present at all — it collapses every other restriction into one.

7 · Self-check #

Q1. Why is a system-prompt restriction not a security boundary?

Reveal answer

Because it is processed by the same stochastic mechanism it is trying to constrain. It competes for attention with everything else in context, it can be overridden by injected content that arrives later in the context, and it cannot be verified after the fact. A capability is enforced by code the model does not control. The test: remove the model entirely and ask whether the restriction still holds for an arbitrary actor with the same tool access. If not, it is not a boundary.

Q2. Agent A can read 20 secrets. Agent B can reach 50 network endpoints. Separately their blast is 70 units. Why can the union be far worse, and what makes separation real?

Reveal answer

Because "read secret" plus "send to network" is an exfiltration action neither capability provides alone — the damage is unauthorized disclosure of the 20 secrets, whose cost is not bounded by their count. The union's blast is not 70; it is the entire secret set, permanently. Separation is real only if the two agents cannot exchange data. Concretely: separate filesystems, no shared writable volume, no shared network channel, no shared database. If they share a workspace, model them as one agent with the union — because that is what they are.

Q3. Your agent has exec on the repo. Compute the effective blast radius and say what you would do.

Reveal answer

With exec, every other restriction in the same sandbox is moot: the agent can read any file the process can read, write any path the process can write, and reach any host the process can reach. The effective blast radius is not the sum of the listed capabilities — it is bounded only by the process's own permissions. Remedy: either remove exec and express actions as typed tools, or run exec inside a genuinely isolated container (own filesystem namespace, no credentials, restricted egress) whose own permission set is the blast radius. Never treat exec as one capability among several.

Q4. Diagnostic: a run completes with all green checks, but a secret appears in an outbound request log. Where do you look first, and what two fields would have caught it earlier?

Reveal answer

First, the capability inventory for that run: which agent held both secret-read and network-egress (possibly across a shared workspace). The two missing trace fields are (a) per-call taint status — whether the argument data derives from secret or untrusted sources, and (b) the payload-to-source correlation on outbound calls (a hash of the outbound body checked against known secret values). With those, the exfiltration is detectable at call time and the guard's taint rule refuses it, rather than being reconstructed from egress logs afterwards.

Q5. Why does the "read+write repo" pair invalidate your oracle even though neither capability alone is dangerous?

Reveal answer

Because the oracle (tests, lint, a verifier script) lives in the repo. If the agent can write anywhere in the repo, it can modify the thing that judges it — so a passing oracle no longer means the work is correct, and every downstream claim inherits that doubt. In L76 terms, the agent has captured settle(). The fix is structural: the verification harness must live outside the agent's writable scope, and its hash must be recorded in the ledger so that a modified verifier is detectable rather than merely possible.
