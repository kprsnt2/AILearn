L86 · Reranking, query expansion, multi-hop, HyDE

A reranker buys precision and pays in latency, linearly in the number of candidates you feed it. The curve saturates hard: going from 20 to 100 candidates costs 5× the latency for +6.6 precision points, and from 50 to 100 it costs 2× for +0.5. The break-even is a number, not a preference.

~30 min difficulty ●●●●○ build: reranker eval + candidate-count study
bi-encoder vs cross-encoder candidate depth N latency-precision frontier query expansion HyDE multi-hop decomposition recall ceiling vs precision reranker in the loop

1 · Why it exists #

The failure: the right document is at rank 11 and you show the model 8. A bi-encoder embeds query and document independently, so it can never see that a passage containing the answer is a good match — it only knows that the two vectors point roughly the same way. The gold chunk sits in the top-50 but out of the top-8, and the model answers from the eight plausible-but-wrong chunks.

The fix is a cross-encoder: read the (query, passage) pair together with full attention, produce a relevance score. That is much more accurate and much more expensive — you cannot precompute anything, so cost is Θ(N) forward passes per query. Which makes reranking a budget allocation problem: how many candidates N do you pay to rescore, given a latency budget and a precision target?

The second failure is that reranking cannot fix a missing document. If recall@N is 0.62, then 38% of queries have the answer outside the candidate set and no reranker can recover them. Teams routinely add a reranker, see a modest improvement, and conclude reranking is overrated — when the real constraint was candidate-set recall, which requires query expansion or multi-hop decomposition, not a better ranker.

Ask which quantity is binding before choosing a technique. If recall@N is low, no reranker helps — fix candidate generation (expand the query, decompose the question, retrieve from more sources). If recall@N is high but precision@k is low, a reranker is exactly the right tool — and then choose N from the latency budget using the diminishing-returns curve, not from a blog post.

2 · The mental model #

Two-stage retrieval is a recall-then-precision pipeline, and the stages have completely different cost structures:

StageSeesCost per queryStrengthWeakness
Bi-encoder (dense) / BM25query and doc separatelyO(1) query encode + ANN lookup over the whole corpusrecall at scale; can search 106 docscannot model fine-grained interaction
Cross-encoder rerankerquery and doc jointlyO(N) forward passes over N candidatesprecise relevance orderingexpensive; needs a candidate set first
LLM listwise rerankall candidates in one promptone large call; context-boundreasoning about relevanceposition bias (L89), truncation past ~20 docs

Analogy: a stadium search then a panel interview

Stage one is a fast filter that narrows a million applicants to two hundred — cheap per applicant, coarse. Stage two is a panel interview: expensive per candidate, but it reads the whole resume and asks questions. You would not interview the whole stadium, and you would not hire from the filter alone.

Where it breaks

A panel interview can only assess people who reached it — it cannot rescue an applicant the filter excluded. Same here: the reranker's input set is a hard ceiling on achievable recall, and a reranker that is highly confident about the wrong 20 candidates is worse than no reranker, because it suppresses the uncertainty that would have made you widen the search.

Query expansion and HyDE attack stage one. Expansion rewrites one query into several (synonyms, sub-questions) and unions the candidate sets, raising recall@N at the cost of m retrieval calls. HyDE (hypothetical document embeddings) asks the model to write a plausible answer and retrieves with that instead of the question — useful because answers resemble documents more than questions do, and dangerous because a hallucinated answer drags retrieval toward the hallucination.

Multi-hop is a different animal: the answer requires chaining (A names B, B's record names C). No single query retrieves all three hops, so the pipeline must iterate — and each hop's error compounds (L82).

3 · The mechanism #

The two curves that decide everything. Candidate-set recall rises with N and saturates; the reranker's precision rises with N and saturates faster. Their product is what you actually get.

R(N) = Rmax(1 − e−N/k0)      P(N) = p0 + (pmax − p0)(1 − e−N/n0)      L(N) = N · c R(N) = probability the answer is anywhere in the top N (the ceiling), P(N) = precision of the final top-k after reranking, L(N) = added latency, c = per-candidate reranker cost. All three are measured, not assumed. The optimisation is: maximise P subject to L(N) ≤ budget.

The marginal return, which is the number to look at:

ΔP per 10 extra candidates = [P(N+10) − P(N)] × 100 points This derivative collapses fast. With p0=0.55, pmax=0.90, n0=12: N=10→20 gains 8.60 pts, 20→30 gains 3.74, 30→40 gains 1.62, 40→50 gains 0.71, and 50→100 gains only 0.53 total. Stop where the marginal point costs more latency than it is worth.

The pipeline, with the decision points explicit and measured rather than assumed.

import math def choose_depth(budget_ms, cost_per_cand_ms=4.0, n_max=200): # The maximum N the latency budget allows. That is a CEILING, not an optimum. return min(n_max, int(budget_ms / cost_per_cand_ms)) def marginal_curve(p0, p_max, n0, steps=(10,20,30,40,50,100)): def P(n): return p0 + (p_max - p0) * (1 - math.exp(-n / n0)) return [(n, P(n), (P(n) - P(steps[i-1])) * 100) for i, n in enumerate(steps)] def stop_at(curve, min_gain= 2.0): # Stop increasing N once an increment buys less than `min_gain` precision points. return [n for n, p, g in curve if g >= min_gain][-1] # ---- Query expansion: union of candidate sets ---- def union_recall(single_r, m_variants, independence=0.7): # Probability the answer is found by >=1 of m query variants. # independence=0 -> variants identical (no gain); 1 -> fully independent. if independence <= 0: return single_r p_miss = (1 - single_r) ** (m_variants * independence) return 1 - p_miss

Three decisions are encoded in that code. (1) choose_depth gives a ceiling, not an answer — a large budget does not mean you should use it, because the marginal curve has already flattened. (2) stop_at makes the stopping rule a declared threshold rather than a vibe, so it survives a reviewer asking "why 30?". (3) union_recall forces the independence question: three paraphrases generated by the same model from the same question are highly correlated, so independence should be well below 1 — and if your measured gain from expansion is near zero, you have just measured that independence empirically.

Reranker evaluation must hold the candidate set fixed. If you compare "top-8 from dense" against "rerank top-50 then take 8", you have changed two variables and the improvement is unattributable. The audit-grade comparison is: same candidate list, with and without rerank, reporting recall@50 (unchanged by definition) and precision@8 before vs after. Then a separate experiment for N. Log both.

4 · Your hands #

Experiment 1 — Find the depth where reranking stops paying

Candidate-depth sweep with a realistic saturation shape. The last column is the only one that should drive the decision.

import math def recall_at(k, r_max=0.92, k0=18.0): return r_max * (1 - math.exp(-k / k0)) def precision_after(p0, N, p_max=0.90, n0=12.0): return p0 + (p_max - p0) * (1 - math.exp(-N / n0)) COST_MS = 4.0 print("N recall@N precision latency dPrecision_per_10") prev = None for N in (10, 20, 30, 40, 50, 75, 100): p = precision_after(0.55, N) d = "" if prev is None else f"{(p - prev)*100:+.2f} pts per {(N-prev_n)} docs" print(f"{N:3d} {recall_at(N):9.4f} {p:10.4f} {N*COST_MS:7.0f}ms {d}") prev, prev_n = p, N

Observed output: N=10 recall=0.3921 precision=0.7479 latency=40ms · N=20 recall=0.6171 precision=0.8339 80ms · N=30 recall=0.7462 precision=0.8713 120ms · N=40 precision=0.8875 160ms · N=50 recall=0.8628 precision=0.8946 200ms · N=75 precision=0.8993 300ms · N=100 recall=0.9164 precision=0.8999 400ms. Read the marginal column: +8.60 pts going 10→20, then +3.74, +1.62, +0.71, and by 100 candidates the remaining headroom to p_max=0.90 is essentially exhausted. Going from 20 to 100 candidates costs 5× the reranker latency for +6.6 precision points; 30 is the defensible default (the last increment above 2 pts). Falsifier: if your measured curve does not saturate by N=100, your reranker is weak or your corpus is genuinely hard — fit n0 to your data and trust your curve over this one.

Experiment 2 — Query expansion: measure independence instead of assuming it

The union-recall model has one free parameter: how independent the variants are. Sweep it and see how much expansion could possibly buy.

def union_recall(single_r, m, independence): if independence <= 0: return single_r return 1 - (1 - single_r) ** (m * independence) print("single_r=0.62, 4 query variants") for ind in (0.0, 0.25, 0.5, 0.75, 1.0): print(f" independence={ind:.2f} -> union recall = {union_recall(0.62, 4, ind):.4f}") print("\nmeasured-vs-predicted check: you can ESTIMATE independence from data") # If you know single-query recall r1 and observed union recall ru with m variants: import math def estimate_independence(r1, ru, m): if ru >= 1.0 or r1 >= 1.0: return None return math.log(1 - ru) / (m * math.log(1 - r1)) print(" r1=0.62, m=4, observed union=0.70 -> independence =", round(estimate_independence(0.62, 0.70, 4), 3)) print(" r1=0.62, m=4, observed union=0.85 -> independence =", round(estimate_independence(0.62, 0.85, 4), 3))

Observed output: independence=0.00 → 0.6200, 0.25 → 0.6552, 0.50 → 0.6840, 0.75 → 0.7082, 1.00 → 0.7284. Even fully independent variants at m=4 only lift recall from 0.62 to 0.728 — expansion is a modest lever, and the measured-independence function is the useful artifact: an observed union of 0.70 with r1=0.62 implies independence 0.174, i.e. your four variants are largely redundant. That is a concrete instruction to generate more different queries, not more queries. Falsifier: if your measured union recall exceeds the independence=1.0 prediction, the variants are contributing beyond union coverage (e.g. they change the reranker's input too) — re-measure with the reranker held fixed.

Experiment 3 — Attribute the error: recall or precision? (copy-paste)

The diagnostic that tells you whether to buy a reranker or a better candidate generator.

def diagnose(results, k_show=8, n_cands=50): # results: list of dicts {"q": str, "candidates": [ids in ranked order], "gold": id} in_cands = sum(r["gold"] in r["candidates"][:n_cands] for r in results) in_topk = sum(r["gold"] in r["candidates"][:k_show] for r in results) n = len(results) recallN, recallK = in_cands / n, in_topk / n if recallN < 0.80: verdict = "FIX CANDIDATE GENERATION (expansion / decomposition / chunking)" elif recallK / max(recallN, 1e-9) < 0.85: verdict = "RERANK: gold is present but ranked too low" else: verdict = "RETRIEVAL IS FINE: the failure is downstream (generation / prompt)" return {"n": n, "recall@N": round(recallN, 3), "recall@k": round(recallK, 3), "verdict": verdict} # 20 queries; gold is usually in the top-50 but rarely in the top-8 results = [{"q": f"q{i}", "gold": "g", "candidates": (["g"] + [f"d{j}" for j in range(49)]) if i % 5 else ([f"d{j}" for j in range(50)] + ["g"])} for i in range(20)] # put gold at rank 12 for the non-missed ones for r in results: if "g" in r["candidates"] and r["candidates"][0] == "g": r["candidates"] = r["candidates"][1:12] + ["g"] + r["candidates"][12:] print(diagnose(results))

Observed output: {'n': 20, 'recall@N': 0.8, 'recall@k': 0.0, 'verdict': 'RERANK: gold is present but ranked too low'} — gold is in the top-50 for 80% of queries but in the top-8 for none, so the candidate generator is adequate and the ranking is the problem. That is the case a reranker is built for. Flip the construction (gold missing from the candidate set) and the verdict becomes FIX CANDIDATE GENERATION. Falsifier: if recall@N < 0.8 and recall@k ≈ recall@N, the ranker is already doing perfectly on what it is given — buying a reranker would be spending money to reorder a set that lacks the answer.

5 · Failure modes #

  • Reranking a candidate set that lacks the answer. Reranker is applied to a recall-limited top-N. Symptom: modest or zero improvement; recall@N measured below 0.8 while effort goes into reranker prompts.
  • Depth picked from a blog post. N=100 because "more candidates is better". Symptom: p95 latency blown by reranker time; precision gain under 1 point versus N=30.
  • Confounder-laden A/B. Rerank arm uses a different retrieval depth than the control. Symptom: improvement cannot be attributed; the control is not actually a control.
  • HyDE hallucination capture. The hypothetical answer invents specifics and retrieval returns documents agreeing with the invention. Symptom: retrieved chunks are internally consistent but unsupported by the corpus; citations point at real documents that do not say it.
  • Expansion drowning precision. Ten query variants union into 500 candidates. Symptom: recall up, precision down; the model gets a long noisy context and answers worse (L79).
  • Multi-hop with unverified intermediate answers. Hop 1's answer is wrong and hops 2–3 are confidently built on it. Symptom: chain of plausible reasoning ending in an unsupported claim; error compounds as ph (L82).
  • Listwise reranker truncation. 40 candidates in one prompt, model sees the first 20. Symptom: candidates past position ~20 are never selected — measurable by permuting the input order and watching the winner change (L89 position bias).
  • Reranker trained on a different distribution. Applied out-of-domain. Symptom: it compresses scores near 0.5 and reordering is nearly random — check score spread before trusting the ordering.

7 · Self-check #

Q1. You have 800 ms and each reranked candidate costs 4 ms. How many should you rerank, and why is the budget not the answer?

Reveal answer

The budget allows 800/4 = 200 candidates, but from the measured curve the precision gain from 50 to 100 is about 0.53 points and from 100 to 200 is effectively zero, for +400 ms. The right choice is around N=30, the last depth where an increment buys more than ~2 points. Budget gives an upper bound; the marginal-precision curve gives the operating point. Always report both, and report the latency you chose not to spend.

Q2. recall@50 = 0.91, precision@8 = 0.44. Which technique, and estimate the achievable ceiling.

Reveal answer

Reranker — the answer is present 91% of the time, so improved ordering can plausibly reach 0.91 × precision. With a cross-encoder reaching ~0.89 precision on in-set candidates, final precision@8 could approach 0.91 × 0.89 ≈ 0.81 — a large jump from 0.44. The residual 9% of queries are recall failures you cannot fix with reranking; they need better candidate generation. That split — 9% recall, 47% precision — apportions effort honestly.

Q3. Four query variants lift recall from 0.62 to 0.70. Estimate their independence and state the implication.

Reveal answer

independence = ln(1−0.70)/(4·ln(1−0.62)) = ln(0.30)/(4·ln(0.38)) = (−1.20397)/(4·−0.96758) = 0.311. The variants are ~31% as diverse as fully independent ones — largely redundant. Implication: generating more paraphrases of the same question buys little; you need variants that probe different aspects (entities, constraints, alternative phrasings from a different model or a different prompt strategy), or move to multi-hop decomposition if the question genuinely needs chaining.

Q4. Diagnostic: a multi-hop agent answers 2-hop questions at 0.72 but 3-hop at 0.38. What does that imply about per-hop accuracy, and what do you instrument?

Reveal answer

If accuracy compounds as ph: 0.720.5… take p = 0.72^(1/2) = 0.849 per hop; then 3 hops predicts 0.849³ = 0.612, which is well above the observed 0.38. So the model is not simply compounding — hops 2+ are harder than hop 1, most likely because each hop's query is conditioned on a previous answer and errors propagate through the query, not just the final result. Instrument per-hop: the generated sub-question, the retrieved chunk, and whether the hop answer matches gold. That separates "wrong retrieval at hop 2" from "wrong reasoning over a right chunk".

Q5. Why must a reranker A/B hold the candidate set fixed?

Reveal answer

Because changing depth and adding a reranker changes two variables, and depth alone improves recall. A rerank arm that gets top-50 while the control gets top-8 will look better even if the reranker is random — the win belongs to depth. Holding candidates fixed isolates the ordering effect, which is the only thing a reranker claims to do. The clean experiment: same 50 candidates, order by dense score (control) vs cross-encoder score (treatment), report precision@8 for both. Then, separately, vary N with the reranker fixed.
