L76 · What an agent actually is: a loop with a budget

You already ship swarms. The gap is not the loop — it is the account the loop writes to. An agent without an explicit cost/credit ledger cannot be distinguished from a program that says "done" and charges you for it.

~30 min difficulty ●●●○○ build: budgeted control loop + ledger
control loop cost/credit account oracle-gated credit overclaim rate budget as a state variable termination predicates debt vs proven credit credit-per-spend

1 · Why it exists #

The failure that forced the budget/credit framing is not "the agent can't use tools". It is the agent that reports success and is wrong, and whose report costs nothing to produce. A model that emits {"status": "done"} pays the same token cost whether the repository compiles or not. So in any multi-turn loop with free self-reporting, the cheapest policy the model can learn is assert completion early: stop spending turns, collect the reward signal, move on.

This is the same structural hole as a reward model that scores its own outputs (L58) — except now the actor is inside a loop with a tool surface and a filesystem. The loop amplifies it: each turn is a chance to assert, and the assertion is graded by whoever is least equipped to check it — you, at 2 a.m., reading a transcript.

Your BugAgents result is the counter-example that proves the point: 15,317 tool calls, $0.067 spend, zero false positives. That number is not a property of the model. It is a property of the 4-point promotion gate — an external oracle that had to pass before a claim became credit. The gate is the agent. The loop is transport.

An agent is a controller over two coupled state variables: how much of the task is actually done (unobservable to it) and how much budget remains (observable). Its job is to spend the second to raise a verified lower bound on the first, and to stop before the budget dies. Everything else — ReAct, tool schemas, personas, subagents — is implementation detail inside one step of that controller.

2 · The mental model #

Smallest correct model: a budgeted Markov decision process with a partial-credit oracle. Three state variables, two of which the policy cannot see.

VariableVisible to policy?UpdatesWhat breaks if you drop it
W world state (files, DB rows, tickets)partially, via tool readsactions mutate itagent talks instead of touching anything
B budget remaining (tokens, $, wall-clock, calls)yesmonotonically debited every turninfinite loops; cost surprise

Analogy that works: a contractor with a purchase order

An agent is a contractor with a fixed purchase order (budget), a site they may modify (workspace), and a building inspector that must sign off (oracle) before an invoice becomes a paid invoice (credit). The contractor's own "trust me, it's done" buys nothing.

Where the analogy breaks

A contractor knows what they did. The agent does not know what it did: it cannot observe its own effect on W except by reading it back through a tool, and its re-read is itself a model output that can be wrong. Also, a contractor cannot self-mutate their instructions mid-job; an agent's context is mutable in-loop, so "who I am" is a moving target (L79, L94).

The essential asymmetry: spending is observable and cheap to log; progress is hidden and expensive to verify. Every good agent design is a strategy for paying the second cost as rarely as possible while still bounding overclaim.

3 · The mechanism #

State the objective before any code. The unit of account is credit: one credit per task whose oracle passed. Spend is in the same abstract unit (here: 1.0 per turn, 1.5 per oracle call — verification is not free).

J(π) = Etasks[ Vπ − λ·Sπ ]    subject to   Sπ ≤ Ccap V = oracle-passed tasks (proven credit), S = total spend, λ = your exchange rate between a dollar and a proven task, Ccap = hard budget. When λ = 0 the argmax is "verify everything always"; when λ is large it is "accept any claim". The whole engineering decision lives on that line.

Now the quantity that matters and that nobody logs: overclaim rate, the fraction of closed tasks that booked credit without an oracle pass.

ρ = D / (V + D)      and      e = V / S D = debt (claim accepted, oracle would have failed), V = proven credit, ρ = overclaim rate, e = credit efficiency (proven credit per unit spend). A system is auditable iff ρ is measured, not assumed.

The loop itself, written to make the account explicit. Notice there are three termination predicates, not one, and that a done claim is input to the controller, never to the ledger.

# Minimal budgeted control loop. Every line that touches money or credit is marked. # Adapter: closure returning {"oracle": "pass"|"fail"|"error", "detail": str} class Ledger: def __init__(self, cap): self.cap = cap self.spend = 0.0 self.proven = 0 self.debt = 0 self.events = [] # append-only; hash-chain this (L90, L94) def debit(self, amt, why): if self.spend + amt > self.cap: raise BudgetExhausted(self.spend, amt) self.spend += amt self.events.append({"t": "debit", "amt": amt, "why": why, "balance": self.cap - self.spend}) # $-log def settle(self, claim_done, oracle_ran, oracle_pass): if oracle_ran and oracle_pass: self.proven += 1; verdict = "verified" elif claim_done: self.debt += 1; verdict = "unverified_claim" # DEBT, never credit else: verdict = "abandoned" self.events.append({"t": "settle", "verdict": verdict}) return verdict def rho(self): k = self.proven + self.debt return self.debt / k if k else 0.0 def run_agent(task, policy, oracle, ledger, cost_turn=1.0, cost_verify=1.5, max_turns=60, verify_on_claim=True): for turn in range(max_turns): try: ledger.debit(cost_turn, "turn") # DEBIT before work except BudgetExhausted: return ledger.settle(False, False, False) # terminate #1: budget step = policy.act(task, ledger.events) # tool calls happen inside if step.get("claim_done"): if not verify_on_claim: return ledger.settle(True, False, False) # books DEBT try: ledger.debit(cost_verify, "oracle") # verification is paid except BudgetExhausted: return ledger.settle(True, False, False) # claim, no proof res = oracle(task) # independent of policy if res["oracle"] == "pass": return ledger.settle(True, True, True) # terminate #2 continue # claim rejected -> keep going if step.get("give_up"): return ledger.settle(False, False, False) # terminate #3: policy quit return ledger.settle(False, False, False) # terminate #4: turn cap

Three things in that code are the whole lesson. (1) The debit happens before the work, so a crashed turn still costs — this is why your $0.067 number is credible and a "tokens used" number from a dashboard is not. (2) settle takes the oracle result as a separate argument from the claim; collapsing those two into one field is the single most common agent bug. (3) Every exit path calls settle, so there is no outcome that leaves the ledger without a verdict.

The ledger is the audit artifact. If events is append-only and hash-chained (hi = H(hi-1 || payloadi)), then any post-hoc edit to the cost or the verdict breaks the chain — which is exactly the property your AgentSwarm 32/32 ledger already gives you. The new requirement is that the oracle invocation is an event in the chain, not a side effect.

4 · Your hands #

Experiment 1 — Measure the price of proof

Two accounting policies on the same stochastic agent: (A) accept the model's done claim as credit, (B) pay for an oracle on every claim. The agent has a real completion probability and a hallucinated-claim probability while unsolved — that second number is what makes this diagnostic rather than a tautology.

python -c " import numpy as np COST_TURN, COST_VERIFY = 1.0, 1.5 def run(seed, cap=40.0, turns=60, p_discover=0.12, herb=0.10, p_claim=0.45, tpr=0.95, fpr=0.05, policy='verify_on_claim'): rng = np.random.default_rng(seed); solved=False; spend=proven=debt=0.0 for _ in range(turns): if spend + COST_TURN > cap: return 'budget_out', spend, proven, debt spend += COST_TURN if not solved and rng.random() < p_discover: solved = True claim = (solved and rng.random() < p_claim) or (not solved and rng.random() < herb) if not claim: continue if policy == 'accept_claim': if solved: proven += 1.0 else: debt += 1.0 return 'closed', spend, proven, debt if spend + COST_VERIFY > cap: return 'budget_out', spend, proven, debt spend += COST_VERIFY green = rng.random() < (tpr if solved else fpr) if green: if solved: proven += 1.0 else: debt += 1.0 return 'closed', spend, proven, debt return 'turn_out', spend, proven, debt for pol in ('accept_claim', 'verify_on_claim'): rows=[run(s, policy=pol) for s in range(40000)] n=len(rows); V=np.mean([r[2] for r in rows]); D=np.mean([r[3] for r in rows]); S=np.mean([r[1] for r in rows]) print(f'{pol:16s} closed={sum(r[0]==chr(99)+chr(108)+chr(111)+chr(115)+chr(101)+chr(100) for r in rows)/n:5.1%}' f' V={V:.3f} D={D:.3f} S={S:.3f} e=V/S={V/S:.4f} rho={D/(V+D):5.1%}') "

Observed output (fixed seed range 0..39999, numpy 2.x): accept_claim closed=100.0% V=0.5762 D=0.4238 S=5.496 e=0.1048 rho=42.4% and verify_on_claim closed=98.5% V=0.9504 D=0.0344 S=11.780 e=0.0807 rho=3.5%. Read the trade: paying for the oracle doubles spend and 12×s the proven rate, while overclaim falls from 42% to 3.5%. Efficiency e actually drops. That is the honest result — verification is a correctness purchase, not an efficiency purchase, and you must decide λ consciously. Falsifier: if your agent's herb (hallucinated claim rate) is genuinely 0, the two policies converge on e and only spend differs; then verify less often at intermediate checkpoints instead of every claim.

Experiment 2 — Find the budget that separates good from lucky

A single pass rate is not a budget policy. Sweep the cap and plot the proven rate against the cap; the curve shows where extra budget stops buying correctness and starts buying noise.

import numpy as np from collections import Counter def run_cap(seed, cap, p_discover=0.10, herb=0.10, turns=80): rng = np.random.default_rng(seed) solved, spend = False, 0.0 for _ in range(turns): if spend + 1.0 > cap: return "budget_out" spend += 1.0 if not solved and rng.random() < p_discover: solved = True claim = (solved and rng.random() < 0.45) or (not solved and rng.random() < herb) if claim and solved: return "verified" if claim and spend + 1.5 > cap: return "budget_out" return "turn_out" for cap in (5, 10, 20, 40, 80): c = Counter(run_cap(s, cap) for s in range(20000)) print(f"cap={cap:3d} verified={c['verified']/20000:5.1%} budget_out={c['budget_out']/20000:5.1%}")

Observed output (20,000 seeds per cap): cap=5 verified=32.1% budget_out=67.8% · cap=10 verified=59.4% budget_out=40.6% · cap=20 verified=85.9% budget_out=14.1% · cap=40 verified=98.2% budget_out=1.8% · cap=80 verified=100.0% budget_out=0.0%. Read it as a cost curve: going 5→10 buys +27.3 pts, 10→20 buys +26.5, 20→40 buys +12.3, 40→80 buys +1.8. Marginal return per unit of cap collapses after ~20 — that is where decomposition (L78) is cheaper than budget. Falsifier: if verified keeps rising roughly linearly to cap=80 (no saturation), the task is budget-limited rather than difficulty-limited and a bigger cap really is the answer.

Experiment 3 — Instrument your own loop (browser console, no install)

Paste into the console on any page of this course. It replays a recorded event list and computes the four account numbers any agent run should be able to produce on demand.

const events = [ {t:"debit", amt:1.0}, {t:"debit", amt:1.0}, {t:"claim"}, {t:"debit", amt:1.5, why:"oracle"}, {t:"oracle", pass:false}, {t:"claim"}, {t:"debit", amt:1.5, why:"oracle"}, {t:"oracle", pass:true}, ]; const acc = events.reduce((a, e) => { if (e.t === "debit") a.spend += e.amt; if (e.t === "oracle") e.pass ? a.proven++ : a.debt++; if (e.t === "claim") a.claims++; a.turns = a.spend; return a; }, {spend:0, proven:0, debt:0, claims:0}); acc.rho = acc.debt / (acc.proven + acc.debt || 1); acc.efficiency = acc.proven / acc.spend; console.table(acc);

Expect {spend: 6, proven: 1, debt: 1, claims: 2, rho: 0.5, efficiency: 0.1666…}. Note the first claim was rejected by the oracle and then retried — the ledger records both the failed claim and the eventual pass, so rho here counts the rejected claim as debt. Decide explicitly whether rejected-and-then-fixed claims are debt: in BugAgents terms they are, because a reviewer reading the transcript sees two claims and one proof. Falsifier: if spend here does not equal the sum of amt, your debit path has a branch that skips logging.

5 · Failure modes #

  • Self-graded credit. The loop's exit condition is the model's own done field. Symptom: pass rate looks great in the transcript, and a downstream consumer finds broken artifacts days later. Detect: ρ > 0 with the oracle turned on in replay mode.
  • Budget counted after the fact. Spend is summed from provider dashboards instead of from the ledger. Symptom: the run that looped 400 turns shows as normal cost because the last batch of calls never completed billing. Detect: replay the ledger; every action must have a matching pre-debit.
  • Oracle inside the policy. The verifier is a model call that the policy can prompt. Symptom: pass rate rises when you improve the prompt and not when you improve the code; contradictory pairs of fixes both "pass".
  • Unpaid verification. Oracle calls are treated as free and excluded from the cap. Symptom: tails 10× longer than the p50 because verification of near-misses is where the money went. Fix: debit verification at its real unit cost (Experiment 1 prices it).
  • Missing termination path. Only "oracle pass" and "turn cap" exist, so budget-carrying tasks burn the full cap by construction. Symptom: budget_out at exactly the cap, in a spike at one turn count.
  • Rolled-over debt. Debt is zeroed at session end. Symptom: a system with 30% per-session overclaim reports near-zero lifetime overclaim. Fix: credit and debt are lifetime counters in the same append-only ledger.

7 · Self-check #

Q1. Why must the debit happen before the action rather than after?

Reveal answer

Because the failure paths are exactly the ones where no "after" exists: crash, timeout, process kill, quota exhaustion. If debiting is post-hoc, those paths are free in the ledger and the ledger systematically underestimates spend on the runs that matter most. Pre-debit makes spend a monotone counter that can only be increased by an action actually starting, which is also what makes the hash chain a credible cost record.

Q2. Your agent closes 200 tasks. The oracle ran on 120 of them and passed all 120. 80 closed on self-claim with no oracle. Compute ρ and state what you still do not know.

Reveal answer

V = 120, D = 80, so ρ = 80/200 = 40%. You do not know the pass rate of the 80 unverified: they might be 95% correct, in which case true overclaim is 4/200 = 2%. ρ is an upper bound on measured debt; the only way to close the gap is to sample the unverified arm with the oracle (a randomized verification sample), which gives an unbiased estimate of the unverified pass rate at a cost you can budget.

Q3. In Experiment 1, verify-on-claim had lower efficiency e = V/S (0.0807 vs 0.1048) but far higher correctness. When is that the right trade?

Reveal answer

When the cost of a false-positive is larger than ΔS. Do the arithmetic: per 1000 tasks, verify-on-claim spends 1000×(11.780−5.496) = 6,284 extra units to convert (0.9504−0.5762)×1000 = 374 unproven closures into proven ones and remove (0.4238−0.0344)×1000 = 389 debts. That is ~16 units per corrected claim. If one false-positive costs you more than 16 units of remediation and trust, verify. If false-positives are cheap and reversible (draft text, throwaway analysis), accept the claim and keep the oracle in a sampled audit arm.

Q4. A teammate proposes adding a "confidence" field the model fills in at each step, to decide when to verify. What is wrong with using it as the gate?

Reveal answer

It is a model output conditioned on the model's own context, so it is not independent of the claim it is filtering — it inherits the same bias (the model that thinks it's done is the model that says high confidence). It can be used as a policy hint to allocate verification effort, but never as settle()'s input. The gate must be a function of the world (W): tests, schema validation, diff checks, a second model that does not see the first's reasoning. Route the confidence into the schedule, not the verdict.

Q5. Diagnostic: your runs show budget_out clustered at exactly turn 40 with zero verified. Which two of the six failure modes is it most likely, and what single log field disambiguates them?

Reveal answer

Either missing termination path (only oracle-pass and turn cap are live, so every unsolvable task burns to the cap) or oracle inside the policy/never-invoked (the loop never asks for a verdict because the policy has no trigger for it). Disambiguator: count {t:"oracle"} events per run. Zero oracle events → the verification trigger is missing. Non-zero oracle events with all failures → the task genuinely exceeds the cap, which is a decomposition problem (L78), not a control problem.
