L90 · Observability & tracing for agents

Turn 12 of an agent loop costs 5.15× turn 1, and the last three turns are 38.8% of the bill — because context grows and every turn re-pays for it. You cannot see that in a log file. You can see it in a span DAG with per-span cost.

~35 min difficulty ●●●●○ build: trace schema + cost attribution + hash-chained log
span DAG causal parent per-span cost attribution input/output hashing hash-chained event log quadratic context cost replayability trace retention

1 · Why it exists #

The failure: something went wrong in a 40-turn agent run and you cannot reconstruct the causal chain. You have application logs — a stream of lines with timestamps and levels. Somewhere in there is the turn where the agent read a stale file, and the twelve turns after it that built on the stale data. The logs cannot tell you that, because a log line has no parent.

The second failure is economic and invisible: the cost per turn is not constant. Every turn re-sends the whole context, so turn 12's input is roughly twelve times larger than turn 1's. In a 12-turn trace with 1,200 tokens of growth per turn, turn 12 costs 5.15× turn 1 and the final three turns are 38.8% of the total — even though they are only 25% of the turns. Without per-span cost you will attribute the bill to "the model" or "the tool calls" and optimise the wrong thing.

The third failure is trust: the trace itself can be edited. If the evidence of what an agent did lives in a mutable log, then "the agent did X" is a claim, not a record. This is where your AgentSwarm hash-chained ledger already has the right answer, and the work here is extending it to cover every span, including oracle invocations.

A trace is a causal DAG of spans with attached cost and content hashes, and it is written append-only outside the agent's writable scope. Its job is to answer three queries that a log cannot: which span caused this failure, which span cost this dollar, and was this record altered after the fact.

2 · The mental model #

A span is one unit of work with a start, an end, a parent, and (for LLM spans) a token count. A trace is the closure of spans sharing a trace_id. The parent pointer is what turns a list into a tree, and the tree is what makes attribution possible.

Analogy: distributed tracing, which already solved this

A request in a microservice mesh is traced as a tree of spans with a shared trace id and parent pointers. Agent loops are the same shape: a request fans out to tool calls, subagents, and model calls, and the interesting questions are all causal or attributive. Adopt the OpenTelemetry span model rather than inventing one.

Where it breaks

Request tracing assumes spans are deterministic functions of their inputs — replay a span and you get the same result. An LLM span is not: the same input can produce a different output (L94). So a trace needs the hashes and the actual output text (or a pointer to it) to be replayable, and it needs a record of nondeterministic events that the standard span model has no slot for: sampling seeds, serving version, batch composition. Extend the schema; do not assume the standard one suffices.

The practical consequence for retention: a trace without the content is not replayable, but content is large and sensitive. The usual compromise — store hashes plus a pointer to content in a separate, access-controlled store with its own retention — keeps the trace small while preserving the ability to reconstruct. What you must never do is store neither.

3 · The mechanism #

Cost attribution first, because it is the number that changes behaviour. For a loop where each turn re-sends the growing context:

Ctotal = ∑t=1T [ (b + g·t) pin + o pout ]   →   Ctotal = O(T²) in the growth term b base context, g growth per turn, o output tokens, p prices. The growth term is quadratic in T, so halving the number of turns quarters the context cost. With b=800, g=1200, o=300 and 12 turns: total $0.03286, of which the last turn alone is $0.00459 — 14% of the bill for one turn.

Then the integrity chain. Every span event is hashed together with the previous hash, so altering any event breaks all subsequent hashes:

hi = SHA256( hi−1 ‖ canonical_json(spani) ) ‖ = concatenation. The chain must be appended to storage outside the agent's writable scope (L84), or the agent can rewrite its own history and re-chain it. Verification is a single pass recomputing h from genesis; a 32/32 intact check is exactly this.

The implementation. A tracer that emits spans into a hash-chained append-only file.

import hashlib, json, time, os def canon(obj): return json.dumps(obj, sort_keys=True, separators=(",", ":")) class Tracer: def __init__(self, path, prices): self.path = path # MUST be outside the agent's writable scope self.prices = prices # {"in": $/tok, "out": $/tok, "cache": $/tok} self.prev = "0" * 64 # genesis self.spans = [] def span(self, kind, parent=None, model=None, tokens_in=0, tokens_out=0, cached_in=0, input_obj=None, output_obj=None, status="ok", meta=None): t0 = time.monotonic() cost = (tokens_in * self.prices["in"] + tokens_out * self.prices["out"]) rec = { "span_id": hashlib.sha256(canon([kind, parent, t0, tokens_in]).encode()).hexdigest()[:16], "parent_id": parent, "kind": kind, "model": model, "t_start": t0, "tokens_in": tokens_in, "tokens_out": tokens_out, "input_hash": hashlib.sha256(canon(input_obj).encode()).hexdigest()[:16] if input_obj is not None else None, "output_hash": hashlib.sha256(canon(output_obj).encode()).hexdigest()[:16] if output_obj is not None else None, "status": status, "cost_usd": cost, "meta": meta or {}, } rec["t_end"] = time.monotonic() rec["h_prev"] = self.prev rec["h"] = hashlib.sha256((self.prev + canon(rec)).encode()).hexdigest() self.prev = rec["h"] self.spans.append(rec) with open(self.path, "a", encoding="utf-8") as f: f.write(canon(rec) + "\n") return rec["span_id"] def verify_chain(path, genesis="0"*64): prev = genesis n = 0 for line in open(path, encoding="utf-8"): rec = json.loads(line) h = rec.pop("h") if rec["h_prev"] != prev: return {"ok": False, "at": n, "reason": "h_prev mismatch"} if hashlib.sha256((prev + canon(rec)).encode()).hexdigest() != h: return {"ok": False, "at": n, "reason": "hash mismatch"} prev = h; n += 1 return {"ok": True, "n": n, "head": prev[:12]}

Four details in that code are not optional. (1) time.monotonic(), not wall clock — NTP steps and clock skew produce negative durations that poison latency attribution. Wall-clock timestamps can be stored alongside; they just must not be the measurement. (2) Content is hashed, not stored in the span — keeps the chain small and lets sensitive content live in a separate store. (3) The chain starts from a genesis hash, so deleting the first event is detectable, not just editing the middle. (4) Verification replays the chain from genesis, and returns the index of the first break, which is the difference between "the log was altered" and "the log was altered at event 47".

The audit query a trace must support, stated as a test: given a failed output, return the ordered list of spans from root to the span that introduced the bad data, with each span's input hash and cost. If your trace cannot answer that, everything downstream — evals, incident review, cost optimisation — is guesswork dressed as analysis.

4 · Your hands #

Experiment 1 — Cost is quadratic, and the tail dominates

A 12-turn loop where context grows 1,200 tokens per turn. Per-turn and cumulative cost, then the same trace with prefix caching.

PRICE_IN, PRICE_OUT = 0.28/1e6, 1.10/1e6 def simulate(turns=12, base=800, grow=1200, out=300): ctx, rows, cum = base, [], 0.0 for t in range(turns): ctx += grow c = ctx*PRICE_IN + out*PRICE_OUT cum += c rows.append((t, ctx, c, cum)) return rows rows = simulate() for t, ctx, c, cum in rows: print(f"turn {t:2d} in={ctx:6d} cost=${c:.5f} cum=${cum:.5f}") total = rows[-1][3] print(f"last/first = {rows[-1][2]/rows[0][2]:.2f}x last3 share = " f"{sum(r[2] for r in rows[-3:])/total:.1%}")

Observed output: turn 0 in=2000 cost=$0.00089 · turn 11 in=15200 cost=$0.00459, cumulative $0.03286. Then last/first = 5.15x and last3 share = 38.8%. The measurement changes your optimisation target: the last three turns (25% of turns) are 38.8% of the bill, so ending the run earlier is worth far more than making early turns cheaper. Compaction (L79) and a tighter budget (L76) attack this directly; shaving the system prompt does not. Falsifier: if your trace shows a flat per-turn cost, you either have prefix caching working or your context is not growing — check tokens_in per span before concluding the agent is efficient.

Experiment 2 — Prove the ledger cannot be edited (copy-paste)

Write five events, verify the chain, tamper with the middle, verify again. The second verification must fail and name the position.

import hashlib, json, tempfile, os def canon(o): return json.dumps(o, sort_keys=True, separators=(",",":")) def append(path, prev, ev): ev = dict(ev, h_prev=prev) ev["h"] = hashlib.sha256((prev + canon(ev)).encode()).hexdigest() with open(path, "a") as f: f.write(canon(ev) + "\n") return ev["h"] def verify(path): prev, n = "0"*64, 0 for line in open(path): ev = json.loads(line); h = ev.pop("h") if ev["h_prev"] != prev: return (False, n, "h_prev") if hashlib.sha256((prev + canon(ev)).encode()).hexdigest() != h: return (False, n, "hash") prev = h; n += 1 return (True, n, prev[:10]) p = os.path.path.join(tempfile.gettempdir(), "ledger.jsonl") if os.path.exists(p): os.remove(p) prev = "0"*64 for i in range(5): prev = append(p, prev, {"i": i, "tool": f"t{i}", "cost": 0.01*(i+1)}) print("intact: ", verify(p)) lines = open(p).readlines() ev = json.loads(lines[2]); ev["cost"] = 999.0 # tamper lines[2] = canon(ev) + "\n" open(p, "w").writelines(lines) print("tampered:", verify(p))

Expect intact: (True, 5, '<10 hex chars>') and tampered: (False, 2, 'hash') — verification names event index 2, exactly where the edit happened. That is the property that makes a trace evidence rather than documentation: an edit is not just detectable, it is located. Falsifier: if tampering with the last event still verifies, your verification is only checking h_prev chains and not recomputing h — a common implementation bug that leaves the tail forgeable.

Experiment 3 — Answer the causal query (browser console)

A trace as an array; the query walks parents from a failed span back to root. This is the operation a log file cannot do.

const spans = [ {id:"r", parent:null, kind:"decision", status:"ok"}, {id:"a1", parent:"r", kind:"tool", status:"ok", note:"read stale cache"}, {id:"a2", parent:"a1", kind:"llm", status:"ok", tokens_in:4100}, {id:"a3", parent:"a2", kind:"tool", status:"ok", note:"write migration"}, {id:"a4", parent:"a3", kind:"oracle", status:"error", note:"schema mismatch"}, ]; const byId = Object.fromEntries(spans.map(s => [s.id, s])); function chain(id) { const out = []; let cur = byId[id]; while (cur) { out.unshift(cur); cur = cur.parent ? byId[cur.parent] : null; } return out; } const failed = spans.filter(s => s.status === "error"); for (const f of failed) { console.log("failure at", f.id); for (const s of chain(f.id)) console.log(" " + s.id, s.kind, s.note ?? ""); }

Expect the chain r decision → a1 tool read stale cache → a2 llm → a3 tool write migration → a4 oracle error schema mismatch. The provenance note on a1 is the answer to "why did this happen", and it is only reachable by following parents. Note tokens_in: 4100 on a2 — cost attribution says the expensive span is not the one that failed. Falsifier: if any failed span has no path to a root, your trace has an orphan — a span emitted without its parent recorded, which usually means the parent id was assigned after the child was created. Fix by generating span ids before the call, not after.

5 · Failure modes #

  • Logs instead of spans. Flat lines with timestamps. Symptom: incident review cannot answer "which step caused this"; the timeline is reconstructed by eyeballing ordering.
  • Missing parent ids. Spans emitted without causality. Symptom: orphaned spans, and multi-agent runs where attribution between agents is impossible.
  • Wall-clock durations. NTP correction mid-run. Symptom: negative durations, impossible overlaps, latency dashboards that disagree with reality.
  • Cost estimated, not measured. Dashboards multiply tokens by a price table that drifted. Symptom: the invoice and the dashboard disagree by a growing factor; nobody knows which is right.
  • Ledger inside the workspace. The agent can write its own trace. Symptom: the chain verifies, but events contradict the artifacts — a re-chained history. This is the one that invalidates every other guarantee.
  • Hashes without content. Replayable hashes but the content was discarded. Symptom: you can prove two runs differed but cannot see how.
  • Unbounded trace growth. Full spans for every turn retained forever. Symptom: observability cost rivals inference cost; storage grows quadratically with context length.
  • No trace in eval. Evals run without tracing. Symptom: a score drops and there is no per-item span to explain why; the eval cannot be debugged, only re-run.

7 · Self-check #

Q1. Why is time.monotonic() mandatory for span durations rather than wall-clock time?

Reveal answer

Because wall-clock time can jump — NTP correction, DST, manual time changes, VM migration — and a jump during a run produces negative or absurd durations. Monotonic clocks are guaranteed non-decreasing and are the correct instrument for measuring elapsed time. Store wall-clock timestamps in addition (you need them for correlation with external systems), but compute duration and ordering from monotonic values. A negative duration in a trace is always a wall-clock bug, never a real concurrency anomaly.

Q2. In a loop with base 800 tokens, growth 1,200/turn, output 300/turn, what fraction of a 12-turn run's cost is in the last three turns?

Reveal answer

Context at turn t is 800 + 1200(t+1): turn 9 = 12,800; turn 10 = 14,000; turn 11 = 15,200. Sum of last three inputs = 42,000 tokens vs total input 12×800 + 1200×(1+2+…+12) = 9,600 + 93,600 = 103,200. So the last three turns are 42,000/103,200 = 40.7% of input tokens — matching the measured 38.8% of total cost (the difference is the output term, which is constant per turn). The operational reading: the final quarter of a run accounts for ~two-fifths of spend, so shortening the run is the highest-leverage cost action available.

Q3. You tamper with event 3 of 10 in a chained ledger and the chain still verifies. What is wrong?

Reveal answer

Two possibilities. (a) The verifier only compares h_prev links and never recomputes h from the event content — so content edits pass and only reordering is caught. (b) The verifier compares against a stored h field that was recomputed by the same tamperer. Both mean the chain is decorative. Correct verification recomputes h = SHA256(h_prev ‖ canon(rec)) from the event content and compares it to the stored h; tampering with content changes the recomputation at the edited index and every subsequent index also fails by construction. Fix by writing a tamper test into CI — the one in Experiment 2 — and asserting it fails at the right index.

Q4. Diagnostic: your cost dashboard says $0.031 for a run; the provider invoice allocates $0.048 to it. What do you check, in order?

Reveal answer

(1) Cached vs uncached input tokens — if the trace prices all input at the standard rate but the provider bills cache reads/writes differently, the totals diverge; add cached_in to the span. (2) Retries and failed calls — a timed-out call that the trace marks as an error span may still have been billed for its input tokens; log cost on error spans too. (3) Model/price version — a price table update the trace did not pick up. (4) Spans outside the trace — embedding calls, reranker calls, or a subagent whose span was never emitted. The general rule: reconcile the ledger against the invoice weekly, and treat a persistent gap as a missing span kind rather than a pricing error.

Q5. Why must the ledger be written outside the agent's writable scope, when the chain already detects tampering?

Reveal answer

Because detection is only useful if the attacker cannot also fix the evidence. An agent with write access to the ledger can edit an event and then recompute every subsequent hash — producing a chain that verifies perfectly. Hash chaining protects against undetected edits, not against an adversary who owns the whole file. You need both: the chain to make any edit detectable, and the out-of-scope storage so the agent cannot re-chain what it edited. This is precisely why the ledger must be a separate process/volume from the workspace, and why the verifier should record its own head hash somewhere the agent never sees.
