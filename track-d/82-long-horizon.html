L82 · Long-horizon autonomy: failure compounding, drift, stuck detection

The horizon at which an autonomous agent stops being trustworthy is not a function of how good each step is — it is a function of how fast you notice that a step went wrong. At 99% per-step success, halving detection cuts the horizon by 4.6×.

failure compounding detection latency autonomy horizon silent failure goal drift stuck detection novelty / information gain renewal vs patch

1 · Why it exists #

The failure is specific and it happens at a specific step count. An agent runs 40 steps correctly, then confidently continues from a wrong state for another 30. Every step after the mistake is locally reasonable. The transcript has no error in it. The final report is wrong, and the mistake is 30 steps in the past, buried in a summary that has been compacted twice.

Two quantities govern this, and they are usually confused. Reliability is how often a step is correct. Detection latency is how many steps pass before a wrong step is caught. Reliability is what you optimise with better models and prompts. Detection latency is what you optimise with oracles, invariants, and checks — and it dominates, because an undetected error makes every subsequent step wasted work plus its own cost.

The third failure is stuckness: the agent is not failing, it is looping. It re-reads the same file, applies the same patch, and gets the same test failure, twelve times, at real cost per cycle. A loop that terminates is expensive; a loop that does not terminate is an incident.

Autonomy is a budgeted experiment in compounding error. You do not extend the horizon by making steps better — you extend it by making failures visible sooner. The engineering deliverable is not a longer-running agent, it is a shorter-latency detector, plus a hard stop for the case where the detector says "this is not progressing".

2 · The mental model #

Think of the run as a chain of steps where each step has three outcomes, not two: correct, failed-and-detected, and failed-and-silent. A binary success/failure model hides the third category, and the third category is where long-horizon agents die.

OutcomeProbability (per step)ConsequenceRecoverable?
correctpproceed—
failed, detected(1−p)·drepair, one extra stepyes
failed, silent(1−p)·(1−d)poisons all subsequent workonly by a later oracle

d is the detection rate — the fraction of wrong steps that some check catches. It is the most under-instrumented number in agent engineering. You almost certainly know your p (models are benchmarked on task success). You very likely do not know your d, because measuring it requires deliberately corrupting a step and seeing whether anything notices — a fault-injection test (L92).

Analogy: a chain of buckets with a leak detector

Each step fills a bucket from the previous one. Some buckets leak (errors). Without a detector, leaked water flows downstream and the final measurement is wrong by an unknown amount. A detector at every third bucket does not stop leaks — it bounds the volume lost before a leak is found, which is the quantity that determines whether the whole chain is usable.

Where it breaks

Water leaks are conserved and thus reversible. Errors are mutations of state: a wrong step writes to the filesystem or the database, and downstream steps build on top of the mutation. Detecting the error does not let you subtract the damage — you must roll back to a checkpoint (L78) or start over. So the model needs a third axis the bucket analogy lacks: irreversibility, which turns a detected error into an incident rather than a retry.

The design consequence: put detectors at points where you can act on the result — before irreversible steps, at plan step boundaries, and immediately after any step that mutates shared state. A detector at a point where you cannot roll back is just a notification that you have already lost.

3 · The mechanism #

First the survival model. A step is "clean" if it is correct, or if it fails but is detected and repaired. The probability a whole run of n steps completes correctly is the clean-step probability raised to the run length.

P(clean step) = p + (1−p)·d·p      P(clean run of n) = [p + (1−p)·d·p]n p = per-step correctness, d = detection rate (of failures), n = steps. The repair term is (1−p)·d·p because a detected failure costs one retry, which itself must succeed.

Now the number that matters operationally — the horizon, the run length at which a clean run becomes less likely than not:

H1/2 = ln(0.5) / ln[ p + (1−p)·d·p ] At p=0.99, d=0.9: clean = 0.9989, H = 636 steps. At p=0.99, d=0.5: clean = 0.9950, H = 137. Same model quality, 4.6× different autonomy horizon, entirely from detection.

Second, the drift term. Even with perfect detection, a silent error wastes all the work after it. If errors occur at rate r per step over a horizon H and an error at step i wastes the remaining H−i steps, the expected waste is the sum of remaining work over all positions:

E[wasted] = r · ∑i=1H (H − i) = r · H(H−1)/2 At r=0.03, H=50: 0.03 × 1225 = 36.75 wasted steps — 73.5% of the horizon. The quadratic in H is the entire reason long-horizon autonomy is hard: waste grows with the square of how long you let it run unattended.

The stuck detector. Not "is it failing" but "is its state still changing":

import hashlib, json def h(x): return hashlib.sha256(json.dumps(x, sort_keys=True).encode()).hexdigest()[:8] def stuck_signals(history, window=6, repeat=3): # history: list of (action, *args). Two independent signals: # max_same_call : repeated identical action+args in the trailing window # max_same_out : repeated identical observation (e.g. same test failure) w = history[-window:] calls = [h([a[0], *a[1:-1]]) for a in w] outs = [h(a[-1]) for a in w] mc = max(calls.count(c) for c in calls) mo = max(outs.count(o) for o in outs) return { "max_same_call": mc, "max_same_out": mo, "novelty": novelty(w), # fraction of unseen tokens "stuck": mc >= repeat and mo >= repeat, } def novelty(window): seen = set() for a in window: seen |= set(str(a[-1]).split()) return len(seen) / max(1, sum(len(str(a[-1]).split()) for a in window))

The two conditions are conjoined deliberately. Repeated calls alone is normal (polling a build status is legitimate). Repeated outputs alone is normal (reading the same file twice after editing it). Repeated calls and repeated outputs together means the agent's action no longer changes the world — that is the definition of stuck, and it is checkable without any model.

The audit artifact for a long run is not the final answer. It is the detection ledger: every oracle invocation with its result and the step index it referred to. From that you can compute d empirically (detected failures / all failures found later by offline replay) and therefore the actual horizon your production runs operate within. An agent without a detection ledger has an unknown horizon, which is the same as having none.

4 · Your hands #

Experiment 1 — Detection rate sets the horizon

Three-outcome step model. Hold reliability fixed and sweep detection — the column that changes is the one that matters.

import math def survival(steps, p_ok, p_detect): p_clean = p_ok + (1 - p_ok) * p_detect * p_ok # ok, or fail+detect+repair ok return p_clean ** steps for p_ok in (0.99, 0.97, 0.95): for p_det in (0.9, 0.5): p_clean = p_ok + (1 - p_ok) * p_det * p_ok h = math.log(0.5) / math.log(p_clean) print(f"p_ok={p_ok:.2f} d={p_det:.1f} clean={p_clean:.5f} " f"P(ok@10)={survival(10,p_ok,p_det):.3f} P(ok@50)={survival(50,p_ok,p_det):.3f} H={h:6.1f}")

Observed output: p_ok=0.99 d=0.9 clean=0.99891 P(ok@10)=0.989 P(ok@50)=0.947 H=636 · p_ok=0.99 d=0.5 clean=0.99495 P(ok@10)=0.951 P(ok@50)=0.776 H=137 · p_ok=0.97 d=0.9 clean=0.99619 H=182 · p_ok=0.97 d=0.5 clean=0.98455 H=44 · p_ok=0.95 d=0.9 clean=0.99275 H=95 · p_ok=0.95 d=0.5 clean=0.97375 H=26. The headline: at 99% step reliability, a 50-step run is 94.7% clean with good detection and 77.6% clean with poor detection — and the horizon differs by 4.6×. Improving p from 0.95 to 0.97 at d=0.5 moves the horizon from 26 to 44 steps; improving d from 0.5 to 0.9 at p=0.95 moves it from 26 to 95. Falsifier: if your detected failures are not actually repaired (repair itself fails often), the (1−p)·d·p term overstates survival — measure repair success rate separately and multiply it in.

Experiment 2 — The quadratic cost of letting it run

Expected wasted steps when silent errors occur at rate r over horizon H. The point is how fast this exceeds H itself.

def wasted(r, H): return r * H * (H - 1) / 2 for r in (0.01, 0.03, 0.05): for H in (20, 50, 100): w = wasted(r, H) print(f"r={r:.2f} H={H:3d} -> E[wasted]={w:7.2f} ({w/H:6.1%} of horizon)")

Observed output: at r=0.03: H=20 → 6.30 (31.5%), H=50 → 36.75 (73.5%), H=100 → 148.5 (148.5% — more than the entire run). At r=0.05, H=100 the waste is 247.5 steps, i.e. you would need 2.5 full runs to get one clean one. That is the quantitative reason an unattended 100-step agent at 5% silent error rate is not economical even if each step is cheap: you pay the whole run repeatedly. Falsifier: if errors are detected within the same step (d near 1), the waste term collapses — recompute with effective r → r(1−d) before concluding that long horizons are uneconomical.

Experiment 3 — Separate a stuck run from a healthy one (copy-paste)

Two nine-step traces: one looping, one progressing. The signals are computed, not eyeballed.

import hashlib, json def h(x): return hashlib.sha256(json.dumps(x, sort_keys=True).encode()).hexdigest()[:8] STUCK = [("read","src/retry.py"), ("read","src/retry.py"), ("read","src/retry.py"), ("edit","src/retry.py","patch-v1"), ("test","FAIL same assertion"), ("edit","src/retry.py","patch-v1"), ("test","FAIL same assertion"), ("edit","src/retry.py","patch-v1"), ("test","FAIL same assertion")] HEALTHY = [("read","src/retry.py"), ("edit","src/retry.py","patch-v1"), ("test","FAIL a"), ("read","src/retry.py"), ("edit","src/retry.py","patch-v2"), ("test","FAIL b"), ("read","src/queue.py"), ("edit","src/queue.py","patch-v3"), ("test","PASS")] def signals(seq, window=6, repeat=3): w = seq[-window:] calls = [h([a[0], *a[1:-1]]) for a in w] outs = [h(a[-1]) for a in w] mc = max(calls.count(c) for c in calls) mo = max(outs.count(o) for o in outs) seen = set() for a in seq: seen |= set(str(a[-1]).split()) nov = len(seen) / max(1, sum(len(str(a[-1]).split()) for a in seq)) return {"max_same_call": mc, "max_same_out": mo, "novelty": round(nov,3), "stuck": mc >= repeat and mo >= repeat} print("STUCK ", signals(STUCK)) print("HEALTHY", signals(HEALTHY))

Observed output: STUCK {'max_same_call': 3, 'max_same_out': 3, 'novelty': 0.333, 'stuck': True} and HEALTHY {'max_same_call': 1, 'max_same_out': 1, 'novelty': 0.833, 'stuck': False}. Three independent separations: repetition counts (3/3 vs 1/1) and novelty (0.333 vs 0.833). Novelty is the useful continuous one — set a threshold (e.g. mean novelty < 0.4 over 10 steps → warn) to catch slow drift before the hard stuck condition fires. Falsifier: if your healthy runs show low novelty because they legitimately re-read the same files, the novelty signal will false-positive — use the conjunction max_same_call & max_same_out as the hard stop and novelty only as a warning.

5 · Failure modes #

  • Silent failure propagation. A wrong step is not detected and 30 subsequent steps build on it. Symptom: final artifact wrong, every step in the transcript looks locally reasonable, blame ambiguous. This is the default outcome of missing oracles, not an edge case.
  • Goal drift. Late-run context is dominated by the agent's own prior outputs, so it optimises for finishing its summary rather than the task. Symptom: the last third of a run references intermediate artifacts and stops mentioning the original acceptance criteria.
  • Infinite loop with progress illusion. Each cycle makes a trivial change (reformats a file, rewords a comment) so nothing is identical. Symptom: hash-based repeat detection never fires; only novelty or cost-per-novel-fact catches it.
  • Compaction-driven amnesia. The failure gets compacted out of context but persists in state. Symptom: the agent cannot remember it made the mistake but keeps replicating it — acts like a fresh agent with a corrupted workspace.
  • Detection without rollback. An oracle fires after an irreversible step. Symptom: alerts with no corrective action; incident review finds the detector was working and useless.
  • Repair loop. A failed step is retried with the identical context so it fails identically. Symptom: max_same_call at the retry limit; error strings identical across attempts.
  • Horizon overrun. The run continues past the point where clean completion is unlikely. Symptom: cost per completed task rises sharply with run length while completion rate falls — the economical output is the early checkpoint, which nobody looked at.

7 · Self-check #

Q1. Your step reliability is 0.96 and detection is 0.8. What is the clean-step probability and the horizon?

Reveal answer

clean = 0.96 + 0.04 × 0.8 × 0.96 = 0.96 + 0.03072 = 0.99072. Horizon = ln(0.5)/ln(0.99072) = 0.6931/0.009323 = 74.3 steps. So a 74-step task is a coin flip. If you raise detection to 0.95: clean = 0.96 + 0.04×0.95×0.96 = 0.99648, horizon = 196 steps — a 2.6× improvement from detection alone, no model change.

Q2. At a 3% silent-error rate, how much of a 60-step run is wasted work on average, and what does that imply about pricing?

Reveal answer

r·H(H−1)/2 = 0.03 × 60 × 59/2 = 0.03 × 1770 = 53.1 wasted steps — 88.5% of the horizon. Implication: the effective cost per clean completion is not 60 steps, it is roughly 60 × P(clean) amortised, and with heavy waste you may need multiple full runs. Price the run by cost per verified completion, not cost per run — otherwise a 3% silent-error agent looks 1.7× cheaper than it is.

Q3. Diagnostic: a run shows normal latency and token burn, all steps succeed, but the final diff is wrong. What class of failure, and what single instrument would have caught it earlier?

Reveal answer

Silent failure propagation — a wrong intermediate state was never contradicted. The instrument is a post-step invariant oracle on shared state (e.g. "the migration is reversible", "no duplicate rows", "the ledger chain verifies") invoked right after every mutating step, not just at the end. End-of-run oracles tell you the run failed; per-mutation oracles tell you which step did it and let you roll back to the previous checkpoint.

Q4. Why does an agent that reformats a file on each cycle defeat hash-based stuck detection, and what catches it?

Reveal answer

Because the state is changing every cycle — the file content differs, so no hash repeats. It is "progress illusion": the agent is burning budget on changes that do not reduce the gap to goal. Catch it with a goal-distance signal, not a state-identity signal: track the oracle's failure output (same assertion failing, same test count), or measure novelty of the evidence rather than the state. The general rule: hash detecting works for exact loops, but you need a monotone progress metric for directed stuckness.

Q5. Why is "add self-critique so the agent notices its own errors" less reliable than an external oracle for raising d?

Reveal answer

Because self-critique is the same model reading the same context — its errors are correlated with the errors it is supposed to detect, so it raises d for failure classes where the mistake is visible in text (formatting, obvious logic gaps) and not at all for classes where the model's belief is the bug (wrong assumption, stale fact, misread requirement). An external oracle — tests, schema validation, hash verification, a diff check — is statistically independent of the actor's belief. That is why your 4-point promotion gate works where "review your own work" would not.
