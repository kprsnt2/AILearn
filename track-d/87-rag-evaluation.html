L87 · RAG evaluation: recall, faithfulness, groundedness, A/B

A single end-to-end accuracy number is useless for RAG because it destroys attribution: recall 0.95 with faithfulness 0.60, recall 0.60 with faithfulness 0.95, and 0.755/0.755 all score 0.570 and need opposite fixes. Decompose or you are tuning blind.

~30 min difficulty ●●●●○ build: RAG eval harness
retrieval recall faithfulness / groundedness attribution decomposition abstention correctness Wilson interval golden-set sizing paired A/B test contradiction vs unsupported

1 · Why it exists #

The failure: you have one accuracy number and no idea what to fix. Your RAG system answers 57% of questions correctly. Is that because retrieval misses (and you should work on chunking and expansion), or because the model ignores good evidence (and you should work on prompts and grounding)? Both produce 0.57. The score cannot tell you, and every change you make after this point is a guess. Worse: a change that improves retrieval and a change that improves generation both move the same number, so you cannot tell your last two weeks from noise.

The second failure is subtler and more dangerous: plausible answers that the evidence does not support. The retrieved chunk mentions the promotion gate; the answer says the gate runs four checks; the chunk says "some checks". The answer is fluent, topically correct, and false. End-to-end accuracy with a correct-answer key will catch it, but only if the key is exhaustive — and users rarely report the answers that sound right.

RAG evaluation is a factorisation, not a score. Report at least three numbers, always together: recall@k (did the evidence arrive?), faithfulness (given the evidence, did the answer stick to it?), and answer correctness (does it match the truth?). A single number hides which of three very different systems you built; three numbers name the defect and therefore name the fix.

2 · The mental model #

A RAG answer is the product of two conditional steps. Step one is a filter: does the retrieved context contain the evidence? Step two is a transformation: does the generator use it faithfully? Errors in each step need different fixes, and the only way to see them is to measure each conditional separately.

Analogy: a library and a summariser

Recall is whether the librarian brought the right book. Faithfulness is whether the summariser read it or made things up. A great summariser with bad books produces confident nonsense; good books with a bad summariser produce missed answers. You would never evaluate a library by asking "was the final summary good?" without knowing which of those failed.

Where it breaks

The product assumption P(correct) ≈ P(recall) × P(faithful | recall) fails in two ways. First, the model can answer correctly without the evidence, from parametric memory — so correctness is not bounded above by recall, and high correctness with low recall is a contamination signal (L74), not a success. Second, faithfulness is conditioned on what was retrieved, so a system that retrieves nothing and answers "I don't know" is perfectly faithful and perfectly useless. Never report faithfulness without recall.

The last point deserves emphasis because it is a favourite way to game a dashboard: faithfulness rewards silence. A model that says "insufficient information" for every query scores 1.0 on faithfulness and 0.0 on answer correctness. That is why abstention correctness needs its own set, and why the three numbers must be read together or not at all.

3 · The mechanism #

The decomposition, stated so it is testable:

P(correct) ≈ R · F      where   R = recall@k,   F = P(answer entailed by context | evidence retrieved) Treat this as a diagnostic identity, not a law. It tells you where to spend effort; it does not predict correctness for systems answering from parametric memory. Report R, F, and P(correct) separately — when the product diverges materially from the measured correctness, you have found either a contamination problem or an unanswerable-question leak.

Because these are proportions estimated from a finite golden set, every number needs an interval. The naive Wald interval collapses at p near 0 or 1 and is wrong at small n; use Wilson:

CI = [ p + z²/2n ± z√( p(1−p)/n + z²/4n² ) ] / (1 + z²/n) p = observed proportion, n = golden-set size, z = 1.96 for 95%. Wilson stays inside [0,1] and behaves at extremes. At p=0.90, n=20 the interval is [0.699, 0.972] — a 27-point-wide interval from 20 questions, which is why "we ran 20 evals and got 90%" is not a claim.

The harness. It computes all three metrics with intervals, and it fails loudly when the golden set is too small to support the decision being made.

import math def wilson(p, n, z=1.96): if n == 0: return (0.0, 1.0) d = 1 + z*z/n c = (p + z*z/(2*n)) / d h = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d return (max(0.0, c - h), min(1.0, c + h)) def rag_report(items, z=1.96): # item: {"q", "gold_chunk", "retrieved": [ids], "answerable": bool, # "supported": bool | None, "correct": bool | None} n = len(items) ans = [i for i in items if i["answerable"]] unans = [i for i in items if not i["answerable"]] R = sum(i["gold_chunk"] in i["retrieved"] for i in ans) / max(1, len(ans)) r_lo, r_hi = wilson(R, len(ans), z) # faithfulness is conditioned on evidence having been retrieved got = [i for i in ans if i["gold_chunk"] in i["retrieved"] and i["supported"] is not None] F = sum(i["supported"] for i in got) / max(1, len(got)) f_lo, f_hi = wilson(F, len(got), z) C = sum(i["correct"] for i in ans if i["correct"] is not None) / max(1, len(ans)) c_lo, c_hi = wilson(C, len(ans), z) A = sum(isinstance(i.get("abstained"), bool) and i["abstained"] for i in unans) / max(1, len(unans)) return {"n_ans": len(ans), "n_unans": len(unans), "recall": (round(R,3), round(r_lo,3), round(r_hi,3)), "faithful": (round(F,3), round(f_lo,3), round(f_hi,3)), "correct": (round(C,3), round(c_lo,3), round(c_hi,3)), "abstention": round(A,3), "product_RxF": round(R*F,3)} def decide(report, min_gap=0.05): # A/B decision rule: two systems are distinguishable only if the CIs do not overlap a, b = report if a["correct"][1] > b["correct"][2] or b["correct"][1] > a["correct"][2]: return "distinguishable" return "inconclusive: intervals overlap, need a larger golden set"

Two design decisions in that code carry the lesson. (1) Faithfulness is computed only over items where the gold chunk was actually retrieved — otherwise you are measuring the model's ability to be faithful to context it should not trust. (2) decide uses interval overlap, not a point-estimate comparison: two systems at 0.72 and 0.78 are not different when each has a ±0.06 interval on 100 questions.

The audit question for a RAG eval: for each failed item, is the failure attributed to retrieval or generation, and is the attribution recorded? A per-item record of {retrieved_ids, gold_id, supported, correct} lets a reviewer re-derive every aggregate you reported and verify that the aggregate was not cherry-picked. Without per-item records, "we improved from 0.57 to 0.63" is unverifiable — and in practice it is usually a change in the golden set, not the system.

4 · Your hands #

Experiment 1 — The attribution trap

Three systems, one end-to-end score. The point is that you cannot tell them apart without decomposing.

def e2e(recall, faithful): return recall * faithful for name, rec, fth in (("great retrieval, ungrounded LLM", 0.95, 0.60), ("bad retrieval, excellent LLM", 0.60, 0.95), ("mediocre at both", 0.755, 0.755)): print(f"{name:32s} recall={rec:.3f} faithful={fth:.3f} end2end={e2e(rec,fth):.3f}")

Observed output: great retrieval, ungrounded LLM recall=0.950 faithful=0.600 end2end=0.570 · bad retrieval, excellent LLM recall=0.600 faithful=0.950 end2end=0.570 · mediocre at both recall=0.755 faithful=0.755 end2end=0.570. All three are 0.570. The first needs grounding work, the second needs a retriever rebuild, the third needs both. If your dashboard shows one number, you cannot distinguish these — and you will spend the next sprint on the wrong component with a 1-in-3 chance of guessing right. Falsifier: if your real systems show e2e materially above R×F, the generator is answering from memory — check for contamination (L74) before claiming the decomposition is wrong.

Experiment 2 — How many golden questions do you actually need?

Wilson intervals at a range of n and p. This is the sizing chart for the eval set.

import math def wilson(p, n, z=1.96): d = 1 + z*z/n c = (p + z*z/(2*n)) / d h = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / d return c - h, c + h print(" n p 95% CI width") for n in (20, 50, 100, 300, 500, 1000): for p in (0.90, 0.60): lo, hi = wilson(p, n) print(f"{n:5d} {p:4.2f} [{lo:.3f}, {hi:.3f}] {hi-lo:6.3f}")

Observed output (excerpt): 20 0.90 [0.699, 0.972] width 0.273 · 20 0.60 [0.387, 0.781] width 0.395 · 100 0.90 [0.826, 0.945] width 0.119 · 100 0.60 [0.502, 0.691] width 0.189 · 300 0.90 [0.861, 0.929] width 0.068 · 1000 0.90 [0.880, 0.917] width 0.037. Read it as a decision tool: if you need to detect a 3-point improvement, your interval half-width must be well under 1.5 points, which needs n in the many hundreds at p≈0.9. With n=20 the interval is 27 points wide — you cannot detect anything short of a total redesign. Falsifier: if your A/B shows a 5-point gain at n=50, the intervals ([0.786,0.957] vs [0.462,0.724]) do separate — that is a real effect, but note it took a large effect to be visible; small effects need more items, or a paired design (same questions, both systems).

Experiment 3 — Lexical overlap cannot measure faithfulness (copy-paste)

Two answers, identical text, opposite truth. Any token-overlap metric scores them as equal.

def overlap(answer, context): a = set(answer.lower().split()) c = set(context.lower().split()) return len(a & c) / len(a) cases = [ ("The gate runs four checks.", "The promotion gate requires four independent checks.", True), ("The gate runs four checks.", "The gate runs some checks before merge.", False), ] for ans, ctx, truly_supported in cases: print(f"overlap={overlap(ans, ctx):.2f} truly_supported={truly_supported} ctx={ctx[:44]!r}")

Observed output: overlap=0.80 truly_supported=True and overlap=0.60 truly_supported=False. Overlap gives 0.80 vs 0.60 — it directionally separates them here, but both values are high and any threshold you pick is arbitrary. Reverse the case (a supported answer that paraphrases heavily) and overlap drops while truth is unchanged. The correct instrument is entailment: does the context logically support the claim — which in practice means an NLI-style model or a calibrated judge (L89), with the "four checks" vs "some checks" distinction being exactly the kind of numerical quantification a judge must be trained or prompted to catch. Falsifier: if your overlap-based faithfulness metric correlates >0.9 with human judgements on a labelled sample, it is adequate for your corpus — verify on at least 100 human-labelled pairs before relying on it.

5 · Failure modes #

  • Single-number evaluation. Only end-to-end accuracy is tracked. Symptom: sprints spent improving the wrong component; two consecutive changes produce the same delta.
  • Faithfulness measured on unrecovered items. Faithfulness computed over all questions including retrieval misses. Symptom: faithfulness looks high while answers are wrong — the model is faithful to the wrong context it received.
  • Abstention gaming. A model that refuses more scores higher on faithfulness. Symptom: faithfulness up, correctness down, abstention rate climbing silently.
  • Interval-free A/B. Two point estimates compared without intervals. Symptom: "significant" wins of 2 points at n=40 that fail to reproduce; repeated reversals between runs.
  • Golden-set contamination. Eval questions were written by looking at retrieved passages, or appear in the corpus. Symptom: recall@k near 1.0 with poor user-reported quality.
  • Unanswerable set missing. No questions without evidence. Symptom: the system never learns to abstain; hallucination rate is invisible in the eval.
  • Moving golden set. Items added/removed between runs. Symptom: score jumps that do not reproduce; per-item comparison impossible. Fix: version the set, compare on the intersection.
  • Recall measured at the wrong k. recall@50 reported while production serves top-8. Symptom: eval says 0.91, users see 0.44 precision.

7 · Self-check #

Q1. System A: recall 0.88, faithfulness 0.71. System B: recall 0.62, faithfulness 0.94. Which do you improve first and why?

Reveal answer

Both products are close: 0.88×0.71 = 0.6248 vs 0.62×0.94 = 0.5828. A is better end-to-end, but the diagnoses differ. For A, the binding term is faithfulness (0.71) — the evidence is there and the generator ignores it, which is usually the cheaper fix (grounding prompt, citation requirement, lower temperature). For B, the binding term is recall (0.62) — a retriever rebuild (chunking, expansion) is more work. So improve A's faithfulness first: cheaper per point, and A starts ahead. The general rule: fix the term furthest from its ceiling, and prefer the cheaper intervention for equal distance.

Q2. You observe 72/100 correct. Give the Wilson 95% interval and state what improvement you can detect with a second 100-item run.

Reveal answer

p=0.72, n=100, z=1.96: p + z²/2n = 0.72 + 0.0192 = 0.7392, 1 + z²/n = 1.0384, centre 0.7392/1.0384 = 0.7118; half-width 1.96×√(0.2016/100 + 0.000384)/1.0384 = 1.96×0.04488/1.0384 = 0.0847. Interval [0.625, 0.799] (width 0.173). A second run at n=100 has a similar interval, so to distinguish two systems the point estimates must differ by roughly 17 points for disjoint intervals. Detectable effect sizes at n=100 are therefore large; for a 3-point question you need a paired design (same questions, both systems) or many hundreds of items.

Q3. Why must faithfulness be conditioned on "gold chunk was retrieved"?

Reveal answer

Because faithfulness asks "does the answer follow from the context it was given", and if the gold chunk was never retrieved, the answer is being judged against context that cannot support a correct answer — so scoring it as unfaithful conflates a retrieval failure with a generation failure. That conflation destroys the attribution that is the whole point. Conditioning gives you: retrieval failure = 1−R, generation failure = R×(1−F), and these sum correctly: (1−R) + R(1−F) = 1 − RF = 1 − P(correct). That identity is worth memorising.

Q4. Diagnostic: faithfulness 0.98, correctness 0.41, abstention rate 0.55. What is happening?

Reveal answer

The system is abstaining its way to a high faithfulness score. Abstentions count as faithful (nothing asserted, nothing unsupported) but as incorrect, and an abstention rate of 0.55 caps correctness at about 0.45. Faithfulness rewards silence; that is why it must never be reported alone. Check the abstention rate and the "insufficient evidence" trigger threshold — it is almost certainly firing on answerable questions because of a conservative prompt or a coverage check that is too strict (which in turn may be a genuine recall problem showing up as abstention rather than as a wrong answer).

Q5. Your eval reports recall@50 = 0.93 but users complain about precision. Name the measurement error and the fix to the harness.

Reveal answer

The harness measures recall at a k that production does not use. Recall@50 says the answer is somewhere in the 50 candidates; production serves 8 to the model, so the user-facing metric is precision@8. Fix: measure and report recall at the serving depth as the primary number (call it recall@8 or "hit rate at served k"), and keep recall@50 as a diagnostic for the candidate generator only. Two numbers, two purposes: recall@50 diagnoses the retriever, precision@8 diagnoses the ranker+serving path, and only precision@8 predicts user experience.
