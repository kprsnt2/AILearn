PART TWO · THE STOP CONDITION

The kill-switch is a theorem, not a button.

Any autonomous system that cannot be stopped deterministically is not deployable, no matter how capable it is. But "we can stop it" is a claim, and claims need a test. Here is the test: three computable conditions, each evaluated at every cycle boundary, each with a threshold you can defend. Below, a working calculator so you can tune them against a real run.

Why a manual stop does not count

A human watching a dashboard is not a stop condition. It fails on the only case that matters: the overnight run. If your protection requires someone to notice, it is not protection; it is a hope with a dashboard attached. The conditions below are computed by the harness itself, and the harness must be able to halt without a model in the loop — which means they must be arithmetic, not judgment.

Condition 1 — Replication floor

if divergence_pct(last 3 cycles) > D → HALT

The fraction of claims that failed independent replication. This is the only measure of whether the system is still telling you true things.

Default D = 0.15. Above 15% your "verified" work is not verified. Set it from your own history: run the harness for 10 cycles, measure the variance, then set D at mean + 2σ. Do not pick it from the air — pick it from data.

Condition 2 — Any hazard

if hazard_attempts > 0 → HALT and page a human

Any attempt at an action outside the declared scope, or any irreversible action without a pre-registered rollback. Not "if it succeeds" — an attempt is enough.

Threshold is zero, deliberately. There is no acceptable rate of unauthorized irreversible actions. If you set a tolerance here, you have defined an attack budget, and an adversary will spend it.

Condition 3 — Identity drift

if authority_mass < 0.5 × previous → HALT

The sum of the earned authority of the skills the agent actually used, per cycle. A sudden halving means the thing that is running is not the thing that was audited.

This clause is the one nobody builds. It catches the failure mode where an agent silently changes its scope or behaviour and the change is masked by a stable- looking success rate. It is the difference between "is it working" and "is it still the same."

The part that makes it a theorem

A stop condition is only a theorem if you can say what it guarantees. This one guarantees a bounded exposure:

exposure ≤ D × cycles_since_last_clean_replication × value_per_claim In words: the damage a drifting system can do is capped by the replication floor times how long it has been drifting times the value of a claim. If you halve D, you halve the worst case but double the false-alarm rate. That tradeoff is the whole engineering problem — and it is a tradeoff you can compute, not a judgement call.

Pick D, run 10 clean cycles, count false halts. Adjust. Now you have a stop condition you can defend in a review, because you have measured its two parameters instead of asserting them.

This is the same structure as a statistical process control chart from manufacturing, and the same logic as an audit sampling plan. You spent seven years learning that a control limit is set from measured variance and not from a manager's intuition. Apply it here.

What to build, in order

  1. The meter, not the brake. First record divergence_pct, hazard_attempts and authority_mass per cycle for two weeks. Do not halt yet. You need the distribution.
  2. The brake, in shadow mode. Compute the halt decision, log it, do not enforce it. Count how often it would have fired. Tune D.
  3. The brake, enforced. Only once false-alarm rate is acceptable. Enforcement without a tuned threshold trains everyone to ignore the alarm.
  4. The page. A halt must reach a human through a channel that works at 3am, with the reason string attached. A silent halt is a second failure.
