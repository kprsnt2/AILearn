L69 · Thinking mode, reasoning effort, and thinking-in-tool-use

Always thinking hard is unshippable; always thinking fast never solves the hard 5%. Effort is a per-request budget decision with a measurable objective, and the allocator is a knapsack you can compute in twenty lines.

~25 min difficulty ●●○○○ build: effort-router policy
reasoning_effort thinking tokens per-band accuracy marginal accuracy per token latency ceiling knapsack routing thinking in tool-use escalation

1 · Why it exists #

A model that always thinks as hard as it can is unshippable. A routing question gets 4,000 reasoning tokens; an incident triage call that needs an answer in 300 ms queues behind it. The failure is not accuracy, it is uncontrolled spend and latency on the majority of traffic that does not need it — and the mirror failure: forcing everything to be fast so the hard 5% never gets solved.

state as of 2026-10 Serving stacks expose this directly. The DeepSeek API's deepseek-flash model has a thinking mode with reasoning_effort set to low, high, or max, with thinking tokens billed even though users never see them. That triple is a product interface to a policy decision, and it exists because the cost difference between the levels is large enough to change which workloads are viable.

Reasoning effort is a budget parameter, and choosing it per request is a routing problem with a measurable objective: maximise accuracy per unit cost under a latency ceiling. The interesting part is that the right level is a property of the request, not of the model — so effort policy is a classifier you own, not a setting you pick.

2 · The mental model #

The mental model: three levels are three points on a cost/accuracy curve. Low is cheap and shallow; high is the default; max is expensive and best only where depth matters. Two things about that curve are routinely forgotten:

  • It is not monotone in usefulness per dollar. On easy traffic, max and low give the same answer; on hard traffic, low can be much worse. The gap between levels is the only quantity that matters for routing, and it is band-dependent.
  • Thinking interacts with tools. The current generation integrates thinking into tool-use: a turn can include reasoning, a tool call, its result, and more reasoning. That means the "effort" budget is spent across a tool loop, not in one block, and a tool call's latency adds to it.
LevelWhat it is forTypical failure if misusedWhat to measure
lowClassification, extraction, routing, short lookups, latency-criticalSilently wrong on items that needed multi-step reasoning; errors are confidentAccuracy on the hard band, not the average
highDefault for analysis and most user-facing reasoningCost on easy traffic where low would have been identicalMarginal accuracy over low, per 1k tokens
maxHard problems where depth pays: proofs, multi-constraint planning, debuggingLatency SLO breach; length inflation without gainAccuracy on the hardest band; p95 latency

What "three points on a curve" gets right

It makes effort a measurement question. Fit per-band accuracy and cost for each level, and the router falls out of the arithmetic.

Where it breaks

The levels are coarse and the model's behaviour changes with context length and tool availability, so a curve fitted on short single-turn prompts may not describe the same model inside a 40-turn agent loop. Refit per workload, not per model version.

3 · The mechanism #

The effort policy, as an optimisation with an explicit constraint:

maxe(q)  Σq acc( q, e(q) )   s.t.   Σq cost( q, e(q) ) ≤ C  and  p95( latency ) ≤ L e(q) is the effort chosen for query q. This is a knapsack: pick the level per request whose marginal accuracy per token is highest, until the budget binds.

The greedy version is what you implement: sort (queries × levels) by marginal accuracy per token and take levels while the budget lasts. The key input is Δacc / Δtokens between adjacent levels on the same band — if going low → high buys 2 points for 3,000 extra tokens on a band, that is 0.67 points per 1k tokens, and it competes against every other band's option.

Below is the whole allocator: a banded table of measured accuracy and cost per effort level, a budget, and a greedy selection. Run it with the default table and then with a different budget.

# L69: reasoning effort as a knapsack. Measured per-band table in, per-request levels out. # Pure stdlib. TRAFFIC = {"extract": 0.62, "classify": 0.24, "analyse": 0.11, "prove": 0.03} # (accuracy, TOTAL tokens per request including reasoning tokens) LEVELS = { "extract": {"low": (0.98, 180), "high": (0.98, 1500), "max": (0.98, 5200)}, "classify": {"low": (0.91, 240), "high": (0.93, 1800), "max": (0.93, 6000)}, "analyse": {"low": (0.61, 900), "high": (0.76, 4200), "max": (0.79, 11000)}, "prove": {"low": (0.18, 1400), "high": (0.44, 9000), "max": (0.52, 24000)}, } BUDGET = 2500.0 # mean tokens per request you are willing to spend def evaluate(policy): acc = sum(TRAFFIC[b] * LEVELS[b][policy[b]][0] for b in TRAFFIC) tok = sum(TRAFFIC[b] * LEVELS[b][policy[b]][1] for b in TRAFFIC) return acc, tok print(f"{'band':<10}{'share':>7}{'acc low':>9}{'acc high':>9}{'acc max':>8}" f"{'pts/1k low->high':>19}{'pts/1k high->max':>19}") for b, share in TRAFFIC.items(): lo, hi, mx = LEVELS[b]["low"], LEVELS[b]["high"], LEVELS[b]["max"] d1 = (hi[0] - lo[0]) / ((hi[1] - lo[1]) / 1000) d2 = (mx[0] - hi[0]) / ((mx[1] - hi[1]) / 1000) print(f"{b:<10}{share:>7.2f}{lo[0]:>9.2f}{hi[0]:>9.2f}{mx[0]:>8.2f}{d1:>19.3f}{d2:>19.3f}") policy = {b: "low" for b in TRAFFIC} acc, tok = evaluate(policy) print(f"\nall-low baseline: accuracy {acc:.4f} at {tok:.0f} mean tokens/request") # every possible single-level upgrade, ranked by accuracy gained per 1k tokens added options = [] for b in TRAFFIC: for prev, target in (("low", "high"), ("high", "max")): a0, t0 = LEVELS[b][prev] a1, t1 = LEVELS[b][target] gain = TRAFFIC[b] * (a1 - a0) add = TRAFFIC[b] * (t1 - t0) if gain > 1e-12: options.append((gain / (add / 1000), b, prev, target, gain, add)) options.sort(key=lambda o: -o[0]) print(f"\n{'upgrade':<24}{'pts/1k':>9}{'accuracy':>10}{'mean tok':>10}{'':>4}") for ratio, b, prev, target, gain, add in options: if policy[b] != prev: continue if tok + add > BUDGET: print(f"{b + ' ' + prev + ' -> ' + target:<24}{ratio:>9.3f}{'':>10}{tok + add:>10.0f} over budget") continue policy[b] = target acc += gain tok += add print(f"{b + ' ' + prev + ' -> ' + target:<24}{ratio:>9.3f}{acc:>10.4f}{tok:>10.0f} accepted") print(f"\nfinal policy {policy}") print(f"accuracy {acc:.4f} at {tok:.0f} mean tokens/request (ceiling {BUDGET:.0f})") all_high = {b: "high" for b in TRAFFIC} a_hi, t_hi = evaluate(all_high) print(f"for comparison, everything on high: accuracy {a_hi:.4f} at {t_hi:.0f} tokens")

4 · Your hands #

Three labs: allocate a token budget greedily across bands and levels, price a latency ceiling, and compute the marginal return of the third level on your own traffic.

Experiment 1 — run the allocator on a four-band traffic mix

Greedy buys analyse low → high first (0.045 pts/1k), then prove low → high, classify, then the two max upgrades at less than 0.005 pts/1k. The result: 0.9333 accuracy at 2,474 tokens, against 0.9276 at 2,094 for everything-on-high. The router spends 18% more and buys 0.6 points — and if your budget is the binding constraint, the honest answer is that neither is obviously right until you price the accuracy point.

Experiment 2 — no budget increase, different traffic mix

Set BUDGET = 1200 and re-run. Then change TRAFFIC so prove is 20% of requests and extract is 40%.

BUDGET = 1200.0 TRAFFIC = {"extract": 0.40, "classify": 0.19, "analyse": 0.21, "prove": 0.20}

With a 1,200-token budget the greedy list stops after the first two upgrades, and max never appears — the allocator refuses the expensive level because it cannot afford it, which is the correct behaviour and a useful thing to be able to show in a design review. With 'prove' at 20% of traffic, the prove upgrade becomes the single most valuable item, because its weight in the objective changed.

Experiment 3 — find the loop-level leak

Effort is set per turn, but the budget you care about is per task. Measure both, for the same workload.

single-turn probe : mean 2,100 tokens/request at effort=low agent loop, 5 turns : mean 11,400 tokens/task at effort=low <- 5.4x per-turn reasoning : turn 1 3,100 turn 2 2,400 turn 3 2,100 turn 4 1,900 turn 5 1,900 re-derivation share : turns 3-5 restate context that turn 1 already established

The leak is in turns 3-5, which re-derive established context. Budget the task, not the request: cap total" " reasoning tokens across the loop, and lower effort on continuation turns where the context is already in the window. A" " single-turn measurement would have told you the workload was cheap.

5 · Failure modes #

  • Uniform 'high'. Symptom: cost scales with traffic while accuracy on the easy bands was already at ceiling; the marginal accuracy over low is under one standard error.
  • Effort chosen by the model's self-report. Symptom: the model says the question is easy and gets it wrong; the classifier was never validated against outcomes.
  • Thinking tokens unaccounted. Symptom: the cost model and the invoice disagree by a factor; reasoning tokens are billed but absent from the response the cost model counted.
  • Latency p95 breach from max. Symptom: a small fraction of max-effort requests dominate p95 and blow the SLO for everyone; measure per-level latency, not the average.
  • Tool-loop budget leak. Symptom: an agent asked for 'low' effort still burns 30k tokens because each tool turn re-reasons; the effort setting applies per turn, not per task.
  • Refusal to escalate. Symptom: hard items stay on low because the router cannot detect them; the fix is a cheap confidence check and one escalation step, not a global bump.

Report accuracy and cost per effort level per band, plus p95 latency per level. A single "we reduced cost 40% by defaulting to low" is not a result until the per-band accuracy table is beside it — the reduction may be entirely on the band where accuracy fell 15 points.

7 · Self-check #

Q1. Three levels, a band where low/high/max give 0.61/0.72/0.74 accuracy at 300/2800/9000 tokens. Which level do you default to for that band and why?

Reveal answer

It depends on the budget, but the marginal numbers are the argument: low → high costs 2,500 tokens for 11 points(4.4 points per 1k tokens); high → max costs 6,200 tokens for 2 points (0.32 points per 1k tokens). Max is 14x lessefficient on this band. Unless the budget is slack and the band is critical, the default is high with max reserved for aflagged subset.

Q2. Why must reasoning tokens be in the cost model even though the user never sees them?

Reveal answer

Because they are billed and they occupy the context and the latency. A cost model built from response length underestimatesspend by the reasoning/reply ratio, which can be an order of magnitude. The practical consequence: cascade economics computedfrom visible tokens can recommend a configuration that loses money.

Q3. Diagnostic: p95 latency breached, mean latency fine, after enabling max effort. What is the mechanism and what do you measure?

Reveal answer

A small tail of requests consumes a large fraction of the total time: max effort has a long-tailed token distribution, so a fewrequests produce multi-second generations and dominate p95. Measure latency per effort level and per band, and the share ofrequests at max. The fix is a concurrency cap on max-effort requests or a stricter routing rule, not a faster model.

Q4. In a multi-turn agent loop, what does 'low effort' actually control, and what is the trap?

Reveal answer

It applies per turn, not per task. An agent that uses five tool calls spends the effort budget five times, and each turn'sreasoning may re-derive context it already had. The trap is budgeting from a single-turn measurement: a workload that measured2k tokens per request may cost 12k per task in a loop. Measure per task.

Q5. How would you validate an effort router that predicts difficulty?

Reveal answer

Hold out a labelled set, let the router pick the level, and compare end-to-end accuracy and cost against two baselines: always-highand always-low. The router only earns its complexity if it beats always-high on cost without losing accuracy, and beats always-lowon accuracy without exceeding the cost budget. Report per-band confusion between predicted and actual difficulty; the failure thatmatters is sending hard items to low.
