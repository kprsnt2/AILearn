TRACK C · POST-TRAINING & REASONING

L53 · The standard pipeline: pretrain → SFT → RL → staging, and the gates between

Every stage can pass its own criteria while the composition silently rewrites the product contract. The fix is not a better stage, it is a gate: a frozen eval, a minimum effect size, and a capability floor anchored at the base checkpoint.

~26 min difficulty ●●○○○ build: pipeline gate checklist + evaluator
gated transformation frozen eval set minimum detectable effect capability floor KL budget checkpoint hash lineage record staging drift

1 · Why it exists #

A post-training run that produced a genuinely better model gets rolled back, and nobody can say why. The failure is procedural, not scientific: there was no gate between the stages. Stage 2 was started because stage 1's loss dropped, stage 1's loss dropped because the data changed, the data change moved a behaviour nobody measured, and by the time anyone noticed, four checkpoints were in flight and no baseline existed to compare against.

The second, subtler failure: staging drift. Each intermediate stage is fine on its own criteria, and the composition quietly rewrites the product contract. SFT on chatty data makes the model verbose; the reward model, trained on the SFT model's own outputs, prefers verbose; RL then optimises for verbose. Three individually defensible choices produce a model that cannot shut up. No single stage violated its gate, because the gates were local and the drift was global.

A post-training pipeline is a sequence of gated transformations with a frozen baseline at the end of every stage. The gate is not "loss went down". The gate is a fixed, re-runnable evaluation of the product contract, evaluated against the previous stage, with a stop rule that is written before the run starts.

state as of 2026-10 — the published frontier pipelines follow this shape: DeepSeek-R1 (arXiv:2501.12948) describes a cold-start SFT stage, a reasoning-RL stage, a rejection-sampling SFT stage that folds in non-reasoning data, and a final RL stage; InstructGPT (arXiv:2203.02155) describes SFT → reward modelling → PPO. The stages differ in content; the shape — every stage produces a checkpoint that is evaluated before the next stage may consume it — is invariant.

2 · The mental model #

The mental model: think of the pipeline as a compiler with type checks. Each stage transforms a checkpoint and a dataset into a checkpoint; the gate is the type check at the boundary. A gate has three parts: what is measured, against what, and what happens when it fails.

StageInputWhat actually changesGate (must pass before the next stage)
0 · BasePretrained checkpointNothing — this is the reference everything is compared toReproduce the vendor-reported eval within tolerance. If you cannot reproduce the baseline, nothing downstream is interpretable.
1 · SFTCurated demonstrationsFormat, register, task followingFormat/schema compliance up, general capability down by less than tolerance, no answer leakage, no template mismatch.
2 · Preference / RMPairwise labelsThe ordering the model assigns to outputsPairwise held-out accuracy up; length delta between chosen and rejected is not the only signal the model learned.
3 · RL (PPO/GRPO)Reward model or verifierExploration into regions SFT never showedProxy reward up and the audit bracket up; KL within budget; pass@1 and pass@k reported separately.
4 · DistillAccepted traces from stage 3Compression of the teacher into a cheaper studentStudent within a stated gap of the teacher on the bracket, at the stated cost per query.
5 · ServeFinal checkpoint + sampler configNothing — but the config is part of the productSame checkpoint, same prompts, same sampler settings reproduce the eval numbers bit-for-bit.

What the compiler analogy gets right

Ordering is enforced, not advisory. A stage cannot consume a checkpoint that failed its type check, and the type check is a program, not a meeting. Failures are caught at the earliest stage that can produce them.

Where it breaks

Compilers have decidable type systems; here the "type" is a statistical estimate with error bars on a finite eval set, so a gate can pass by luck and fail by luck. Every gate is therefore a hypothesis test, and lesson 88's statistics apply: an eval of n items has a sampling error you must know before you compare.

3 · The mechanism #

A gate is a decision rule over measured deltas. Write it as arithmetic, not adjectives:

pass  ⇔  Δprimary ≥ δmin  ∧  Δcapability ≥ −τcap  ∧  KLdrift ≤ Kmax Δ are measured on frozen eval sets against the previous checkpoint. δmin is the minimum effect you would act on, not zero. τcap is the regression you tolerate.

Two numbers make this honest. First, the minimum effect: with a 200-item eval and a 50% ceiling, the standard error of an accuracy estimate is about √(0.5·0.5/200) ≈ 3.5 points, so a 1-point movement is noise and must not pass a gate. Second, the capability floor: a primary metric can rise while a general capability silently falls (the classic alignment-tax signature), so the gate needs a regression term, not just a gain term.

The runnable version below is a gate evaluator. It takes per-stage measurements and returns pass/fail with the reason. Plug in made-up numbers from two toy runs and see which stage fails and why.

# L53 snippet A: a gate is arithmetic, not adjectives. Standard library only. import json, math def se_prop(p, n): """Standard error of an accuracy estimate.""" return math.sqrt(max(p * (1 - p), 1e-9) / n) def min_effect(n, p=0.5, z=1.96): """Smallest detectable difference in two independent proportions of size n.""" return z * math.sqrt(2) * se_prop(p, n) # One stage's measurement. All numbers come from a frozen eval set. STAGE = { "name": "sft-cold-start", "eval_n": 200, # items in the frozen primary eval "primary": {"before": 0.50, "after": 0.53}, "capability": {"before": 0.62, "after": 0.61}, "kl": 0.42, } GATE = {"delta_min": 0.05, "tau_cap": 0.02, "k_max": 1.0, "eval_n": 200} d_primary = STAGE["primary"]["after"] - STAGE["primary"]["before"] d_cap = STAGE["capability"]["after"] - STAGE["capability"]["before"] mde = min_effect(GATE["eval_n"]) checks = [ ("primary >= delta_min", d_primary, GATE["delta_min"], d_primary >= GATE["delta_min"]), ("capability >= -tau_cap", d_cap, -GATE["tau_cap"], d_cap >= -GATE["tau_cap"]), ("kl <= k_max", STAGE["kl"], GATE["k_max"], STAGE["kl"] <= GATE["k_max"]), ("delta >= MDE (signal not noise)", d_primary, mde, abs(d_primary) >= mde), ] print(f"stage {STAGE['name']} eval_n={GATE['eval_n']} MDE={mde:.3f} (absolute accuracy points)") verdict = True for label, val, bound, ok in checks: verdict &= ok print(f" {label:<34} value={val:+.3f} bound={bound:+.3f} {'PASS' if ok else 'FAIL'}") print(" VERDICT:", "PROMOTE" if verdict else "BLOCK") # How large does the eval have to be to see a 3-point effect at 5% significance? need = 2 * (1.96 * 0.5 / 0.03) ** 2 print(f"\neval items needed to detect a 3-point delta at 5%: {math.ceil(need)}") print(f"current eval has {GATE['eval_n']} items -> a 3-point move is {d_primary / se_prop(0.5, GATE['eval_n']):.2f} SE")

4 · Your hands #

Three labs: evaluate a sequence of gates, compute how big a delta you can even detect with your eval size, and template the gate record you store next to every checkpoint.

Experiment 1 — evaluate one stage's gate

A 200-item frozen eval, a +3 point primary movement, a small capability regression, and a KL budget. The gate computes the minimum detectable effect from the eval size and refuses to pass a delta that is inside it.

The gate BLOCKS on two grounds: the primary gain of +3 points is below the 5-point minimum effect, and it is 0.85 standard errors, which is noise. The eval would need about 2,135 items to detect a 3-point delta at 5% significance. This is the first question a reviewer should ask about any stage that claims a small win: how many items were in the eval?

Experiment 2 — the global gate catches what local gates miss

Four metrics measured at every stage, all anchored to the base checkpoint: task score, format compliance, mean length, and refusal rate. Stage-local gates would pass all three stages because each improves on its own input.

Experiment 3 — the run card for a stage

Five immutable artefacts per stage. If any is missing, the stage cannot be shown to have improved anything.

stage: rl-verifiable-v2 data_hash : sha256:... checkpoint : runs/4120/ckpt-final sha256:... gate_json : {"primary":+0.11, "capability":-0.01, "kl":0.31, "verdict":"PASS"} sampler_config : {"temp":0.6, "top_p":0.95, "stop":["<|end|>"], "max_tokens":8192} diff_vs_prev : gate_prev.json -> gate_cur.json (one line per metric)

The sampler config is the field people omit and the one that makes an eval unreproducible in serving. The diff is" " what turns five snapshots into a history; a gate result without the previous stage's result is a number without a baseline.

5 · Failure modes #

  • Gate on a moving eval set. Symptom: every stage passes and staged comparisons are meaningless, because the eval was regenerated between stages. Freeze eval sets by hash and pin them in the run card.
  • Training loss used as the gate. Symptom: the stage that overfits hardest looks best at the gate, and the drop shows up two stages later as a capability regression nobody can localise.
  • No capability floor. Symptom: the target behaviour improves 8 points and an unrelated capability regresses 4 points, and nobody notices because it was not in the gate.
  • Distributed data with no lineage. Symptom: a rejection-sampling stage folds teacher outputs into the SFT set and the contamination check is now impossible, because you cannot say which records came from which model.
  • Sampler settings not part of the artifact. Symptom: the eval reproduces in the training harness and not in serving, because serving uses a different temperature, top-p, or stop sequence. The checkpoint is not the product; checkpoint + sampler config is.
  • Staging drift compounding. Symptom: three stage gates pass, the final model is verbose, and each stage's author can point to their own green gate. The fix is a global metric (length, refusal rate, format compliance) evaluated identically at every stage against the base, not the previous stage.

Keep the pipeline auditable with five immutable artefacts per stage: dataset hash, checkpoint hash, gate results as machine-readable JSON, the sampler config, and the diff versus the previous stage's gate results. If any of the five is missing, you cannot prove the stage improved anything — you can only assert it.

7 · Self-check #

Q1. Your eval has 200 items and the base model scores 50%. A new stage scores 53%. Can the gate pass at a 5% significance level?

Reveal answer

Standard error of a single proportion is √(0.5·0.5/200) ≈ 0.035, i.e. 3.5 points. For a difference of two independentestimates the SE is about √2·3.5 ≈ 5.0 points. A 3-point delta is 0.6 SE — nowhere near the 1.96 SE neededfor a two-sided 5% test. The gate must not pass; you either accept a larger minimum effect or grow the eval.

Q2. Why is the capability floor measured against the base checkpoint rather than the previous stage, while the primary metric is measured against the previous stage?

Reveal answer

Primary metrics are incremental: you want each stage to improve on its input, so the previous checkpoint is the rightcomparator. Capability regressions compound silently across stages, so a floor must be anchored at the base where thecontract was defined. Anchoring the floor to the previous stage lets each stage regress a little and pass.

Q3. A pipeline reports: SFT primary +6, capability −1; preference +0.4, capability −0.2; RL proxy +0.9, bracket +0.3. Which gate is the strongest evidence and which is the weakest?

Reveal answer

Strongest: the RL stage, because it moves the proxy and an independent bracket together by a meaningful amount — that isthe one pattern that is hard to fake. Weakest: the preference stage, because a pairwise accuracy gain of 0.4 points on anunknown-size set is indistinguishable from noise, and the inputs to it are not described. Compute the SE before accepting either.

Q4. Diagnostic: the gate passes in training and the same eval fails on the served model. Name the three most likely causes in order of cheapness of the check.

Reveal answer

(1) Sampler config mismatch: compare temperature, top-p, stop sequences, and max tokens — one diff. (2) Chat templatemismatch: dump token IDs from both paths and diff. (3) Quantisation or serving-engine precision change: same checkpoint, differentnumerics. All three are checks that take minutes; none of them require retraining, which is why they go first.

Q5. You must fold 20k teacher traces into your SFT set before the next gate. What lineage record is non-negotiable, and what gate item does it protect?

Reveal answer

Per-record provenance: teacher model id and version, generating prompt, sampler settings, and the acceptance rule that kept it.It protects two gate items: contamination (you must be able to subtract trace-derived data from any eval comparison) andcapability attribution (if a regression appears, you can segment it by source and tell whether teacher traces caused it).
