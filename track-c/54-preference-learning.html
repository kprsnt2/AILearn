L54 · Preference data: pairwise comparisons and annotator bias

A reward model is a compression of your annotation protocol including its biases. This page measures the instrument before you build anything on it — chance-corrected agreement, length bias recovery, and the per-pair fields without which no disagreement is ever attributable.

~26 min difficulty ●●○○○ build: a preference dataset with a protocol
pairwise label Bradley-Terry Cohen's kappa chance correction length bias position bias annotator drift rubric version

1 · Why it exists #

The demonstration has run out. You can show a model one good answer, but you cannot show it the reason one answer beats another — and the moment the task is "which of these two explanations a clinician would trust", the demonstration does not encode the judgement at all. Worse, the two failure modes of preference data are opposite and simultaneous:

  • Preference data that is an easy ranking scripted by one criterion. If every pair is "longer wins", the model learns verbosity, and you have not captured judgement at all; you have captured a rule you could have written in one line of code.
  • Preference data that is genuine but noisy. Ten annotators, no rubric, no tie option, no attention checks. Agreement is below chance on hard pairs, and that noise is not neutral: it biases toward the confident, fluent, wrong answer, because fluency is what annotators can actually see.

Both failures produce the same symptom at the end of the pipeline: the learned preference ordering transfers to the reward model, the reward model trains the policy, and the policy gets more of a behaviour your evaluation says is not better.

Preference data is not "A vs B". It is a pair, a rubric, an annotator population, and a tie policy — and the reward you eventually learn is exactly as good as the smallest of those four decisions. A reward model is a compression of your annotation protocol, including its biases.

2 · The mental model #

The mental model: an annotator is a noisy sensor of a latent quality score, read out through a threshold. Each pair is one comparison of two sensor readings. What you actually measure is not quality; it is quality plus annotator-specific bias plus comparison noise.

P(A ≫ B) = σ( q(A) − q(B) + bannotator(A,B) ),   b = length bias, fluency bias, position bias q is the latent quality you want. If b is correlated with a visible property, the learned reward is q + b, and RL will maximise b.

What "sensor" gets right

It separates the signal (a latent ordering) from the instrument (a person with a rubric). You can calibrate an instrument, measure its noise, and weight readings by reliability, all of which are meaningless for "labels are labels".

Where it breaks

Sensors do not have differing theories. Two annotators can disagree because they define quality differently, not because one is noisier, and no weighting scheme resolves a disagreement about the target. That is why the rubric is part of the data.

3 · The mechanism #

Measure the instrument before you build anything on it.

Cohen's κ = ( po − pe ) / ( 1 − pe ) po = observed agreement. pe = agreement expected if both annotators guessed from their own marginals. κ corrects for chance; raw agreement does not.

The chance-correction is not pedantry. If 80% of your pairs have the same winner, two annotators who randomly pick the majority 80% of the time agree on 68% of pairs while knowing nothing. Raw agreement would call that "good"; κ calls it zero. The snippet below computes both, then uses a logistic regression to expose a bias you cannot see by reading transcripts: the annotator's rule is longer wins.

The generative model is a Bradley–Terry read-out with two additive biases:

P(choose A) = σ( qA − qB + α(lenA − lenB) ) q is true latent quality (0-1), len is response length in characters. α is the annotator's length bias — the number you must drive toward zero.
# L54: measure the instrument before you build on it. Pure stdlib -- no numpy needed. import math, random rng = random.Random(7) ALPHA_TRUE = 0.0035 # annotator's real length bias, logits per character POS_LEAN = 0.25 # extra logit for "the left column looks better" def quality(i): return 0.30 + 0.40 * ((i * 37 % 11) / 10.0) def length(i): return 120 + (i * 53 % 17) * 22 def sig(z): if z >= 0: return 1 / (1 + math.exp(-z)) e = math.exp(max(z, -700)) # clip: exp underflows gracefully, never raises return e / (1 + e) def annotate(i, j, position): z = quality(i) - quality(j) + ALPHA_TRUE * (length(i) - length(j)) if position == "BA": z = -z + POS_LEAN return 1 if rng.random() < sig(z) else 0 pairs = [] for k in range(600): i, j = rng.randrange(12), rng.randrange(12) if i != j: pairs.append((i, j, "BA" if k % 2 else "AB")) labels = [annotate(i, j, p) for i, j, p in pairs] a2 = [annotate(i, j, p) for i, j, p in pairs] b2 = [1 - annotate(j, i, p) for i, j, p in pairs] def kappa(x, y): n = len(x) po = sum(u == v for u, v in zip(x, y)) / n pa, pb = sum(x) / n, sum(y) / n pe = pa * pb + (1 - pa) * (1 - pb) return po, pe, (po - pe) / (1 - pe) po, pe, kap = kappa(a2, b2) print(f"two annotators, columns swapped: p_o={po:.3f} p_e={pe:.3f} kappa={kap:+.3f}") # y = 0 means "left column chosen". Features: dq = quality difference, dl = length difference. rows = [] for (i, j, pos), y in zip(pairs, labels): left, right = (i, j) if pos == "AB" else (j, i) rows.append((quality(left) - quality(right), length(left) - length(right), y)) # 2-parameter Bradley-Terry by Newton steps, gradients in closed form beta, alpha = 0.5, 0.0 for _ in range(40): gb = ga = hbb = hba = haa = 0.0 for dq, dl, y in rows: p = sig(beta * dq + alpha * dl) e = y - p w = p * (1 - p) gb += e * dq ga += e * dl hbb += w * dq * dq hba += w * dq * dl haa += w * dl * dl hbb += 1.0 haa += 1.0 det = hbb * haa - hba * hba db = (haa * gb - hba * ga) / det da = (hbb * ga - hba * gb) / det beta, alpha = beta + db, alpha + da print(f"fitted beta(quality)={beta:+.3f} alpha(length)={alpha:+.5f} [true alpha={ALPHA_TRUE:+.5f}]") print(f"recovered share of the true length bias: {alpha / ALPHA_TRUE:.0%}") # is the reward a length detector? correlation of the two features in this generator dq_l, dl_l = [r[0] for r in rows], [r[1] for r in rows] mx, my = sum(dq_l) / len(dq_l), sum(dl_l) / len(dl_l) sxy = sum((x - mx) * (y - my) for x, y in zip(dq_l, dl_l)) sxx = sum((x - mx) ** 2 for x in dq_l) syy = sum((y - my) ** 2 for y in dl_l) print(f"R^2 between quality and length in this generator: {sxy * sxy / (sxx * syy):.3f}") print("an uncorrelated length feature still gets a large weight: that weight IS the protocol bug.")
two annotators, columns swapped: p_o=0.543 p_e=0.498 kappa=+0.089 fitted beta(quality)=+0.417 alpha(length)=+0.00252 [true alpha=+0.00350] recovered share of the true length bias: 72% R^2 between quality and length in this generator: 0.237 an uncorrelated length feature still gets a large weight: that weight IS the protocol bug.

4 · Your hands #

Three labs: build a preference dataset with a protocol attached, measure annotator quality properly, and recover the bias that the protocol failed to remove.

Experiment 1 — recover your annotator's length bias

A synthetic annotation protocol with a known bias of 0.0035 logits per character. You are given only the pair outcomes, then asked to recover the bias by fitting two coefficients.

The fit recovers roughly three-quarters of the true length coefficient from 600 pairs, and the two annotators' raw agreement is only about 0.54 with kappa near 0.09 — near-chance. If your real pairs show kappa below about 0.4, stop collecting preferences and rewrite the rubric.

Experiment 2 — the position-bias swap test

Every reward model gate should include this. Take 200 held-out pairs, score them, then swap A and B in each pair and" "score again. The mean absolute change is your position leak.

import json def swap_report(path="pairs.jsonl"): n = changed = 0 for line in open(path): r = json.loads(line) # your scorer MUST be order-canonical: score(text) with no pair context raise SystemExit("plug in your scorer here") return changed / max(n, 1) # the invariant, stated as a test: # for every pair, |score(A) - score(B)| must be identical before and after swapping columns # a scorer that reads "the first answer" instead of "this answer" fails this test.

Any non-zero rate means the scorer leaks column position. If your scorer takes the pair as input" " rather than scoring responses independently, the test is also telling you something about your API shape.

Experiment 3 — the per-pair record you must store

Copy this schema into your dataset. Each field exists because a specific failure becomes unattributable without it.

{"pair_id": "p_000123", "prompt_hash": "sha256:...", "resp_a_hash": "sha256:...", "resp_b_hash": "sha256:...", "shown_order": "AB", "chosen": "A", "annotator_id": "ann_017", "rubric_version": "2026-10-r3", "seconds_to_decide": 41, "flags": ["length_mismatch_gt_2x"], "label": "usable"}

Remove shown_order and position bias becomes unmeasurable forever. Remove" " rubric_version and you cannot explain a reward shift. Remove annotator_id and no" " future disagreement is attributable. These three fields are the audit minimum.

5 · Failure modes #

  • Verbosity bias. Symptom: chosen answers are systematically longer than rejected ones by a margin that reproduces across annotators; the learned reward correlates with token count better than with any rubric criterion.
  • Position bias. Symptom: reward model accuracy drops when you swap the order in each pair. Measure it: the delta between original and swapped accuracy is your position-bias leak.
  • Sycophancy leakage. Symptom: pairs where the response agrees with a false premise in the prompt are systematically chosen, because agreement reads as confidence. This bias is inherited by RLHF and is one of the hardest to remove later.
  • Annotator drift over a long project. Symptom: the same pairs, re-annotated with a fresh cohort, disagree at a higher rate than the original cohort does with itself.
  • Forced-choice on indistinguishable pairs. Symptom: high label noise concentrated on the pairs closest in quality — which is precisely the region the reward model most needs to be right about.
  • Selection bias in sampling pairs. Symptom: the pair distribution over prompts differs from the prompt distribution at serving time; the reward model is excellent on the data you collected and blind to the traffic you serve.

Record per pair: prompt hash, both response hashes, chosen side, the order shown, annotator id, time taken, rubric version, and a mandate to mark "unusable". Without the shown-order field you cannot measure position bias; without the rubric version you cannot explain a shift in the reward; without annotator id every future disagreement is unattributable.

7 · Self-check #

Q1. Two annotators agree on 68% of 1000 pairs. Their marginal preference for option A is 80% each. What is kappa, and what does it mean?

Reveal answer

p_e = 0.8·0.8 + 0.2·0.2 = 0.68. p_o = 0.68. kappa = (0.68 − 0.68)/(1 − 0.68) = 0. Their agreement isexactly what chance would produce given their shared bias toward option A. This is the canonical scripted-data case: the label carries the annotator's prior, not the comparison.

Q2. Quantitative: your chosen responses average 410 characters and rejected average 300. An annotator measures quality as q + 0.002·(Δlength). How large is the bias term on a typical pair?

Reveal answer

Δlength = 110 characters, so the bias adds 0.002 × 110 = 0.22 nats of logit in favour of the longer answer.With true quality differences often around 0.1-0.3 nats, the length term is comparable to the signal — the annotator isroughly half-measuring verbosity. That is the number the logistic-regression coef in the lab recovers.

Q3. You swap the order of every pair and re-run the reward model. Accuracy drops from 0.71 to 0.64. What have you learned, and what do you do?

Reveal answer

Seven points of accuracy are position-driven, not quality-driven. Immediately: randomise or balance the shown orderin the dataset (and regenerate anything already trained). Then: add a swap-augmented validation split to the rewardmodel's gate, so any future position leak is caught automatically.

Q4. Diagnostic: the reward model scores 0.78 on held-out pairs but the RL policy's outputs get longer every day and judges rate them flat. Is the preference data bad, or is it the RL?

Reveal answer

Most likely the preference data: if chosen-minus-rejected length is positive and systematic, the reward learnedverbosity and RL is faithfully maximising it. Test it directly: regress the reward model's score on log-length forfixed-quality samples. An R² above about 0.3 means your reward is a length detector. The RL is not the bug;it is the messenger.

Q5. Why must the rubric version be stored per pair rather than per project?

Reveal answer

Because rubrics get edited mid-project to resolve disagreements. Without a per-pair version you cannot tell whether ashift in the reward model comes from the data, the model, or a redefinition of the target. With it, you can segmentaccuracy by rubric version and measure whether the change helped.
