L61 · Test-time compute: sampling, verifiers, and the budget allocation problem

Spending more compute helps only when the remaining error has the right structure — voting needs uncorrelated errors, deeper reasoning needs serial work, verifiers need a better discriminator than the generator. This page turns the budget into a fitted router and shows where each axis stops paying.

~26 min difficulty ●●●○○ build: budget allocator
depth vs width self-consistency best-of-n verifier reranking optimal k accuracy per token effort router truncation rate

1 · Why it exists #

A system that answers every request with the same effort is leaving money on the table in both directions. It over-spends on "what is the capital of France" (a 9,000-token reasoning chain for a lookup) and under-spends on "prove this bound holds for all n" (a 200-token answer that gives up early). The failure is not accuracy on any single item; it is that the budget is not a function of the item.

The second failure is subtler and more expensive: buying test-time compute in the wrong currency. Sampling 32 answers and taking the plurality is cheap and works when errors are random. Sampling 32 answers and reranking with a weak verifier is expensive and can be worse than sampling 4, because the verifier's errors are correlated with the model's. The distinction matters: whether extra compute helps depends on the structure of the remaining error, not on the amount spent.

Test-time compute is a portfolio allocation problem. You have four assets — more reasoning tokens, more samples (self-consistency), a verifier/reranker, and an escalation to a stronger model — each with a cost and a return that depends on the question's difficulty. The skill is not spending more; it is routing each query to the asset with the best marginal return at its difficulty.

2 · The mental model #

The mental model: three compute axes, each attacking a different limitation.

AxisWhat it addsHelps whenUseless when
Deeper (more reasoning tokens per sample)Serial stepsThe item needs a long dependent chainThe item is a lookup, or the model already gets it
Wider (k samples, vote)Independent chancesErrors are uncorrelated and the correct answer is the modeErrors are concentrated on one wrong answer (lesson 60 §4)
Smarter verify (verifier, reranker, unit tests)Selection qualityYou can score candidates better than the generator produces themThe verifier shares the generator's blind spots

What "portfolio" gets right

It makes the budget decision explicit and measurable: for each difficulty band, an expected accuracy and an expected cost, so you can choose the allocation with the best accuracy-per-dollar rather than the best average accuracy.

Where it breaks

Real returns are not monotone and not independent. Accuracy can plateau (more tokens do nothing), the vote can hurt (correlated errors), and the verifier can be gamed. The allocator's parameters must be re-fit on fresh data, because they encode a single model's failure structure at a single point in time.

3 · The mechanism #

The allocation rule, written so it can be computed rather than argued about:

util. = P(correct | q, a) / cost(q, a)   |   a*(q) = argmaxa∈A [ P(correct | q, a) / cost(q, a) ] subject to budget a ranges over actions: answer directly, reason deeper, sample k and vote, verify-and-rerank, escalate. P(correct | q, a) must be estimated per difficulty band, not globally.

The self-consistency half has a closed form worth knowing, because it sets the ceiling on what "wider" can buy:

k* ≈ log( 1 / ( β · C ) ) / log( 1 / (1 − p) ) Optimal number of samples when each costs C, the reward per correct answer is β, and a single sample is correct with probability p. Returns diminish geometrically in k.

That formula is why "just sample more" is a bad default: the marginal gain per sample decays geometrically, so past a small k you are buying nothing. The lab below implements a router fitted on binned data and compares it against fixed policies on the same task distribution.

5 · Failure modes #

  • Uniform effort. Symptom: cost is dominated by easy items that gained nothing from the budget; the accuracy gain per 1k extra tokens is below noise.
  • Voting on correlated errors. Symptom: k-sampling lowers accuracy on whole categories at once, not a few items — the majority is wrong systematically, not randomly.
  • Verifier reranking a weak generator. Symptom: pass@k rises but pass@1 after reranking falls; the verifier prefers fluent wrong answers (lesson 59's flourish problem).
  • Budget truncation reported as model failure. Symptom: accuracy drops precisely on the items with the longest solutions, and the stop reason in the logs is "budget" rather than "answer found".
  • Cost accounting that omits reasoning tokens. Symptom: the cost model says a cascade is cheaper while the bill says otherwise, because thinking tokens are billed even though the user never sees them.
  • Router drift. Symptom: after a model upgrade the same routing policy sends the hardest items to the cheapest path, because the router's bins were fitted on the old model's difficulty curve.

Report test-time compute as a curve, not a number: accuracy against cost per 1k tokens, for each action, with the harness's truncation rate and the router's fallback rate attached. A single accuracy figure without the cost is uncomparable to any other run, including your own next week.

7 · Self-check #

Q1. Batch has two difficulty bands. Easy: 1000 items, accuracy 0.95 direct, 0.95 with 4k extra tokens, cost 200 vs 4200 tokens. Hard: 100 items, 0.30 direct, 0.55 deep, cost 800 vs 12000. Which band should get the deep budget, per token?

Reveal answer

Easy: 0.95/200 = 4.75 accuracy-per-1k-tokens (no gain at all, so the deep path is pure waste). Hard: directly 0.30/0.8 = 0.375per-1k; deep 0.55/12 = 0.046 per-1k. The deep path buys 25 accuracy points on 100 items for 100 × 11.2k tokens. Pertoken the direct path is still more efficient on the hard band, which is exactly the point: routing should be driven bythe marginal gain on the specific band, not by the global average.

Q2. For p = 0.6, cost C = 1 and β = 1, what is the optimal k for majority voting, and why is it not `as many as affordable`?

Reveal answer

k* ≈ log(1/1)… the formula gives zero at equality, so the correct reading is that the marginal sample adds0.4 of a reward against a cost of 1 — sampling does not pay until the reward per correct answer is raised. In generalthe marginal gain decays geometrically, so the optimal k is small; past it, each sample costs C and addsless than C. If a policy tells you to sample 64 times, check what it assumed about the reward.

Q3. Why can reranking with a verifier make pass@1 worse even though pass@k improves?

Reveal answer

pass@k measures whether any sample was correct. Reranking adds a selection step, and selection errors are newerrors: if the verifier is fooled by fluent wrong answers, it will pick them out of a set that contained a correct one.So the generator's improvement is real and the selector throws it away. This is why a verifier must be evaluated onselection accuracy, separately from generation coverage.

Q4. Diagnostic: accuracy drops 12 points after a harness change, concentrated on long-solution items only. What is the first hypothesis and what single log field confirms it?

Reveal answer

Budget truncation: the new harness reduced max reasoning tokens or changed the stop condition. The confirming field is thestop reason per request — budget against natural. If truncated requests account for most of the drop, the modelis unchanged and the harness is the regression.

Q5. When is escalation to a stronger model the right buy over deeper reasoning on the same model?

Reveal answer

When the failure is capability, not depth: the weaker model fails because it does not know the method, not because it ranout of steps. Diagnose by checking whether accuracy on that band rises with more tokens at all — if it does not, morecompute on the same policy is wasted, and escalation is the only axis left.
