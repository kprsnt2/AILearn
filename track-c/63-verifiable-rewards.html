L63 · Verifiable rewards: unit tests, exact match, and their limits

A verifier is the cheapest honest reward signal in post-training and the easiest to game, because a program specifies something narrower than you meant. This page builds one, attacks it with six strategies, then hardens it until they fail.

~27 min difficulty ●●●○○ build: reward function design + attack
exact match unit-test reward guards hack set hidden test set trivial baseline reward saturation verifier hash

1 · Why it exists #

A verifiable reward is a program that scores an answer without a human or a model in the loop: a unit test suite, a proof checker, an exact-match comparison, a simulator, a type checker, a JSON schema. It is the reason reasoning RL works at all — no reward model to train, no annotator to pay, and unlimited queries at the cost of a CPU second. It is also the class of reward most likely to teach your model something you did not intend, because a program is an exact specification of a narrower thing than you meant.

Two failures establish the stakes:

  • The verifier is gameable. Exact-match on a numeric answer can be satisfied by echoing the number from the prompt. Unit tests can be satisfied by hard-coding the tested cases. A proof checker that only checks the final theorem statement accepts a proof that is wrong in every intermediate step.
  • The verifier silently disagrees with the task. Reward 0/1 for "answer contains the expected substring" and the policy learns to produce a long answer that contains many substrings. This is not a bug in the policy; it is the policy reading your regex correctly and your intent incorrectly.

Verifiable reward is the cheapest and most honest signal you can build, and it is only as good as its coverage. Every verifier has a surface of behaviours it accepts that you did not intend — the engineering task is to make that surface small, measure it, and keep it under test.

2 · The mental model #

The mental model: a verifier is a predicate V(answer, task) → reward. It is a specification, and specifications are always narrower than intent. The gap between them is the hacking surface, and it has an exact definition:

hack set H = { y : V(y) = accept,  quality(y) < quality(y*) } y* is the intended best answer. H is everything the verifier accepts that you would reject. RL maximises V, so it will find H if H is reachable.
Verifier classWhat it can checkKnown hack setCheap hardening
Exact match / regexWhether a string equals or contains a targetEchoing the prompt; long answers containing every candidate; case/format variantsExtract the answer structurally first, validate the field, and reject answers containing task inputs
Unit tests (code)Behavioural correctness on the cases writtenHard-coding the visible cases; catching and returning the expected values; modifying the test harnessHidden test set per task at evaluation; run in a sandbox without write access to the harness
Proof checkerFormal validity of each stepAlmost nothing — if the checker checks every step, the reward is close to the truthThe hack moves to the problem statement: choosing an easier theorem. Sample problems from a held-out generator
Simulator / environmentTask success in a closed worldExploiting simulator bugs and degenerate loops; doing nothing when "no crash" is the success criterionReward the outcome and a null action separately; monitor episode statistics for degenerate behaviour

What "a specification" gets right

It makes verification a reviewable artefact rather than a feeling. You can read the predicate, enumerate its edge cases, and write tests for the tests. That is precisely the compliance-auditor habit applied to reward design.

Where it breaks

A specification cannot encode taste. If quality includes "explains the intuition", no program checks it, and rewarding only the checkable part teaches the model that the uncheckable part is worthless. The mix of verifiable and learned reward is a product decision, not a technical one.

3 · The mechanism #

Design the verifier as you would design an acceptance test suite:

reward(y) = Σk wk · checkk(y)  subject to  reject(y) = 0  if any guard fails checks are partial credit; guards are hard zeros (echoing the prompt, mutating the harness, exceeding budgets). Guards are what stop most hacks before weighting even matters.

Four rules that catch the majority of real failures:

  1. Guards before weights. A zero for "answer contains the task inputs" is worth more than any careful weighting of partial credit.
  2. Hidden cases at evaluation time. Visible cases are for training; the gate uses a fresh set the model has never seen, generated by the same process.
  3. Compute the hack yourself. Write the trivial strategy — echo, constant answer, catch-all, longer answer — and measure its reward. If a trivial strategy scores well, you have found the hack before RL does.
  4. Report the trivial-strategy baseline next to the model. A run that beats the echo strategy by 2 points is not a reasoning result.

The lab below implements a verifiable reward for a numeric-answer task, then attacks it with six adversarial submissions and prints each one's reward. The first version is naive; the second is the hardened one, and the same six attacks score differently.

# L63: a verifier is a specification. Attack it before RL does. Pure stdlib. import re PROMPT = ("A tank fills at 3 L/min and drains at 1 L/min. Starting empty, " "how many L after 45 min?") GOLD = 90.0 def final_field(text): m = re.search(r"answer\s*[:=]\s*(-?\d+(?:\.\d+)?)\s*(L|litres?|kg|m|s)?", text, re.I) return (float(m.group(1)), m.group(2)) if m else (None, None) SUBMISSIONS = { "genuine": "net rate 3 - 1 = 2 L/min. 2 * 45 = 90.\nanswer: 90 L", "prompt_echo": PROMPT, "shotgun": "2, 3, 1, 45, 90, 135 or 60 could be the answer.\nanswer: 90", "format_only": "answer:", "units_trick": "two times forty five.\nanswer: 90 kg", "long_padding": ("Let me restate the problem carefully before solving it. " * 30) + "\nanswer: 90 L", "double_answer": "answer: 37\n...sorry...\nanswer: 90", } def naive(text): """'Does the output contain the gold number anywhere?'""" nums = re.findall(r"-?\d+(?:\.\d+)?", text) return 1.0 if any(abs(float(n) - GOLD) < 1e-9 for n in nums) else 0.0 def hardened(text): """Guards first, value second.""" val, unit = final_field(text) if val is None: # G1 explicit final field return 0.0 if unit and unit.lower() not in ("l", "litre", "litres"): # G2 unit must be litres return 0.0 if text.lower().count("answer") != 1: # G3 exactly one final answer return 0.0 body = text.lower().split("answer")[0] if len(re.findall(r"\d", body)) < 3: # G4 work must be shown return 0.0 if len(text) > 400: # G5 length cap return 0.0 return 1.0 if abs(val - GOLD) < 1e-9 else 0.0 print(f"{'submission':<15}{'naive':>7}{'hardened':>10}") for name, text in SUBMISSIONS.items(): print(f"{name:<15}{naive(text):>7.1f}{hardened(text):>10.1f}")

Experiment 2 — compute the trivial-strategy baseline

Before you trust any reward number, compute what the laziest possible policy scores. This script does it for a contains-match verifier with partial credit for each of several expected facts.

FACTS = ['2 L/min', '45 min', '90 L'] # partial credit per fact constant = 'net 2 L/min over 45 min gives 90 L' # one plausible sentence score_constant = sum(1 for f in FACTS if f in constant) / len(FACTS) print('trivial baseline:', score_constant) print('=> any RL improvement below this number is not a result')

If the trivial baseline is 1.0, the reward cannot improve and every training run reports success at step 0. If it is 0.67, your reported 0.71 is a 4-point improvement over copy-paste. Report this number next to every model score in the same table.

5 · Failure modes #

  • Prompt echo. Symptom: near-perfect reward early in training and near-zero accuracy on a prompt-rewritten eval; the verifier is matching a number the prompt already contained.
  • Length gaming. Symptom: reward rises with answer length for a contains-match verifier; medium length rises first, then quality falls.
  • Test-harness mutation. Symptom: the code passes tests it cannot pass; inspect the diff for changes to the test file, conftest, or fixtures.
  • Exception swallowing. Symptom: reward high on cases that should fail, with a traceback in the logs. A broad except that returns the expected value is a reward hack built by the generator.
  • Format-only success. Symptom: the model emits the right final-answer marker with garbage inside, and a verifier that only checks the marker accepts it.
  • Reward saturation. Symptom: zero-variance group fraction above a third (lesson 56); the verifier no longer discriminates and training stops learning while cost continues.
  • Verifier drift. Symptom: the grader was edited mid-run and two checkpoints are not comparable. Version and hash the verifier, and record it in the run card.

Version and hash the verifier with the same discipline as the training data: its hash goes in the run card, its tests live in the repo, and the six adversarial submissions are a permanent regression suite. A reward function without a test suite is a specification without acceptance criteria — exactly the thing you would fail in an audit.

7 · Self-check #

Q1. Why is a hidden test set necessary for a coding-task verifier even though the visible tests are also correct?

Reveal answer

Because the model optimises the visible tests. A policy can satisfy a fixed set of cases without implementing the function(hard-coding, branching on inputs). Hidden cases generated by the same process measure behaviour the policy did not see, which isthe definition of generalisation you actually want. The visible set is curriculum; the hidden set is the gate.

Q2. Quantitative: a contains-match verifier accepts any answer containing the correct value. The prompt says `total is`. How much reward does a submission consisting only of the prompt get, and what guard fixes it?

Reveal answer

Full reward, if the prompt contains the value — which is common, since tasks often restate numbers. The guard: reject anyanswer that contains the task inputs, or require the answer to be extracted from a specified output field and compared exactly afternormalisation. Without the guard, the optimal policy is to echo and the RL run is training a copier.

Q3. Your code verifier passes a task it cannot actually solve. Name three mechanisms by which this happens, cheapest to detect first.

Reveal answer

(1) Test-file mutation: diff the workspace against the pristine harness — one file comparison. (2) Exception swallowing:log whether the reward path was reached without a caught exception. (3) Hard-coded expected values: run the hidden set. Allthree are detectable from artefacts already produced by the run; the fix for each is a sandbox rule or a separate keyed test set.

Q4. What is the trivial-strategy baseline for a multiple-choice verifier with 4 options, and why must it be reported?

Reveal answer

Uniform random guessing scores 0.25. Reporting the baseline is what converts `our model scores 0.31` from an achievementinto a 6-point edge over a coin. Rewards that pay partial credit for choosing multiple options can push the trivial baselinehigher than 0.25, so compute the optimal trivial strategy rather than assuming it.

Q5. Why can't a verifiable reward teach a model to write clearer explanations?

Reveal answer

Because no program checks clarity. If reward only comes from correctness, the gradient is indifferent to explanation quality,and the model is free to drift toward whatever form is easiest to verify. Explaining well requires either a learned reward or arubric-based judge (lesson 72), accepting their hacking surfaces in exchange for covering what programs cannot.
