TRACK C · POST-TRAINING & REASONING

L67 · Synthetic data and agent-environment synthesis

You cannot hand-label trajectories for every tool sequence and every error state. You can write a generator that produces task, environment and verifier together — and then the only question is whether its acceptance test still tells you anything.

~27 min difficulty ●●●○○ build: env generator for one task family
environment synthesis task generator final-state assertion null-action test reference solution difficulty binning seeded determinism template leakage

1 · Why it exists #

An agent that is good at twelve tasks is untested on the thirteenth. You cannot hand-label trajectories for every tool sequence, every error state, every recovery path — the combinatorics alone kill it, and expert trajectories cost far more than expert answers. The failure is environment scarcity: there is no place to try the behaviour you want to train.

The answer that scaled is not cleverer annotation, it is programmatic world generation. Rather than writing trajectories, you write a generator that produces tasks + a runnable environment + a verifier together, so that success is measurable without a human. state as of 2026-10 DeepSeek-V3.2 (Dec 2025 release) is described as introducing a massive agent training-data synthesis method covering 1,800+ environments and 85k+ complex instructions, and as the first DeepSeek model to integrate thinking directly into tool-use. The number that matters is not the count; it is that 1,800 environments is a coverage claim you can audit task by task.

Synthetic data has exactly one honest quality metric: does the acceptance test tell you something the model did not already know? A generator that produces 1.8M trajectories with a verifier that the current policy already passes 99% of the time has produced a million copies of the same lesson. Yield, coverage, and difficulty distribution are the audit, not volume.

2 · The mental model #

The mental model: an environment is a triple (state, actions, verifier). A task family is a generator over that triple. You are not producing data; you are producing a testable distribution, and then sampling from it until the pass rate is in the band where learning happens.

env = ( S, A, δ: S×A → S,  V: trajectory → [0,1] ) S is the state space, A the action space (tool calls), δ the deterministic transition, V the verifier. Determinism is what makes it a test rather than a game.

What "a testable distribution" gets right

It makes coverage countable and difficulty measurable. You can bin environments by pass rate, and route the ones in the 30-70% band to training, the easy ones to regression, and the zero-yield ones to a diagnosis queue.

Where it breaks

Reality is not a parameterised template. The parts of the task that are hardest to synthesise — ambiguous instructions, adversarial users, partially broken dependencies — are exactly the parts that break production agents, so a synthetic suite is systematically easier than the world.

3 · The mechanism #

Write the verifier first, then the environment, then the instruction template. That order exists because a verifier is the only component whose failure invalidates everything else.

accepted(trajectory)  ⇔  assert1(Sfinal)  ∧  …  ∧  assertn(Sfinal)  and optionally  budget(s) ≤ B Assert on FINAL STATE, not on the transcript. Transcript assertions reward narrating the work; state assertions reward doing it.

The three audits every generated environment must pass:

  1. Reference solution exists. A scripted policy passes the environment. If you cannot write a passing solution by hand, the task is not well-posed.
  2. Null action fails. Doing nothing scores zero. If the empty trajectory passes, the verifier is satisfied by the initial state.
  3. Seeded determinism. The same seed produces the same initial state and the same verifier outcome across runs and machines.

4 · Your hands #

Three labs: generate tasks for one family and audit the three properties, bin the family by difficulty, and compute how much of the generated set is actually training signal.

Experiment 1 — audit your generator with four canned agents

One task family, four agents: a reference solution, a null action, a partial agent that fixes two of three fields, and an echo agent that claims the work and changes nothing. The verifier asserts on final state only.

Reference 100%, null action 0%, echo 0% — the three audits pass. The partial agent passes 34%, which is the subtle finding: this verifier is all-or-nothing on three independent fields, so a partial attempt succeeds whenever the two fields it did fix happen to be the task's full requirement. If the family intends 'all three required', the verifier is correct; if it intends 'fix what is asked', the generator is producing ambiguous tasks. Either way, the number is now visible.

The curve is a cliff, not a slope: 0% until 3 of 3, then 100%. A cliff family gives the group baseline nothing to work with on most tasks (lesson 56's zero-variance problem) and no partial credit. Families that train well have a graded middle — vary the number of fields, or add partial-credit checks for intermediate state, and the histogram fills in the 30-70% band.

Experiment 3 — the provenance record for a generated environment

Store these five fields per environment family. Without them the family cannot be trusted as an eval, let alone as a reward source.

{"family": "record-update-v3", "generator": {"module": "gen_record.py", "sha256": "...", "seeds": [0, 2999]}, "verifier": {"module": "verify_record.py", "sha256": "..."}, "audit": {"reference_pass": 1.00, "null_action_pass": 0.00, "partial_agent_pass": 0.34, "current_policy_pass": 0.41}, "band_histogram": {"0-30%": 0.12, "30-70%": 0.55, "70-100%": 0.33}}

If current_policy_pass is above about 0.95, the family is a regression test, not training data." If it is below about 0.05, it is a difficulty ceiling you should investigate rather than train on. The histogram is what tells" you which, and it costs one line to compute.

5 · Failure modes #

  • Verifier satisfied by the initial state. Symptom: null-action trajectory passes; the agent learns to do nothing, politely.
  • Transcript assertions. Symptom: agents that narrate the right actions without performing them pass; check by running the tool-call log, not the text.
  • Template leakage. Symptom: huge gains on the synthetic eval, no gain on a hand-written holdout with different phrasing.
  • Simulator bug as reward. Symptom: success rate above 95% on tasks the reference solution finds hard; someone's stub returns the expected value.
  • Difficulty collapse. Symptom: 80% of generated tasks are trivial for the current model; zero-variance groups dominate and the run costs money without learning.
  • Unseeded nondeterminism. Symptom: the same seed gives different verifier outcomes; flaky environments produce noisy rewards and irreproducible eval numbers.
  • Instruction ambiguity. Symptom: two reasonable agents produce different final states and both are "right"; the verifier picks one arbitrarily.

For every generated environment family, store: the generator version and seed, the verifier hash, the reference-solution result, the null-action result, and the current-policy pass rate. An environment without those five fields cannot be trusted as an eval, let alone as a reward source — and 1,800 of them is only impressive if all 1,800 have them.

7 · Self-check #

Q1. Your generator produces 1,000 tasks and the current policy passes 96% of them. What is wrong, and what is the number to compute?

Reveal answer

Almost all of the generated set is in the saturated band: pass rates near 1 mean zero-variance groups and no learning signal(lesson 56). Compute the pass-rate histogram across bins and the share in the 30-70% band. Then either raise task difficulty,add harder variants, or use these as regression tests rather than training data.

Q2. Why must the verifier assert on final state rather than on the transcript?

Reveal answer

Because the transcript is generated text and can assert anything. A transcript-only verifier rewards describing theaction; a state verifier rewards performing it. The only exception is when the transcript IS the product (a report, an email),in which case the transcript is the final state and gets its own structured assertions.

Q3. Quantitative: 1,800 environments, 85,000 instructions. How many instructions per environment on average, and what is the audit risk if the distribution is uneven?

Reveal answer

About 47 instructions per environment on average. If the distribution is long-tailed — a few environments with thousandsand many with one — then the '1,800 environments' coverage claim is a claim about the head, not the tail, and the agent willbe trained mostly on a small number of task shapes. Audit: print the histogram of instructions per environment and the numberof environments with fewer than 10.

Q4. Diagnostic: agent passes the synthetic suite at 88% and the hand-written holdout at 51%. Name three candidate causes and the check for each.

Reveal answer

(a) Template leakage: check whether holdout prompts share templates with training. (b) Simulator cleanliness: check whetherthe synthetic suite injects faults; a holdout with messy real APIs will fail. (c) Instruction phrasing: check ambiguity andverbosity of the holdout's prompts. Each check is a property of the data, not of the model.

Q5. What is the null-action test and why is it non-negotiable?

Reveal answer

A deliberately empty trajectory must score zero. If it passes, the verifier is satisfied by the initial state, and thecheapest successful policy is to do nothing — which the optimiser will find within a few hundred steps. It is non-negotiablebecause it is cheap, it catches the most catastrophic class of verifier bug, and it never gives false positives.
