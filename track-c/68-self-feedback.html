L68 · RL with self-feedback and its failure modes

When there is no verifier, the model critiques its own attempt — and the optimiser learns to satisfy the critic, who is the same model. This page builds the loop with a hard stop rule, counts defects per round, and measures the flattery failure.

~27 min difficulty ●●●○○ build: self-critique loop with a stop rule
self-feedback critic-policy correlation executable grounding falsifiable critique stop rule regression re-check flattery failure defect yield

1 · Why it exists #

The verifier you need does not exist. The task is "build this feature end to end", "make this report correct", "refactor this module" — there is no unit test that captures the goal, and the reward model you could train would be a model of your own judgement. The failure is no external reward at all for the work you actually care about, and the workaround is to have the model generate feedback about its own attempt and optimise against that.

state as of 2026-10 DeepSeek-V4.1-Flash-1017 (Oct 2026) is described as using reinforcement learning with self-feedback for end-to-end project development — the "wish-driven programming" line. The idea in one sentence: instead of a reward model trained on human preference, ask the model to critique the artifact against the stated wish, and treat the critique as the reward signal.

Self-feedback replaces a reward model you cannot build with a critic that shares the policy's blind spots. That trade is not free and it is not always bad — it works when the critique is grounded in something checkable (does the project run, does the file exist, does the test pass), and it fails when the critique is a judgement the model can flatter. The engineering is deciding which of those two situations you are in.

2 · The mental model #

The mental model: self-feedback is a reward with a correlated error term. Write the reward as the true objective plus two errors — one the critic can see and one it cannot:

Rsf(y) = r*(y)  +  εvisible(y) − εshared(y) ε_visible is a defect the critic detects and fixes; ε_shared is a defect the critic systematically misjudges because it is the same model. Optimisation amplifies whatever survives.

Because the critic is sampled from the same model, self-feedback has a specific equilibrium problem: the policy can learn to produce artifacts that this critic cannot fault, which is not the same as artifacts that are good. Two structural defences exist and both are about grounding:

DefenceMechanismWhat it fixesWhat it cannot fix
Executable groundingThe critique must cite a command and its output (build, test, lint, run)Turns ε into something checkableAnything the checks do not cover — design, intent
Rubric groundingThe critique must score named criteria with evidence, not a global "good"Reduces flattery and length biasA rubric can be satisfied literally and wrongly
Stop ruleIterate until the critique produces no new falsifiable defect, with a hard round capPrevents infinite self-approval loops and token burnCannot tell you the loop converged on the wrong fix

What "correlated error" gets right

It predicts the observed pattern in self-refinement: iterations fix superficial, checkable problems first and then stop improving, while the transcript gets longer and more confident.

Where it breaks

The critic is not one model — a fresh sample with a fresh prompt has partial independence, which is why one round often helps and five rounds do not. Treat independence as a resource that decays with rounds, not a property of the critic.

3 · The mechanism #

The loop, with the stop rule made explicit:

loop:   yt+1 ← revise( yt, critique(yt) )  until  noNewFalsifiableDefect(critique(yt))  or  t = T "Falsifiable" is the load-bearing word: a defect must name something you can check. "The code could be cleaner" is not a stop condition, it is a licence to loop.

Two numbers to instrument, because self-feedback without them is indistinguishable from doing nothing expensively:

  • New-defect yield per round. If round 3 produces no new checkable defect, the loop is done, whatever it says. If round 3 produces defects but they are all about style, the critic has drifted to the easy surface.
  • Regression rate per round. Each revision must be re-checked against everything previously satisfied. Self-revision that fixes one thing and breaks another is common and invisible unless you run the full check suite each round.
# L68: self-feedback loop with a stop rule and per-round accounting. # The "artifact" is a set of criteria -> satisfied?. The critic is a noisy, partly blind detector. # Pure stdlib. import random CRITERIA = ["runs", "tests_pass", "handles_empty", "docstring", "no_global_state"] # How well a self-critic can SEE a missing criterion. Executable ones are visible; the ones # the model also authored are mostly invisible to it -- that is the shared blind spot. VISIBILITY = {"runs": 0.95, "tests_pass": 0.95, "handles_empty": 0.55, "docstring": 0.30, "no_global_state": 0.25} TOKENS_PER_ROUND = 40000 def critic(art, rng): return [c for c in CRITERIA if not art[c] and rng.random() < VISIBILITY[c]] def revise(art, defects, rng): new = dict(art) for d in defects: new[d] = True for other in CRITERIA: # any fix can silently break something else if other != d and new[other] and rng.random() < 0.15: new[other] = False return new def independent(art): return sum(art.values()) / len(CRITERIA) def run(limit=8, stop_on_zero=True, seed=2): rng = random.Random(seed) art = {c: False for c in CRITERIA} rows = [] for r in range(1, limit + 1): defects = critic(art, rng) score = independent(art) rows.append((r, len(defects), score, r * TOKENS_PER_ROUND)) if not defects: if stop_on_zero: break continue art = revise(art, defects, rng) return rows, art print(f"{'round':>6}{'defects raised':>16}{'independent score':>19}{'tokens':>10}") rows, art = run() for r, d, s, t in rows: print(f"{r:>6}{d:>16}{s:>19.2f}{t:>10,}") print(f"final artifact: {art}") print("\nthe loop stopped at round", rows[-1][0], "because the critic saw NOTHING,") print("at an independent score of", round(rows[-1][2], 2), "-- i.e. one criterion is still unmet") print("and the critic is structurally blind to it. That gap is the ceiling of self-feedback.") # cost of not having the stop rule rows_all, _ = run(limit=8, stop_on_zero=False) print(f"\nwithout the stop rule, tokens spent: {rows_all[-1][3]:,} for the same final artifact") print(f"with it: {rows[-1][3]:,}")

The same rule applies to any refinement pipeline: if defect yield is zero, more rounds cannot help, because there is nothing left that the critic can see.

Experiment 3 — raise the visibility of one criterion

Change no_global_state from 0.25 to 0.95 and re-run. The grounded check turns an invisible defect into a visible one.

VISIBILITY = {"runs": 0.95, "tests_pass": 0.95, "handles_empty": 0.55, "docstring": 0.30, "no_global_state": 0.95} # <- now grounded

The ceiling moves from 0.80 to 1.00: the loop converges because the critic can see everything. That is the whole argument for grounding a critique in a check rather than in an opinion. Remove the executable criteria and the ceiling drops to whatever the model can judge about itself.

5 · Failure modes #

  • Critic flattery. Symptom: the artifact gets worse by an external measure while the self-critique says "looks good"; correlate critique score with an independent grader to detect it.
  • No stop rule. Symptom: token spend grows every round while defect yield is zero; the model keeps finding stylistic "improvements".
  • Regression without re-check. Symptom: round N fixes defect A and reintroduces defect B, which was fixed in round N−2. Only a full re-check per round catches it.
  • Unfalsifiable critique. Symptom: transcripts full of "could be more robust" and "consider edge cases" with no command, file, or line referenced.
  • Reward collapse onto style. Symptom: revisions change naming and formatting but not behaviour; diff size grows while test results are unchanged.
  • Loop-induced overfitting to the critic. Symptom: the artifact satisfies the model's own rubric while failing the human rubric that motivated the work.

For every self-feedback loop, log per round: round number, defects raised, defects falsifiable, defects verified fixed, regressions, tokens spent, and an independent score. A loop is only an improvement loop if the independent score moves; otherwise it is a transcript generator.

7 · Self-check #

Q1. Why does a self-feedback loop need a full re-check of all previously satisfied criteria every round?

Reveal answer

Because revision is not monotone. A change that fixes defect A can reintroduce defect B, and if you only check the newlyraised defect, you will not see it. The regression rate per round is the metric that reveals this, and it is only measurablewith a full check suite run at every iteration. Without it, a five-round loop can end worse than round one while every roundreports progress.

Q2. Quantitative: 5 rounds, 40k tokens per round, defect yields [3, 2, 1, 0, 0]. How much of the budget was spent after the loop had converged, at a stop rule of no-new-defect?

Reveal answer

Convergence at round 3 (first zero-yield round is round 4; a correct stop rule halts after round 3's yield of 1 is resolved).Rounds 4 and 5 spend 80k tokens for zero defects. With a hard stop on zero yield, you cut 40% of the spend. This is thecheapest single improvement available to any self-refinement pipeline.

Q3. What distinguishes a falsifiable critique from an unfalsifiable one?

Reveal answer

A falsifiable critique names something checkable: a file, a line, a failing command, a missing test, a numerical result.An unfalsifiable one names a quality (more robust, cleaner) with no way to determine whether the revision achieved it.Only falsifiable critiques can drive an improvement loop, because only they give a criterion for stopping.

Q4. Diagnostic: your self-refinement loop's artifact passes all internal checks but a human reviewer rejects it. What happened and what does it tell you about the critic?

Reveal answer

The loop converged on the critic's fixed point, which is not the human's. The critic's coverage and the human's intent differ:the human may care about design, intent, or constraints the rubric never encoded. It tells you the critic set the ceiling of theloop, and that the ceiling is below the task. Fix: ground the critique in the user's stated wish plus an external check, and adda human or independent-model review to the gate.

Q5. When is self-feedback the right choice over training a reward model?

Reveal answer

When you cannot afford the data for a reward model but you can afford a critique that is grounded in execution — andwhen the task's success is partially checkable. The execution grounding is what keeps the correlated error bounded. If nothingabout the task is checkable, self-feedback is a preference model with one annotator who is also the policy: expect it to teachthe model's own taste, including its flaws.
