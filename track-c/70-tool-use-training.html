L70 · Training tool use: format, execution feedback, recovery

Formatting a tool call is the easy half. The behaviour that separates a demo from an agent is what happens after the tool returns an error — and only execution feedback can train it.

~26 min difficulty ●●●○○ build: tool-call-from-execution trainer
tool schema argument validation fault injection recovery rate final-state verifier step budget execution feedback tool hallucination

1 · Why it exists #

A model that emits a perfect tool call with the wrong argument types is worse than one that does not call the tool at all: the failure is silent, the retry is invisible, and the agent's transcript looks confident. The failure this lesson addresses is format without execution — models trained on tool-call syntax but not on what happens when the call runs.

Execution feedback changes the learning signal in a way that is hard to overstate. Once a call actually runs, you get three free supervision signals that no amount of textual imitation supplies:

  • Validity: the arguments parse against the schema and the tool accepts them.
  • Outcome: the result is the one the task needed, checkable by the environment's verifier.
  • Recoverability: the model's response to an error — timeout, 500, malformed JSON — is observable and trainable, and this is the behaviour that separates a demo from an agent.

Tool use is not a formatting skill, it is a control problem: choose a call, predict its effect, verify the result, recover from failure. Train it against execution or you are training a text generator that happens to emit JSON. state as of 2026-10 — DeepSeek-V3.2 is described as the first DeepSeek model to integrate thinking directly into tool-use, which is the same observation from the model side: the model reasons about the tool result, not just before the call.

2 · The mental model #

The mental model: a tool call is a typed function application with an unknown return value. The training environment is a loop:

plan → call(tool, args) → validate(schema) → execute → observe(result | error) → reason → call | answer

There are five places it can break, and each needs its own supervision:

StageFailureWhat trains it
SelectionWrong tool, or no call when one is neededDemonstrations + outcome reward
ArgumentsRight tool, schema-invalid argumentsSchema validation as a hard gate; deterministic error message as feedback
ExecutionTool errors: timeout, 4xx/5xx, empty resultFault-injected environments; train the recovery, not just the happy path
InterpretationReads the result wrong, or ignores itOutcome reward on final state; tasks where the result must be used
StoppingLoops forever, or stops before the state is correctStep budget as part of the reward; final-state verifier

What "typed function application" gets right

It makes the argument layer decidable: a schema validator is a verifier with no ambiguity, and an invalid call is a training signal with a precise error message attached.

Where it breaks

Real tools are not pure functions. They have side effects, rate limits, partial failures and stale reads. A model trained only on clean stub responses learns a world that does not exist, and the first production incident teaches it something no amount of schema validation will.

3 · The mechanism #

The reward, written so each component can be switched off to measure its contribution:

R = 1[final state correct]  +  λs · 1[all calls schema-valid]  −  λb · (steps / B) The state term is the objective, the schema term is a guard against degenerate formatting, the step term prices the budget. Never reward call COUNT: that trains looping.

Two design choices that experiments will make for you:

  • Reward the recovery, not the retry. If a failed call followed by a correct call scores the same as a first-try success, the model learns nothing about diagnosis. Give a small penalty for each error observed and a larger one for failing to recover.
  • Never reward the plan text. A well-written plan that is not executed is worth zero; the final state is the only thing the environment can verify.

Returns (ok, result_or_error).""" if tool == "get_balance": return True, {"balance": START_BALANCE} if tool == "transfer": r = rng.random() if r < faults.get("timeout", 0): return False, "timeout" if r < faults.get("timeout", 0) + faults.get("flaky_500", 0): return False, "http_500" if args["amount"] > START_BALANCE - args.get("already_sent", 0): return False, "insufficient_funds" return True, {"sent": args["amount"]} return False, "unknown_tool" def run_episode(policy, faults, seed): rng = random.Random(seed) history, sent = [], 0 for step in range(1, 9): action = policy(history, sent) if action is None: return finish(history, sent, step - 1) tool, args = action if tool == "get_balance": ok, payload = execute(tool, args, faults, rng) else: ok, payload = execute(tool, {**args, "already_sent": sent}, faults, rng) if ok: sent += args["amount"] history.append((tool, args, ok, payload)) return finish(history, sent, 8) def finish(history, sent, steps): errors = sum(1 for _, _, ok, _ in history if not ok) return dict(final_ok=sent >= TARGET, steps=steps, errors=errors, recovered=errors > 0 and sent >= TARGET) def reward(ep, lam_b=0.1, budget=8): """Final-state objective minus a step price. Never a reward for call count.""" return (1.0 if ep["final_ok"] else 0.0) - lam_b * (ep["steps"] / budget) def blind_policy(history, sent): """One big transfer, ignores every error.""" return ("transfer", {"amount": 250}) if not history else None def adaptive_policy(history, sent): """Reads the error. Asks for the balance first, retries transient faults, shrinks on funds.""" if not history: return ("get_balance", {}) last_ok = history[-1][2] last_payload = history[-1][3] remaining = TARGET - sent if remaining <= 0: return None if not last_ok and last_payload == "insufficient_funds": return ("transfer", {"amount": max(remaining - 40, 1)}) if not last_ok and last_payload in ("timeout", "http_500"): return ("transfer", {"amount": remaining}) if sent == 0: return ("transfer", {"amount": 250}) # over-asks on purpose -> learns from the error return None print(f"{'policy':<12}{'faults':<20}{'final ok':>9}{'errors/ep':>11}{'recovered':>11}{'reward':>9}") for name, pol in (("blind", blind_policy), ("adaptive", adaptive_policy)): for label, faults in (("clean", {}), ("timeout 20%", {"timeout": 0.2}), ("timeout+500 40%", {"timeout": 0.2, "flaky_500": 0.2})): eps = [run_episode(pol, faults, seed) for seed in range(200)] print(f"{name:<12}{label:<20}" f"{sum(e['final_ok'] for e in eps) / len(eps):>9.3f}" f"{sum(e['errors'] for e in eps) / len(eps):>11.2f}" f"{sum(1 for e in eps if e['recovered']) / len(eps):>11.3f}" f"{sum(reward(e) for e in eps) / len(eps):>9.3f}")

4 · Your hands #

Three labs: run an execution loop against a deterministic stub with fault injection, score it with the reward above, and measure how much recovery behaviour the reward actually teaches.

Experiment 1 — two policies, three fault regimes

A bank-transfer task, a deterministic stub with a seeded fault injector, and two scripted policies: one that makes a single large call and ignores every error, one that reads the error and adapts. The reward is the final state minus a step price.

The blind policy is perfect on a clean environment and falls to 0.785 and 0.590 as faults are injected. The adaptive policy stays at 1.000 in every regime. This is the argument for fault injection: the difference between the two policies is invisible on clean data, so a training suite without faults teaches the blind policy and reports success.

Experiment 2 — remove the step price and re-run

Set lam_b = 0.0, then set the budget to 2 so the 8-step cap is punitive.

With no step price, a policy that reads the balance on every step scores the same as one that finishes in two, and the reported reward is dominated by episode length. With a tight budget the price is paid on every episode and final success no longer dominates — which is the cost you deliberately accept when latency is the product constraint.

Experiment 3 — the episode record you need for tool-use training

These fields per episode are what make a tool-use run debuggable and auditable.

{"episode": 17, "calls": [{"tool": "get_balance", "ok": true}, {"tool": "transfer", "args": {"amount": 250}, "ok": false, "error": "insufficient_funds"}, {"tool": "transfer", "args": {"amount": 160}, "ok": true}], "steps": 3, "schema_violations": 0, "tool_errors": 1, "recovered": true, "final_state_ok": true, "reward": 0.9625}

Aggregate recovered / tool_errors across episodes: that ratio is the recovery rate, the number that" " predicts production behaviour. Without per-episode records you can compute final accuracy and nothing else — which is how a" " model that never recovers from a 500 ships without anyone noticing.

5 · Failure modes #

  • Format-only mastery. Symptom: valid JSON in 100% of calls, invalid semantics in a large fraction; check by validating arguments against constraints, not just types.
  • Never-recovers. Symptom: after a tool error the model repeats the same call verbatim; the environment never injected errors during training.
  • Loops within budget. Symptom: step count at the cap on most tasks, with the final state unchanged; reward has no step term or the cap is too loose.
  • Ignores the result. Symptom: the final answer contradicts the tool output it just received; the outcome verifier should catch it — if it only checks the answer string, it will not.
  • Tool hallucination. Symptom: calls to tools that do not exist or with fields the schema never defined; a schema validator as a hard gate fixes the reward, not the model.
  • Overfitting to stubs. Symptom: excellent on the synthetic environment, poor on the real API; the realistic difference is latency, pagination, rate limits and partial data.

Log per episode: calls made, schema violations, tool errors, recoveries, steps used, final-state correctness. The interesting one is recoveries — a tool-use model that never recovers is a formatter, and the recovery rate is the number that predicts production behaviour.

7 · Self-check #

Q1. Why does rewarding the number of successful tool calls train looping?

Reveal answer

Because the reward is unbounded in the action count: if each successful call pays, the optimal policy is to make as manycalls as the cap allows. This is lesson 75's pattern in miniature. Reward the final state, guard the format, and price thesteps — then the only way to score is to reach the goal in few calls.

Q2. Quantitative: 1,000 episodes, 3,200 calls, 210 schema violations, 140 tool errors, 96 recoveries, mean steps 3.2. What is the recovery rate and what does it tell you?

Reveal answer

Recovery rate = 96/140 = 0.686. Two thirds of tool errors are eventually recovered from, one third leave the episode failedor looping. If that number is near zero, the environment never taught recovery; if it is near one, the errors injected were tooeasy to detect.

Q3. A schema validator rejects 8% of the model's calls at serving time while training had 1%. Give two hypotheses and one check each.

Reveal answer

(a) Schema drift: the serving tool schema differs from the one used in training — check by diffing the two schemas. (b) Prompt orcontext difference: the model sees a different tool description at serving — check by dumping the exact tool list in each path. Bothare configuration, not model, defects, which is why the first 10 minutes of any tool-use incident is schema diffing.

Q4. Why is 'recovers from a 500 by retrying once, then switching strategy' worth more as a training signal than 'makes a valid call on the first try' in production terms?

Reveal answer

Because first-try validity is already near-saturated in training, while recovery is the behaviour that determines whether theagent completes tasks when the world misbehaves. The marginal value in production is entirely in the tail: retries with backoff,fallback tools, and graceful partial answers. The training environment must inject these faults deliberately, because thehappy-path data dominates by default.

Q5. Design the smallest environment that can teach recovery, and list its three required properties.

Reveal answer

A stub tool with a seeded fault injector, a task verifier on final state, and a step budget. Required properties: (1) seededdeterminism so faults are reproducible; (2) a distinct error message per fault type, so recovery can be conditioned on it; (3) thefault schedule is not inferable from the prompt, so the model must use the observed error rather than the task text.
