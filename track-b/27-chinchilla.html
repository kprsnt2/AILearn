L27 · Chinchilla: Compute-Optimal Data vs Params

A 280B model on 300B tokens and a 70B model on 1.4T tokens cost the same compute, and the small one won. Fixed budget, two substitutable inputs, one best split — and 2021 practice was consistently on the wrong side of it.

~30 min difficulty ●●●○○ build: compute-optimal calculator
compute-optimal split 20 tokens per param parametric loss law C = 6ND budget line unique-token ceiling data-hungry regime under-trained vs over-trained

1 · Why it exists #

From 2020 to mid-2022 the dominant strategy was buy parameters. GPT-3: 175B parameters on ~300B tokens (about 1.7 tokens per parameter). Gopher: 280B on 300B tokens (about 1.1 tokens per parameter). Loss was believed to be dominated by parameter count, so the data was an afterthought.

That is a mistake because training compute is a product, not a sum: C ≈ 6ND. Doubling N at fixed C forces you to halve D. Every lab was picking a point on that trade-off, and nobody had measured where the minimum was.

The same order of money. A 4× smaller model on 4.7× more data, with 17% more compute, beat the big one on essentially every benchmark. Hoffmann et al., Training Compute-Optimal Large Language Models arXiv:2203.15556, concluded that many contemporary large models were substantially under-trained: they had bought parameters they could not feed.

Your budget fixes N×D. One split of that product minimises loss, it is near 20 tokens per parameter, and picking wrong means you paid full price for a model that scores like one at half the compute. Chinchilla is the difference between a research bet and a procurement decision.

2 · The mental model #

Analogy (labelled): a fixed budget for a kitchen. Burners = N, cooking hours = D. Buying more burners without more hours is waste; more hours without burners just queues food. One ratio is best.

The precise picture is an isoFLOP slice. Hold C fixed. For each candidate N, set D = C/(6N) and plot loss against N on a log axis. You get a convex U: too few parameters cannot represent the function (the B/D term is fine, the A/Nα term is not), too many parameters means starved data (now A/N is fine and B/D dominates). The bottom of the U is Nopt(C). Stack the bottoms from many budgets and you get a line — and that line is a power law, which is why one ratio works at every scale for a while.

What the analogy gets right

Two substitutable inputs, one interior optimum, a smooth convex penalty for being off it. It also gets the asymmetry right: starving data hurts more than overspending parameters, at every ratio above the optimum.

Where it breaks

Real kitchens have a hard ceiling: you cannot cook more hours than there are distinct recipes. Chinchilla assumes unlimited high-quality tokens. Past the unique-data wall the U's right arm is clipped and the true optimum is against the wall — deliberately over-trained. That is lesson 28.

3 · The mechanism #

Hoffmann et al. propose three ways to fit the same law. The one that is easy to reason about has an additive parametric term and an additive data term:

L(N, D) = E + A / Nα + B / Dβ E ≈ 1.69 is irreducible loss (the entropy of text itself); A/Nα is the parameter shortfall; B/Dβ is the data shortfall. Fitted values reported by the paper: A ≈ 406.4, B ≈ 410.7, α ≈ 0.34, β ≈ 0.28. N is non-embedding params, D is tokens.

Minimise subject to C = 6ND. A Lagrange multiplier gives ∂L/∂N = λ·6D and ∂L/∂D = λ·6N; eliminating λ gives αA/Nα+1 · N = βB/Dβ+1 · D, which rearranges to the allocation exponents:

Nopt ∝ Cβ/(α+β) = C0.4516   ,   Dopt ∝ Cα/(α+β) = C0.5484 The two exponents sum to exactly 1 because β + α over α + β is 1. Consequence: σ a 10× larger budget wants 100.4516 = 2.83× more parameters and 100.5484 = 3.53× more tokens.

Because they sum to 1, the ratio D/N ∝ C0.0968. That exponent is small enough that over six decades of budget (1020 to 1026 FLOPs) the optimal ratio only moves 100.581 = 3.8×, and over four decades only 2.44×. That is the honest justification for the “20 tokens per parameter” rule of thumb: it is not exact, it is robustly approximately correct, and the exponents are what make it so.

The calculator you will actually use

If you fix the ratio r = D/N (from 20, or from a measurement), the allocation is trivial:

N = C / (6 r)      D = r N = C / 6 The tokens you need depend only on compute, not on r at all — because C = 6ND fixes D = C/6 once you have spent C. Choosing r is choosing how many parameters to split those tokens across.
Budget Cr = 20 ⇒ ND = C/6Verdict

1025 FLOPs1025/120 = 8.33×10131.67×102483T params — physically absurd

That last row is the real lesson of the post-Chinchilla era. The compute-optimal point leaves the available data almost immediately; no one has 1.67 quadrillion unique tokens. So the frontier does not follow Chinchilla, it stops at the data wall and then deliberately over-trains — which is L28.

Make r auditable. Every pretraining run should log (N, Dunique, C = 6ND, r, loss). Then “was this run compute-efficient?” is one recomputable ratio, not a narrative. Same discipline as your JobAgents scoring: the answer is the artefact, not the opinion.

4 · Your hands #

Experiment 1 — score any two runs on the same axis

This is the calculation from section 3, runnable. Change N and D to your own candidates; the loss is directly comparable only because C is the same.

# Chinchilla parametric law: L = E + A/N^alpha + B/D^beta E, A, B, al, be = 1.69, 406.4, 410.7, 0.34, 0.28 def loss(N, D): return E + A / N**al + B / D**be for name, N, D in [("Gopher ", 280e9, 300e9), ("Chinchilla", 70e9, 1.4e12)]: print(f"{name} N={N/1e9:6.0f}B D={D/1e12:5.2f}T C={6*N*D:.3e} L={loss(N,D):.4f}") # Gopher N= 280B D= 0.30T C=5.040e+23 L=1.9932 # Chinchilla N= 70B D= 1.40T C=5.880e+23 L=1.9366

0.0566 nats in favour of the smaller model at essentially the same compute. If you get a different picture — Gopher winning — you swapped the exponents (they are easy to swap; α belongs to N).

Experiment 2 — walk an isoFLOP slice and read its shape

Explore what happens when you hold C fixed and sweep the ratio. Use a budget small enough to see the U (22 FLOPs is the smallest at which the parabola is not lost in the noise of E; even here it is shallow, which is a finding rather than a bug).

E, A, B, al, be = 1.69, 406.4, 410.7, 0.34, 0.28 C = 1e23 for r in (1.7, 5, 10, 20, 50, 100, 200, 400): N = C / (6 * r); D = C / 6 print(f"r={r:6.1f} N={N/1e9:9.1f}B L={E + A/N**al + B/D**be:.4f}")

The honest result at 1023 FLOPs is that the slice is almost flat — loss barely moves between r = 1.7 and r = 200 because the data term is already tiny at D = 1.67×1022 tokens. That is a real property, not a bug: the ratio only matters where D is small enough for a token to be worth something. The U-curve becomes visible at realistic N (109–1011) where, holding N = 70B and raising r from 20 to 200, loss falls from 1.9366 to 1.8591. Falsification for this lab: if your slice genuinely curves into a visible U at 1023 FLOPs with these constants, you have a typo in the exponents.

Experiment 3 — prove the ratio drifts, so you know how much to trust it

Three lines of exponent arithmetic. If a vendor tells you “the optimal ratio is fixed forever,” this shows how it actually moves.

python -c " al,be=0.34,0.28 a_n=be/(al+be); a_d=al/(al+be) print('N grows C^%.4f, D grows C^%.4f, D/N grows C^%.4f' % (a_n,a_d,a_d-a_n)) for dec in (2,4,6): print('%d decades -> D/N moves %.2fx' % (dec, 10**(dec*(a_d-a_n)))) for x in (0.5,2,10): print('%.1fx compute -> N x%.2f, D x%.2f' % (x, x**a_n, x**a_d)) "

D/N exponent = 0.0968; 2 decades → 1.56×, 4 decades → 2.44×, 6 decades → 3.81×. The per-multiplier lines: 10× compute → N ×2.83, D ×3.53; 2× compute → N ×1.37, D ×1.46. If your numbers differ, check that you used (a_d − a_n) and not (a_d + a_n) — the sum is 1 and would give a nonsense 10× drift per decade.

5 · Failure modes #

  • Applying the law past the data wall. Symptom: the plan needs 16.7T unique tokens, the corpus has 8T, so you run 2 epochs — and the loss curve knees at exactly one epoch and finishes above prediction.
  • Counting tokens instead of unique tokens. Symptom: two corpora with identical token counts produce a repeatable loss gap; one had 3× the deduplicated content. Log unique_tokens next to tokens.
  • N includes embeddings. Symptom: predictions are a few percent optimistic, and the error is larger for large-vocab / shallow models. The law's N excludes embedding and unembedding matrices.
  • Coefficient transplant. Symptom: you refit on your own domain (clinical notes, code, log lines) and get a materially different exponent — typically lower α, because low-entropy text makes data the binding constraint. Refit on a 6–8 point ladder before trusting any published E, A, B.
  • Reading nats as benchmark points. Symptom: a 0.02-nat difference looks negligible in a report but corresponds to a visible benchmark gap, so a run gets cancelled that should not have been — or the reverse. Never convert one to the other with a rule of thumb.

7 · Self-check #

Q1. Why do the allocation exponents β/(α+β) and α/(α+β) sum to 1, and what does that force on the D/N ratio?

Reveal answer

Trivially: (β + α)/(α + β) = 1. So both Nopt and Dopt are proportional to Csome power and their growth is symmetric in log space, leaving D/N ∝ C0.0968. Because the exponent of the difference is small, the optimal ratio is nearly constant — the entire justification for a fixed tokens-per-parameter rule over the scales anyone builds at.

Q2. You have 6×1023 FLOPs. What is D = C/6, what N does r = 20 require, and how many H800-hours is the run at MFU 0.40 (989 TFLOP/s dense bf16)?

Reveal answer

D = C/6 = 1.0×1023 tokens. N = C/(6×20) = 5×1021 — five trillion parameters, which is exactly the absurdity. GPU-hours = C / (3600 × 0.40 × 989×1012) = 6×1023 / 1.424×1018 = 4.21×105 = 421,000 H800-hours. The arithmetic is easy; the feasibility is the entire engineering problem, and it is why L28 and L30 exist.

Q3. Diagnostic: your 20:1 planned run finishes 0.03 nats above prediction and the loss curve has a knee at exactly one epoch. Name the cause and the one chart that proves it.

Reveal answer

Data repetition at the unique-token wall. The knee is the moment the sampler revisits seen tokens. The chart: loss against unique tokens consumed. If the curve snaps back onto the scaling-law prediction on that x-axis, the wall was the cause and the fix is more unique data or fewer parameters — not more steps.

Q4. Two plans, same compute: (A) 70B / 1.4T, (B) 140B / 700B. Score both with the parametric law and state the direction of the error a naive “bigger is better” instinct makes.

Reveal answer

Both are 6ND = 5.88×1023. L(A) = 1.69 + 0.0835 + 0.1632 = 1.9367; L(B) = 1.69 + 406.4/(1.4×1011)0.34 + 410.7/(7×1011)0.28 = 1.69 + 0.0660 + 0.1981 = 1.9541. B is 0.0174 nats worse. Direction: halving the data costs more than doubling the parameters buys. The instinct systematically over-parameterises.

Q5. Your VP says “Chinchilla proved big models are unnecessary.” Correct that in one quantitative sentence.

Reveal answer

Chinchilla showed that for a fixed budget you should trade parameters for tokens — not that parameters stop mattering. With 10× the compute the compute-optimal N still grows 2.83× (C0.4516) alongside 3.53× more tokens (C0.5484). Big models remain necessary; the 2021-era ones were simply being built on 1/20th of the data they needed.
