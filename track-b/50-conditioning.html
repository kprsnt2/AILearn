L50 · Conditioning, In-Context Learning, and Why Prompts Work

A prompt is not an instruction the model obeys — it is a prefix that the model conditions on, writing features into the residual stream that later layers read. That distinction predicts exactly when few-shot examples help, when a distractor destroys a task, and when you need fine-tuning instead.

1 · Why it exists #

The failure this lesson kills is the mental model itself. If a prompt were an instruction, then adding more clarifications would monotonically improve output, examples would always help, and the order of sections would not matter. None of that is true, and teams spend weeks reordering words to chase effects they cannot explain.

What is actually happening state as of 2026-10: the model is a causal sequence predictor, and the prompt is the sequence. Every token in it writes into the residual stream (L48) and changes the distribution over the next token at every subsequent position. There is no separate "instruction channel" — a system prompt that says “answer as a JSON object with keys a and b” helps because the model has seen that pattern in pretraining and because the tokens prime the format, not because the model reads it as a specification.

The cost side is equally concrete. Each few-shot example is ordinary prompt tokens: at 150 tokens per example, five examples cost 750 tokens of prefill, and at 13B active that is 2 × 13×109 × 750 = 1.95×1013 FLOPs on every single call, plus 750 × 70,272 = 52.7 MB of cache. Prompt engineering is therefore also a cost discipline, and the two trade off — more examples cost more and do not monotonically help.

Prompts work by conditioning, not by instructing. So more text is not more control: what matters is whether the context contains a pattern the model has learned to complete, and whether competing patterns are present.

2 · The mental model #

Analogy (labelled): a tapestry weaver who has studied thousands of patterns. You show them a fragment of pattern and they continue it in that style. Showing one clean fragment sets the pattern more reliably than describing it in words; showing a fragment that is almost the right pattern sets the wrong one.

What the analogy gets right

Completion of a demonstrated pattern is more reliable than a verbal description, and near-miss demonstrations steer toward the wrong pattern. It also explains why the first fragment matters most — it sets what the rest is read against.

Where it breaks

A weaver has intentions and understands what you want. There is no such channel here: the model is doing weighted next-token prediction, so "instruction" and "example" and "data" all compete as tokens in one causal context. That is why a long document with an instruction buried in the middle can be worse than the instruction alone.

The three mechanisms behind in-context learning

MechanismWhat it doesEvidence / observable
Pattern completionInduction circuits copy the mapping from the demonstrated examplesInduction score (L49) is high; accuracy collapses with ambiguous examples
Task identificationExamples select among behaviours the model already has in its weightsPerformance jumps between 1 and a few examples, then flattens
Format primingThe shape of the output is copied from the last example seenOutput style tracks the final example, not the average

All three are the same underlying phenomenon — context changes the conditional distribution — but they have different consequences. Task identification explains why zero-shot sometimes beats one-shot (if the single example misleads), and format priming explains why the last example in a prompt disproportionately sets style.

3 · The mechanism #

p(y | prompt) = pθ(y | x1, …, xk, xquery)  —  conditioned, not instructed Every prompt token shifts the model's conditional distribution. Formally there is no distinction between "system instruction", "example" and "user data" except their position in one causal chain. That is the entire mechanism; everything below is a consequence.

The cost is linear and completely predictable, which means the decision rule is too: add shots only while the accuracy gain exceeds the cost and, crucially, while it does not add ambiguity. In practice task identification saturates by 3–5 examples, and beyond that you are paying for tokens that mostly act as competitors to the induction match (L49, Experiment 2) — which is why the accuracy curve often declines past ~10 shots before flattening.

Why distractors are worse than missing examples

A missing example leaves the pattern under-specified, so the model falls back on priors — usually the safest behaviour. A wrong example actively writes the wrong pattern into the context and gives the induction circuit a competing match. That is why one off-format example can cost more than removing all examples, and why curated few-shot beats plentiful few-shot for anything with a strict output contract.

Order effects and the recency gradient

Because attention is positional and the stream is causal, tokens near the end of the prompt are read by more layers as “recent context” and have disproportionate influence on formatting. Two measurable consequences:

  • Style follows the last example. Put your canonical example last.
  • The instruction should be near the end, not the beginning, when both compete — but putting it first maximises prefix-cache hits (L45). This is a real trade: cache savings versus conditioning strength. For a stable system prompt the cache win usually dominates; for an instruction that must beat conflicting context, place it late.

When in-context learning is the wrong tool

Use conditioning when…

The task is a pattern the model has seen in pretraining, the contract is simple, and the data changes per request. Few-shot and clear format examples genuinely work here, and iteration is cheap.

Fine-tune when…

The behaviour must be reliable under adversarial input, the output contract is strict and machine-validated, or per-call token cost matters at volume. Every demonstration is repaying prefill on every call; a fine-tune pays once and moves the pattern into the weights, which is the difference between conditioning and learning (L41, L51–L52).

Treat a prompt as a versioned artifact with a measured contract. The artifact is: prompt text hash, number of shots, shot ordering, token count, per-case output validity (does it parse? does it match schema?), and an accuracy figure with a confidence interval. Any of those changing without a version bump is an unreproducible result waiting to happen.

4 · Your hands #

Experiment 1 — measure the shot curve and find the saturation point

The experiment that replaces prompt folklore. Start at zero shots, add one at a time, and stop where the curve stops paying. Report cost on the same axis.

# Pseudo-API: replace with your client. The structure is the point. def evaluate(n_shots, cases, make_prompt, call): correct = 0; tokens_used = 0 for c in cases: prompt = make_prompt(n_shots, c) out = call(prompt) tokens_used += len(prompt) correct += int(out.strip() == c["gold"].strip()) return correct / len(cases), tokens_used / len(cases) for n in (0, 1, 2, 3, 5, 8, 12, 20): acc, toks = evaluate(n, cases, make_prompt, call) print(f"shots={n:2d} acc={acc:.3f} prompt_tokens={toks:7.0f} " f"FLOPs/call={2*13e9*toks:.2e} \$index={2*13e9*toks:.2e}")

Expect accuracy to rise sharply from 0 to 2–3 shots and then flatten or wobble. The decision rule: pick the smallest shot count within one standard error of the best — the extra shots buy nothing and cost prefill on every call. If accuracy declines at high shot counts, you are seeing induction competition, and the fix is curation (fewer, cleaner examples), not more examples.

Experiment 2 — quantify distractor damage

A controlled test of the claim that a wrong example is worse than no example. Run all four conditions on the same case set so the comparison is fair.

python -c " conditions = [ ('zero-shot', 0, 0), ('3 clean shots', 3, 0), ('3 clean + 1 partial',3, 1), ('1 partial only', 0, 1), ] for name, clean, partial in conditions: tokens = clean*150 + partial*150 print(f'{name:22s} clean={clean} partial={partial} tokens={tokens:4d} prefill FLOPs={2*13e9*tokens:.2e}') print() print('prediction: partial-only < zero-shot < 3 clean + 1 partial < 3 clean') "

The prediction to falsify is the ordering: a partially-correct example should damage performance more than no example at all (it writes the wrong pattern and competes for the induction match), and a good set plus one bad example should be worse than the good set alone. If your results do not show that ordering, either the task is too easy for conditioning to matter or your "partial" example is not actually near-matching the target pattern.

Experiment 3 — the position/order sensitivity check

Test whether the same prompt content in different orders gives materially different results. This is cheap to run and is the single best argument for versioning prompts.

import random, itertools random.seed(50) shots = ["ex1", "ex2", "ex3", "ex4"] def score(order, cases): # placeholder: replace with real evaluation return len(order), order accs = [] for perm in itertools.permutations(shots): n, order = score(perm, cases=None) accs.append(n) print(f"orderings tested: {len(accs)} (4! = 24)") print(f"prompt token count identical across orders? {len(set(accs)) == 1}")

All 24 orderings have identical token counts and identical prefill cost — and, in real evaluations, meaningfully different accuracy. That is the experiment to run before blaming a model: if your best and worst orderings differ by more than your percentile noise, your prompt's reliability is partly luck of ordering, and it will not survive a model upgrade.

5 · Failure modes #

  • Prompt-as-specification. Symptom: adding more clarifying sentences makes output longer and no more correct, and the important constraint gets ignored because it is buried. Move the constraint near the end and make it a demonstrated format, not a description.
  • Shot bloat. Symptom: token cost per call grows every sprint while accuracy is flat. The shot curve has saturated; every added example now costs prefill on every request for no gain.
  • Distractor contamination. Symptom: accuracy drops after someone adds a "helpful" edge-case example that is only half on-format. Audit examples for format fidelity, not just correctness.
  • Order dependence shipped as reliability. Symptom: accuracy collapses when examples are shuffled by the prompt builder, which some frameworks do automatically. Pin the ordering, and test the shuffle.
  • Conditioning where learning is needed. Symptom: prompt tweaks plateau at 85% while the requirement is 99.5% with schema validation. That plateau is the ceiling of conditioning; move to fine-tuning on validated examples (L52) or add a deterministic validator.

7 · Self-check #

Q1. Eight shots at 150 tokens each on a 13B-active model. What is the prefill cost per call, and what fraction of a 1,000-token prompt is that?

Reveal answer

Tokens = 8 × 150 = 1,200, so prefill = 2 × 13×109 × 1,200 = 3.12×1013 FLOPs. Against a 1,000-token base prompt (2.6×1013 FLOPs), the examples add 120% — more than doubling the prefill cost of every call. Cache cost: 1,200 × 70,272 = 84.3 MB per concurrent request.

Q2. Why can one wrong example be worse than zero examples?

Reveal answer

Zero examples leave the conditional distribution close to the model's prior, which is usually reasonable. A wrong example actively writes the wrong pattern into the context and gives the induction circuit a high-scoring competing match, so it steers toward the wrong format with confidence. The failure is not dilution but mis-conditioning — and it is why curated few-shot beats plentiful few-shot for strict output contracts.

Q3. Diagnostic: a prompt is 94% accurate in testing and 71% in production, same model version, and the input distribution looks similar. Name three prompt-level suspects.

Reveal answer

(a) Prompt-component ordering differs in production because the framework assembles sections dynamically (order effects); (b) production inputs trigger distractor competition — real data contains near-duplicates or off-format rows and the test set does not; (c) the production prompt injects variable content (retrieved chunks, timestamps) at the front, displacing the conditioning pattern and also destroying prefix cache hits. Compare full prompt bytes, not just templates.

Q4. You need 99.5% schema-valid output on a structured extraction task. Explain why conditioning alone will not get you there and what the two-part fix is.

Reveal answer

Conditioning shifts a probability distribution; it cannot guarantee a hard constraint, so some fraction of outputs will violate the schema regardless of prompt quality. The fix is (a) make the contract mechanical — constrained decoding / grammar-validated output (L18) — and (b) where accuracy still falls short, fine-tune on validated examples so the pattern lives in the weights rather than depending on per-call conditioning. Prompt engineering plus a validator is the engineering answer; prompt engineering alone is a hope.

Q5. Summarise Track B in three sentences: what governed model cost and capability from L26 to L50?

Reveal answer

(1) Capability follows a smooth power law in compute and data, with one right spend ratio — and once data runs out, deliberate over-training trades training dollars for cheaper serving. (2) The dominating operational cost shifted from parameters to memory traffic: sparse activation (MoE), compressed caches (MLA, token compression), sparse reads (DSA) and bandwidth-aware kernels (FlashAttention) all attack the same bytes-per-token term. (3) Architecture is now chosen against the serving bill rather than the loss alone — asymmetric phases, block paging, prefix caching and load balancing are all cost model entries, and the model's behaviour inside that budget (L48–L50) is conditioning, not instruction.
