L47 · Native Multimodal: Vision Encoding Into the Token Stream

A 1024×1024 image at patch size 16 is 4,096 tokens — more than a long article, and it hits the KV cache, prefill and concurrency bills exactly like text. Patch size, resolution and adapter design are cost decisions disguised as quality decisions.

~28 min difficulty ●●●●○ build: patchify an image, count tokens
patchify patch size vs tokens vision encoder projector / adapter native multimodal image token budget resolution trade-off cross-modal attention cost

1 · Why it exists #

An image is not free input. A language model consumes tokens, so the first thing any multimodal system must decide is how much of the image to turn into tokens — and that decision propagates straight into the bills from L33 to L45.

The canonical approach splits an image into fixed-size patches and treats each patch as a token. For an image of P×P pixels with patch size s, the token count is

tokens = (P / s)² This is a square of the resolution-to-patch ratio, so halving patch size multiplies tokens by 4, and doubling resolution also multiplies tokens by 4. Token cost is quadratic in the thing everyone wants more of (detail).

Worked: a 1024×1024 image at s = 16 gives (1024/16)² = 64² = 4,096 tokens. At s = 32 it is 32² = 1,024 tokens — a 4× difference for the same image. Now check it against the cache arithmetic: at 70,272 B/token that single image occupies 4,096 × 70,272 = 274.5 MiB of KV cache at patch 16 versus 68.62 MiB at patch 32. Ten images in one request would need 2.68 GiB versus 0.67 GiB of cache — the difference between serving 100 concurrent users and 400.

The failure mode that motivated native multimodal architectures: bolting a separate vision encoder onto a frozen language model creates a seam where visual information must be squeezed through an adapter trained on far less data than either side. It works for describing photos and fails on the tasks that matter — reading a table in a screenshot, comparing two diagrams, following a chart's axis. 2026 frontier models that advertise native multimodal training process images in the same token stream as text, sharing the attention and cache machinery.

An image is a token bill. Patch size and resolution decide the bill, the adapter decides how much of the image survives the trip into the model, and only native training removes the seam between them.

2 · The mental model #

Analogy (labelled): reading a document through a grid of peepholes. Few large peepholes mean cheap reading and coarse understanding; many small peepholes mean expensive reading and fine detail. You choose the grid before you look, and you cannot un-choose it later.

What the analogy gets right

The token budget is set by a structural choice made up front, and the trade is detail against cost. It also gets position right: each patch needs to know where it is, so positional encoding must be 2-D.

Where it breaks

Patches are not independent peepholes: attention lets patches see each other, so the model reconstructs spatial relations — which is why coarse patches sometimes work surprisingly well on layout questions while failing on small text. And an image's patch count does not include the cost of resizing the image intelligently, which is where real systems spend most of their engineering.

3 · The mechanism #

Step 1: patchify

Split the image into non-overlapping s×s patches, flatten each into a vector of s²×channels values, and project it to the model's dmodel. That projection is the only new parameters required, and it is small: s²×C × dmodel. At s = 16, C = 3, dmodel = 4096 that is 768 × 4,096 = 3,145,728 ≈ 3.15M parameters — negligible next to the language model, which is exactly why the naive approach looks cheap and then underperforms.

Twenty such images in a document request is 21.4 GiB of cache and 21.4 seconds of prefill. That is a product decision, and it is being made by whoever chooses the default resolution in the client.

Step 3: the adapter, and why it is where quality is lost

Between the vision encoder and the language model sits a projector, typically an MLP or a cross-attention block. It has two jobs that conflict:

  • Map visual features into the language model's embedding space (a representation change).
  • Compress — often a resampler reduces N patch tokens to M < N query tokens, which is the main lever for controlling cost.

Compression is where information is lost, and it is lossy in the same way the KV cache rank cap is (L33): a fixed number of query tokens cannot represent arbitrary visual detail. Table-reading and dense-text tasks are exactly where this shows up, because they need many independent small details rather than global scene understanding.

Step 4: the cost lands on every downstream lesson

Once image tokens are ordinary tokens, every previous cost model applies without modification:

  • Prefill (L35) is 2Nactive per token — images are expensive prompts.
  • KV cache (L33) holds image tokens exactly like text: 70,272 B each, and they are typically cache-hitting across turns, which makes prefix caching (L45) unusually valuable for image conversations.
  • Concurrency (L44) drops in proportion to images per request.
  • Quantization (L40) applies to image tokens' cached states with no special case.

That is the practical argument for native multimodal: when the architecture is one stack, the cost model is one stack. Adapters create two cost models — encoder compute plus language-model tokens — and two failure surfaces.

Log image tokens as a first-class metric, separated from text tokens, in every request trace. A workload that "doubled its token spend" is usually a client change to default resolution. Without per-modality token accounting you cannot see it, and no amount of model-side optimisation will recover it.

4 · Your hands #

Experiment 1 — patchify a real image and count the tokens

Do it on an actual image, not a number. This makes the token bill concrete and gives you the accounting you should emit per request.

# pip install pillow from PIL import Image def patch_tokens(path, patch=16): img = Image.open(path).convert("RGB") W, H = img.size pw, ph = W // patch, H // patch n = pw * ph print(f"{path}: {W}x{H}, patch {patch} -> {pw}x{ph} grid = {n:,} tokens") print(f" cache at 70,272 B/token: {n*70272/1024**2:.1f} MiB") print(f" prefill FLOPs (13B active): {2*13e9*n:.3e}") return n patch_tokens("screenshot.png", 16) patch_tokens("screenshot.png", 32)

A 1024×1024 screenshot: 64×64 = 4,096 tokens (274.5 MiB cache) at patch 16, and 32×32 = 1,024 tokens (68.62 MiB) at patch 32. Run it on your own screenshots and compute the monthly token bill for your actual image volume — that is the number that decides whether you need a resampler.

Experiment 2 — the token-budget planner

Given a detail requirement and a budget, solve for patch size. This is the calculation that should precede any multimodal product decision.

def plan(P, budget_tokens, max_patch=64): # smallest patch (most detail) that fits the token budget for s in range(8, max_patch + 1, 2): n = (P // s) ** 2 if n <= budget_tokens: return s, n return None, 0 for P in (448, 1024, 2048): for budget in (256, 1024, 4096): s, n = plan(P, budget) print(f"{P}px budget={budget:5d} -> patch={s} ({n} tokens, {P/s:.0f}px per patch)")

At 1024px with a 1,024-token budget the planner chooses patch 32 — 32 pixels per patch, which is enough for scene understanding and too coarse for 10px text. With a 4,096 budget it chooses patch 16 (4,096 tokens exactly). At 2048px the same budgets give patch 64 and patch 32 — the planner trades resolution for patch size automatically, which is precisely the decision a product team needs to see. The planner turns a vague “we need better image understanding” into a specific cost line, and shows the CEO exactly what detail buys.

Experiment 3 — images versus text in one context budget

Compare an image-heavy request against a text-heavy one. The point is that images are not a separate budget line — they compete directly with documents.

python -c " tok=70272; tokens_per_page=500 for imgs,patch in ((1,16),(4,16),(20,16),(1,32)): img_tokens=(1024//patch)**2*imgs pdf_pages=(128000-img_tokens)//tokens_per_page print(f'{imgs} images @patch{patch} = {img_tokens:6,} tokens ({img_tokens*tok/1024**3:.2f} GiB cache) -> room for {pdf_pages:5,} PDF pages in 128k') "

One 1024px image at patch 16 leaves room for 247 PDF pages in a 128k window; four images leave 223; twenty images consume 81,920 tokens and leave only 92 pages. Cache cost for twenty images is 5.36 GiB — comparable to a single 78k-token text prompt. The budget is shared, and images are the expensive side.

5 · Failure modes #

  • Resolution creep. Symptom: token spend doubles while request volume is flat, because a client update raised default image resolution. Log image tokens per request and alert on changes.
  • Adapter compression hiding detail loss. Symptom: model describes a chart's trend correctly and misreads its axis labels. The resampler kept scene-level information and discarded small text. Raise resolution or use a detail-preserving tokenisation for text-heavy images.
  • Vision encoder cost not attributed. Symptom: cloud bills contain GPU time your token accounting does not explain. A separate encoder is a second compute system; it needs its own metric.
  • Cache invalidation on image re-order. Symptom: image conversations have much lower prefix-cache hit rates than text ones because the client sends images in a different order each turn. Fix the ordering.
  • Testing on natural photos only. Symptom: strong demo quality, poor production quality, because production traffic is screenshots, scanned forms and dashboards — the dense-text cases where patch resolution is exactly the binding constraint.

7 · Self-check #

Q1. A 1536×1536 image at patch size 16. How many tokens, how much KV cache at 70,272 B/token, and what happens if patch size doubles to 32?

Reveal answer

(1536/16)² = 96² = 9,216 tokens; cache = 9,216 × 70,272 = 617.6 MiB. At patch 32: (1536/32)² = 48² = 2,304 tokens; cache = 154.4 MiB. Quadrupling-less: the token count falls 4× exactly, because token count is (P/s)² and s doubled.

Q2. You have a 128k context, one 1024px image at patch 16, and want to include PDF pages at ~500 tokens each. How many pages fit, and how does that change at patch 32?

Reveal answer

Patch 16: 4,096 image tokens leaves 131,072 − 4,096 = 126,976 tokens → 253 pages. Patch 32: 1,024 image tokens leaves 130,048 → 260 pages. So halving visual detail buys only 7 extra pages (2.7%) — but costs half the image fidelity. That asymmetry is the argument for spending tokens on images only when the task needs detail.

Q3. Diagnostic: the model reads tables in screenshots correctly in demos and fails on the same screenshots in production. Name the two most likely causes.

Reveal answer

(a) Resolution or patch size differs between demo and production pipelines (the client downscales, or the serving config defaults to a coarser patch); (b) the production images differ in type — different renderer, DPI, compression artefacts, or scaling that makes small text sub-patch. Check by logging the actual pixel dimensions and token counts per request rather than assuming the pipeline is identical.

Q4. Why is prefix caching especially valuable for image conversations?

Reveal answer

Image tokens are typically static across turns — the user references the same screenshot while asking follow-up questions — and they are expensive (4,096 tokens each at patch 16). So they sit in the cached prefix and are paid once. A text conversation where the user retypes context gets less benefit because more of the prompt changes. In practice, image-heavy chat is the highest-value cache workload after long system prompts.

Q5. What does "native multimodal" actually buy, architecturally, over a bolted-on vision adapter?

Reveal answer

Three things: (1) one cost model instead of two compute systems; (2) joint training so the vision representation is optimised for the tasks the language model must solve, rather than for a proxy objective then adapted; (3) no capacity bottleneck at the adapter, which is usually a small projection trained on comparatively little data. The cost is that pretraining must carry image data from the start, which is a much larger commitment than fine-tuning an adapter.
