L45 · Context Caching, Prefix Caching, and Cache-Aware Pricing

An agent loop re-sends its entire transcript every turn, so turn 6 pays to re-prefill turns 1–5 — 22,000 redundant tokens in a ten-turn example. Prefix caching removes that, but only if your prompt is built prefix-stable, which is an engineering discipline, not a billing feature.

1 · Why it exists #

Every multi-turn interaction and every agent loop re-sends the whole transcript. Turn 2 sends turn 1's prompt plus the answer. Turn 3 sends all of that again. For a ten-turn agent loop with 400 new tokens per turn:

∑t=1..10 400t = 400 × (10×11/2) = 22,000 tokens re-processed The Nth turn costs 400N tokens of prefill, and the sum over ten turns is triangular. Of those 22,000 tokens processed, only 4,000 are new — 82% is re-prefill of content the model has already seen, byte-for-byte identical.

That is the failure prefix caching was invented to stop. Prefill is expensive (L35): a 16,384-token prompt is 2 × 13×109 × 16,384 / 3.956×1014 = 1,076.8 ms of compute on one GPU. Reading the same prefix from cache costs a fraction of that — the arithmetic below puts the two side by side.

The second failure is economic. Because re-prefill is pure waste, providers that bill per input token are effectively charging customers for their own inefficiency. Cache-aware pricing (a cheaper rate for tokens that hit a cached prefix) aligns the bill with the marginal cost. DeepSeek's API state as of 2026-10 is the canonical example of a two-rate structure, alongside the peak/off-peak split where off-peak is 50% of peak.

Your prefix is a billing decision. If the first N tokens of every request are byte-identical, you pay cache-read prices for them; if you put a timestamp or a shuffled tool list at the front, you pay full prefill for the whole prompt. Nothing else about the request changed.

2 · The mental model #

Analogy (labelled): a museum cloakroom. Everyone's coat goes in once; re-entry needs the ticket, not a new coat. The catch: the ticket works only for the exact coat — change one button and it is a different coat, and you must hang it again.

What the analogy gets right

Caching is exact-prefix matching. It is not similarity search, not "mostly the same" — a single changed byte at the front invalidates everything after it, because every token's attention depends on all prior tokens.

Where it breaks

In a cloakroom, a changed coat costs one hang. Here the granularity is blocks (typically 16 tokens), and the match is longest common prefix in block units — so a change at position 3,000 of a 4,000-token prompt still preserves the first ~3,000 tokens of cache. The loss is partial, not total, and the exact break-point is what determines your hit rate.

Where the cache sits in the stack

Prefix caching is only possible because of two earlier lessons: the model is causal (L37), so a prefix's states are final and reusable; and the cache is paged in fixed-size blocks (L44), so two sequences can point at the same physical blocks. The mechanism is a pointer, not a copy.

3 · The mechanism #

cost = Pin (1−h) Nprefix + Pcache h Nprefix + Pin Nnew + Pout Nout h = fraction of the prefix that hits, Pin = normal input price per token, Pcache = cache-read price per token (typically a small fraction of Pin), Nnew = newly appended tokens. Everything in this lesson follows from this one line; the only uncertain input is h, which you measure.

Worked: 100k-token prefix, 1k-token answer

Set Pin = 1.0 and Pout = 1.0 in arbitrary units, and take a cache read at 0.1× the input price — representative of the "cache hit is a small fraction of input" structure. Sweep the hit rate:

The 1k output tokens cost the same in every row, which is why the ceiling is 9.18× rather than 10×. The real lesson is the shape: the saving is almost entirely determined by h, and h is entirely determined by how you build the prompt. A cache-aware application at 90–100% hit rate is 5–9× cheaper on input than one that is not, for identical output.

Why the latency win is even bigger than the cost win

Cost is one axis; time is the other. Prefill of a 16,384-token prompt is 1,076.8 ms of compute. Reading a cached prefix of the same size is a bandwidth operation: at 70,272 B/token and 3 TB/s, 16,384 tokens is 16,384 × 70,272 = 1.151 GB → 0.384 ms. That is a ~2,800× reduction in the work, which is why cached TTFT is qualitatively different rather than marginally better.

The ratio is constant because both terms are linear in prefix length — prefill in FLOPs, cache read in bytes. What changes with length is the absolute time saved: 3.07 s per turn at 128k. On a ten-turn agent loop that is 30 seconds of machinery the user does not wait for.

Prefix stability: the only thing you actually control

Cache hits require the prefix to be byte-identical, in order, from the start. Ranked by how much damage each pattern does to hit rate:

PatternEffect on hit rate
Timestamp / UUID / random nonce at position 00% — destroys the entire prefix
Tool definitions serialised from a dict with unstable key order0% — same reason, invisible in code review
System prompt, then tools, then history (stable order)high — the whole prefix matches
Retrieved documents inserted before the system promptlow — RAG chunk changes invalidate everything
Retrieved documents inserted after the stable prefixhigh — only the tail is new
Transcript appended monotonicallyhigh — each turn extends the previous prefix
Transcript with an evolving summary prepended at the front0% — compaction rewrites the prefix

Read the last two rows together: monotone appending is ideal, and compaction (L79) is the most common accidental cache-destroyer in agent systems. The fix is a stable prefix followed by an append-only region, with summaries placed in the changing region rather than at the front.

Peak vs off-peak: caching's sibling lever

Cache pricing is a marginal-cost signal; peak/off-peak pricing is a demand signal. When off-peak is 50% of peak — the structure DeepSeek publishes state as of 2026-10 — batch work (evals, synthetic data generation, distillation trace collection) should be scheduled off-peak, and the two levers compose: an off-peak, cache-hitting batch job pays a fraction of the peak uncached price for the same output.

Measure your hit rate from the response body, not from a dashboard. Log the cached-token count the API reports per call, compute h = cached / (cached + uncached input), and aggregate by prompt template. A per-template hit rate is the only way to find which prompt is silently breaking the cache — aggregate hit rate hides one bad template behind three good ones.

4 · Your hands #

Experiment 1 — the hit-rate cost curve

The model behind every cache decision. Put your own prices in; the shape does not depend on them.

def cost(N_prefix, N_new, N_out, h, P_in, P_cache, P_out): return (N_prefix * (1-h) * P_in + N_prefix * h * P_cache + N_new * P_in + N_out * P_out) base = cost(100_000, 0, 1_000, 0.0, 1.0, 0.1, 1.0) for h in (0, 0.25, 0.5, 0.75, 0.9, 1.0): c = cost(100_000, 0, 1_000, h, 1.0, 0.1, 1.0) print(f"h={h:4.0%} cost={c:10,.0f} saving={base/c:5.2f}x")

Experiment 2 — measure a real prompt's stability

The experiment you run against your own code, with no provider needed: simulate a multi-turn loop under three prompt layouts and compute the prefix actually shared between consecutive requests.

def common_prefix(a, b): n = 0 for x, y in zip(a, b): if x != y: break n += 1 return n SYS, TOOLS = "S" * 2000, "T" * 1000 turns = ["u" * 400 * i for i in range(1, 11)] # layout A: stable prefix (system + tools), then append-only history A = [SYS + TOOLS + t for t in turns] # layout B: timestamp injected first B = [str(i) + SYS + TOOLS + t for i, t in enumerate(turns)] # layout C: rolling summary prepended (changes every turn) C = ["R" * (500 + 50*i) + SYS + TOOLS + t for i, t in enumerate(turns)] for name, lay in (("A stable", A), ("B timestamp", B), ("C summary-first", C)): hits = [common_prefix(lay[i], lay[i+1]) for i in range(len(lay)-1)] total = sum(len(x) for x in lay[1:]) print(f"{name:16s} shared tokens={sum(hits):6d} / {total:6d} hit_rate={sum(hits)/total:6.2%}")

Measured: layout A shares 45,000 of 48,600 tokens — 92.6%. Layout B shares 0 tokens of 48,609, because the first character differs. Layout C shares 6,300 of 55,350 — 11.4% — and note the shared amount shrinks relative to the total as the summary grows, so the hit rate degrades over a long conversation. Falsification: if B and C score the same as A, your common_prefix is comparing lengths rather than content.

Experiment 3 — the triangular cost of not caching

Quantify what a ten-turn loop costs with and without prefix reuse, so the caching work can be justified in dollars rather than latency.

python -c " per_turn=400; turns=10; P_in=1.0; P_cache=0.1 nocache=sum(per_turn*t for t in range(1,turns+1)) cache=per_turn # only the first turn is a miss tail=sum(per_turn*(t-1) for t in range(1,turns+1)) # prior tokens, read from cache print(f'tokens processed without cache: {nocache:,}') print(f'prefill tokens with cache: {per_turn:,} new + {tail:,} cache-read') print(f'cost without: {nocache*P_in:,.0f} cost with: {cache*P_in + tail*P_cache:,.0f}') print(f'saving: {(nocache*P_in)/(cache*P_in + tail*P_cache):.2f}x') "

Without cache: 22,000 tokens at full price = 22,000 units. With cache: 400 at full price + 18,000 at cache price = 400 + 1,800 = 2,200 units. Saving: exactly 10× — the turn count, in the limit where the cache price is negligible. That linear-in-turns growth is why long agent loops are uneconomical without caching and cheap with it.

5 · Failure modes #

  • Cache-busting prefix. Symptom: hit rate is 0–5% despite a long system prompt. A timestamp, request id, user name or a randomly-ordered tool list sits at the front. Sort keys, move volatile fields to the end.
  • Compaction resets the cache every turn. Symptom: hit rate spikes then collapses cyclically, matching the compaction interval. Summaries must be appended in the changing region, not prepended.
  • TTL expiry between turns. Symptom: hit rate depends on user think-time — short conversations hit, long gaps miss. Know the provider's cache lifetime and design retry/queue behaviour around it, not against it.
  • Protecting against bad cache state. Symptom: after a code change, cached prefixes from the previous version are still being hit and the model behaves oddly. Version your prefix (a stable, cheap version marker inside the cached region) so a deploy invalidates cleanly.
  • Assuming caching is free. Symptom: a workload with low hit rates plus cache-write surcharges is more expensive than no cache. Some providers bill cache writes at a premium; compute the expected cost across your real h distribution before enabling.

7 · Self-check #

Q1. A 50,000-token prefix, 500 new tokens, 500 output tokens, hit rate 80%, Pin = 1, Pcache = 0.15, Pout = 2. Compute the cost and the saving versus h = 0.

Reveal answer

With cache: 50,000 × 0.2 × 1 + 50,000 × 0.8 × 0.15 + 500 × 1 + 500 × 2 = 10,000 + 6,000 + 500 + 1,000 = 17,500. Without: 50,000 + 500 + 1,000 = 51,500. Saving = 51,500/17,500 = 2.94×.

Q2. A ten-turn agent loop appends 800 tokens per turn. How many tokens are processed in total without caching, and what does caching reduce that to?

Reveal answer

Triangular: 800 × (10×11/2) = 800 × 55 = 44,000 tokens. With a perfect prefix cache, turn 1 prefills 800 and turns 2–10 prefill only their new 800 each (7,200 new tokens total) while reading 35,200 from cache. So prefill-grade work drops from 44,000 to 8,000 tokens — a 5.5× reduction in the expensive class of work, with the rest priced as cache reads.

Q3. Diagnostic: hit rate is 0% only for your RAG endpoint, and 95% for chat. What is the likely cause?

Reveal answer

Retrieved documents are placed at the front of the prompt, so every new retrieval changes the very first tokens and invalidates the entire prefix. Move the retrieved content after the stable system/tool block (or after as much stable content as possible) so only the tail changes. Note this is a prompt-layout change with no effect on model quality — pure cost win.

Q4. Why is the latency saving from cache (a ~2,800× reduction in work) so much larger than the cost saving (up to ~9×)?

Reveal answer

Because they measure different things. Latency saving compares prefill work (compute-bound, 2N FLOPs per token) against cache read work (bandwidth-bound, bytes per token) — two different units, giving a huge FLOPs-vs-bytes ratio. Cost saving compares billed tokens at two price points, and the output tokens are billed at full price regardless and cannot be cached, which caps the achievable ratio. Neither number is "the" benefit: quote both, for the axis you are deciding on.

Q5. When does enabling prefix caching make a workload more expensive?

Reveal answer

When cache writes are billed at a premium and the hit rate is low — you pay the write surcharge on every request and rarely recover it. Also when the cache is frequently invalidated by TTL expiry between turns, or when a prompt template is unstable so each request writes a new prefix. Compute expected cost across your real hit-rate distribution, including write pricing, before enabling — and always measure h from the response body rather than assuming it.
