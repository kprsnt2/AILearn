L37 · Encoder–Decoder and the V4.1 Asymmetric Split

Reading a prompt and writing an answer are different workloads: prefill is a throughput problem, decode is a latency problem. Baking that asymmetry into the architecture — 8B active for input, 16B for output — cuts the dominant cost for prompt-heavy traffic by about half.

causal encoder encoder–decoder split asymmetric active params prefill vs decode prompt-heavy vs output-heavy cost per query workload asymmetry

1 · Why it exists #

Every decoder-only model makes one implicit bet: that the cost of processing a prompt token and the cost of generating an output token should be equal. They both use 2Nactive FLOPs per token. But the workloads are radically different.

Prefill processes p tokens in parallel — it is a big matmul, throughput-bound, and can saturate the GPU. Decode generates one token at a time, re-reading the entire weight stream and cache — it is latency- and bandwidth-bound, and mostly wastes the compute units. Charging them the same price is like pricing a freight train per passenger the same as a taxi per passenger.

The failure shows up as product economics. A RAG assistant that sends 20,000-token prompts and receives 200-token answers is 99% prefill by token count. A reasoning model that thinks for 8,000 tokens from a 50-token question is 99% decode. A single architecture tuned for both under-serves at least one, and per-token pricing forces customers with one shape to subsidise the other.

DeepSeek-V4.1-Flash state as of 2026-10 is described as using a new Causal Encoder–Decoder architecture with 8B active parameters for input and 16B for output, in a 552B-total MoE. That is precisely a declaration that the two phases deserve different widths. The encoder is a causal encoder — not the bidirectional encoder of the T5 arXiv:1910.10683 or BERT arXiv:1810.04805 lineage — which matters for prefix caching (L45): a bidirectional encoder cannot be cached incrementally token by token.

Prefill and decode have different bottlenecks, so they should have different active widths. Splitting 8B/16B cuts the bill on prompt-heavy traffic roughly in half and shifts compute to output tokens, where a unit of compute genuinely buys more quality.

2 · The mental model #

Analogy (labelled): a translation agency with a reading team and a writing team. Reading a 200-page brief is a bulk-scanning job; writing one perfect sentence is a craft job. Staffing them for the same headcount is obviously wrong once you know the mix of jobs you take.

What the analogy gets right

The two phases have genuinely different unit economics and can be staffed separately. The total bill is a weighted sum whose weights come from your traffic mix.

Where it breaks

A reading team cannot hand over a half-read brief. Here the phases share state — the encoder's cache feeds the decoder — so they cannot be optimised in isolation: shrinking the encoder reduces cache quality available to the decoder. Also, unlike T5-style encoder–decoder, the encoder here is causal, so the boundary is a width change rather than a masking change.

The cost identity that decides everything

For a prompt of p tokens and an output of o tokens, total FLOPs are proportional to

cost ∝ Nin  p  +  Nout  o Nin = active parameters used to encode the prompt, Nout = active parameters used per generated token. With a decoder-only model Nin = Nout; the asymmetry reduces to a ratio. Everything on this page follows from the two-line ratio o/p, the output-to-prompt token ratio.

3 · The mechanism #

The asymmetry compared against both symmetric alternatives

Take the V4.1-Flash figures: Nin = 8B, Nout = 16B. Compare total work against a 16B symmetric model and an 8B symmetric model on four realistic workload shapes:

Workload (p → o)Asymmetric 8B/16B16B symmetric8B symmetricAsym / 16B-sym
RAG answer (1,000 → 100)9.60×10121.76×10138.80×10120.545
Chat (1,000 → 1,000)2.40×10133.20×10131.60×10130.750
Reasoner (100 → 1,000)1.68×10131.76×10138.80×10120.955
Long-doc summarise (10,000 → 200)8.32×10131.632×10148.16×10130.510

The reading: the asymmetric model is 45% cheaper than a 16B symmetric model on prompt-heavy traffic and only 4.5% cheaper on output-heavy traffic. So it is a strict improvement over 16B everywhere, and a large one for the workloads that dominate enterprise usage. It is not, however, better than an 8B symmetric model on prompt-heavy traffic (8.32 vs 8.16) — because it spends 2× on the output side, and that is the price of the quality claim: the asymmetric model is supposed to be better than 8B, not merely cheaper than 16B.

The crossover: which workloads favour which design

Set the asymmetric cost equal to a symmetric model at width N and solve for the output/prompt ratio r = o/p:

8p + 16o = N(p + o)  ⇒  r* = (N − 8) / (16 − N) For N = 16: r* = (16−8)/(16−16) → ∞, so the asymmetric model is cheaper at every finite ratio. For N = 8: r* = (8−8)/(16−8) = 0, also cheaper at every ratio — but here the asymmetric model is the expensive one whenever o > 0. Read the two cases together: 8/16 sits strictly between the two symmetric designs in cost, at every workload shape. The design therefore cannot be justified by cost alone; only by quality per unit cost.

That algebra is worth internalising because it kills a common but wrong argument. An asymmetric design does not create a new region of the cost space — it picks a point between the two symmetric designs. Its justification must be quality: that 16B of width on output tokens buys capability that 16B on prompt tokens does not, so paying for it is worth more than paying for the other. The cost table only tells you the price of the bet, not whether it wins.

Why a causal encoder changes the accounting

This is the architectural detail that makes the split viable in production, and it is often missed:

  • Bidirectional encoders are not incrementally cacheable. If prompt token 500 can attend to prompt token 900, then adding token 901 changes the representation of token 500. You cannot cache a prefix. Every request's prompt must be re-encoded as a whole.
  • A causal encoder is cacheable. Each prefix state is final once computed. So the encoder's cache can be stored, reused across requests sharing a prefix, and priced as a cache read (L45).
  • The 1/4 HBM and 1/8 SSD cache requirement state as of 2026-10 is meaningful only if the cache is reusable — and reusability is exactly what causality grants.

So the causal-encoder choice is not cosmetic. It converts the encoder from a per-request cost into a per-unique-prefix cost, which is the entire basis of context caching economics.

Prefill-heavy vs decode-heavy, in seconds

Cost in FLOPs is not the whole story because the two phases convert FLOPs to time at very different efficiencies. Using Seff = 3.956×1014 FLOP/s per GPU at 40% MFU for prefill, and a memory-bandwidth-bound model for decode (roughly 2Nout×2 bytes fetched per token at ~3×1012 B/s):

PhaseWorkLimiterEfficiency
Prefill, 10,000 tokens, Nin = 8B1.6×1014 FLOPscompute (large matmul)high — 0.40 s on one GPU
Decode, 200 tokens, Nout = 16B6.4×1012 FLOPsbytes, not FLOPslow — 32 GB streamed at 3 TB/s is ~10.7 ms/token, 2.13 s for 200

Note what happens: the long prompt costs more FLOPs but runs efficiently; the short answer costs fewer FLOPs but takes more than five times as long because it cannot use the machine. That is why Nout is the number that matters for latency and Nin for throughput cost. Any architecture decision that conflates them will optimise the wrong term.

The audit artifact for a serving-cost claim is a two-row cost sheet: (N_in, prefill_FLOPs, prefill_seconds) and (N_out, decode_bytes, decode_ms_per_token), each evaluated at your p90 prompt and answer lengths. A single blended “cost per token” hides the asymmetry that the whole architecture is designed around.

4 · Your hands #

Experiment 1 — your own workload mix, priced

Feed in your real prompt/length distribution and get the asymmetry ratio. This is the number that tells you whether an asymmetric model is worth waiting for.

def cost(p, o, n_in, n_out): return n_in * p + n_out * o loads = [("RAG answer", 1000, 100), ("Chat", 1000, 1000), ("Reasoner", 100, 1000), ("Long-doc summary", 10000, 200)] for name, p, o in loads: asym = cost(p, o, 8e9, 16e9) sym16 = cost(p, o, 16e9, 16e9) sym8 = cost(p, o, 8e9, 8e9) print(f"{name:18s} asym={asym:.3e} vs16B={asym/sym16:.3f}x vs8B={asym/sym8:.3f}x o/p={o/p:.3f}")

Measured ratios to 16B: 0.545 / 0.750 / 0.955 / 0.510. Ratios to 8B: 1.091 / 1.500 / 1.909 / 1.020. Notice the pattern: the more prompt-heavy the workload, the closer the asymmetric model comes to 8B pricing; the more output-heavy, the closer it comes to 16B. Your mix tells you where you land.

Experiment 2 — the latency split that FLOPs hide

Compute both the FLOPs and the wall-clock for the two phases. The inversion — long prompt is cheaper in time than a short answer — is the most useful surprise on this page.

python -c " eff=989e12*0.40; bw=3e12 p,o,n_in,n_out=10000,200,8e9,16e9 pf=2*n_in*p; dc=2*n_out*o print(f'prefill FLOPs {pf:.3e} time {pf/eff:.3f}s') print(f'decode FLOPs {dc:.3e} bytes/token {2*n_out*2/1e9:.1f}GB time/token {2*n_out*2/bw*1000:.2f}ms total {2*n_out*2/bw*o:.3f}s') print(f'decode is { (2*n_out*2/bw*o)/(pf/eff) :.2f}x slower in wall-clock despite {pf/dc:.1f}x fewer FLOPs') "

Precision: prefill is 0.40 s for 1.6×1014 FLOPs; decode is 32 GB per token at 3 TB/s = 10.67 ms/token, so 2.13 s for 200 tokens — 5.3× slower than the prefill despite 25× fewer FLOPs. That is the asymmetry that justifies splitting the architecture, and the reason Nout controls your p99.

Experiment 3 — does caching make the encoder nearly free?

The causal-encoder claim: because the encoder is causal, its output is cacheable per prefix, so a repeated prefix costs a cache read instead of a full prefill. Quantify the saving for a realistic repeated-system-prompt scenario.

sys_prompt = 4_000 # shared prefix tokens user_turns = 6 per_turn = 800 # new tokens each turn n_in = 8e9 def flops(tokens): return 2 * n_in * tokens uncached = flops(sys_prompt + user_turns*per_turn) * user_turns cached = flops(sys_prompt) + flops(user_turns*per_turn) print(f"uncached: {uncached:.3e} FLOPs") print(f"cached: {cached:.3e} FLOPs ({uncached/cached:.2f}x less)")

For 6 turns sharing a 4,000-token system prompt plus 800 new tokens per turn: uncached is 6 × 8,800 = 52,800 tokens of encoder work; cached is 4,000 + 4,800 = 8,800 — 6× less. That ratio is exactly the turn count when each turn only adds new tokens, which is why prefix caching is decisive for agent loops and why a causal encoder is a prerequisite for it.

5 · Failure modes #

  • Pricing assumed symmetric. Symptom: your cost model is wrong by 2× on prompt-heavy traffic in one direction and correct on chat. Blended $/token pricing hides which phase you are paying for; always evaluate at your p90 p and o separately.
  • Non-causal encoder silently used. Symptom: prefix caching does not work despite a documented cache feature; every request re-encodes the full prompt, and cache-hit rate is zero. Check that the encoder is causal before promising cache economics.
  • Cache invalidation across the encoder/decoder boundary. Symptom: a long-context task works with a single turn and fails subtly across turns — the encoder's cached states were produced under different instructions. Cache keys must include the full prefix bytes, not just a session id.
  • Assuming asymmetric means faster end to end. Symptom: throughput improves but p99 latency does not, because decode was the latency term all along. Split the SLO by phase: time-to-first-token is an encoder metric, inter-token latency is a decoder metric.
  • Confusing the causal encoder–decoder with T5. Symptom: architectural decisions justified with T5 literature (cross-attention from decoder to a bidirectional encoder) that do not apply. Here the encoder is causal and the split is a width change per phase, not a masking change.

7 · Self-check #

Q1. Compare total FLOPs for (p = 4,000, o = 200) on asymmetric 8B/16B versus a 16B symmetric model. What is the ratio?

Reveal answer

Asymmetric: 8B×4,000 + 16B×200 = 3.2×1013 + 3.2×1012 = 3.52×1013. Symmetric 16B: 16B×4,200 = 6.72×1013. Ratio = 0.524. Roughly half the work — and almost all of the saving is in the prompt term, because p/o = 20.

Q2. You have a 10,000-token prompt and generate 200 tokens on Nin = 8B, Nout = 16B. At 40% MFU on 989 TFLOP/s for prefill and 3 TB/s for decode weight streaming, which phase takes longer?

Reveal answer

Prefill: 2×8×109×104 = 1.6×1014 FLOPs / 3.956×1014 = 0.405 s. Decode: bytes per token = 2 (K and V not relevant here — it is the weight stream) — using 2 Nout × 2 bytes bf16 ≈ 32 GB per token; 32 GB / 3×1012 B/s = 10.67 ms; 200 tokens = 2.13 s. Decode is 5.3× slower despite using 25× fewer FLOPs, because decode cannot use the compute units. This is why Nout drives latency.

Q3. The asymmetric model is cheaper than 16B at every output ratio and more expensive than 8B at every ratio. What does that imply about the justification for the design?

Reveal answer

That the justification cannot be cost — 8B symmetric is cheaper for prompt-heavy traffic and the asymmetric point is a convex combination of the two. The justification must be quality per unit cost: extra width on output tokens buys more capability than the same width on input tokens, so a model that spends 16B on generation can beat both an 8B model (which it is dearer than) and a 16B model (which it is cheaper than) on output quality. Without a quality argument the split is pointless.

Q4. Why does the encoder have to be causal for prefix caching to work, and what would a bidirectional encoder cost you?

Reveal answer

In a causal encoder a token's representation depends only on earlier tokens, so a prefix's states are final and reusable. In a bidirectional encoder, adding token 901 changes token 500's representation, so no prefix state is stable and every request must re-encode from scratch. The cost of a bidirectional encoder is therefore the entire 6× re-prefill penalty in Experiment 3 — you would lose incremental caching completely.

Q5. Diagnostic: throughput went up after switching to an asymmetric model, but users complain about latency. What did you measure, and what should you measure?

Reveal answer

You measured aggregate tokens/sec, which is dominated by the encoder's efficient parallel phase. Users feel inter-token latency, which is governed by Nout and by decode bandwidth. Measure time-to-first-token (encoder metric) and inter-token latency (decoder metric) separately, and set separate SLOs. A throughput win can coexist with a p99 latency regression.
