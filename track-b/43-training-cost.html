L43 · Training Cost Modeling: FLOPs, MFU, and $ Per Run

Six numbers turn a proposed run into a budget: N, D, the 6ND multiplier, the accelerator's peak FLOP/s, an honest MFU, and the price per GPU-hour. DeepSeek-V3's published 2.788M H800-hours back-solves to a 33.1% MFU — that is your calibration point.

6ND FLOPs MFU GPU-hours $/run error budget wall-clock vs cost cross-check against a published run

1 · Why it exists #

The failure this lesson prevents is the one you live with: a cost estimate off by 3× turns a viable plan into an overrun, and nobody notices until the run is 60% complete. The estimates go wrong in one specific way — people use peak FLOP/s instead of achieved FLOP/s, or count the cost of the model but not of the parallelism needed to run it.

Three concrete numbers to anchor the scale. A 500B-active model trained on 15T tokens needs 6 × 500×109 × 15×1012 = 4.5×1025 FLOPs. At 35% MFU on 989 TFLOP/s accelerators that is 36.11M accelerator-hours. At $2/h — a reasonable 2026 rate for rented H800-class capacity state as of 2026-10 — that is $72.2M. At 25% MFU it is $101.1M. The MFU assumption moves the budget by $29M, so getting MFU right is not academic bookkeeping; it is the difference between an approved project and a cancelled one.

The one public data point that pins MFU for a state-of-the-art sparse model is DeepSeek-V3 arXiv:2412.19437: 671B total / 37B active, 14.8T pretraining tokens, and 2.788M H800 GPU hours. That is enough to derive the number every other estimate depends on.

Cost = (6 × Nactive × D) / (MFU × peak FLOP/s × 3600) GPU-hours × $/hour. Four multiplications and one division. Do them before the money is committed, not after.

2 · The mental model #

Analogy (labelled): a road trip budget from distance and fuel economy. Distance is fixed by the model and data; fuel economy (MFU) is a property of the vehicle and the road; price per litre is the market. Most estimates go wrong on the fuel economy because they use the manufacturer's best-case figure instead of the vehicle's real consumption with a load.

What the analogy gets right

Distance and price are stable; efficiency is the variable that carries the uncertainty and should be sourced from measurement, not a datasheet.

Where it breaks

Fuel economy is roughly constant per vehicle. MFU depends on the configuration: pipeline bubble, TP all-reduce, expert all-to-all and failure restarts all reduce it. The same model on the same hardware can run at 20% or 40% MFU depending on the parallel plan (L42) — so MFU is a design output, not a constant.

MFU: what it means and what it is not

MFU = achieved FLOP/s ÷ peak dense FLOP/s    and    achieved = 6 Nactive D / (GPU-hours × 3600) Note Nactive, not Ntotal: a sparse model only spends FLOPs on active parameters, so MFU computed against total parameters would be meaningless (you would show 3% “efficiency” for a perfectly efficient MoE). This is the single most common modelling error.

3 · The mechanism #

The anchor: back-solving MFU from DeepSeek-V3

We know Nactive = 37B, D = 14.8T, GPU-hours = 2.788M, and the device is an H800. So:

FLOPs = 6 × 37×109 × 14.8×1012 = 3.286×1024
achieved = 3.286×1024 / (2.788×106 × 3600) = 3.274×1014 FLOP/s = 327.4 TFLOP/s
MFU = 327.4 / 989 = 33.1% 989 TFLOP/s is the H800's dense bf16 peak used throughout this track. The implied 327 TFLOP/s is the achieved rate. Everything a plan claims must be consistent with this number: if your estimator assumes 50% MFU you are claiming 1.5× better than a published frontier run.

That is the most valuable number in the track. It says: ~33% MFU is what a world-class sparse training run actually achieves after pipeline bubbles, tensor-parallel all-reduces, expert all-to-all, and the fact that not every step is a clean matmul. Use 30–35% for planning. Use 50% only if you can show the profile that justifies it.

Every cell is one multiplication chain away from the formula, and the 25%–45% spread is a 1.8× budget range — a $45M swing on a single assumption. This is why the deliverable of this lesson is a cost sheet with the MFU assumption stated explicitly on the same line as the total, never a single number.

From GPU-hours to wall-clock: the second half of the plan

36.11M GPU-hours on 4,096 accelerators is 36.11×106 / 4,096 = 8,816 hours = 367 days at perfect utilisation; at 88% it is 417 days. On 16,384 GPUs the nominal figure is 2,204 hours (92 days). So cluster size buys time, not money.

wall-clock = GPU-hours / (GPU count × (1 − failure_rate)) At 16k GPUs, hardware failures and restarts are not an edge case — they are the dominant scheduling concern. Effective utilisation of 85–90% from restarts and checkpoint recovery is typical, so a 92-day nominal run is really ~103–108 days.

The consequence: the cost is fixed by FLOPs and MFU, but the schedule is a separate budget item with its own risk. A cheaper-per-hour contract on a smaller cluster can be more expensive if it doubles the calendar time and delays revenue.

The MoE twist: which N goes in 6ND

For a sparse model you must use Nactive, and the difference is enormous:

Using total parameters overstates compute by 18.1× and would produce a >$1B estimate for a run that cost a fraction of that. Whenever you see a training-cost figure for an MoE, check which N it used before believing it.

The cost sheet, as an artifact: Nactive, D, FLOPs = 6ND, peak FLOP/s per device, MFU (with its justification), GPU-hours, $/GPU-hour with its source and date, total $, cluster size, wall-clock, and one comparison against a published run with the implied MFU. Every subsequent change should update this sheet, and the delta should be explainable in one line.

4 · Your hands #

Experiment 1 — back-solve MFU from a published run

Always calibrate before extrapolating. This reproduces the 33.1% anchor and shows you the arithmetic to redo for any published run you trust.

# Known: DeepSeek-V3, 37B active, 14.8T tokens, 2.788M H800 GPU-hours N_act, D, gpu_hours, peak = 37e9, 14.8e12, 2.788e6, 989e12 flops = 6 * N_act * D achieved = flops / (gpu_hours * 3600) mfu = achieved / peak print(f"FLOPs = {flops:.3e}") print(f"achieved FLOP/s= {achieved:.4e} ({achieved/1e12:.1f} TFLOP/s)") print(f"implied MFU = {mfu:.3f} ({mfu*100:.1f}%)")

FLOPs = 3.286×1024; achieved = 3.274×1014 FLOP/s = 327.4 TFLOP/s; MFU = 0.331 (33.1%). Use this as your planning MFU. Falsification of any plan assuming >45%: ask for the profile, because it would beat a frontier run by 35%.

Experiment 2 — the full cost sheet for any proposed run

One function, all the outputs a decision needs. Change N and D to your candidate.

def cost_sheet(N_act, D, peak=989e12, mfu=0.331, usd_h=2.0, gpus=4096, fail=0.88): flops = 6 * N_act * D hours = flops / (3600 * mfu * peak) usd = hours * usd_h wall_days = hours / (gpus * fail) / 24 return flops, hours, usd, wall_days for N, D, tag in [(37e9, 14.8e12, "V3-like"), (49e9, 20e12, "V4-Pro-ish"), (13e9, 30e12, "Flash over-trained"), (500e9, 15e12, "500B dense-ish")]: f, h, u, w = cost_sheet(N, D) print(f"{tag:20s} FLOPs={f:.2e} hours={h/1e6:7.2f}M \${u/1e6:7.1f}M wall={w:6.1f} d @4096 GPUs")

Measured: V3-like → 3.29×1024 FLOPs, 2.79M hours, $5.6M, 32.2 days. V4-Pro-ish (49B × 20T) → 5.88×1024, 4.99M hours, $10.0M, 57.7 days. Flash over-trained (13B × 30T) → 2.34×1024, 1.99M hours, $4.0M, 23.0 days. 500B × 15T → 4.5×1025, 38.2M hours, $76.4M, 441 days. (The V4-Pro-ish row is an illustrative token count, not a published figure.) Notice the last row: the wall-clock is the binding constraint, not the dollars.

Experiment 3 — sensitivity: which assumption moves the budget most?

Cost models are usually argued about on the wrong variable. This ranks the sensitivities in one pass.

python -c " base=dict(N=500e9,D=15e12,peak=989e12,mfu=0.35,usd=2.0) def hours(d): return 6*d['N']*d['D']/(3600*d['mfu']*d['peak']) h0=hours(base) for k,factor in [('mfu',0.8),('mfu',1.2),('D',1.2),('N',1.2),('usd',1.2),('peak',1.2)]: d=dict(base) if k=='usd': print(f'{k} x{factor}: cost \${h0*base[\"usd\"]*factor/1e6:.1f}M (hours unchanged)') else: d[k]=base[k]*factor; h=hours(d) print(f'{k} x{factor}: {h/1e6:.2f}M hours, \${h*base[\"usd\"]/1e6:.1f}M ({(h/h0-1)*100:+.0f}%)') "

A 20% MFU error moves cost by ±20% (from $72.2M to $90.3M or $60.2M); a 20% data error moves it 20%; a 20% price error moves it 20%. All the same magnitude — but MFU is the one you have the least evidence for, which is why it deserves the sensitivity range rather than a point estimate.

5 · Failure modes #

  • Using Ntotal for an MoE. Symptom: estimates are 10–20× too high and the plan looks impossible. Check which N the estimate used; FLOPs must use active parameters.
  • Assuming datasheet MFU. Symptom: the run takes 2–3× longer than planned. Use the ~33% anchor from this page, or measure your own on a 100-step probe.
  • Ignoring restart and checkpoint cost. Symptom: wall-clock is 15–25% longer than the GPU-hours/GPU-count figure, with no single catastrophic failure to blame. Model utilisation at 85–90%.
  • Pricing at list rate for a reserved contract (or the reverse). Symptom: the budget differs from the invoice by the committed-use discount. Pin the $/GPU-hour with its source and date on the sheet.
  • Forgetting the post-training bill. Symptom: pretraining is budgeted and RL/SFT (L51–L62) adds 20–100% on top, especially with long chain-of-thought rollouts. The full run cost is not the pretraining cost.

7 · Self-check #

Q1. Back out the MFU implied by 37B active, 14.8T tokens, 2.788M H800-hours at 989 TFLOP/s peak. Show each step.

Reveal answer

FLOPs = 6 × 37×109 × 14.8×1012 = 3.286×1024. Seconds = 2.788×106 × 3600 = 1.00368×1010. Achieved = 3.286×1024/1.00368×1010 = 3.274×1014 FLOP/s = 327.4 TFLOP/s. MFU = 327.4/989 = 33.1%. This is the calibration point for every estimate in this lesson.

Q2. A 500B-active model on 15T tokens. Compute GPU-hours and dollars at 35% MFU and $2/GPU-hour, and the wall-clock on 4,096 GPUs at 88% utilisation.

Reveal answer

FLOPs = 6×5×1011×1.5×1013 = 4.5×1025. GPU-seconds = 4.5×1025/(0.35×989×1012) = 1.30×1011 s → /3600 = 36.11M GPU-hours; × $2 = $72.22M. Wall-clock = 36.11×106/(4096×0.88)×24-1 = 36.11×106/3604.5 = 10,018 hours = 417 days. That is why such a run needs a much larger cluster or a smaller model.

Q3. Why would computing MFU against 671B instead of 37B be wrong, and by how much would it mislead you?

Reveal answer

A sparse model only performs FLOPs on active parameters, so dividing 6×671B×D by achieved FLOP/s understates MFU by 671/37 = 18.1×: the published run would appear to have a 1.8% “MFU”, which would suggest enormous headroom for improvement that does not exist. Conversely, computing predicted FLOPs from 671B overstates the run's cost by 18.1×. Always use active parameters for compute, total for memory.

Q4. Diagnostic: your 4,096-GPU run was budgeted at 60 days and is on day 75 at 80% complete. What two measurements separate “MFU was lower than planned” from “utilisation was lower than planned”?

Reveal answer

(1) Achieved FLOP/s during active training steps — measured from a profiler or from step time × known FLOPs per step; if this is below the plan's assumption, it is an MFU problem (bubble, comms, kernel efficiency). (2) Fraction of wall-clock spent in active training vs restarts, checkpoint writes and idle — if the fraction is below the planned 88%, it is a utilisation problem (failures, data stalls, scheduling).

Q5. Two proposals: (A) 16,384 GPUs at $2.30/h, (B) 8,192 GPUs at $1.90/h. Both produce the same GPU-hours. Which is cheaper and what else must be considered?

Reveal answer

For identical GPU-hours H, A costs 2.30H and B costs 1.90H, so B is 17.4% cheaper in absolute spend. But B takes 2× the wall-clock, so the decision also depends on time-to-market, the cost of capital, and the risk that a longer run is more exposed to hardware/price changes. Also, MFU is not identical between the two: a larger cluster has more failure events and restart overhead, which can partially offset the price difference. The mistake is comparing $/hour without computing total wall-clock and effective utilisation.
