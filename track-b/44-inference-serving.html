L44 · Serving: Batching, Continuous Batching, PagedAttention, Prefill/Decode Split

One request at a time wastes 99% of a GPU because decode is bandwidth-bound and the weights are re-read per token. Batching fixes that up to a point, paging fixes the memory waste that limits the batch, and separating prefill from decode is what lets each phase run efficiently.

~30 min difficulty ●●●●● build: throughput/latency calculator

1 · Why it exists #

A naive server processes one request at a time. On a 13B-active model at bf16 with 3 TB/s of bandwidth, one decode step re-reads 26 GB of weights to produce a single token: 8.67 ms — about 115 tokens per second for the whole accelerator, regardless of how many users are waiting.

The GPU is idle for almost all of that time. Decode does 2N FLOPs and reads 2N bytes per token; at 989 TFLOP/s and 3.35 TB/s that is an arithmetic intensity of 1 FLOP/byte against a ridge point of 295 — three orders of magnitude below the compute roof. So the machine sits waiting on memory, and the obvious fix is to give it more work per memory read: batch.

Batching then reveals a second bottleneck. Every concurrent sequence needs its own KV cache, allocated as one contiguous region of size max_context. If a request arrives with 200 tokens but the server reserved 8,192, you waste 97% of that allocation — and that waste is what silently caps your batch size and therefore your throughput. PagedAttention (the vLLM design) fixed this by paging the KV cache like an operating system pages memory, and continuous batching fixed the head-of-line blocking that static batching creates.

Serving throughput state as of 2026-10 is (batched tokens) / (bytes re-read per step). Batching raises the numerator, paging raises the batch you can fit, and disaggregating prefill from decode stops the two phases from ruining each other's efficiency.

2 · The mental model #

Analogy (labelled): a bus. Sending one passenger per bus costs a full bus per passenger (batch 1). Loading the bus fully amortises the trip (batching). But if you must reserve a full row of seats for every passenger in case they need it (contiguous allocation), the bus fills up with empty seats and you cannot sell the remaining capacity — which is exactly the paging problem.

What the analogy gets right

Fixed cost per trip, amortised across passengers. The amortisation is real and large, and it stops being free when a passenger's luggage (the KV cache) takes up the seats.

Where it breaks

Passengers do not arrive mid-trip. In LLM serving they do: a new request can join the batch at any decode step, which is continuous batching, and that changes the scheduling problem from “fill the bus” to “admit a new sequence without stalling the ones in flight.”

The two metrics that are always in tension

  • Time-to-first-token (TTFT) — dominated by prefill. Long prompt, long wait. Helps when batched aggressively.
  • Inter-token latency (ITL) — dominated by decode bandwidth per step. Grows with batch size because each step now reads more KV. This is what users feel as “slowness” while the answer streams.

Maximising throughput means maximising batch; maximising responsiveness means minimising batch. Every real deployment picks a point on this curve, often different points for different endpoints.

3 · The mechanism #

Batching arithmetic: where the wins stop

Per decode step a batch of B sequences at context L reads weights once plus B caches:

bytesstep = 2 Nactive + B × L × bytestoken  →  tokens/s = B ÷ (bytesstep / bandwidth) The weight term is paid once per step regardless of B — that is the whole point of batching. The cache term grows linearly with B, which is why throughput gains decelerate and eventually reverse.

With Nactive = 13B (2 bytes → 26 GB of weights), compressed cache at 17,568 B/token, 32k context, 3 TB/s:

Batch BBytes per stepStep timeThroughputITL per user
126.58 GB8.86 ms112.9 tok/s8.86 ms
830.61 GB10.20 ms784.2 tok/s10.20 ms
3244.42 GB14.81 ms2,161.1 tok/s14.81 ms
12899.69 GB33.23 ms3,852.1 tok/s33.23 ms

Read the last two columns together. Going from B = 1 to B = 8 multiplies throughput 6.9× and adds 15% to latency — an obvious trade. Going from B = 32 to B = 128 multiplies throughput only 1.78× and doubles latency. Somewhere in that range, ITL crosses the human-noticeable threshold and the endpoint becomes “fast but unusable.”

PagedAttention: why memory fragmentation caps throughput

A contiguous allocator reserves max_model_len bytes per request. Actual usage is prompt + generated, unknown in advance. Two wastes:

  • Internal fragmentation — the difference between reserved and used. A 200-token request with an 8,192 reservation wastes 97.6%.
  • External fragmentation — free space exists but is not contiguous, so it cannot be allocated.

Paging fixes both: the cache is stored in fixed-size blocks (for example 16 tokens each) with a per-sequence block table, so allocation is exactly what is needed, blocks need not be contiguous, and blocks can even be shared between requests that share a prefix (which is the foundation of L45). The measurable result is that the effective batch size rises, which raises throughput at a fixed memory budget.

Worked: a pool of 640 GiB, per-token cache 17,568 B, average context 4,096 → each sequence needs 17,568 × 4,096 = 71.96 MB. A contiguous 32k-reservation scheme needs 17,568 × 32,768 = 575.67 MB per sequence — 8× more — so the pool holds 1,193 sequences instead of 9,549. Paging is an 8× throughput multiplier on that workload, achieved purely by not reserving for a worst case.

Continuous vs static batching

Static batching: collect a batch, run it to completion, then take the next. Throughput is lost to head-of-line blocking — a 300-token answer finished inside a batch of 2,000-token answers idles its slot until the batch ends.

Continuous batching schedules at the level of decode steps: when a sequence finishes, its slot is immediately refilled with a waiting request. The saving is exactly the wasted tail. With answers ranging 100–2,000 tokens in a batch of 32, expected waste can easily be 30–50% of generated tokens — continuous batching recovers most of it.

Prefill/decode disaggregation

Prefill is compute-bound and benefits from large batches of prompt tokens; decode is bandwidth-bound and benefits from many concurrent sequences. Running them on the same device causes prefill interruption: a long-prompt arrival stalls inter-token latency for every streaming user.

Disaggregation runs them on separate pools: prefill workers produce KV blocks, which are transferred to decode workers. The bill is the transfer: for a 4,096-token prompt at 17,568 B/token, that is 4,096 × 17,568 = 71.96 MB moved per request — at 100 GB/s of inter-node fabric, 0.72 ms, negligible against a prefill of tens of milliseconds. The economics work because KV transfer is cheap relative to the work it decouples.

The serving artifact is a four-number record per configuration: TTFT at p50/p99, ITL at p50/p99, throughput in tokens/s, and cache utilisation (bytes used / pool size). A deployment reporting throughput without the other three is reporting the one number that improves when you make the service worse.

4 · Your hands #

Experiment 1 — the batching curve for your own model

Sweep batch size and print throughput alongside per-user latency. The knee is where you should set your max batch, and it is workload-specific.

def batch_curve(N_act, bytes_tok, ctx, bw=3e12, Bs=(1,8,32,128,256)): w = 2 * N_act for B in Bs: b = w + B * ctx * bytes_tok step_ms = b / bw * 1000 print(f"B={B:4d} {b/1e9:8.2f} GB {step_ms:7.2f} ms {B/(step_ms/1000):8.1f} tok/s ITL={step_ms:6.2f} ms") print("13B active, compressed cache, 32k ctx") batch_curve(13e9, 17568, 32768) print("13B active, compressed cache, 4k ctx") batch_curve(13e9, 17568, 4096)

Measured at 32k: 112.9 / 784.2 / 2,161.1 / 3,852.1 / 4,429.8 tok/s at B = 1/8/32/128/256 with ITL 8.86 / 10.20 / 14.81 / 33.23 / 57.79 ms. At 4k context the same batches give 115.1 / 903.1 / 3,391.9 / 10,905.8 / 17,289.0 tok/s with ITL only 8.69 → 14.81 ms — far more of the batching budget is free because KV per step is 8× smaller. The curve stays flat far longer — short context is where batching is nearly free. That is the single most useful operational insight on this page: max batch should vary with expected context length.

Experiment 2 — the capacity your allocator silently throws away

Compute effective batch sizes for contiguous reservation versus paging. This is the number to show when someone asks why the server only handles 200 concurrent users on 640 GB.

python -c " bytes_tok=17568; pool=640*1024**3 for avg_ctx, reserve in ((4096,8192),(4096,32768),(200,8192)): used=bytes_tok*avg_ctx; reserved=bytes_tok*reserve print(f'avg_ctx={avg_ctx:5d} reserve={reserve:6d}: need {used/1e6:7.2f} MB, allocator takes {reserved/1e6:8.2f} MB') print(f' contiguous batch={pool//reserved:5d} paged batch={pool//used:5d} gain={used/reserved:.1%} utilisation') "

At avg 4,096 with an 8,192 reservation: 71.96 MB needed vs 143.92 MB allocated → 4,774 vs 9,549 sequences (2×). At avg 4,096 with a 32,768 reservation: 1,193 vs 9,549 (8×). At avg 200 tokens with 8,192 reserved: 3.51 MB vs 143.92 MB → 4,774 vs 195,581 sequences (41×). The lesson: the damage from contiguous allocation scales with the ratio of reservation to actual use, so short-request workloads benefit most — and they are exactly the workloads whose latency users notice.

Experiment 3 — when prefill interruption ruins your SLO

Model a mixed workload: 100 short streaming requests plus periodic long prompts. Compare ITL with and without disaggregation.

eff = 989e12 * 0.40; bw = 3e12; N = 13e9 long_prompt, arrivals_per_sec, active = 32768, 2, 100 prefill_s = 2 * N * long_prompt / eff for mode in ("colocated", "disaggregated"): interfered = arrivals_per_sec if mode == "colocated" else 0 stalled_ms = interfered base_itl = (active * 4096 * 17568 + 2*N) / bw * 1000 print(f"{mode:14s} prefill={prefill_s*1000:.1f} ms stalls/s={stalled_ms} base ITL={base_itl:.2f} ms")

Measured: a 32k-token prefill is 2,153.6 ms of compute on one GPU, while the streaming decode baseline (B = 100 at 4k context) steps in 11.07 ms. So one long-prompt arrival is two full seconds during which no streaming sequence advances — two arrivals per second means the endpoint never recovers. Disaggregation removes that entirely; its price is moving the prompt's KV, 32,768 × 17,568 = 575.67 MB per request (0.58 GB), which at 100 GB/s is 5.76 ms. The arithmetic makes the trade obvious: 5.76 ms of transfer to remove 2,153.6 ms of interference.

5 · Failure modes #

  • Batch size tuned on one context length. Symptom: throughput collapses when long-context traffic arrives. Re-derive max batch from observed context distribution; admission-control on estimated cache bytes, not request count.
  • Fragmentation masquerading as OOM. Symptom: the server rejects requests at 60–70% pool utilisation because no contiguous block is large enough. That is the paging bug — check allocator efficiency, not pool size.
  • Head-of-line blocking. Symptom: p99 latency tracks the longest response in each batch, not the typical one. Static batching; switch to continuous.
  • Prefill stalls. Symptom: occasional 1–3 second gaps in streaming output for all users simultaneously, correlated with a large request arriving. Colocated prefill; disaggregate or chunk large prefill.
  • Optimising the wrong metric. Symptom: throughput doubles, churn increases, because per-user latency crossed the threshold where people give up. Always report TTFT and ITL next to throughput.

7 · Self-check #

Q1. 13B active, bf16, 32k context, compressed cache 17,568 B/token, 3 TB/s. Compute decode step time and throughput at B = 1 and B = 32.

Reveal answer

Weights = 2 × 13×109 = 26 GB. B = 1: KV = 32,768 × 17,568 = 0.576 GB, total 26.58 GB → 8.86 ms → 112.9 tok/s. B = 32: KV = 18.42 GB, total 44.42 GB → 14.81 ms → 2,161.1 tok/s. So 32× the batch gives 19.1× the throughput and 1.67× the latency — sublinear throughput gain because the KV term has become 41% of the step.

Q2. A pool of 640 GiB, 17,568 B/token, average 4,096-token contexts. How many concurrent sequences with paging, and how many if the allocator reserves 32,768 tokens per request?

Reveal answer

Per sequence used = 17,568 × 4,096 = 71.96 MB = 0.0672 GiB. Paged: 640/0.0672 = 9,524. Reserved: 17,568 × 32,768 = 575.7 MB = 0.537 GiB, so 640/0.537 = 1,192. Paging is an 8× capacity gain, which is an 8× throughput gain at equal latency per step (until compute limits take over).

Q3. Diagnostic: streaming output freezes for ~2 s for all users at random intervals, then resumes. What is happening and what are two mitigations?

Reveal answer

A large prefill is running on the same device and has monopolised it: prefill is compute-bound and batched, so a 32k-token prompt is ~2.15 s of work that blocks decode steps for every streaming sequence. Mitigations: (a) disaggregate prefill and decode onto separate pools; (b) chunk large prefills into slices interleaved with decode steps (chunked prefill), so no single request monopolises the device.

Q4. Why does PagedAttention enable prefix sharing, and what does that hand to L45?

Reveal answer

Because the cache is stored in non-contiguous fixed-size blocks referenced by a per-sequence block table, two sequences with an identical prefix can point at the same physical blocks and only diverge on copy. That makes prefix caching a pointer operation rather than a copy — which is exactly the mechanism behind context caching and cache-aware pricing: a shared prefix is stored once and billed as a cheap read for every subsequent request.

Q5. Your endpoint has a 25 ms ITL SLO. Using the table, what is the maximum batch at 32k context, and what throughput does that give?

Reveal answer

B = 32 gives 14.81 ms (within SLO); B = 128 gives 33.23 ms (violates it). Interpolating, the boundary sits somewhere between 32 and 128 — solving 26 + B×0.576 GB ≤ 25 ms × 3 TB/s = 75 GB gives B ≤ (75−26)/0.576 = 85. At B = 85, bytes per step = 26 + 85×0.576 = 74.96 GB, step time 24.99 ms, so throughput = 85/0.02499 ≈ 3,401 tok/s. So the SLO caps you at ~85 rather than 128 — and that is the number to size the cluster with.
