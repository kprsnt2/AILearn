L31 · Router Design, Load Balancing, Auxiliary Loss vs Auxiliary-Loss-Free

An MoE's capacity is only real if the router spreads traffic. Left alone, a router is a rich-get-richer machine: popular experts get more gradient, get better, get more tokens. The standard fix — an auxiliary loss — works by fighting the language objective, and the modern fix stops fighting.

1 · Why it exists #

Lesson 30 bought capacity by splitting the FFN into E experts and routing each token to the top k. There is a self-reinforcing failure waiting inside that design.

Suppose expert 3 wins slightly more tokens early (random init, a lucky direction, the first batch). It receives more gradient updates. It becomes better at the tokens it sees. It wins more tokens. Expert 40 receives almost none, so its weights barely move, so it stays worse. Within a few thousand steps the effective model is a dense model with E − few experts and a great deal of dead memory. You paid for 64 experts and shipped 6.

The observable cost is brutal because it compounds with the capacity mechanism: if experts are sized for tokens×k/E, a router that sends 40% of tokens to three experts overflows those three experts' slots and drops the excess tokens — they skip the FFN entirely. So collapse doesn't just waste memory: it silently degrades quality while every monitor shows green, because nothing throws an exception.

This page covers the three answers: the auxiliary load-balancing loss (GShard/Switch lineage), the capacity-factor mechanism that makes dropping observable, and the auxiliary-loss-free bias introduced in DeepSeek-V3 arXiv:2412.19437, which steers the router's choices without injecting a conflicting gradient into the language objective.

An MoE is only as large as its used experts. Load balance is not a hygiene metric — it is the mechanism that converts money spent on parameters into capability, and its two failure directions (collapse and over-balancing) both cost quality silently.

2 · The mental model #

Analogy (labelled): a queue system where server speed depends on past traffic. Fast servers attract traffic, get faster, attract more. The system converges to a few overloaded servers and many idle ones.

Two knobs exist for fixing it. You can penalise the system whenever load is uneven — which means adding a term to the objective that tells the model “don't put all your tokens in one basket,” competing with “predict the next token well.” Or you can adjust the dispatch weights — nudge the perceived attractiveness of each expert up or down until load evens out, leaving every gradient purely on the language objective.

What the analogy gets right

The feedback loop is the cause. Balance must be enforced continuously, not once at init; any static assignment converges to imbalance under a rich-get-richer dynamic.

Where it breaks

Perfectly even load is not the goal and can be harmful: if all experts see every token, they all learn the same thing and you have paid 64× for one expert with 64 copies. Some specialisation is desirable. The target is balanced-but-specialised, which is why a bias on assignment beats a penalty on the objective: it permits specialisation to survive.

The two failure directions

  • Collapse — max load fraction → 1, router entropy → 0, most experts dead, capacity drops spike.
  • Over-balancing — load fraction is perfectly uniform (1/E each) but trivially so: the router assigns near-uniformly and ignores the input. Router entropy is at its maximum log E, and quality is that of a smaller dense model because no expert specialises.

Both are visible in the same two-number diagnostic: max load fraction and router entropy. You want max load fraction near 1/E and entropy below log E but far above zero.

3 · The mechanism #

(a) The auxiliary load-balancing loss

&lagr;aux = α · E · ∑i=1E fi · Pi  ,  fi = (fraction of tokens in batch sent to expert i),   Pi = (mean router prob for i) f is non-differentiable (it is a count), P is differentiable, so the gradient flows only through P. Uniform routing gives f = P = 1/E and ∑ f·P = E·(1/E²) = 1/E, so &lagr; = α·1 — that is the minimum. Full collapse gives f·P concentrated and ∑ f·P = 1, so &lagr; = α·E, E times worse.

Worked: E = 64. Uniform: ∑ fiPi = 64 × (1/64)² = 1/64 = 0.015625, so &lagr; = α · 64 × 0.015625 = α. Total collapse (all mass on one expert): ∑ = 1, so &lagr; = 64α. The penalty range is exactly [α, Eα] — a 64× span — and the gradient of that term is what competes with next-token prediction.

(b) The auxiliary-loss-free bias

gi ← logitsi + bi  (for selection only) ,  bi ← bi − γ · sign(loadi − ℓi) bi is a per-expert bias used only when choosing top-k — the gate weight applied to the expert's output still comes from the unbiased scores. Update direction: if expert i is overloaded relative to the ideal ℓi, decrease its bias; if underloaded, increase it. γ is a small step size. No term is added to the loss, so the language gradient is untouched.

This is the deep difference. The auxiliary loss changes what the model wants; the bias changes what the router sees. You can make the bias arbitrarily strong without moving the loss surface, so there is no quality/speed trade-off knob to leave out of a paper.

(c) Capacity factor and the drop counter

capacityi = ceil( capacity_factor × tokens_in_batch × k / E ) Any expert receiving more than its capacity drops the excess (GShard/Switch lineage) or defers it. Tokens dropped skip the FFN and pass through the residual. With capacity_factor = 1.0 and a perfectly balanced router, every expert is already full — any wobble drops tokens, so production runs use 1.25–2.0.

The number to watch is not the percentage dropped in aggregate but which tokens are dropped. If drops correlate with sequence position or with rare tokens, you are systematically degrading the long tail while your average loss looks fine.

Three counters per MoE layer, logged every N steps, make routing auditable: max load fraction (target ≈ 1/E), normalised router entropy (target clearly between 0 and 1), and drop fraction split by token position bucket. A run without these is unreproducible in the one dimension that decides whether the capacity was real.

4 · Your hands #

Experiment 1 — collapse a router, then fix it two ways

A 16-expert, top-2 router with a mild rich-get-richer dynamic (experts that win tokens drift toward their inputs) and a warm attractor on expert 0. Run three modes: no balancing, auxiliary-loss-style bias, loss-free bias. This is the experiment that tells you whether your fix actually works.

import numpy as np, math E, K, N = 16, 2, 20000 def run(mode, gamma=0.03, seed=3): rng = np.random.default_rng(seed) W = rng.normal(0, 1, (E, 8)); X = rng.normal(0, 1, (N, 8)) bias = np.zeros(E); load = np.zeros(E) for t in range(N): x = X[t]; logits = W @ x + bias top = np.argsort(-logits)[:K]; load[top] += 1 p = np.exp(logits - logits.max()); p /= p.sum() fr = load / load.sum() if mode == "aux": bias -= gamma * E * (fr * p) # loss-derived pressure elif mode == "biasfree": bias -= gamma * np.sign(fr - 1.0/E) if 0 in top: W[0] += 0.002 * x # rich-get-richer on the winner else: W[0] *= 0.9999 d = load / load.sum() return d, -(d * np.log(d + 1e-12)).sum() for m in ("plain", "aux", "biasfree"): d, H = run(m) print(f"{m:9s} max_load={d.max():.3f} min_load={d.min():.4f} H={H:.3f} / {math.log(E):.3f}")

Measured output: plain max_load=0.142 min_load=0.0134 H=2.619 / 2.773; aux max_load=0.066 min_load=0.0583 H=2.772 / 2.773; biasfree max_load=0.067 min_load=0.0604 H=2.772 / 2.773. Unbalanced, the best expert takes 14.2% of tokens (ideal 6.25%) and the worst 1.3% — entropy 2.62 of a maximum 2.77. Both fixes restore near-uniform load. Note the aux mode buys balance by adding a hidden gradient; the bias mode reaches the same place without one. Falsification: if plain ends uniform, your rich-get-richer term is too weak to test anything.

Experiment 2 — the geometric fact behind capacity drops

Experiment 3 shows that a uniform router still drops tokens at capacity_factor = 1.0. Before accepting that, verify it is not a bug: at cf = 1.0 the capacity equals the mean load, and the load distribution is a multinomial, so by construction roughly half the experts exceed their mean. This table is the sanity check that the capacity mechanism is doing what it claims.

def drops(max_load_frac, E, cf=1.0): capacity = cf / E return max(0.0, (max_load_frac - capacity) / max_load_frac) for E in (8, 64, 256): for mult in (1.0, 1.5, 2.0, 4.0): for cf in (1.0, 1.25): print(f"E={E:3d} load={mult}x ideal cf={cf} -> {drops(mult/E, E, cf):.1%} of that expert's tokens dropped")

Measured: at 1.5× ideal load, cf = 1.0 drops 33.3% and cf = 1.25 drops 16.7%; at 2.0×, 50.0% and 37.5%; at 4.0×, 75.0% and 68.8% — identical for every E, because the ratio is scale-free. The exact identity: drops = 1 − cf / mult. Falsification: if your E = 8 and E = 256 rows differ, the capacity formula is probably using a constant instead of a per-expert share.

Experiment 3 — the same arithmetic, laid out as the drop table

Balance and capacity interact, so a router that looks “slightly” unbalanced can drop a large fraction of a hot expert's tokens. Compute it directly.

def drops(max_load_frac, E, cf=1.0): # one hot expert taking max_load_frac of all tokens; capacity = cf/E of tokens capacity = cf / E return max(0.0, (max_load_frac - capacity) / max_load_frac) for E in (8, 64, 256): ideal = 1.0 / E for mult in (1.0, 1.5, 2.0, 4.0): fr_val = ideal * mult for cf in (1.0, 1.25): print(f"E={E:3d} load={fr_val:.4f} ({mult}x ideal) cf={cf} -> drops {drops(fr_val,E,cf):.1%} of that expert's tokens")

At E = 256, cf = 1.0, and an expert receiving 2× ideal load, half of its tokens are dropped; at cf = 1.25 that is 37.5%. This is why the capacity factor is not a performance knob but a correctness knob: raising it trades throughput for not silently discarding the model's most-requested knowledge.

5 · Failure modes #

  • α too high. Symptom: load histogram is perfectly flat but validation loss is worse than the dense baseline; router entropy sits at ≈log E. The model is spending capacity on balance instead of prediction.
  • Bias step γ too aggressive. Symptom: expert assignment oscillates step to step — the same token type routes differently on consecutive batches, and throughput jitters because batch composition changes.
  • Capacity drops hidden by averaging. Symptom: aggregate drop rate is 0.5% (acceptable) but 40% of drops come from one layer, or are concentrated in sequences > 8k tokens. Per-layer, per-position logging is the only way to see it.
  • Batch-composition specialisation. Symptom: quality on the web mix is fine and quality on code is terrible, because the data pipeline puts them in different batches so the router never has to arbitrate. Mixture matters as much as balancing.
  • Balance measured on the training distribution only. Symptom: a deployed MoE has a hot expert and drops tokens on out-of-distribution traffic even though training looked balanced. Router overconfidence on unseen inputs systematically overloads the dominant expert with inputs that look like everything.

7 · Self-check #

Q1. With E = 64, compute the auxiliary loss value at perfect balance and at total collapse (in units of α). What is the ratio?

Reveal answer

Balanced: fi = Pi = 1/64, so ∑ fiPi = 64 × (1/64)² = 1/64, and &lagr; = α·64·(1/64) = α. Collapsed: all f and P on one expert, ∑ = 1, &lagr; = 64α. Ratio = 64×, exactly E. The penalty's dynamic range is the expert count, which is why large-E models require small α.

Q2. E = 128, k = 8, batch = 8,192 tokens, capacity_factor = 1.25. What is the per-expert capacity and what fraction of tokens is dropped if one expert receives 3× ideal load?

Reveal answer

Ideal per expert = 8192 × 8/128 = 512 tokens. Capacity = ceil(1.25 × 512) = 640. An expert at 3× ideal receives 1,536 tokens, so it drops 1,536 − 640 = 896, which is 896/1536 = 58.3% of its tokens. Aggregate drop fraction = 896/8192 = 10.9% of the batch — catastrophic, from one expert being 3× hot.

Q3. Diagnostic: router entropy is pinned at its maximum, load is perfectly uniform, and quality is that of a dense model half the active size. What happened and which knob do you turn?

Reveal answer

Over-balancing: α (or γ) is too strong, so the router is effectively ignoring the input and assigning uniformly. Every expert learns the same function; the model is a 1/1 dense model with E× the memory. Turn α/γ down and watch entropy drop below log E while max load stays near 1/E. The signature to target is “balanced but not uniform”.

Q4. Why does the auxiliary-loss-free bias leave the language objective's gradient untouched, and why does that matter for reproducibility?

Reveal answer

The bias is added only inside the top-k selection comparison, not to the gate weight applied to the expert output, and it is updated by a rule based on load counts rather than by backprop. So no term is added to the loss and no gradient flows through b. It matters because the loss curve is then a function of the language objective alone, which means α-like hyperparameters cannot secretly trade quality for balance and you can compare runs across balance policies without confounds.

Q5. Training looked balanced, but production shows a hot expert. Name the most likely cause and the cheapest mitigation.

Reveal answer

Router overconfidence on out-of-distribution inputs: inputs unlike the training mixture produce peaked router scores and pile onto the expert whose weights are largest, because the bias was tuned on the training distribution. Cheapest mitigation: raise capacity_factor for serving (or replicate the hottest expert across replicas) and add a serving-side load histogram per layer; the correct fix is to include representative production traffic in router tuning or to re-balance periodically with an EMA of serving load.
