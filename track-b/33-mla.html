L33 · Multi-head Latent Attention: KV Compression as a Low-Rank Cache

At long context the KV cache, not the weights, decides how many users one GPU can serve. MQA and GQA shrink it by sharing heads; MLA shrinks it by caching a compressed latent and re-expanding it just in time — buying 10× the cache for a ~0.5% compute tax.

1 · Why it exists #

Autoregressive decoding is not compute-bound. It is memory-bound, and the memory that matters is not the weights — it is the cache of every past token's keys and values.

Here is the failure that forced MLA into existence. Take a standard multi-head attention layer with 128 heads of dimension 128, bf16, across 61 layers (the shape of a large dense model). Each cached element is 2 bytes and you store a key and a value for every head, every layer, every past token:

bytestoken = 2 × L × nkv × dhead × 2 bytes The leading 2 is (K and V); L is layer count; nkv is the number of distinct KV heads; dhead is head dimension; the trailing 2 is bytes per bf16 element. Compute this once per model and you can price any context length.

For the 128-head config: 2 × 61 × 128 × 128 × 2 = 3,997,696 bytes/token = 3,904 KiB per token. At a 1M-token context that is 3,997,696 × 106 = 3.998×1012 bytes = 3,723 GiB = 3.64 TiB for a single conversation. Ten concurrent users need 36 TiB of HBM. There is no GPU cluster on Earth where that is a viable serving model.

That is the whole motivation. DeepSeek-V2 arXiv:2405.04434 introduced Multi-head Latent Attention because GQA's head-sharing had run out of compression, and it was carried into V3 arXiv:2412.19437 and the V4 family. The claim you should verify by arithmetic: MLA fits cache for a 1M-token context into a fraction of the memory GQA needs, while keeping full-rank per-head expressivity.

KV cache is the unit economics of inference. Halve it and you double concurrent users on the same hardware at the same latency. MLA gets roughly 10× more out of the same silicon than GQA at the same head count, and that is why 1M contexts became a product instead of a demo.

2 · The mental model #

Analogy (labelled): archiving camera footage. MHA stores every full-resolution frame per camera. MQA films all rooms with one wide-angle camera — tiny storage, terrible detail. GQA films groups of rooms per camera — a middle setting. MLA instead stores a compressed exposure of each room plus a small signed “which direction was the light” blob, and reconstructs full-resolution frames on demand using a learned decoder.

Decode is exactly that: for each new token, per layer, MLA reads a small latent from the cache and runs two small matrix multiplies to reconstruct K and V at full head width. Compression happens on the way in (encode); expansion happens at use time (decode).

What the analogy gets right

Storage drops by the compression ratio; read amplification is paid in compute, which during decode is cheap because you are memory-bound anyway. Trading bandwidth for FLOPs is the right trade at every decoder step.

Where it breaks

Reconstruction is not lossless. The latent has a rank cap: the model can only express K/V directions that its up-projection matrices can produce. If a head needs a K direction outside that subspace, MLA pays for it in quality. The design question is where the rank cap sits, and the answer (512 for the non-RoPE key path in V3) is a tuned number, not a free parameter.

What is actually stored, precisely

A standard layer caches per token: k (one vector per KV head) and v (one per KV head). MLA caches per token: one latent vector c_KV of rank 512 plus one shared RoPE key k_R of dimension 64, with the number of KV heads set to 1 because everything is derived from the shared latent. That is 512 + 64 = 576 bf16 elements = 1,152 bytes per layer per token — regardless of how many attention heads the model has.

3 · The mechanism #

(a) MHA → MQA → GQA: factorize the heads

MHA: bytes = 2 L nh dh b  |  GQA: bytes = 2 L nkv dh b  |  MQA: nkv = 1 nh = query heads, nkv = distinct key/value heads, G = nh/nkv query heads sharing each KV head. GQA's saving is exactly nh/nkv = G. Quality degrades as G grows because every group member must agree on its keys and values.

(b) MLA: low-rank the content rather than sharing heads

cKV = WDKV x ∈ ℝ512  (cached)
kiC = WUK(i) cKV,   viC = WUV(i) cKV  (derived at use time) x is the token's activation. WDKV is the down-projection (d_model → 512); WUK(i), WUV(i) are per-head up-projections (512 → 128). Crucially WUK can be folded into WQ at inference, so the key path costs almost nothing per step; the value path cannot be folded and is the real decode tax.

(c) Decoupled RoPE — the trick that makes it work

RoPE mixes positional information into keys by rotating them. Rotation is not linear-commutative with the up-projection, so you cannot cache a compressed key and then rotate it — the rotation would have to be applied to full-width keys. MLA splits the key into two parts: a content part (derived from the 512 latent, no RoPE) and a positional part (a 64-dim key, carried through RoPE, cached and shared across all heads). The cache entry is therefore c_KV (512) + k_R (64) = 576 elements per layer per token, the kv_lora_rank + qk_rope_head_dim pair.

The decode tax, computed

The one thing MLA genuinely costs: each decode step must up-project 61 latents of rank 512 into 128-head K and V. The value side cannot be algebraically folded away, so price it per token:

extra FLOPs/token = 2 × L × nh × dh × dc = 2 × 61 × 128 × 128 × 512 = 7,995,392 per layer, × 61 layers ≈ 0.488 GFLOP/token Against a ~37B-active model at 2 × 37e9 = 74 GFLOP/token, that is 0.488/74 = 0.66% of decode compute — but note the earlier line already counted 61 up-projections twice, so read 0.488 GFLOP as the per-token total and the tax as 0.66%. For a sub-1% compute tax the cache drops from 3,723 GiB (MHA) to 65.45 GiB at 1M tokens: 57× less. That is the trade in one sentence.

The decisive row comparison is MLA versus MQA: MLA's cache is 65.4 GiB at 1M tokens against MQA's 29.1 GiB — MLA is 2.25× larger than the most aggressive possible sharing scheme, and yet MLA keeps 128 independent attention heads whereas MQA collapses them all to one. GQA at 8 groups needs 232.7 GiB for the same context. So MLA delivers full-head expressivity at 0.28× the GQA memory.

What token-wise compression adds on top

DeepSeek-V4's architecture state as of 2026-10 adds token-wise compression on top of DSA. The published operational numbers for V4.1-Flash are that its KV cache needs 1/4 the HBM and 1/8 the SSD of the previous generation. Applying that to the 65.4 GiB figure:

  • HBM: 65.45 / 4 = 16.4 GiB per 1M-token context.
  • SSD spill: 65.45 / 8 = 8.2 GiB, which is the more striking number — it means a 1M-token conversation can be offloaded and reloaded from storage, so cache eviction becomes a paging problem rather than a quality cliff.

At 16.4 GiB per session, a 640 GB pool holds 39 concurrent 1M-token sessions instead of 9.8 — that is the entire product difference between “long context for enterprise batch jobs” and “long context for an API.”

(e) Why the cache is the dominant inference cost

Three independent arguments, each checkable:

  1. It sets concurrency. Weights are a fixed, shared cost; KV cache is per-session and grows linearly with context. At 1M tokens it is 65.45 GiB per user in the MLA config above. Your ceiling on users is (HBM − weights) / cache-per-user.
  2. It sets decode bandwidth. Each generated token must read the entire K/V history for its layer. At 1M tokens that is 68.6 KiB × 61 = 4.19 MiB per token from cache before you touch any weights — and it is re-read every single step.
  3. It sets the prefill/decode balance. Prefill is compute-bound and can be batched aggressively; decode is bandwidth-bound and cannot. The only lever that moves decode throughput is bytes fetched per token, which is exactly what MLA/GQA/quantization target (L38, L44, L40).

The audit artifact for a serving claim is kv_bytes_per_token computed from the published config and compared against the vendor's stated context limit. If 1M tokens × bytes/token exceeds the HBM pool, the context limit is only achievable with offload, compression, or a smaller effective window. This has caught real spec inflation.

4 · Your hands #

Experiment 1 — the cache calculator every serving decision needs

One function, four schemes, any context. Run it against your own deployment: the number that matters is the last column, which is how many sessions a pool holds.

def kv_bytes(L, n_kv, d_head, bytes_el=2, extra=0): # extra = additional elements cached per layer per token (MLA's RoPE key, etc.) return 2 * L * n_kv * d_head * bytes_el + L * extra * bytes_el L, n_h, d = 61, 128, 128 schemes = {"MHA": kv_bytes(L, n_h, d), "GQA-8": kv_bytes(L, 8, d), "MQA": kv_bytes(L, 1, d), "MLA": kv_bytes(L, 0, d, extra=512+64)} for name, b in schemes.items(): for ctx in (131072, 1_000_000): gib = b * ctx / 1024**3 print(f"{name:6s} {b:10,d} B/token ctx={ctx:>9,} -> {gib:9.2f} GiB") for pool in (96, 640): print(f"pool {pool} GB, MLA @1M -> {pool/(schemes['MLA']*1_000_000/1024**3):.1f} sessions")

Measured: MHA 3,997,696 B/token (488.0 GiB @128k, 3,723.1 GiB @1M); GQA-8 249,856 B (30.5 GiB, 232.7 GiB); MQA 31,232 B (3.8 GiB, 29.1 GiB); MLA 70,272 B (8.6 GiB, 65.45 GiB). At 1M context a 96 GB pool holds 1.5 MLA sessions and a 640 GB pool holds 9.8 — note how brutally a 1M context limits concurrency even after MLA, which is exactly why V4's token-wise compression (1/4 the HBM) is the difference between 1.5 and 39 sessions per 640 GB. Falsification: if MLA comes out below MQA you built the extra term with the wrong sign or forgot the layer count.

Experiment 2 — the compression-ratio / decode-tax trade-off curve

MLA's rank is a knob, not a constant. Sweep the latent rank and see what each setting buys in memory and costs in compute. This is the calculation that picks kv_lora_rank.

L, n_h, d, N_act = 61, 128, 128, 37e9 print("rank B/token 1M-GiB extra GFLOP/token % of decode FLOPs") for rank in (64, 128, 256, 512, 1024): b = L * (rank + 64) * 2 extra = 2 * L * n_h * d * rank / 1e9 print(f"{rank:5d} {b:9,d} {b*1e6/1024**3:8.2f} {extra:18.3f} {100*extra/(2*N_act/1e9):17.2f}%")

Measured at rank 64/128/256/512/1024: 15,616 / 23,424 / 39,040 / 70,272 / 132,736 bytes per token; 14.54 / 21.82 / 36.36 / 65.45 / 123.62 GiB at 1M context; decode tax 0.128 / 0.256 / 0.512 / 1.023 / 2.047 GFLOP per token, i.e. 0.17% / 0.35% / 0.69% / 1.38% / 2.77% of the 74 GFLOP/token active compute. Memory scales linearly with rank while the compute tax also scales linearly — so the choice is pure quality-per-byte, which is why it is tuned empirically rather than derived.

Experiment 3 — prove the cache dominates at long context

The claim in section (e). Compare bytes fetched per decoded token from weights versus from cache as context grows. The crossover point is where the serving bottleneck changes character.

python -c " L, rank, n_h, d = 61, 512, 128, 128 cache_per_token = L*(rank+64)*2 weights_active_bytes = 37e9*2 # bf16, 37B active for ctx in (8192, 32768, 131072, 1000000): c = cache_per_token*ctx print(f'ctx={ctx:>8,}: cache {c/1e9:8.3f} GB vs weights {weights_active_bytes/1e9:.1f} GB -> cache/weights = {c/weights_active_bytes:6.2f}x') "

Measured: at 8k context the cache is 0.576 GB, which is 0.01× the 74 GB of active-weight bytes. At 32k it is 2.30 GB (0.03×); at 128k, 9.21 GB (0.12×); at 1M, 70.3 GB (0.95×). So at 1M tokens a single session's KV cache is nearly the same size as the model's entire active weight stream, and unlike the weights it cannot be amortised across the batch because every session has its own. Past ~1.05M tokens the cache becomes the larger stream; at 128k it is a 12% overhead, real but second-order. The reason the cache still dominates the bill at ordinary contexts is point 1 in section (e): it is per-session and caps concurrency, while weights are shared once.

5 · Failure modes #

  • Counting only one of K/V. Symptom: your cost model is exactly 2× optimistic from the first estimate onward, and it never closes. The formula has a leading 2 for K and V and a 2 for bytes per element.
  • Ignoring WUV at decode. Symptom: measured decode latency is higher than your FLOPs-only model predicts by a few percent at short context and much more at long context. The value up-projection cannot be folded into WQ, so it runs every step.
  • Assuming MLA gives 128 independent K/V heads. Symptom: you expect MLA to beat GQA on quality and on long-context retrieval and find it loses on some needle tests. All heads share one latent, so heads become correlated through the shared down-projection; the rank cap is a real bottleneck (see L34 and the long-context evals).
  • Precision assumptions abroad. Symptom: you compute the cache at fp8 to double concurrency and find quality loss on long-context tasks specifically, because quantization error accumulates over 1M cached elements per layer while having no effect on short prompts. KV quantization needs a different calibration set than weight quantization (L40).
  • Trusting the context spec. Symptom: a documented 1M context is real but the provider silently routes you to a short context, or throughput collapses. Check: 1M tokens × bytes/token ≤ HBM per replica, otherwise admission control or offload must be doing the work.

7 · Self-check #

Q1. L = 32, nh = 32, dh = 128, bf16. Compute bytes/token for MHA, and for GQA with 4 KV heads. What is the saving factor?

Reveal answer

MHA: 2 × 32 × 32 × 128 × 2 = 524,288 B/token = 512 KiB. GQA-4: 2 × 32 × 4 × 128 × 2 = 65,536 B = 64 KiB. Saving = 524,288/65,536 = exactly 8×. At 1M tokens: 488.3 GiB vs 61.0 GiB.

Q2. A model has L = 61, kv_lora_rank = 512, qk_rope_head_dim = 64, bf16. Compute bytes/token and the number of concurrent 128k-context sessions in a 192 GB pool.

Reveal answer

Per layer per token: (512 + 64) × 2 = 1,152 bytes. × 61 layers = 70,272 B/token. At 128k context: 70,272 × 131,072 = 9.21×109 B = 8.58 GiB per session. A 192 GB pool holds 192/8.58 ≈ 22 sessions (ignoring weights: with 1 TB of weights on a cluster and 192 GB of pool per replica, ~22). If the same model used GQA-8 at 249,856 B/token, that would be 30.5 GiB per session and only 6.3 sessions — which is the product difference MLA buys.

Q3. Why can't you just cache 128-dimensional keys and apply RoPE to the cached key later, the way a dense model does?

Reveal answer

You can, but then the key must be stored at full width — which is exactly the memory you were trying to save. MLA's inference is to cache a low-rank content latent that is never rotated, plus a separate low-dim RoPE key that is rotated and shared across heads. The content key is reconstructed after being cached and combined with the rotated positional key; the up-projection for the key path folds into the query projection so it costs nothing extra.

Q4. MLA's 1M-token cache is 65.4 GiB; V4.1-Flash is stated to need 1/4 the HBM and 1/8 the SSD of the previous generation. Give the resulting HBM and SSD figures and say what the SSD number changes about serving design.

Reveal answer

HBM: 65.4/4 = 16.4 GiB per 1M-token session. SSD: 65.4/8 = 8.2 GiB. The SSD figure means a session's cache fits on a local NVMe device, so eviction and re-admission become a paging problem with a known latency cost instead of a loss of conversation state. That converts long context from an HBM-capacity-limited feature into a storage-throughput-limited one, and lets a single node hold far more sessions than its HBM alone allows.

Q5. Diagnostic: your long-context traffic shows decode throughput collapsing non-linearly as context grows past ~100k tokens, far worse than the linear cache model predicts. Name two causes.

Reveal answer

(a) Cache paging/offload kicking in: once the working set exceeds HBM, every step pays transfer latency, so throughput falls faster than linearly. (b) Attention kernel efficiency: at very long sequences, block-sparse kernels and FlashAttention tiling change behaviour, and if the implementation falls back to a materialised attention matrix the O(L²) memory traffic dominates. Distinguish by measuring cache read bytes per step vs the theoretical 70,272 × L bytes, and GPU memory-migration counters.
