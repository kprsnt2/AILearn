L42 · Parallelism: DP, TP, PP, EP, ZeRO/FSDP, and the Comms Math

Parallelism is not “use more GPUs” — it is a partitioning problem where every choice has a bill measured in gigabytes per step. Naive pipeline parallelism with 32 stages and 8 microbatches wastes 79.5% of the cluster; the arithmetic that tells you so fits on one line.

1 · Why it exists #

A 671B-parameter model in bf16 is 671×109 × 2 = 1.342×1012 B = 1,249.8 GiB. Mixed-precision AdamW training also stores gradients (another 1,249.8 GiB in bf16) and optimizer state — two fp32 moments plus an fp32 master copy, conventionally 12 bytes per parameter = 7,499.0 GiB. Add activations and the total is well over 11 TiB before a single forward pass. No accelerator holds that. state as of 2026-10 Nothing about a modern model fits anywhere, which is why parallelism is the discipline this track has been walking toward.

The failure that forces real engineering is not “it does not fit” — it is that the naive fixes each destroy something:

  • Pure data parallelism replicates the whole model on every GPU (redundant weights) and all-reduces gradients, which requires one full copy of the model to exist per device anyway. Useless above ~10B.
  • Tensor parallelism splits each matmul across GPUs and adds an all-reduce inside every layer. Communication volume scales with model size and latency sits on the critical path — fine within one NVLink domain, painful across nodes.
  • Pipeline parallelism splits layers across GPUs and introduces idle time (the bubble) proportional to stage count.
  • Expert parallelism (the MoE-specific axis) scatters experts across GPUs and pays an all-to-all per block.

The practical question is never “which one” — it is which combination, for this model, on this interconnect. And every combination can be scored before you launch.

Parallelism spends bandwidth to buy memory. Every configuration is a trade with a computable price in GB-per-step and idle-percent, and the wrong choice silently burns 40–80% of a multi-million-dollar cluster.

2 · The mental model #

Analogy (labelled): printing a huge document on many machines. Split by copies (data parallel: each machine prints a different batch of pages — but each needs the whole document), by chapters (pipeline: machines pass pages downstream and sometimes wait), by columns of each page (tensor: everyone works on every page and must synchronise constantly), or by topic (expert: pages go to whichever machine specialises).

What the analogy gets right

Each strategy splits a different axis, and each has an unavoidable synchronisation cost. Mixing them is how real runs work: split chapters with pipeline, columns with tensor, batches with data.

Where it breaks

In printing, waiting is cheap. Here the synchronisation is a collective over the fastest interconnect, and the cost depends on topology (NVLink inside a node vs InfiniBand across nodes). The same split that is free within a node can be catastrophic across one.

And ZeRO/FSDP is a refinement of DP: instead of replicating optimizer state, gradients and weights, it shards them across the DP group and gathers what it needs just in time. That converts DP from a memory-duplicating scheme into a memory-saving one, at the cost of more communication.

3 · The mechanism #

Memory, sharded three ways

For N parameters with bf16 weights (2N), bf16 gradients (2N) and Adam state (12N), a DP group of size D:

ZeRO-1: 2N + 2N + 12N/D  |  ZeRO-2: 2N + (2N + 12N)/D  |  ZeRO-3 (FSDP): (2N + 2N + 12N)/D ZeRO-1 shards only optimizer state, ZeRO-2 also gradients, ZeRO-3 also parameters. Only ZeRO-3 makes per-device memory scale as 1/D for everything, which is what lets a model larger than a single GPU's memory be trained with plain data parallelism.

Read the columns, not the rows. ZeRO-1 and ZeRO-2 cannot fit this model at any DP size — they asymptote to 2,500 GiB and 1,258 GiB because weights and gradients stay replicated. Only ZeRO-3 gets you to 9.8 GiB/device. That is why FSDP is the default for anything above a few billion parameters in ordinary distributed training.

Tensor parallelism: the all-reduce bill

A ring all-reduce moves 2N(S−1)/S bytes for N total bytes and S ranks — roughly 2N for large S. Per training step, TP must synchronise gradients; the volume is the whole model:

bytesTP = 2 × Nparams × 2 bytes × (S−1)/S  ≈  4N For 671B parameters at bf16 and S = 8: 2 × 671×109 × 2 × 7/8 = 2,348.5 GB moved per optimizer step. At an effective 300 GB/s per link that is 7.8 s of pure communication per step, against a step time of maybe 20–40 s. TP is not free even at S = 8.

This is the single most important number for choosing TP degree: 2.35 TB per step. It is why TP is confined within a node (NVLink class bandwidth) and crossed with PP or DP rather than extended across an InfiniBand fabric where the same 2.35 TB would take an order of magnitude longer.

Pipeline parallelism: the bubble

bubble = (P − 1) / (M + P − 1) P = number of pipeline stages, M = number of microbatches in flight. Every stage must wait at the start and end of the step while the pipeline fills and drains. The formula is for the standard 1F1B schedule; interleaved schedules improve the constant but not the asymptotic.

The trap is that P = 32 with M = 8 wastes 79.5% of the cluster — you rented 32 stages' worth of GPUs and got 20% of the throughput. To make 32 stages worthwhile you need M ≥ 64–128 microbatches, which in turn means the global batch must be large enough to split that finely, which constrains the learning-rate schedule (L14). This is why pipeline depth and batch size are chosen together, never independently.

Expert parallelism: an all-to-all per block

Each MoE layer moves every token to the GPUs holding its top-k experts and back: k × dmodel × 2 bytes per token, twice. At d = 7,168 and k = 6: 6 × 7,168 × 2 = 86,016 B → 84.0 KiB per token per layer (112.0 KiB at k = 8). For a 4,096-token batch across 61 layers that is 4,096 × 84 × 1,024 × 61 ≈ 21.5 GB of all-to-all per forward pass, per direction. EP is unavoidable for large MoE but it makes the network fabric, not the GPUs, the binding resource.

Activation memory: the constraint nobody budgets for

Activations are the reason batch size is small at long sequence lengths. Per token per layer a transformer stores several dmodel-sized tensors in bf16; at d = 7,168 a rough count of four such tensors is 2 (bf16) × 7,168 × 4 = 57,344 B per token per layer. Across 61 layers that is 57,344 × 61 ≈ 3.5 MB per token. A batch of 4,096 tokens × 4,096 sequence = 16.8M tokens → ~58.5 TB of activations without gradient checkpointing.

That number is why gradient checkpointing (recompute in backward, trading ~33% extra FLOPs for a large memory reduction) and sequence parallelism are mandatory, and why the practical batch size is usually set by activation memory rather than by optimizer preference.

The auditable artifact for a parallel config is a table with five rows: per-device memory by component (weights / grads / optimizer / activations), TP all-reduce bytes, PP bubble %, EP all-to-all bytes, and expected MFU. Any config proposal without the bubble and comms numbers is a guess dressed as a plan.

4 · Your hands #

Experiment 1 — the config picker

Given model size, GPUs, and a memory-per-device budget, this reports which ZeRO stage could work and what the PP bubble would be. Run it before ordering hardware.

def cfg(N, D, M=8, P=8): gib = 1024**3 w = 2*N; g = 2*N; o = 12*N z1 = (w + g + o/D)/gib; z2 = (w + (g+o)/D)/gib; z3 = (w + g + o)/D/gib bubble = (P - 1)/(M + P - 1) return z1, z2, z3, bubble for D in (8, 64, 512, 1024): z1, z2, z3, b = cfg(671e9, D, M=32, P=8) print(f"D={D:5d} ZeRO1={z1:8.1f} ZeRO2={z2:8.1f} ZeRO3={z3:7.1f} GiB/device bubble(M=32,P=8)={b:.1%}")

Measured: D = 8 → 3,437.0 / 2,343.4 / 1,249.8 GiB; D = 64 → 2,616.8 / 1,386.5 / 156.2; D = 512 → 2,514.3 / 1,266.9 / 19.5; D = 1024 → 2,507.0 / 1,258.4 / 9.8. Conclusion for a 671B model: only ZeRO-3 works, and only at D ≥ 64 does it come close to fitting an 80 GB device. Falsification: if ZeRO-1 shows scaling with D in your output, the optimizer-state term is missing.

Experiment 2 — the bubble sweep you should run before choosing PP

Pipeline depth is chosen to fill GPUs, so the temptation is always to go bigger. This sweep shows why that is usually wrong.

python -c " for M in (8,16,32,64,128): row=[(P-1)/(M+P-1) for P in (8,16,32)] print(f'M={M:3d}: ' + ' '.join(f'P={P}:{b:6.1%}' for P,b in zip((8,16,32),row))) "

M = 8: 46.7% / 65.2% / 79.5%. M = 128: 5.2% / 10.5% / 19.5%. The rule that falls out: M should be at least 4× P before the bubble is tolerable; at M/P=4 the bubble is (P−1)/(5P−1) ≈ 20% regardless of P. If your global batch cannot be split into that many microbatches, use fewer stages — a shallower pipeline with a full batch beats a deep pipeline that idles.

Experiment 3 — is TP feasible on this interconnect?

Compare the TP all-reduce time against the compute time per step. If comms exceed ~20% of compute, the TP degree is too high for the fabric.

N, bits = 671e9, 16 for S, bw in [(8, 300e9), (8, 50e9), (16, 300e9)]: bytes_moved = 2 * N * bits/8 * (S-1)/S t = bytes_moved / bw print(f"TP={S} bw={bw/1e9:.0f} GB/s: {bytes_moved/1e9:,.0f} GB per step = {t:.2f} s")

TP = 8 on a 300 GB/s fabric: 2,348.5 GB → 7.83 s per step. The same degree on a 50 GB/s fabric: 47 s — larger than the compute time, making TP useless. TP = 16 at 300 GB/s: 2,516.2 GB → 8.39 s, barely worse than TP = 8, so extending TP past the NVLink domain of 8 GPUs buys almost nothing. That is why TP degrees are essentially always 8 (or ≤ the NVLink domain size).

5 · Failure modes #

  • Bubble too large. Symptom: MFU of 20–30% while GPU memory is comfortable; the run is slower than a shallower configuration on fewer GPUs. Compute the bubble before launch, and prefer more DP over more PP.
  • TP across a slow fabric. Symptom: step time grows superlinearly with TP degree; NCCL all-reduce time dominates the profile. Keep TP inside one NVLink domain; use PP or EP across nodes.
  • Activation blowup at long sequence. Symptom: OOM at a batch size that worked at half the sequence length, in a run where the parameters have not changed. Activations scale with batch×sequence; add gradient checkpointing or sequence parallelism before increasing PP.
  • EP stragglers. Symptom: all-to-all completes but per-rank compute times vary widely, so the collective is dominated by the slowest expert-parallel rank. Combine EP with a balanced router (L31).
  • Config chosen for memory, not throughput. Symptom: the model fits and every GPU is at 35% utilisation. Memory fit is a constraint, not an objective — sweep (TP, PP, M) against measured step time.

7 · Self-check #

Q1. A 671B model, bf16, AdamW. At DP size 64, what is per-device memory under ZeRO-3, and what is the dominant term?

Reveal answer

Total bytes = (2 + 2 + 12) × 671×109 = 1.0736×1013 B = 9,998.7 GiB. Divided by 64 = 156.2 GiB. The dominant term is optimizer state: 12N of the 16N total, i.e. 75% — which is why ZeRO-1 (sharding only optimizer state) is the cheapest useful first step for models that otherwise fit.

Q2. Pipeline with P = 16 stages and M = 16 microbatches. What fraction of the cluster is idle, and how many microbatches would you need for a 10% bubble?

Reveal answer

Bubble = (16−1)/(16+16−1) = 15/31 = 48.4%. For a 10% bubble: (P−1)/(M+P−1) = 0.10 ⇒ 15 = 0.1(M+15) ⇒ M + 15 = 150 ⇒ M = 135 microbatches. That is 8.4× the stage count and constrains the global batch accordingly — a real, often unnoticed cost of deep pipelines.

Q3. TP = 8 on a 671B model. How many bytes does the gradient all-reduce move per step, and what does that imply about which fabric it must run on?

Reveal answer

2 × 671×109 × 2 B × 7/8 = 2.3485×1012 B ≈ 2.35 TB per step. At 300 GB/s that is 7.83 s; at 50 GB/s, 47 s. So TP must live inside an NVLink-class domain — on InfiniBand the communication would exceed realistic step time and destroy throughput.

Q4. Diagnostic: step time grows 3× when you double the sequence length, while FLOPs should only double. Name two causes specific to parallelism.

Reveal answer

(a) Activation memory forced a smaller batch and therefore fewer microbatches in flight, increasing the pipeline bubble; (b) sequence-parallel collectives (attention all-gather/reduce-scatter) grow with sequence length and, if TP is used, the per-layer all-reduce volume grows too. Both are communication effects that raw FLOP accounting misses — always profile comms separately.

Q5. Why is pure DP unsuitable for a 671B model even on 512 GPUs, and which single change fixes it?

Reveal answer

Pure DP replicates weights, gradients and optimizer state on every device: 16N = 1.0736×1013 B = 9,998.7 GiB per device regardless of how many GPUs you have. Nothing fits. The single change is FSDP/ZeRO-3, which shards all three and reduces per-device memory to 19.5 GiB at D = 512 — a 512× reduction — at the cost of an extra all-gather per layer in the forward and backward pass.
