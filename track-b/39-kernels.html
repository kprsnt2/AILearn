L39 · CUDA / Triton / TileLang Kernels in Practice

The same softmax written as three framework ops versus one fused kernel moves 6× the bytes and runs 5× slower. Below the model there is a layer where the languages are Triton and TileLang, and where a wrong block size costs more than a wrong architecture.

1 · Why it exists #

You can write a correct model in PyTorch and still pay 3–5× too much. The reason is that a framework expresses computation as a graph of separate operations, and each operation is a separate kernel launch that writes its output to HBM and reads it back at the next op.

Take softmax, the simplest non-trivial op, on a tensor of shape 1024 rows × 4096 columns in fp32 (16 MiB). The framework version is at least four kernels: subtract max, exponentiate, sum, divide. Each writes a 16 MiB intermediate and the next one reads it. Traffic:

  • read x (16 MiB) + write t1 (16) + read t1 (16) + write t2 (16) + read t2 (16) + write t3 (16) + read t3 (16) + write out (16) = 128 MiB across four tmp/out-sized buffers (x read plus 3 buffers written and re-read plus the output), for an operation whose arithmetic is 1024 × 4096 × 4 FLOPs ≈ 16.8 MFLOP.
  • Intensity is 1.68×107 / 1.34×108 = 0.125 FLOP/byte against a ridge of 295 — 2,360× below it. It runs at 0.04% of peak math and ~100% of memory bandwidth.
  • A fused kernel does one read and one write: 32 MiB, a 4× traffic reduction, and it is limited only by achievable HBM bandwidth.

Scaled up, this is the difference between a 40% MFU training run and a 25% one, and between a serving cluster that pays for 8 GPUs and one that pays for 3. Kernel work is where architecture becomes operational cost. The three practical languages in 2026 state as of 2026-10 are CUDA (total control, slowest to write), Triton (Python DSL, block-level programs, what most research kernels use) and TileLang (a tile-oriented DSL that exposes pipeline and layout control more directly than Triton while staying above raw CUDA).

A correct model is not a fast model. Software that raises effective FLOP/s above the memory bound is worth as much as architecture changes, and it composes with them — you get both.

2 · The mental model #

Analogy (labelled): a workshop with a workbench (SRAM, ~228 KB per SM) and a warehouse (HBM, tens of GB). A kernel is good when it carries a crate to the workbench once, does all the operations on it there, and carries the result back. A framework graph is a process where each worker walks to the warehouse for every step.

What the analogy gets right

Locality and trips dominate. Fusing two operations removes a whole round trip; that is why fusion beats micro-optimising arithmetic.

Where it breaks

The workbench is tiny and shared by many threads. Fitting a block of data in SRAM constrains the algorithms you can express (that is exactly why flash attention needed an online softmax), so fusion is not free — it changes what is computable in one pass rather than merely how it is written.

What a Triton program actually is

Triton's unit of work is a block — you write one program that operates on a tile, and the compiler launches many instances and manages SRAM/registers, swizzled layouts and vectorisation for you. TileLang exposes a further layer: explicit tiles and copy/compute pipelines so you can express what a CUDA engineer would hand-write, without writing CUDA. Both exist because hand-tuned CUDA kernels for each new attention variant stopped scaling as a strategy.

3 · The mechanism #

The traffic model you must write before the kernel

bytesunfused = ∑k 2 × N b   vs   bytesfused = 2 × N b     speedupceiling = k k = number of fused ops, N = element count, b = bytes per element. Each unfused op pays a read and a write of the whole tensor; the fused version pays one of each regardless of k. So the ceiling on fusion speedup is the op count — and you get it only if the kernel is actually bandwidth-bound, which for elementwise chains it always is.

Worked: softmax on 1024 × 4096, fp32

ImplementationKernelsHBM trafficTime at 1.5 TB/s achieved
Framework (max, exp, sum, div)480 MiB (5 × 16 MiB, x read once)55.9 µs
Fused single kernel116 + 16 = 32 MiB22.4 µs
Fused + fp32→bf16 output116 MiB read + 8 MiB write = 24 MiB16.8 µs

Note the arithmetic never changed: 16.8 MFLOP in every row. The 3.6× from 80 to 22.4 µs is pure data movement, and the extra row shows the output dtype is a kernel decision too — writing bf16 from a fused kernel saves another 8 MiB.

Why block size matters so much

A Triton softmax over rows of 4096 elements processes each row in tiles. With BLOCK = 1024, four tiles per row and a cross-tile reduction; with BLOCK = 4096, one tile and no cross-tile pass but too much register pressure. To see the effect numerically: the reduction has to carry a running max and sum, and each extra pass over the row is another read of the tile.

BLOCK for a 4096-wide rowTiles per rowSRAM per tile, fp32Registration pressure
128320.125 KiBlow, but 32 reduction steps (latency chain)
1,024416 KiBmoderate — the usual choice
4,096164 KiBhigh; may spill registers and lose more than it saves

The optimum is an empirical curve, not a law: bigger blocks reduce reduction steps but increase register pressure, and the knee depends on the dtype and the row width. This is why kernel tuning is benchmark-driven and why autotuners exist.

What fusion cannot fix

Reductions across the whole tensor

A global sum needs every element before it finishes, so it cannot be fused into a producer without a two-pass or atomic scheme. Softmax avoids this by being row-wise.

Launch overhead

At small tensors, a kernel launch costs ~3–10 µs of CPU/GPU latency. Fusing 8 ops into 1 saves 7 launches — for a 100-element tensor that dominates. Your agent's per-request tensors are often that small.

Kernel changes need a falsifiable measurement: achieved bandwidth (GB/s) as a fraction of the device peak, and achieved FLOP/s as a fraction of MFU, logged before and after. Without those two ratios, “we optimised the kernel” is indistinguishable from a regression that happened to ship with a faster GPU.

4 · Your hands #

Experiment 1 — a real Triton fused softmax (needs a GPU and `pip install triton`)

The canonical first kernel: one program per row, whole row in a tile, numerically stable, one read and one write.

import torch, triton, triton.language as tl @triton.jit def softmax_kernel(x_ptr, out_ptr, n_cols, stride, BLOCK: tl.constexpr): row = tl.program_id(0) cols = tl.arange(0, BLOCK) mask = cols < n_cols x = tl.load(x_ptr + row * stride + cols, mask=mask, other=-float('inf')) x = x - tl.max(x, axis=0) # stability: subtract row max num = tl.exp(x) y = num / tl.sum(num, axis=0) tl.store(out_ptr + row * stride + cols, y, mask=mask) def softmax_fused(x): rows, cols = x.shape out = torch.empty_like(x) BLOCK = triton.next_power_of_2(cols) softmax_kernel[(rows,)](x, out, cols, x.stride(0), BLOCK=BLOCK) return out x = torch.randn(1024, 4096, device='cuda') print((softmax_fused(x) - torch.softmax(x, dim=-1)).abs().max()) # ~1e-7

Max error around 10-7 (fp32 rounding, not an approximation). Then time it against torch.softmax with torch.cuda.synchronize() outside the loop. Falsification of the fusion story: if the fused kernel is not faster, PyTorch is already fusing this op — check with a profiler before concluding that hand kernels do not help.

Experiment 2 — the traffic model, before you write any kernel

Never start with code. Start with the byte count; if the ceiling improvement is not worth the maintenance, stop. This script gives the ceiling.

python -c " N=1024*4096 for name,ops,fb in [('framework softmax',4,4),('fused fp32 out',1,4),('fused bf16 out',1,2)]: rd = N*fb if name!='framework softmax' else N*4*4 wr = N*fb total = rd+wr print(f'{name:20s} kernels~{ops} traffic={total/2**20:7.1f} MiB at 1.5TB/s = {total/1.5e12*1e6:7.1f} us') "

Framework 80.0 MiB / 55.9 µs; fused fp32 32.0 MiB / 22.4 µs; fused bf16 output 24.0 MiB / 16.8 µs. Fusing is 2.5× on traffic and time; dropping the output to bf16 adds another 1.33×. Note that the measured ratio (2.5×) is less than the ceiling implied by 4 kernels, because the first read of x is shared and the framework version need not materialise every intermediate — which is why you measure rather than trust the op count.

Experiment 3 — simulate the tiling to feel the reduction cost (no GPU needed)

Model a tiled row-softmax in pure Python and count the reduction steps and tile reads for each block size. This is how you choose BLOCK on a machine you do not have access to.

def tiled_cost(cols, block, dtype_bytes=4): tiles = -(-cols // block) # ceil division tile_reads = tiles # sequential passes over tiles reduction_steps = tiles # running max + running sum per tile sram = block * dtype_bytes return tiles, reduction_steps, tile_reads, sram print("cols=4096") for b in (128, 256, 512, 1024, 2048, 4096): t, r, tr, s = tiled_cost(4096, b) print(f"BLOCK={b:5d} tiles={t:3d} reduction_steps={r:3d} SRAM={s/1024:6.1f} KiB")

BLOCK 128 gives 32 tiles and 32 reduction steps with 0.125 KiB of SRAM per tile; BLOCK 4096 gives one tile and zero cross-tile reductions but 64 KiB per tile and far higher register pressure. The workable region is BLOCK ∈ [256, 1024] in practice: enough tiles to fill the machine, few enough reduction steps to hide latency. That trade is the entire art of writing the kernel.

5 · Failure modes #

  • Fusing something that was not memory-bound. Symptom: lots of work, no speedup. Measure intensity first; fusion only pays for bandwidth-bound op chains.
  • Wrong dtype in the fused kernel. Symptom: correctness is fine but traffic is 2× too high, or accumulated sum overflows in fp16. fp32 accumulation over a bf16/fp16 input is usually mandatory for reductions.
  • Uncoalesced access. Symptom: achieved bandwidth is 20–40% of peak and no arithmetic fix helps. Check that adjacent threads read adjacent addresses; strided loads are the classic cause.
  • Silent autotune regression. Symptom: performance changes between runs on the same hardware because the autotuner picked different configs, so A/B comparisons are noise. Pin the config for measurement, then autotune for production.
  • Numerical drift from reordering. Symptom: reduced-precision kernels produce slightly different outputs run to run, which breaks exact-match determinism tests (L94). If you must reproduce bit-exactly, record the kernel config alongside the seed.

7 · Self-check #

Q1. A chain of 6 elementwise ops on a 100 MiB tensor, fp32. What is the traffic for the unfused version versus a fully fused one, and the speedup ceiling?

Reveal answer

Unfused: each op reads and writes once, so 6 × 2 × 100 MiB = 1.2 GiB. Fused: one read and one write = 200 MiB. Traffic ratio = 6.14× and, being bandwidth-bound, the speedup ceiling is also ~6×. Note you cannot exceed the op count — fusion removes round trips, not arithmetic.

Q2. For a 4096-wide fp32 row-softmax with BLOCK = 256, how many tiles and reduction steps, and how much SRAM per tile?

Reveal answer

Tiles = ceil(4096/256) = 16. Reduction steps = 16 (running max and running sum per tile). SRAM per tile = 256 × 4 B = 1 KiB. Against a 228 KB shared-memory budget that leaves enormous headroom — the constraint is not SRAM but the latency chain of 16 dependent reduction steps, which is why you would raise BLOCK until register pressure or the step count stops improving.

Q3. Diagnostic: a fused kernel matches the reference numerically but is no faster than the framework chain. Two likely causes.

Reveal answer

(a) The framework was already fusing or using a fused backend (check with a profiler whether it launches 1 kernel or 4). (b) Your kernel is not bandwidth-limited but latency- or occupancy-limited: too few blocks to fill the SMs, or a long dependent reduction chain. Also possible: memory access is uncoalesced, capping achieved bandwidth well below peak.

Q4. Why does the fused-kernel speedup ceiling equal the op count only for bandwidth-bound chains?

Reveal answer

Fusion removes the read/write round trips, so it reduces bytes by a factor of k while leaving FLOPs unchanged. If the original is bandwidth-bound that maps directly to time. If it is compute-bound, bytes were not the limiter — removing them changes nothing and the ceiling is 1. That is why you compute intensity before writing a kernel.

Q5. A vendor claims their kernel gives a 4× inference speedup. What four measurements do you request?

Reveal answer

(1) Achieved bandwidth as a % of device peak, before and after. (2) Achieved MFU/FLOP utilisation, before and after. (3) The workload shape (batch size, sequence length, dtype) — kernel wins are shape-specific. (4) Whether the baseline was the framework default or a fair tuned baseline. Without these, the 4× may be a comparison against a deliberately slow path.
