L35 · Long Context: What 1M Tokens Actually Costs

Marketing says “1M context.” Operations need four numbers: GiB of HBM per session, seconds of prefill, the quadratic attention term, and the decode bandwidth that caps concurrency. This page computes all four for concrete configurations.

~30 min difficulty ●●●●○ build: context cost model in $ and GB
cache GiB per session prefill time quadratic attention term concurrency ceiling 1M context economics offload to SSD cost per prompt token

1 · Why it exists #

Long context is sold as a capability and billed as a utility. When customers start using it, four separate resource pools get consumed in ways that do not scale together, and teams discover the cost only after the feature is in production. The failure is not that a 1M context is impossible — it is that a product built on “we support 1M context” can be economically non-viable while still being technically correct.

The concrete traps:

  • Memory per session grows linearly with context but concurrency is inverse-linear — so a 32× context increase cuts concurrent capacity 32× for the same HBM pool.
  • Prefill compute is linear in prompt tokens, so a 1M-token prompt costs 1M × 2Nactive FLOPs before a single output token is generated — and that is a one-shot cost paid again on every retry.
  • The attention term is quadratic and, computed honestly, dwarfs everything else from a few hundred tokens onward — 631.6 seconds of GPU time for one 1M-token prefill at 13B active in the numbers below.
  • Decode re-reads the entire cache every token, so output latency on a long prompt is set by memory bandwidth, not compute.

DeepSeek-V4 state as of 2026-10 ships 1M context as standard (V4-Pro 1.6T total / 49B active, V4-Flash 284B / 13B active) with token-wise compression and DSA — i.e. the 1M number is only affordable because two of the four bills were attacked structurally. This page prices the whole thing.

Long context costs four bills in four different units: GiB (memory), seconds (prefill), FLOPs (attention, quadratic), and GB/s (decode). A budget that names only one of them is not a budget.

2 · The mental model #

Analogy (labelled): renting a hall by the number of people seated, not standing. Seating capacity (KV memory) is fixed per session and grows with context. Getting everyone in the door (prefill) takes time proportional to crowd size. Having the crowd constantly shuffle (attention) gets quadratically worse as they grow. Serving drinks (decode) is rate-limited by how fast you can walk the aisles — bandwidth.

What the analogy gets right

Four independent bottlenecks coexist; the slowest one sets throughput and the biggest one sets cost. You cannot fix a memory problem with more compute.

Where it breaks

Unlike a hall, part of the crowd can be moved to a parking lot and brought back (SSD offload), and unlike people, tokens can be summarised (token-wise compression). So the ceiling is not hard — it is a latency-versus-cost trade you choose.

3 · The mechanism #

C(L) = (HBMbytes / (L × bytestoken))    sessions
Tprefill(L) = 2 Nactive L / (η S)     Tattn(L) = 2 lay H d L² / (η S) S = FLOP/s per accelerator, η = MFU. The first line is the concurrency ceiling and it is the one long-context products die on. The second and third are per-prefill times; the third is quadratic in L and already exceeds the second at L ≈ 114 tokens for a 13B-active model; the crossover scales as √N, so a 49B-active model crosses at L ≈ 221. Dense attention is never free, which is why questions about long context are really questions about efficient attention.

All numbers below use: H800-class accelerator at 989 TFLOP/s dense bf16, η = 0.40, so Seff = 3.956×1014 FLOP/s per GPU; a 61-layer model; and the MLA cache at 70,272 bytes/token from L33, with a V4.1-style compressed variant at 17,568 bytes/token (the published 1/4 HBM figure).

At $2/GPU-hour, an 8-GPU 1M-token prefill on the 8B-active path is 5.06 GPU-s × 8 = 40.5 GPU-seconds = $0.0225. The 49B path is $0.1376. That is the per-call cost of reading one million tokens — and it is paid again on every retry, every tool-loop turn that re-sends the transcript, and every user who refreshes.

The hidden multiplier is re-prefill. An agent loop that re-sends a 1M-token transcript on each of 5 turns pays prefill 5 times unless the provider caches the prefix. That is why prefix caching (L45) is not an optimisation but a business model for long-horizon agents.

Bill 3 — the quadratic attention term

Attention costs 2 FLOPs per query–key pair per head dim, for both QKT and the AV product, so with causal masking of half the pairs the total is 2·layers·heads·dhead·L². With 61 layers, 128 heads of dim 128:

This is the single most important number on the page, and it is much worse than intuition suggests: dense attention already exceeds the entire body-compute prefill term at roughly 114 tokens for a 13B-active model (√(2N/(2·61·128·128))), and at 1M tokens it is 77× larger. A dense-attention model cannot prefill 1M tokens in any practical time: 631.6 GPU-seconds across 8 GPUs is over 10 minutes of pure attention.

So the arithmetic does not merely recommend MLA and DSA — it says dense attention makes 1M context impossible regardless of memory. The entire “long context” story is an efficient-attention story:

  • FlashAttention (L38) does not reduce the FLOPs; it reduces memory traffic so the quadratic work actually runs near peak instead of being bandwidth-starved. It makes the 10-minute figure achievable rather than hopeless.
  • DSA (L34) attacks the exponent itself: each query reads m = 2,048 positions instead of L/2, turning the term from quadratic to linear-in-L with a constant factor m.
  • Token-wise compression reduces the number of scored positions, shrinking both bills 1 and 4.

Recompute with DSA's read budget: at 1M tokens each query reads 2,048 instead of 500,000 causal positions, so the attention term falls by 244× from 1.999×1018 to 8.19×1015 FLOPs — about 20.7 seconds on 8 GPUs instead of 631.6, and comparable to the 8.22 s prefill term rather than 77× it.

Bill 4 — decode bandwidth

Every generated token re-reads its whole cache. With the MLA cache at 70,272 B/token and 1M context, a decode step reads 70.272 GB from HBM — on a device with ~3 TB/s of bandwidth that is a 23 ms floor per token, giving a theoretical ceiling of ~43 tokens/sec for that single session, before any weight reads. With 4× compression it is 17.6 GB and ~171 tok/s. This is the number users feel, and it is why long-context decode is bandwidth work, not compute work.

The synthesis: what to quote

One table, all four bills, for a representative configuration. Use this shape for any model you evaluate.

Cost sheet for 1M-context serving on a 13B-active, 61-layer MLA model, 640 GiB pool, 8-GPU prefill at $2/GPU-h: memory 65.45 GiB/session → 9.8 sessions (16.36 GiB / 39.1 sessions at 4× compression); body prefill 8.22 s; dense attention 631.6 s (or ≈20.7 s with a DSA-style 2,048-position read budget); decode 23.42 ms/token from cache reads alone. Compute cost at $2/GPU-h for the 8-GPU prefill: $0.0365 — cheap. The expensive line is not dollars, it is the 631 seconds of attention that sets your queue depth and your p99.

4 · Your hands #

Experiment 1 — the full four-bill calculator

One function, all four bills, any context length. This is the artifact to hand to whoever owns the serving budget.

def ctx_cost(L, layers=61, heads=128, d=128, N_act=13e9, bytes_tok=70272, pool_gib=640, gpus=8, eff=989e12*0.4, usd_per_gpu_h=2, bw=3e12): cache_gib = bytes_tok * L / 1024**3 prefill_flops = 2 * N_act * L attn_flops = 2 * layers * heads * d * L * L # QK^T + AV, causal avg t_prefill = prefill_flops / (eff * gpus) t_attn = attn_flops / (eff * gpus) decode_ms = bytes_tok * L / bw * 1000 usd = t_prefill / 3600 * gpus * usd_per_gpu_h return cache_gib, t_prefill, t_attn, decode_ms, usd, pool_gib / cache_gib for L in (131_072, 1_000_000): for bt in (70272, 17568): c, tp, ta, dm, u, sess = ctx_cost(L, bytes_tok=bt) print(f"L={L:>9,} b/tok={bt:6d} cache={c:7.2f}GiB prefill={tp:6.2f}s attn={ta:6.2f}s " f"decode={dm:6.2f}ms \${u:.4f} sessions={sess:6.1f}")

Measured: L = 131,072 with 70,272 B/token → cache 8.58 GiB, prefill 1.08 s, attention 10.85 s, decode 3.07 ms, $0.0048, 74.6 sessions. With 17,568 B/token → cache 2.14 GiB, same prefill and attention, decode 0.77 ms, 298.4 sessions. L = 1,000,000 with 70,272 → cache 65.45 GiB, prefill 8.22 s, attention 631.6 s, decode 23.42 ms, $0.0365, 9.8 sessions. With 17,568 → cache 16.36 GiB, decode 5.86 ms, 39.1 sessions. Note the shape of the result: compression fixes bills 1 and 4, prefill fixes bill 2, and nothing except sparsity fixes bill 3 — which at 1M dominates everything by two orders of magnitude.

Experiment 2 — where does the prefill money go? (the crossover nobody expects)

Rank the body-compute and attention terms as context grows. The result is the most counter-intuitive line in the course: attention is already the bigger term at a few hundred tokens, and the crossover length scales with √Nactive.

python -c " for N in (8e9,13e9,16e9,49e9): print(f'N={N/1e9:4.0f}B active: attention == prefill at L = { (2*N/(2*61*128*128))**0.5:.0f} tokens') for L in (16384,131072,1048576): pf=2*13e9*L; at=2*61*128*128*L*L print(f'L={L:>9,}: prefill={pf:.3e} attn={at:.3e} attn/prefill={at/pf:8.2f}') "

Measured: attention equals the body term at 89 / 114 / 127 / 221 tokens for 8 / 13 / 16 / 49B active. And attn/prefill is 1.26 at 16k, 10.08 at 128k, 76.88 at 1M. So the linear prefill term is never the dominant cost beyond short prompts — which means the hard question at 1M context is not memory at all, it is whether your attention implementation is sparse. Falsification: if your model reports attn/prefill < 1 at 128k, it is not using dense attention — check whether a sparse or chunked path is silently active.

Experiment 3 — the retry multiplier on a real agent loop

Long context is usually consumed by loops that re-send the transcript. Model the actual monthly cost and see why prefix caching dominates.

L, turns, calls_per_day, days = 200_000, 6, 2_000, 30 usd_prefill_1m = 0.0365 # measured above for 8B-active, 8 GPUs per_call = usd_prefill_1m * (L / 1_000_000) no_cache = per_call * turns * calls_per_day * days cached = per_call * 1 * calls_per_day * days # only the first turn pays print(f"per prefill of {L:,} tokens: \${per_call:.5f}") print(f"monthly, no prefix cache: \${no_cache:,.0f}") print(f"monthly, prefix cached: \${cached:,.0f}") print(f"ratio: {no_cache/cached:.0f}x")

At 200k tokens, 6 turns, 2,000 calls/day: $0.0073 per prefill, $2,628/month uncached versus $438 cached — a 6× difference that is purely a caching decision. (This counts compute only; the provider's cache read price is a separate line, usually far below the prefill price, which is why cache-aware pricing exists at all — see L45.)

5 · Failure modes #

  • Billing the context, forgetting the output. Symptom: cost estimates are low by 2–10× on reasoning models, because long context multiplies the decode path too — output tokens at 23 ms each on a 1M cache add up faster than the prefill.
  • Concurrency collapse as context grows. Symptom: p99 latency spikes exactly when long-context traffic arrives; the queue depth explodes because each session now holds 65 GiB. Fix: admission control by estimated cache size, not by request count.
  • Prefill retries. Symptom: one client sends a 1M-token prompt that times out at 30 s, retries twice, and consumes 3× the compute of a successful call. Retry budgets must be expressed in prefill-seconds, not attempts.
  • Ignoring the quadratic term in capacity planning. Symptom: throughput targets modelled linearly hold at 128k and miss by 30–50% at 1M. The attention term is 30% of prefill at 1M and 0.34% at 131k.
  • Assuming a documented 1M limit means 1M is served at that latency. Symptom: a provider documents 1M context but routes long requests to a slower path or offloads cache to SSD, so time-to-first-token is seconds and throughput is a fraction. Demand per-call timing at the length you intend to use.

7 · Self-check #

Q1. A 640 GiB pool, MLA cache at 70,272 B/token. How many concurrent 1M-token sessions, and how many if the cache is compressed 4×? Express the change as a multiplier.

Reveal answer

70,272 × 106 = 7.0272×1010 B = 65.45 GiB per session. 640/65.45 = 9.8 sessions. Compressed: 17,568 × 106 = 1.757×1010 B = 16.36 GiB, so 640/16.36 = 39.1 sessions. Multiplier: exactly 4×, because the cache size scales linearly and the pool is fixed.

Q2. Prefill a 1M-token prompt on a 13B-active model with 8 GPUs at 40% MFU on 989 TFLOP/s, $2/GPU-hour. Give seconds and dollars.

Reveal answer

FLOPs = 2 × 13×109 × 106 = 2.6×1016. Aggregate throughput = 8 × 3.956×1014 = 3.1648×1015 FLOP/s. Time = 2.6×1016/3.1648×1015 = 8.22 s. Cost = 8.22 s × 8 GPUs / 3600 × $2 = $0.0365. Add 631.6 s of dense attention spread over the same 8 GPUs — 77× the body term.

Q3. Diagnostic: at 32k context everything is fine; at 256k the provider's p99 time-to-first-token is 20× worse than your model, which assumed linear prefill. Name two candidate explanations and the measurement that distinguishes them.

Reveal answer

(a) The quadratic attention term, which any dense-attention path pays: going 32k → 256k multiplies attention by 64× while prefill only grows 8×, so time-to-first-token grows super-linearly exactly as observed — this is the expected behaviour of the formula, not an anomaly. (b) Cache offload to SSD, if the per-session cache exceeds the replica's HBM. Distinguish them by measuring service time against a dense-attention FLOP model: if the measurement matches the quadratic prediction, (a); if it is 5–50× worse than the quadratic prediction, offload or scheduling.

Q4. At 1M tokens, the MLA cache read for one decode step is 70.272 GB. On a 3 TB/s device, what is the floor latency per token, and what does 4× compression do to it?

Reveal answer

70.272 GB / 3×1012 B/s = 23.4 ms per token, i.e. a ceiling near 43 tok/s for that session before weight reads. With 4× compression the read is 17.568 GB, giving 5.86 ms and a ceiling near 171 tok/s. This is why long-context decode is measured in bandwidth, not FLOPs.

Q5. You must choose between (A) 1M context with uncompressed MLA, or (B) 256k context with 4× compression, on the same hardware. Which serves more users and by how much?

Reveal answer

(A) 65.45 GiB/user → 9.8 sessions per 640 GiB. (B) 70,272/4 × 262,144 B = 4.09 GiB/user → 156.3 sessions. So B serves 16× more users at 1/4 the context. The decision is not technical — it is whether the workload actually needs 1M tokens or merely has long documents. If the answers live in the first 100k tokens, B is strictly better; if the task needs full-document cross-reference, A is the only option and you budget for 9 concurrent users.
